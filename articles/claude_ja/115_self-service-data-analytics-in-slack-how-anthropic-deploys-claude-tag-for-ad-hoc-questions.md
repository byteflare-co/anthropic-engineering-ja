# Slack でのセルフサービス型データ分析: Anthropic が単発の質問に Claude Tag をどう活用しているか
- 執筆者

  Clement Peng

  Lily Zhao

[前回の記事](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)では、次の 3 つの主要な仕組みによって、Claude がおよそ 95% の精度でデータ分析の質問に答えられるようにした方法を紹介しました。

- ガバナンスの効いたセマンティックレイヤー
- 分析上の慣習をエンコードした一連のスキルファイル
- パフォーマンスを測定するための評価スイート

その記事は、私たちのデータサイエンティストとデータエンジニアにとって主要な開発サーフェスである [Claude Code](https://claude.com/product/claude-code) と、エージェントの精度を高めるためのベストプラクティスに焦点を当てたものでした。

今回の記事では、Anthropic のデータチームがその基盤を、会社の他のメンバーが働いている場所にどう適用しているかを取り上げます。それを支えているのが、Slack 上のデータ分析エージェントの基盤である [Claude Tag](https://claude.com/product/tag)(パブリックベータ)です。誰でもデータに関する質問をエージェントに投げかけ、**アナリストが使っているのと同じガバナンスの効いた定義**に基づく回答を得られます。

## Slack にデータ分析エージェントをデプロイするためのベストプラクティス

エージェントを*正確*にすることと、それを*アナリストではない人でも使える形でデプロイする*ことは、まったく別の作業だとわかりました。精度に関する前回の記事の推奨事項はここでも変わらず有効なので、繰り返しません。

代わりに、この 1 年間で得た、Slack にデータ分析エージェントをデプロイする上で最も重要な 5 つの学びと、配布方法、権限、鮮度、可観測性についての考え方を取り上げます。

私たちが下した最も重要なアーキテクチャ上の決定は、スキルファイルを一度作って忘れられるものとしてではなく、**継続的に更新される配信コンテンツ**として扱うことでした。

データモデルは 1 日に何度も変わり得ます。たとえば、列名が変更されたり、メトリクスの定義が修正されたり、テーブルが非推奨になったりします。こうした変更のひとつひとつが、比較的短い時間でスキルファイルに反映される必要があります。もし Claude が先週火曜日時点のスキルを読んでいたら、先週火曜日時点の間違った答えを、まったく自信満々に返してしまいます。

この傾向は特に厄介です。というのも、データの受け手は、その回答の正確さを判断するために必要な文脈から完全に切り離されてしまっているからです。彼らは、トレンドラインや関連メトリクスが載ったダッシュボードを見て「感覚的におかしくないか」を確認しているわけではありません。Slack でたった 1 つか 2 つのデータポイントだけを受け取ることも多く、それが普段見慣れているデータでなければ、自信たっぷりに間違った答えをそのまま信じてしまう可能性が高いのです。

この絶えず変化する環境をコントロールするため、Claude Tag のランタイムは私たちのデータリポジトリの skills/ ディレクトリをマウントし、**会話のたびに読み直します**。スキルファイルはディスク上の単なる Markdown であり、エージェントは他のプロジェクトファイルを読むのとまったく同じように読み込みます。

### クエリの書き方だけでなく、それ以上のスキルをエージェントに与える

Claude Tag を使ってデータ分析エージェントをデプロイする際の当初の発想は、「知識スキル」を作ることでした。これは、どのテーブルを使うべきか、私たちのセマンティックレイヤーがどう構成されているかを Claude に教えるだけのものです。しかし、このアプローチでは*正しい数字*は得られても、*役に立つ洞察*には至らないことがすぐにわかりました。

多くのデータ利用者は、「この落ち込みの原因は何?」「月末時点でどこに着地しそうか予測して」「これをファネルとして見せて」といった、オープンエンドで曖昧な質問をしがちです。こうした質問に答えるには、エージェントが*データがどこにあるか*だけでなく、*アナリストならそのデータをどう扱うか*を知っている必要があります。

そこで、この知識スキルに加えて、次のような追加の分析スキルやランブックスキルを Claude Tag にマウントしました。

- **フォレキャスティング**: いつ、どのように単純なトレンドをフィットさせるか、季節性の前提、系列が短すぎたりノイズが多すぎたりする場合にいつ拒否すべきか。
- **コホート分析とリテンション分析**: 標準的なコホートの定義、経営層に報告されているリテンションカーブのテンプレート、そして素朴な実装が陥りがちな落とし穴(左側打ち切り、生存者バイアスなど)。
- **ファネル分析**: 主要なプロダクトファネルにおける標準的なステージ定義。これにより「オンボーディングでユーザーはどこで離脱しているか」という問いに対する回答が、常に一貫したものになります。
- **チャート作成**: どの質問にどのチャートタイプを使うか、配色、テーブルの方がプロットより明快な場合はどんなときか、といった可視化の慣習。
- **分析ライティング**: 発見をどう構成するか(まず要約、次に数字、メカニズム、留保事項の順)、そして確信の度合いに応じてどの程度ヘッジした表現にすべきか。

どのデータチームにも、こうした慣習はおそらくすでに存在しているはずですが、たいていは誰かの頭の中にあるだけで、文書化されるのはまれです。これをスキルとして書き出すことで、あなたのデータサイエンティストと同じくらい一貫した形で Claude がそれを適用できるようになります。

### データウェアハウスだけでなく、ビジネス上の文脈にもつなぐ

知識スキルとランブックスキルを組み合わせても、質問に答えるにはまだ不十分な場合があります。「なぜ火曜日にサインアップが落ち込んだのか?」と聞かれたとき、答えはデータモデルの中にはないことが多く、むしろ Slack のスレッド、インシデントトラッカー、リリースノート、ドキュメントなどに散らばっていることが頻繁にあります。

このギャップを埋めるため、私たちは Claude Tag を社内のナレッジインデックスに接続しています。これは、社内のドキュメント、議論、イベントをカタログ化したものです。エージェントはメトリクスの変動を見つけると、そのインデックスを検索して*同時期の文脈*を探せます。その朝に開かれたインシデント、切り替えられたフィーチャーフラグ、あるチャンネルで共有された競合他社の発表などです。

すると答えは、たとえば「火曜日にサインアップが 12% 落ち込みました。その日の午前 9 時から 11 時にかけて決済サービスのインシデントが発生しており、落ち込みは影響を受けた地域に集中しています」といったものになります。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7e018507d3cd146d2969dd_0990031b.png)

もし組織にナレッジグラフ、社内検索、あるいはよく整理されたインシデント・変更ログのフィードがあるなら、それらを Claude Tag に接続することが、データウェアハウス自体の次に大きなレバレッジを持つ情報源になります。また、[Claude Tag を Slack の主要なチャンネルに接続して、そこから読み取りと文脈取得をさせる](https://claude.com/docs/claude-tag/admins/attach-to-scope#attach-to-a-channel)こともできます。

### サービスアカウントの権限は意図的に設計する

Claude Tag は、質問した人間としてではなく、サービスアカウントとしてデータウェアハウスにクエリを発行します。すべての Slack ユーザーにウェアハウスの資格情報を直接持たせたくはないので、この設計自体は正しいものです。しかしその一方で、[**ボットにメンションできる人は誰でも、そのボットが持つデータアクセス権を手にすることになります**](https://claude.com/blog/agent-identity-access-model)。ユーザーごとの行レベルセキュリティは存在しません。サービスアカウントが読めるものは、そのチャンネルにいる誰でも質問できてしまいます。

私たちはこれに、5 つの方法で対処しています(ここは軽視しがちで、かつ一度間違えると後から取り返しにくい部分なので、真剣に取り組むことをお勧めします)。

**1. サービスアカウントの範囲をガバナンスの効いたデータのみに限定する。** Anthropic では、Claude Tag のサービスアカウントはセマンティックレイヤーの出力テーブルと、それを構成する厳選されたマート(curated mart)のみを読み取れます。生のイベントストリーム、ステージングスキーマ、個人のサンドボックス内のものは一切読めません。質問がその境界の外側のデータを必要とする場合、エージェントは推測するのではなく、その旨を伝えます。ガバナンスの効いたレイヤーの外側にあるデータは検証されていないため、これはユーザー体験としても正しい振る舞いです。

**2. 列レベルで PII を分類し、サービスアカウントにはそのクリアランスを与えない。** ガバナンスの効いたデータが自動的に PII 安全なデータになるわけではありません(たとえば、厳選されたテーブルにもメールアドレスが含まれている場合があります)。私たちは列レベルの系譜(lineage)を持つデータカタログを維持しており、すべての列の由来と下流への流れが把握できます。新しい列が追加されると、Claude がそれをスキャンし、PII の可能性がある候補にフラグを立てて人間のレビューに回します。その後、人間が列のメタデータに分類を適用し、その系譜によって派生テーブルにもそのラベルが伝播します。Claude Tag のサービスアカウントは PII のクリアランスを一切持っていないため、ウェアハウスの列レベルアクセス制御によって、PII を含む列はエージェントから見えなくなります。テーブル自体へのクエリは可能ですが、機微な列だけは単純に読み取れません。

**3. 接続経路そのものをスキル内に文書化する。** 私たちのウェアハウススキルには、エージェントが(CLI 経由か、直接 API 経由か、あるいは MCP サーバー経由かを問わず)*どう*接続するか、そして各経路での認証がどう機能するかを説明する専用のセクションがあります。この地味な工夫のおかげで、エージェントが「このサーフェスからはウェアハウスに到達できません。理由はこうです」ときれいに失敗するケースと、「間違ったプロジェクトに対してクエリが静かに実行される」「本来出るべきでない場所に認証プロンプトが転送される」といった紛らわしい失敗のケースを区別できます。接続の仕組みがスキルの中に書かれていれば、エージェントは自分自身の制約を自分で説明できます。

**4. Claude のチャンネルメンバーシップをアクセス権の付与として扱う。** Claude Tag を Slack チャンネルに追加することは、実質的には、そのチャンネルのメンバーに、エージェントが照会できる範囲のデータへの読み取りアクセス権を与えることになります。私たちはこれを明示的なルールにしました。Claude をチャンネルに追加できるのはデータチームのメンバーのみであり、どのチャンネルに追加するかのリストはデータチームが所有します。

**5. すべてのクエリにラベルを付ける。** ウェアハウスへのクエリごとに、Claude Tag はサーフェス、会話、そして(Slack から取得できる場合は)依頼したユーザーを識別するラベルを付与します。これはクエリ実行時に何かを強制するものではありませんが、コストの帰属や監査証跡を可能にします(後から「4 TB をスキャンしたクエリを誰が依頼したのか」を特定できます)。

私たちの基本的なスタンスは、Slack 上のデータ分析エージェントを、**ガバナンスの効いたウェアハウスの共有読み取りレプリカ**として扱うというものであり、その前提でスコープを設計するようにしています。

### すべての回答を計測する

エージェントが十分な回答をしたかどうかは、目視で判断できるものではありません。

私たちは、Claude Tag が処理するすべての質問について、構造化されたイベントをログに記録しています。これには次のものが含まれます。

- どのスキルファイルが、どのバージョンで読み込まれたか
- ユーザーが 👍 / 👎 でリアクションしたか、あるいは訂正の返信をしたか
- エージェントが触れたテーブルに、未解決のデータ品質に関する警告があるかどうか。また、こうしたデータ品質警告は回答のフッターにも表示するようにしています。古いデータに関する警告が、数字の隣に見える形で表示され、見落とされることがないようにするためです。

このテレメトリは 2 つのビューにフィードされます。ひとつは**採用率**を追跡するもので、サーフェスとドメインごとに、エージェントへの質問のうちどれだけの割合がガバナンスの効いたレイヤーを経由しているか(場当たり的な SQL ではなく)を示します。もうひとつは**正確性**を追跡するもので、ドメインごとの 👎 リアクションと訂正の発生率で測定します。これは評価の実行間を埋める、精度に関するオンラインの代理指標です。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7e018507d3cd146d2969e3_07987b0d.png)

採用率のメトリクスは、私たちが追跡した中で最も実用的な数字だとわかりました。あるドメインでこの数値が下がったときは、ほぼ間違いなく、スキルファイルが古くなっているか、セマンティックレイヤーがまだカバーしていない新しい種類の質問が現れているかのどちらかです。

## これがセルフサービス分析の普及をどう加速させるか

### Claude Tag のスレッドが新しいミーティングになる

私たちのお気に入りで、最も効果的な Claude Tag のスレッドには、たいてい複数の人が参加しています。こうしたケースでは、Claude が実作業を担う一方で、人々はアイデアや文脈を持ち寄っています。

たとえば、あるデータチームのメンバーが、収益ダッシュボードの読み込みがいつもより数分遅くなっている理由を Claude に尋ねました。Claude は、クエリ結果がキャッシュされていないことと、あるバグが結果のページへの到達を遅らせていることを発見しました。

Claude はダッシュボードの担当者に通知し、担当者はバグの修正とは別に、キャッシュの問題を即座に修正することを決めました。

その後、担当者が他にどのダッシュボードが遅くなっているかを尋ねたところ、同じキャッシュのバグの影響を受けているダッシュボードが数十件あることがわかりました。Claude がキャッシュの修正を書き、データチームのメンバーがそれをレビューし、影響を受けたすべてのダッシュボードは 1 時間もかからずに完全復旧しました。

*説明のためのフィクションとして再現した Claude Tag での会話です。インシデントの詳細、名前、ツールはすべて架空のものです。*

こうしたスレッドがオープンであることには、いくつもの利点があります。読み進める人は、誰かが要約を書かなくても、何が壊れたのか、なぜなのか、どう直ったのかという文脈を自然に把握できます。さらに重要なのは、彼らが受け身の読者にとどまる必要がないという点です。何か役立つ知識を持っている人なら誰でも、上の例のチームメンバーがそうしたように、いつでも会話に参加して貢献できます。

だからこそ、エージェントは共有チャンネルに置き、作業は DM ではなくスレッドの中で行うようにしましょう。スレッドは、後から見返せる履歴記録として機能します。

### Claude Tag が反復作業を引き受ける

データに関わる仕事の多くは反復的なものです。パイプラインのヘルスチェック、KPI モニタリングなどです。[Claude にループを作成させる](https://www.youtube.com/watch?v=SlGRN8jh2RI)ことで、こうした周期的なタスクをスケジュールに沿って、あるいは異常な変化に応じて処理させることができます。私たちが実装した、データ特有の例をいくつか紹介します。

- **プロアクティブなレポート**: 週次スタンドアップの前に、Claude が要約を提供します。先週何が動いたか、前週と比べてどうか、注目すべき点は何か、といった内容です。
- **テストのモニタリング**: ローンチや実験をモニタリングしている際、Claude は 1 日に複数回レポートを提供します。最近のある実験では、途中で設定が変わったことに気づき、私たちが早期にそれをキャッチして修正するのを助けてくれました。
- **可観測性**: 他のループは、私たちのパイプラインとダッシュボードをモニタリングします。パイプラインが失敗すると、Claude は調査を開始し、修正案を作成し、オンコール担当者に連絡します。KPI が予期せず動いた場合、Claude は考えられる説明(祝日の影響か、上流のデータ変更かなど)を提示し、誰かがダッシュボードを開く前にそれらを検証します。
- **トリアージ**: 別のループは、私たちのデータ質問チャンネルを監視しています。新しい質問が来るたびに、それを直接答えるか、深い調査を始めるか、人間を呼び込むかを判断します。データチームの誰かが確認する頃には、作業のほとんどはすでに終わっています。

Claude はループの設計そのものも手伝ってくれます。@Claude に、あなたのチャンネルでどんな反復作業を見てきたか、それをどう手伝えるかを聞いてみてください。

### 必要なときに介入する

Claude が会話を読み進め、必要なときに自ら介入するよう、任意のチャンネルでより積極的に振る舞わせることもできます。私たちのあるデータチャンネルでは、この 1 か月間で、Claude Tag は投稿された質問の 75% 以上に答えました。呼びかけがなくても、たいてい 1、2 分以内に応答しています。

たとえば、あるチームメンバーが公開チャンネルで、あるダッシュボードに新しい利用カテゴリが含まれているかどうかを尋ねました。Claude は 90 秒以内に、そのデータがどう定義されているかを答え、新しいセグメントが欠けていることを確認し、修正案を提示して PR を作成しました。データサイエンティストがそれをレビューして承認しました。その後、Claude が PR をマージし、ダッシュボードを更新しました。

## はじめ方

[前回の記事](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)の作業をすでに終えているなら、Slack へのデプロイはほとんど配線作業だけで済みます。ただし、順序が重要です。

1. **まず権限から。** エージェントのコードを書く前に、サービスアカウントが何を読めるかを決めましょう。後からアクセス範囲を広げる方が、後から狭めるよりもずっと簡単です。
2. **次に配布方法。** マウント済みリポジトリを使うか、MCP 経由でスキルを配信するかを選び、鮮度をエンドツーエンドで検証しましょう。スキルファイルを変更してみて、Claude Tag が SLA の範囲内でそれを取り込むことを確認します。
3. **テレメトリは初日から。** 1 か月前の会話に遡って計測を仕込むことはできません。最初の質問の時点から、構造化されたイベントをログに記録しましょう。
4. **可能ならナレッジインデックスも。** ウェアハウスは*何が*起きたかに答え、社内のドキュメントやインシデントフィードは*なぜ*それが起きたかに答えます。データパスが安定したら、できるだけ早くこれらを接続しましょう。
5. **分析スキルは最後に。** まずはデータアクセスのスキルを作り、実際の質問から、同僚が本当に必要としている分析スキル(フォレキャスティング、コホート、ファネルなど)を見極めましょう。

*この記事は、Anthropic のデータサイエンス・データエンジニアリングチームのメンバーである Clement Peng と Lily Zhao が、Josh Cherry と Michael Segner の協力を得て執筆しました。*
