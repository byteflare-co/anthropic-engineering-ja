# Claude Tag におけるエージェント ID: 自律的でチーム全体に広がる AI のための新しいアクセスモデル

AI エージェントが人間とエージェントのチームで最大限の力を発揮するには、人間と同じツール、ドキュメント、コンテキストにアクセスできる必要があります。

「シングルプレイヤー」型の AI 体験（一人のユーザーが一つのアシスタントとチャットする形）では、それは簡単な話です。自分のアカウントを接続すれば、エージェントが自分の代わりに動いてくれます。しかし [Claude Tag](http://anthropic.com/news/introducing-claude-tag) のような「マルチプレイヤー」型の AI 体験では、Claude は多くの人々が同時に参加する共有チャンネルに居合わせ、特定の個人ではなく *ワークスペース* に属するツールやコンテキストを引き出して仕事をします。

マルチプレイヤー体験を機能させるには、Claude 自身が、管理者によって設定されワークスペースに紐付けられた、そのツール用の独自アカウントを持つ必要があります。私たちはこのアクセスモデルを ***エージェント ID（agent identity）*** と呼んでいます。

この記事では、エージェント ID がどのように機能し、権限をユーザー単位からチャンネル単位へとどう移行させ、自分のワークスペースでどう適切にスコープを切るべきかを説明します。

## **「ユーザーとして振る舞う」が破綻する理由**

AI を個人アシスタントとして使うときには、Google Drive、GitHub、カレンダーといったプラットフォームを接続し、*あなたの* アクセス権限を使ってそれらを読み書きさせることができます。

このモデルは、Claude Tag では次の 2 つの理由でうまくいきません。

- **増していくエージェントの自律性。** AI エージェントが単独で確実にこなせるタスクの長さは、[およそ 4 か月ごとに倍増](https://www.anthropic.com/institute/recursive-self-improvement) しています。エージェントは今や、自分のタスクを後の時間にスケジュールし、依頼した人がログオフしてからずっと後に発生したイベントに応答するようになっています。ユーザーは特定の状況でエージェントを発動させるルーティンを設定しますが、エージェントはおおむね自律的に動くのです。

- **マルチプレイヤーのチーム。** Claude Tag は、チームがすでに作業している共有スペース — 例えば 3 人のエンジニアと 1 人の PM が一緒にデバッグしているチャンネル — に Claude を配置します。しかし複数の人が舵を切っているとき、誰の権限が適用されるべきでしょうか？ 常に正しい「一人」を選ぶことは不可能です。だからこそ、Slack 上でエージェントに何ができるかを関与する人間とは独立に管理者が定義でき、Slack 上で行われたことを個別に追跡できる仕組みが必要になります。

### Claude は Claude として振る舞う

Claude Tag が有効なチャンネルでは、Claude は特定のユーザーの代理として振る舞いません。Claude が触れる各システムで、Claude は自分自身のアカウントを持っています。Slack には Claude アプリとして投稿し、プルリクエストは Claude GitHub App として開き、データウェアハウスへのクエリは管理者がプロビジョニングしたサービスアカウント経由で実行します。

そして個人ユーザーの認証情報は一切関与しないため、共有チャンネルが誰かのプライベートなドキュメントへの裏口になることは決してありません。

### 権限の継承

エージェント ID モデルでは、管理者はワークスペースレベルで ID — Claude がどこででも保持する接続とスキルのベースラインのセット — を定義し、各チャンネルはデフォルトでそれを継承します。そして、必要に応じてチャンネル単位でそれを上書きできます。たとえば、エンジニアリングチャンネルに GitHub とデータウェアハウスへのアクセスを与えたり、CRM 接続を 1 つのプライベートチャンネルに限定したりするのです。

認証情報に加えて、管理者は次のものも定義します。

- **リポジトリアクセス:** Claude が読み書きできるリポジトリ。
- **コネクタ:** Claude が仕事を行うために使うツールと API キー。組織全体では、異なる API キーが同じサービスに対して異なる権限レベルで接続できます（たとえば、一般チャンネルでは Claude にウェアハウスへの読み取り専用アクセスを与え、データチームのプライベートチャンネルでは書き込みアクセスを与える、など）。
- **スキルとプラグイン:** Claude が動的にロードして特殊なタスクのパフォーマンスを高めるための、指示・スクリプト・リソースのフォルダ。
- **常駐の指示:** 各チャンネル向けのカスタム指示とコンテキスト。

このモデルは「明確に区別された Claude の ID」を中心に作られているため、ID を取り消せば、その ID が使われていたあらゆる場所で Claude のアクセスは終了します。これは、数十のユーザーアカウントにまたがる個別のエージェントの行動を監査するよりも、はるかに少ない労力で管理できます。

## エージェント ID モデルの仕組み

エージェント ID は、「このユーザーは何ができるか？」という問いを、「このエージェントはこの区画の中で何ができるか？」という問いに置き換えます。これはユーザー単位の Access Control List からの離脱を意味します。つまり、リポジトリへの直接アクセス権を持たないチャンネルメンバーであっても、そのチャンネルのプロファイルが Claude にその権限を与えていれば、Claude にそのリポジトリを読むよう頼めるということです。

これは異例ですが、自律的・マルチプレイヤーなエージェントに合うアクセスモデルへ向かうための必要な一歩だと考えています。以下では、その境界線をどう考えるかをスケッチしていきます。

### ID の境界の仕組み

Claude Tag は、各プライベートチャンネルに対して異なる ID を作成します。ワークスペース内のパブリックチャンネルは、ワークスペースレベルの ID を共有します。法務チャンネルにおける Claude の ID は、そこで付与されていないコードには到達できませんし、エンジニアリングチャンネルでの ID は、そこで付与されていない法務ドキュメントを読むことはできません。記憶もアクセスもこれらの境界を尊重します。Claude がプライベートチャンネルで学んだことが、より広いワークスペースに現れることはありません。

ID はチャンネルに属するので、デフォルトではそこにいる誰もが Claude をタグ付けでき、管理者は各チャンネルのプロファイルを最小権限のメンバーに合わせてスコープできます。Enterprise プランでは、ロールベースのアクセス制御によって、管理者はそもそも誰が Claude を呼び出せるかを決められるところまで踏み込めます。つまり、チャンネルはエージェントが何に到達できるかだけでなく、誰が依頼できるかも統治できるのです。

### ツールとコンテキストへの広めのデフォルトアクセス

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a3a0eae87418506ee6e5b08_agent-access-scoping%20(2).jpg)

チームが Claude Tag で Claude のツールアクセスをどうスコープするか: 広く、低リスクの統合はエージェント ID の下、共有チャンネルで実行され、個人的・チーム固有のツールは DM の中に留まり、ユーザーとして実行されます。

Anthropic 社内で Claude Tag を運用してみると、その価値はツールとコンテキストへのアクセスとともに複利的に増していくことが分かりました。接続された各システムが、他のすべてのシステムをより有用にしていくのです。Claude は、Slack の議論スレッド、Drive のドキュメント、トラッカーのチケット、ウェアハウスのクエリといったコンテキストを横断して組み合わせ、単一のツールでは出せない一つの答えを返すことができるからです。

Claude をもっとも引き出せているチームは、最初に大きめのアクセスを与え、そこから組織の管理者の好みに応じてアクセスを絞っていきます。エージェント ID は、Claude が有用なクロスシステム作業を行えるだけの十分なスコープを管理者に与えつつ、付与されていない場所にそのアクセスが旅をしないだけの堅い境界を保ちます。私たちのアドバイスは、いくつかのチャンネルでベースラインのプロファイルから始め、監査証跡を読み、仕事がそれを正当化する場所で、意図的に一つずつ、アクセスを広げていくことです。

さらに細かさを求める組織のために、管理者は特定のチャンネルで Claude Tag を無効化することもできます。また、ロールベースのアクセス制御（RBAC）を適用して、Claude Tag へのアクセスを特定のユーザーに限定することもできます。

### ダイレクトメッセージ

Claude Tag において、ダイレクトメッセージは共有チャンネルとは異なる動き方をします。DM はユーザー個人の claude.ai アカウントの上で動きます。コネクタも、認証情報も、結果に載る名前も、その個人のものです。これは、メールの下書きやライセンスを自分しか持っていないソフトウェアのように、チャンネルには絶対に置きたくないツールやタスクで Claude と作業する正しい場所が DM であるということです。

### セキュリティと監査

管理者がチャンネルのプロファイルに接続を追加すると、認証情報は独立に保管され、そのチャンネルの ID にマッピングされ、リクエスト時にネットワーク境界で注入されます。管理者が許可していないホストへのアウトバウンドトラフィックは、そのままブロックされます。監査の面では、エージェントの認証情報で行われたすべてのルーティン、メモリへの書き込み、ネットワーク呼び出しは記録されます。そして Claude は自身のサービスアカウントの下で動いているため、それらの行動は接続された各システム自身のログにも残ります。

## 次に来るもの

エージェント ID は、Claude Tag のアクセスモデルの基盤です。今後、私たちは Claude Tag のセキュリティの提供を強化していき、ジャストインタイムでの認証情報の付与 — ユーザーがその場で 1 回限りのセンシティブなアクションを承認しつつ、エージェントのスコープを恒久的に広げずに済む仕組み — や、より複雑なクリアランス構造を持つ組織向けの ID 認識オーバーレイなどを加えていく予定です。これは、エージェントのスコープの上にユーザーレベルのチェックを重ねるもので、チャンネルのプロファイルとリクエストしたユーザー自身の権限の両方が許可した場合にのみ、Claude が行動するようになります。

Claude Tag のような製品におけるシングルプレイヤーからマルチプレイヤー AI への移行は、長時間に及ぶチームベースの作業を可能にします。エージェント ID は、Claude のツールへのアクセスが有用であるだけの広さを保ちつつ、エンタープライズ規模で安全であるだけのスコープに留まることを保証するものです。
