# 医療機関は Claude Tag をどう活用しているか（How healthcare organizations use Claude Tag）

医療機関は、Claude を[チームメイト](https://academy.claude.com/courses/building-effective-human-agent-teams)として Slack に迎え入れる [Claude Tag（ベータ版）](https://support.claude.com/en/articles/15594475-what-is-claude-tag)を活用し、本番環境のアラートのトリアージ、社内ツールの保守、支払者（payer）ルールに関する質問への回答に役立てています。Claude Tag はまだ Anthropic の [Business Associate Agreement（BAA）](https://support.claude.com/en/articles/8114513-business-associate-agreements-baa-for-commercial-customers)の対象外ですが、すでに複数の医療機関が、保護対象保健情報（PHI）に一切触れないチャンネルとコネクタの範囲で Claude Tag を利用しています。

チャンネルで @Claude とメンションすると、Claude はスレッドを読み、接続されたツールを使って作業を行い、結果を報告します。各チャンネルで起きたことを記憶しているため、長期にわたる作業でも改めて説明し直す必要はありません。また、許可すればチャンネルを見守り、自ら判断して介入することもできます。

Claude Tag がどこで動作し、何にアクセスできるかは管理者が決定します。そのため医療チームは、PHI を保持するチャンネルやシステムから Claude Tag を切り離しておくことができます。

- Claude Tag はデフォルトでオフにしておき、**承認済みのチャンネルでのみ有効化**できます。DM を無効にし、**コネクタをチャンネルごとにスコープ設定**することも可能です。
- Claude Tag は Slack 全体を読むわけではありません。ワークスペースのメンバーが見られるものだけを見ます。ワークスペースのパブリックチャンネルを読み、キーワードで検索することはできますが、招待されていないプライベートチャンネルにはアクセスできません。
- **アクセスバンドル（access bundles）** を使えば、あるチャンネルではコードベースや課題管理ツールなどのデータソースを接続しつつ、EHR（電子カルテ）、臨床システム、患者とのコミュニケーションにはアクセスできないようにすることができます。Claude Tag の[エージェント ID アクセスモデル](https://claude.com/resources/articles/agent-identity-access-model)と全体のアーキテクチャについては[セキュリティとデータ処理に関するドキュメント](https://claude.com/docs/claude-tag/concepts/security-and-data?open_in_browser=1)を、医療機関向けのベストプラクティスについては[こちら](https://claude.com/docs/claude-tag/admins/healthcare)をご覧ください。

Claude Tag を有効化して GitHub と連携した Enterprise 組織には、25,000 ドル分の Claude Tag クレジットが付与されます（10 シート以上の Team 組織には 2,500 ドル分）。なお、これらのクレジットの有効期限は 2026 年 10 月 1 日です。クレジットの詳細は[こちら](https://support.claude.com/en/articles/15575654-claude-tag-launch-promo-for-claude-team-and-enterprise)をご覧ください。

ここでは、Insight Health、Tennr、Medallion が現在 Claude Tag を使ってどのように[人間とエージェントのチーム](https://claude.com/resources/articles/building-effective-human-agent-teams)を構築しているかを紹介します。

#### **Insight Health におけるインシデント対応**

Insight Health は、専門診療科向けの AI 紹介コーディネーター「MagicDocs」を開発しています。MagicDocs は、受信した患者関連文書（FAX、紹介状、事前承認申請、検査結果、診療記録）を読み取り、臨床的な詳細を抽出し、各文書を適切な患者と照合したうえで、構造化データを EHR に書き込みます。同社は 56 の診療科にわたる 1,100 以上の医療機関にサービスを提供しています。

Insight Health の顧客基盤が拡大するにつれ、本番アラートのトリアージが、少人数のエンジニアリングチームが本来より価値の高い仕事に充てたい時間を圧迫するようになりました。そこで同社はこの 3 か月間、PHI を扱わないエンジニアリングおよびサポートのチャンネルで Claude Tag を運用しています。Claude Tag はそこで本番アラートを調査し、チケットの起票と重複排除を行い、PR をレビューし、スレッドをまたいでコンテキストを引き継いでいます。

アラートが大量に流れる本番アラートチャンネルでは、Claude Tag を 2 つ目のエージェントである Zeus（Insight Health が Claude Agent SDK で構築）と組み合わせ、インシデントを最初の通知からテスト済みの修正まで導いています。2 つのエージェントには意図的に異なるアクセス権が与えられています。Claude Tag はコードベースと Linear を参照できるため、コードのパターンやチケットの履歴を把握しています。一方 Zeus は、BAA の対象となっている同社の Claude API 組織上で動作するため、本番データにクエリを実行でき、データが Slack に届く前に PHI をマスキングします。アラートが届くと、2 つのエージェントは調査を行います。本番データにクエリを実行し、コードや最近のデプロイと照らし合わせ、過去のチケットと比較しながら、その進捗を Slack スレッドで報告します。根本原因を特定すると、ドラフト PR を作成してテストを監視し、最後にエンジニアがレビューしてマージします。ここでは Claude Tag のチャンネルメモリが大きな価値を発揮します。新たな苦情が修正待ちの既知の問題であることを見抜き、数週間前の調査内容を思い出し、指示されなくても常設の指示に従って動きます。

「Slack チャンネルにいる全員が、両方のエージェントの推論と、両者がどのように作業を分担しているかを見ることができます」と、Insight Health の共同創業者兼 CTO である Saran Siva 氏は述べています。「その透明性が信頼を築き、エージェントから最大限の価値を引き出す方法をチームに教えてくれるのです」。Claude Tag の稼働以来、Insight Health の重大アラートチャンネルにおけるアラートの 97% がエンジニアの介入なしにクローズされており、チームはコアプロダクトの開発に集中できるようになりました。

インシデント対応以外にも、Insight Health のチームは採用、ベンダーとの交渉準備、契約レビュー（通話記録と条件の照合）、そして一般的な事業運営に Claude Tag を活用しています。

#### **Tennr における社内ツールの保守**

Tennr は患者オーケストレーションプラットフォームです。本来であればケアを停滞させてしまう受付、書類作成、承認、スケジューリングの作業を自動化することで、医療提供者が患者をより早く適切なケアの場へつなげられるよう支援しています。Claude Tag は同社の社内ツールに組み込まれ、非技術系のチームがカスタム社内アプリケーションを構築・保守するのを支援しています。

Tennr のような急成長企業では、社内ツールは作られるのと同じ速さで廃れていきます。誰にもそれを保守する余力がないからです。2026 年 7 月、Tennr は社内ツールの構築において異なるアプローチを取りました。Claude Code で構築した社内向けのオファー提示ポータル recruiting.tennr.com を立ち上げ、専用の Slack チャンネルを通じて Claude Tag をその主たる保守担当者にしたのです。現在では、実際にツールを使う人たち（リクルーター、People チームのメンバー、採用マネージャー、RevOps）が平易な英語で @Claude にリクエストを送り、Claude がコード変更を出荷・デプロイし、結果を報告します。彼らはエンジニアをプロダクト開発から引き離すことなく、ツールを直接改善し続けられます。

約 1 か月で、チームはこの方法で 15 件以上のチケットを出荷しました。アップロードされた 1 ページの PDF をもとに作成した福利厚生の詳細セクション、Dropbox Sign にリンクする「Sign your offer here」バナー、目標ボーナスの項目、セルフサービスの管理機能などです。公開状態になっていたコピー API が指摘されたときには、Claude がその日のうちにロックダウンしました。Ashby からのインポートのバグによって有効なオファーのエクイティがリセットされ続けたときには、Claude がバグを修正し、正しい値を反映させました。別のバグで候補者に変動報酬が一時的に誤って表示されたときには、Claude は頼まれることなく、影響を受けた期間と対処内容をチャンネル全体に告知しました。さらに、ツールのオンボーディングドキュメントを執筆し、権限管理も担っています。

チームはチャンネル内で独自の運用ルールを Claude に教えました。絵文字によるステータス凡例や、チケット番号、依頼者、コミットリンク、スクリーンショット、ライブのテストリンクを含むチケット形式などです。Claude はそれ以降、これらのルールに従うようになりました。リクルーターは実質的にエンジニアリングのチケットを自然言語で（ときにはスクリーンショット 1 枚だけで）起票し、1 時間以内に本番環境への変更を受け取っていました。「社内ツールを成り立たせているのは、まさに Claude Tag です」と、Tennr の事業運営・戦略担当 VP である Abe Griffiths 氏は述べています。「Slack チャンネルを通じて Claude がツールの管理役を担うことで、実際にツールを使う人たちが、エンジニアをプロダクト開発から引き離すことなく、ツールを直接改善できるのです」。

下地が整っていたため、展開は迅速でした。Tennr は PHI を限られたプライベートチャンネルでしか扱わないようにしているため、Claude Tag を広く導入しても新たなデータの問題は生じませんでした。Claude Tag の導入を即決できた決め手は、チャンネルごとのスコープ設定でした。

「オファーツールのチャンネルでは、Claude に積極的に動いてほしいと考えています。問題を修正し、コードを変更し、PR レビューを省略して出荷する、という具合です」と Griffiths 氏は言います。「その姿勢は、たとえば Product や Eng のチャンネルでは明らかに不適切でしょう。そこでの Claude の役割は、情報収集や私たちの整理整頓に近いものだからです。チャンネルごとに線引きできることで、リスクの低い場所では Claude に本当の自律性を与えつつ、それをあらゆる場所で認めずに済んだのです」。

#### **Medallion における支払者に関する専門知識の蓄積**

Medallion は、医療機関向けに医療提供者のクレデンシャリング、免許取得、支払者への登録を自動化しています。その業務の多くは、難解で文書化されていないルールに依存しています。たとえば、グループが登録する前に一定数のクレデンシャル済み医療提供者を求める支払者はどこか、州ごとの規制はどうなっているか、といった類似の疑問が何十とあり、エンジニアはプロセスをプロダクトに落とし込む前にそれらの答えを知る必要があります。これまでそうした答えは、社内の少数の医療ドメイン専門家に属人化しており、コアプロダクト開発の意思決定において人的なボトルネックが常に発生していました。

現在では Claude Tag がこのループに入り、知識のサイロを打ち破っています。エンジニアが Slack で支払者ルールに関する質問をすると、Claude Tag は過去の専門家の回答、履歴データ、非構造化の社内リソースをもとに回答します。専門知識は一人の頭の中ではなく、チャンネルに蓄積されていきます。

「確信が持てないときは、適切な専門家をタグ付けします。そしてその専門家の回答が、関連するトピックに関する今後の回答の土台になるのです」と CTO の Armaan Sarkar 氏は述べています。

Claude Tag の展開に安心して踏み切れた理由は何だったのでしょうか。Sarkar 氏は、PHI を扱わない適切なワークストリームの選定、専門家によるレビュー、そして自動検証を挙げています。Claude Tag はポリシーのレベルで動作します。質問の対象は支払者のルールやプロセスであり、個々の患者や医療提供者ではありません。また、Claude Tag が単独で回答するわけではありません。専門家が監督と訂正を行い、すべてのやり取りは社内の誰もが監査できる Slack チャンネルで行われます。さらに、出力は下流でチェックされます。Medallion のシステムはこれらのポリシーを使ってアクションを実行しますが、そのアクション自体も独自に監査・検証されているからです。

#### **はじめに**

上記のチームはいずれも同じ場所から始めました。エンジニアリング、プロダクト、運用、採用のいずれかのチャンネルで、1〜2 個のコネクタを使い、DM ではなくオープンなスレッドで作業することで、チーム全体がレビューしてコンテキストを把握できるようにしたのです。

まずは医療機関向けの Claude Tag のベストプラクティスを[こちら](https://claude.com/docs/claude-tag/admins/healthcare)で確認し、1 つのチャンネルから始めてください。アラートチャンネルやサポートエンジニアリングのチャンネルで Claude Tag を有効にし、GitHub を接続して、許可リストを広げる前に 2 週間ほどチームに使ってもらいましょう。

***[Claude Tag](https://support.claude.com/en/articles/15594475-what-is-claude-tag) を始めましょう。***
