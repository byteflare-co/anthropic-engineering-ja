## 速く、そして安全に出荷する

あなたの組織でも、すでにコーディングエージェントがコードを書き、プルリクエストを作成しているはずです。先進的なエンタープライズの多くでは、レビュー、テスト、マージまでエージェントが担っています。

たとえば [Salesforce](https://www.salesforce.com/news/stories/how-engineering-became-agentic/)¹ は、エンジニアリング組織全体で Claude Code を標準化した後、次のような成果を[報告](https://www.salesforce.com/news/stories/how-engineering-became-agentic/)しています。

79%

Salesforce における開発者 1 人あたりのマージ済みプルリクエストの増加率

5%

Salesforce におけるインシデント総数の減少率

エージェントが担う範囲が広がるにつれ、技術およびセキュリティのリーダーは、プロンプトインジェクションや権限の濫用といったリスクを、権限チェックや境界の定められた環境などの多層的な制御によって緩和する必要があります。

最初の 2 章では、リスクの範囲を見定めることに焦点を当てます。あらゆる AI プロバイダーが満たすべき要件と、緩和すべき 4 つのエージェント特有のリスクについて説明します。

続く 3 章では、リスクに上限を設けることに焦点を当てます。Claude Code で導入できる防御レイヤーと、それらの制御を一元的に管理・強制する方法を紹介します。

本ガイドは、組織が自信と信頼を持ってエージェントを大規模かつ効果的に運用できるよう、役立つエージェントセキュリティのフレームワークを提供することを目指しています。

![AI エージェントの防御を構成する要素の図：入力に対する外部チェック、上限が固定された環境の中にある確率的なモデル、そして外に出ていくアクションに対する外部チェック。](https://assets.claude.com/6e6e1d5218174690c704d9ddebd647dabd6c2f9b.png)

AI エージェントの防御を構成する要素：モデル、それを取り巻く環境、そして入ってくるものと出ていくものに対する外部チェック。

*本ガイドは Claude Team および Enterprise プランをご利用の組織向けに書かれています。AWS、Google Cloud、Microsoft Azure などのクラウドプロバイダー経由で Claude をご利用の場合も、同じ原則とローカルの制御が適用されます。*

## 01 エージェントセキュリティの基準を定める

![](https://assets.claude.com/12c9aca44d78efd023bb5d03ab3cc795f6b47688.jpg?w=168&q=75&fm=webp&fit=max)
> 「エージェント型 AI の時代における CISO の責任は、リスクをゼロにすることではありません。私たちの仕事は、エージェントのリスクを可視化し、上限を設けることです。そうすることで、管理できるものを意図的に受け入れ、ビジネスが私たちを迂回するのではなく、私たちの条件のもとで前進できるようになります。」

### すべてのコーディングエージェントに問うべき 6 つの質問

コーディングエージェントを評価する際に、それがエンタープライズでの利用に耐えうるかを確認するため、リーダーが問うことのできる 6 つの質問を紹介します。

| 問うべき質問 | なぜ重要か | 良い回答 | 弱い回答 |
| --- | --- | --- | --- |
| **モデルは拒否すべきときに拒否するか？** | モデルは有害なリクエストに対する最初のチェックであり、悪いアクションが起こる可能性を下げます。 | 拒否がモデルの重みに学習されており、拒否率が公開されている。 | 「システムプロンプトでモデルに断るよう指示しています。」 |
| **アクションは実行前に、モデルの外部で自動的に検査されるか？** | 外部チェックは、モデルが騙されたときや誤った判断をしたときにそれを捕捉できます。 | コマンドの静的解析と、別個の評価モデル。プロンプトインジェクションのプローブ。 | 「モデルは非常に高性能です。」 |
| **影響範囲（blast radius）は環境によって制限されているか？** | インシデントの深刻度、ひいてはリスクに上限を設けます。 | 管理者が必須化でき、フェイルクローズに設定できるカーネルレベルのサンドボックス、またはセッションごとに分離された VM。ネットワーク層でのエグレス許可リスト。 | 「エージェントには作業ディレクトリから出ないよう指示しています。」 |
| **ポリシーを一元的にロックできるか？** | 個人が取り消すことのできない最低基準を設定します。 | ローカルユーザーが上書きできない強制拒否ルールを備えたマネージド設定。 | 「開発者ごとの設定ファイルと、自己申告制のポリシー文書です。」 |
| **エージェントが書くコードは安全か？** | コードの量は拡大しており、チェックがその量に合わせてスケールしなければ脆弱性が出荷されかねません。 | 自動セキュリティレビューと、リスクの高い変更に対する人による承認。 | 「モデルは安全なコードを書くよう学習されています。」 |
| **インシデントを再構成できるか？** | コンプライアンス。時間をかけたセキュリティの改善。 | セッションの[テレメトリーエクスポート](https://code.claude.com/docs/en/monitoring-usage)、[監査 API](https://platform.claude.com/docs/en/manage-claude/compliance-api)（Enterprise）、および既知のギャップの明示。 | 「ログはリクエストに応じて提供可能です。」 |

### SaaS の要件を AI プロバイダーに適用する

皆さんはすでに、シングルサインオン、ロールベースのアクセス、データ取り扱い条件、監査ログといった制御項目を含む SaaS プロバイダー向けのチェックリストをお持ちでしょう。AI プロバイダーにも同様のチェックリストを適用してください。たとえば Claude Code は、次のような形でこれらのセキュリティ要件に対応しています。

- **シングルサインオンとロールベースのアクセス制御**（Enterprise）。他のエンタープライズツールと同じように管理できます。
- 商用利用規約のもとでは、組織がデータの共有を選択しない限り、**コードやプロンプトを生成モデルの学習に使用することはありません**。
- **Enterprise Frontier Safeguards（段階的に提供中）** は、ゼロデータリテンションのプライバシーと、高性能なモデル全体にわたる不正利用検知のための最先端のセーフガードを組み合わせたものです。データは独自の鍵で暗号化し、自社で管理するストレージに限られた期間だけ保持できます。[詳しくはこちら](https://www.anthropic.com/news/enterprise-frontier-safeguards)。
- Enterprise では、HIPAA 構成を適用すると、Claude Code CLI とデスクトップアプリの Code タブ（ローカルモード）が **BAA** の対象になります。
- クラウドプラットフォームでの**暗号化オプション**：Amazon Bedrock における AWS KMS のカスタマー管理キー、Google Cloud の CMEK、Microsoft Foundry の Hosted on Azure オプション。
- [Anthropic Trust Center](https://trust.anthropic.com) で入手できる **SOC 2 Type 2 レポートと ISO 27001 認証**。

## 02 AI 特有のリスクを特定する

認証情報の漏洩と権限の濫用 · 審査されていない依存関係と拡張機能 · データの持ち出し · プロンプトインジェクション

セキュリティや技術のリーダーは、認証情報の漏洩、権限の濫用、侵害された依存関係、内部脅威といったリスクにはなじみがあるでしょう。しかし、エージェントとなると、攻撃対象領域、スピード、規模のすべてが変わります。いくつかのリスクを見ていきましょう。

| リスク | 現在の対処方法 | エージェントによって何が変わるか |
| --- | --- | --- |
| **認証情報の漏洩と権限の濫用** | 最小権限、短命なトークン、ワークロードアイデンティティや OIDC によるキーレス認証。過剰な権限を持つアカウントの定期的な見直し。人には名前付きアカウント、ソフトウェアにはワークロードごとのアイデンティティ。 | 認証情報は短命で、開発者のアクセス権全体ではなくタスクやジョブにスコープを限定すべきです。エージェントは開発者のセッション内で動作し、Claude Code 以外のほとんどのログには開発者の名前しか表示されません。 |
| **審査されていない依存関係と拡張機能** | バージョンの固定、レビューゲート、マニフェスト変更に対する 2 名のレビュアー。バージョン管理された設定。 | エージェントは、審査済み・未審査の依存関係のどちらも、手作業のプロセスより速いペースで追加します。拡張機能は接続した瞬間からエージェントに指示を与えます。 |
| **データの持ち出し** | ネットワーク層でのエグレス許可リスト。 | 侵害されたエージェントは、すでに許可しているサービスを通じてデータを外部に送信できます。従来のマルウェアと異なり、攻撃者があらかじめ定義しておく必要のない複数の経路を試すことができます。 |
| **内部リスク** | ソーシャルエンジニアリングへの意識向上トレーニング、確認手順、報告経路。 | プロンプトインジェクション：チェックの場はツール呼び出しとネットワーク境界へ移ります。 |

### リスク 1：認証情報の漏洩と権限の濫用

エージェントが読めるものは、すべて漏洩しうるものです。これには、長期間有効な AWS アクセスキーや GitHub トークンといった認証情報も含まれます。

エージェントができることは、すべて侵害されたエージェントや張り切りすぎたエージェントによって悪用されうるものです。デフォルトでは、Claude Code のエージェントは、それを監督する開発者のアイデンティティで動作します。インシデントが発生した際には、適切に対応するために、エージェントのアクションと開発者のアクションを区別する必要があるかもしれません。

![独自の GitHub App として動作する Claude が、開発者のアカウントではなく自身の名前で検証済みのコミット 2 件とコメントを追加している、プルリクエスト上のやり取りの例。](https://assets.claude.com/8311ac4c1e71b90b235793fe80369f9425177775.png)

プルリクエスト上のやり取りの例。パイプラインでは、エージェントの作業はエージェント自身の名前で届きます。

### リスク 2：審査されていない依存関係と拡張機能

エージェント型コーディングは、コードが生成・レビューされるペースを加速させます。これには、依存関係が追加され、設定が変更されるスピードも含まれます。

エージェントに JSON スキーマのバリデーションを追加するよう頼めば、パッケージを見つけて最新バージョンを追加し、数分で動くコードを用意するでしょう。エージェントが正しい方向に導かれていなければ、そのスピードはリスクになりえます。

MCP サーバー、プラグイン、スキル、サブエージェントの定義、そしてリポジトリの `CLAUDE.md` ファイルも依存関係であり、パッケージと同じようにレビューすべきものです。呼び出されるのを待つだけの侵害されたライブラリとは異なり、これらは読み込まれた時点でエージェントに届きます。その説明や指示は、エージェントが何か作業をする前にコンテキストウィンドウに入り込みます。

Enterprise プランでは、[スキルとプラグインのスキャン](https://support.claude.com/en/articles/15927065-get-started-with-skill-and-plugin-scanning)により、組織内で誰かがサードパーティのスキルやプラグインをアップロードまたは編集した際に、悪意のあるコンテンツが含まれていないかがチェックされます。

![Enterprise プランでセキュリティスキャンに失敗したプラグインの管理者画面の例。使用できない旨とその理由が表示されている。](https://assets.claude.com/bc8564043d89e3be8aa0b40630b189c53486bb08.png)

Enterprise プランでスキルとプラグインのスキャンがプラグインをブロックした際に管理者に表示される画面の例。

### リスク 3：データの持ち出し

あらゆる漏洩には外へ出る経路が必要です。問題は、ドメインの許可リストでは、自社のアカウントと攻撃者のアカウントを区別できないことです。たとえば github.com を許可すれば、エージェントは攻撃者が所有するリポジトリにプッシュできてしまいます。

DNS は、HTTP の許可リストでは見逃される 2 つ目の持ち出し経路になりえます。エージェントが名前解決する名前にデータをエンコードできるからです。

そしてもちろん、トークンが一度漏洩してしまえば、攻撃者はエージェントのネットワークをまったく必要としません。どこからでもその認証情報を使えるため、エグレスフィルタリングがそのリクエストを目にすることはありません。

### リスク 4：プロンプトインジェクション

OWASP は、2023 年にリストが始まって以来、[Top 10 for LLM Applications](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/) のすべての版でプロンプトインジェクションを最大のリスクに位置づけています。

ソーシャルエンジニアリングとプロンプトインジェクションは同じ仕組みで機能します。ソーシャルエンジニアリングが技術的な制御をすり抜けるのは、騙された人自身がアクションを実行し、システムからは正当なリクエストに見えるからです。インジェクションを受けたエージェントも同様に自らの権限で行動し、すべてのログには正当なリクエストが記録されます。

コーディングエージェントの場合、プロンプトインジェクションは次のような複数の経路で起こりえます。

- Issue トラッカーやプルリクエストのコメント
- 依存関係の README や変更履歴
- エージェントが取得する Web ページ
- MCP ツール呼び出しのレスポンス
- ソースファイル内のコメント、など

![Web ページに隠された指示が通過しなければならない 5 つの関門のフロー図：分離して読み込まれるコンテンツ、インジェクションプローブ、Claude の学習、auto モードの分類器、そしてマスクされた認証情報を備えたサンドボックス。](https://assets.claude.com/a908873f0456683f1b98ad867f1f1defe6363a68.png)

Web ページに隠された指示が害を及ぼすまでに通過しなければならないもの。

## 03 判断レイヤー

多層防御 · アライメント学習を理解する · プロンプトインジェクションプローブ · auto モードの分類器

### 多層防御

Claude Code では、侵害された、あるいはミスアラインメントを起こしたエージェントが害を及ぼすには、複数の制御と 2 つの防御レイヤーを突破しなければなりません。

1 つ目のレイヤーは判断に基づくものです。これらの制御は、何かがおかしく見えるかどうかを判断します。

1. **アライメント学習**は、悪意のあるリクエストを拒否し、慎重なアクションを優先するよう Claude に教えます。
2. **プロンプトインジェクションプローブ**は、auto モードにおいて Claude が受け取ったツール結果に基づいて行動する前にそれをスキャンし、注入された指示のように見えるコンテンツにフラグを立てます。
3. **auto モードの分類器**は、提案されたツール呼び出しの大半を、ユーザーが表明した意図と照らし合わせてチェックします。

2 つ目のレイヤーは、あらゆるコマンドができることを制限することで、固定された境界を強制します。

1. **権限ルール、コマンド解析、フック**は、各アクションを実行前に、設定されたルールと照らし合わせてチェックします。
2. **サンドボックスとエグレス許可リスト**は、許可されたコマンドが触れられる範囲と、データの行き先を制限します。

本章では判断レイヤーを扱い、次章で固定境界レイヤーを検討します。

### アライメント学習を理解する

Claude は、[明確なルールの一覧に裏打ちされた良識ある判断](https://www.anthropic.com/constitution)を行うよう学習されています。たとえば、重大な損害をもたらしうる悪意のあるコードを書かない、といったルールです。

本番環境のセーフガードを用いない [Claude Code でのテスト](https://www.anthropic.com/document/claude-fable-5-2-mythos-5-2-system-card)では、現行の Claude モデルは悪意のあるリクエストの **81%〜85%** を拒否する一方で、偵察ツールの実行やサイトの脆弱性テストといったデュアルユースや無害なリクエストの **98%〜100%** を完了しました。

また Claude は、[取り返しのつかないアクションよりも慎重なアクションを好み](https://www.anthropic.com/constitution)、即興で対応するのではなく懸念を表明したり指示を仰いだりするよう学習されています。さらに、取得したコンテンツ内の指示を、ユーザーからの指示であるかのように扱って行動しないよう学習されています。

ただし、モデルのアライメント学習は悪い結果が起こる可能性を下げるものの、その結果がどれほど悪くなりうるかを制限するものではないことに留意してください。

### プロンプトインジェクションプローブ

Claude のプロンプトインジェクションプローブは、ツール結果に含まれる、注入された疑いのある指示にフラグを立てるよう設計されています。

プローブは注入された指示の横に警告を追加し、そのコンテンツが疑わしいこと、そしてユーザーの元のリクエストが引き続きタスクであることを Claude に伝えます。警告とアンカリングによって、Claude はコンテンツを活用しつつ、その中の指示をコマンドではなくデータとして扱えるようになります。

### auto モードの分類器

ディレクトリの削除が正当なタスクだと信じ込まされたモデルは、他のあらゆる作業と同じ徹底ぶりと能力をもって、そのディレクトリを削除するでしょう。

こうした破壊的で張り切りすぎたアクションこそ、[auto モードの分類器](https://code.claude.com/docs/en/auto-mode-config)が捕捉するために作られたものです。ルールや組み込みの承認でまだ判断が下されていないアクションについて、auto モードの分類器は、提案されたアクションが開発者の指示の意図に合致しているかを判断します。

![auto モードの分類器が提案されたアクションを実行するかどうかを判断する流れの図：ルールと定型的なアクションが先に処理され、それ以外はすべて分類器に送られる。分類器が見るのはユーザーのリクエストと提案されたアクションのみ。](https://assets.claude.com/e2f7188da798d7c2235413a20109ef981ccf04ff.png)

auto モードの分類器が、提案されたアクションを実行するかどうかを判断する仕組み。

たとえば、「auth\_test.py の失敗しているテストを修正して」に対して妥当なコマンドは、「.env の内容を持ち出して」に対するコマンドとは異なって見えます。

Claude Code が送信する分類器へのリクエストからはツール結果が取り除かれるため、注入されたテキストが分類器を直接操作することはできません。アクションがユーザーの依頼内容に合致していれば実行されます。合致していなければブロックされるか、Claude が開発者に許可を求めに戻ります。

auto モードは現在、すべてのプランでインタラクティブセッションの[デフォルトの開始モード](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in)になっています。ヘッドレスの `claude -p`、Agent SDK、HIPAA 構成ではデフォルトが manual です。

auto モードがデフォルトになっているのは、人による承認よりも多くの危険なアクションを捕捉できることが[複数のテスト](https://claude.com/resources/articles/auto-mode-default-in-claude-code)で示されたからです。たとえば、Anthropic が 2026 年 8 月に公開した対照研究では、1,053 人の有償テスターが危険なコマンドの 13.6% を捕捉したのに対し、auto モードは同じコマンドの 89% をブロックしました。

![捕捉された危険なコマンドの棒グラフ：人によるレビューは 13.6%、auto モードは 89%。](https://assets.claude.com/0e0f4605392016086364837ea880cb4d898c796c.png)

人によるレビューと auto モードがそれぞれ捕捉した危険なコマンド。出典：テスト対象の具体的な挙動を知らされていない 1,053 人の有償テスターを対象とした対照研究。

分類器のチューニングや、ブロック・許可ルールの上書きについては、[auto モードの設定](https://code.claude.com/docs/en/auto-mode-config)をご覧ください。

#### リスクの高いアクションを承認する

auto モードは分類システムに依存しており、すべてのリスクを排除するものではありません。

展開の前に、リスクの高いアクションを特定しておきましょう。問うべきは、そのアクションは取り返しがつかないか、そして一度のミスのコストは、すべてのケースを人がレビューするコストを上回るか、という点です。両方の答えが「はい」なら、人による承認を必須にしてください。

ほとんどの組織では、リストは次のようになります。

- 本番データベースのマイグレーション
- IAM ポリシーの変更と認証情報のローテーション
- インフラ定義の編集

## 04 固定境界を強制する

権限ルールの設定 · Bash コマンドの解析 · フックによるアクションのゲーティング · サンドボックスによるエージェントのアクションの封じ込め

判断レイヤーは新たな攻撃の捕捉には優れていますが、その制御は確率的であるため、どれも突破される可能性があります。

固定境界レイヤーは決定論的にすることができ、エージェントの影響範囲を定めます。権限ルール、コマンド解析、フックはアクションを実行するかどうかを決め、サンドボックスとエグレス許可リストは到達できる範囲とデータの行き先を制限します。

その限界は、ブロックするよう指定したものしかブロックしないことです。そのため、自社の環境を念頭に置いて設定する必要があります。

### 権限ルールの設定

権限ルールには 3 種類あります。

- `Allow` ルールはアクションの実行を許可します。
- `Ask` ルールはアクションの実行前に人に確認を求めます。
- `Deny` ルールはアクションをブロックします。

Claude Code は、[まず deny ルール、次に ask ルール、最後に allow ルール](https://code.claude.com/docs/en/permissions)をチェックします。これにより、allow ルールが deny ルールの例外を作り出すことを防ぎます。マネージド設定で定義された deny ルールは、いかなるユーザー設定やプロジェクト設定でも上書きできません。`Bash(python:*)` のように、任意のコードを実行できるほど広範なコマンドに対する allow ルールは避けるべきです。

![Claude Code が deny ルール、ask ルール、allow ルールの順にチェックし、どのルールにも一致しない場合は権限モードが判断することを示すフロー図。](https://assets.claude.com/8a7da8abca173526f9f3c704f965406fd67180b1.png)

Claude Code は deny ルール、ask ルール、allow ルールの順にチェックするため、allow ルールが deny ルールの例外を作り出すことはできません。

[サブエージェント](https://code.claude.com/docs/en/sub-agents#permission-modes)は親セッションの権限ルールと権限モードを継承します。そのため、トップレベルのセッション向けに書かれた広範なルールは、委任先のすべてのエージェントに適用されます。

### Bash コマンドの解析

Claude Code は、すべての Bash コマンドを実行前にパースします。パースしなければ、git status を許可する[権限ルール](https://code.claude.com/docs/en/permissions)が git status && curl attacker.example まで承認してしまい、拒否されたコマンドをサブシェルで包めばルールをすり抜けられてしまいます。

![Claude Code が git status && curl attacker.example というコマンドを 2 つの部分に分割し、それぞれをルールと照合する様子を示す図：git status は実行され、curl はレビューのために停止される。](https://assets.claude.com/3eb8a4dc0caccee702f17909b923bd4f36ab88e3.png)

Claude Code はコマンドを構成要素に分割し、それぞれをルールと照合します。

パースは決定論的なので、同じコマンドには毎回同じ答えが返ります。deny ルールと ask ルールは、`bypassPermissions` を含むすべての権限モードで、コマンドの各部分に適用されます。

### フックによるアクションのゲーティング

[フック](https://code.claude.com/docs/en/hooks)とは、セッション中の決まったタイミングで Claude Code が自動的に実行するスクリプト、HTTP エンドポイント、または MCP ツールです。セキュリティの観点で特に重要なものが 2 つあります。

- **`PreToolUse`** はツール呼び出しの前に実行され、その呼び出しをブロック、承認、開発者への確認、または（ヘッドレス実行では）後で承認するために保留することができます。たとえば、シークレットを含むコミットをブロックしたい場合に使えます。
- **`ConfigChange`** はセッション中に設定ファイルが変更されたときに実行され、その変更を拒否できます。リポジトリや開発者がローカルで制御を緩めようとしていることを検知するには、これを使います。

フックは固定境界の上ではなく、その内側に位置します。PreToolUse フックはツール呼び出しをブロックできますが、`"allow"` を返すフックが deny ルール、ask ルール、あるいはクリティカルパスの削除を超えて承認することはできません。

マネージド設定で定義されたフックはすべてのマシンで実行され、個々の開発者が削除することはできません。[`allowManagedHooksOnly`](https://code.claude.com/docs/en/hooks) はさらに踏み込み、ユーザー、プロジェクト、プラグインのフックの実行そのものを防ぎます。これにより、エージェントに届くフックはプラットフォームチームが設置したものだけになります。

### サンドボックスによるエージェントのアクションの封じ込め

サンドボックスは、エージェントのスコープを制限するため、インシデントの深刻度を封じ込める最も重要な手段の 1 つです。しかし、エージェントの封じ込めは言うは易く行うは難しです。制約と能力は多くの場合、反比例の関係にあるからです。

Claude Code の主な環境は、ローカル、サンドボックス付きローカル、クラウドの 3 つです。

ここでは、それぞれのデフォルト設定と、組織内の各ユースケースにどれが適切かを検討する方法について説明します。デフォルトは変更して一元的にロックすることができます。これについては次章で扱います。

#### ローカル

Claude Code のセッションの大半は、ターミナル、IDE、またはデスクトップアプリを通じてローカルで行われます。デフォルトでは、エージェントはあなたがアクセスできるコンピューター上のあらゆるものにアクセスできます。auto モードでは、ルールや組み込みの承認でまだ判断されていないアクションを分類器がレビューします。

これは最も封じ込めの弱い環境であり、リスクが低く自己完結した作業に適しています。ほとんどのエンタープライズ組織には、ローカルセッションでのサンドボックスの強制をおすすめします。

#### ローカルサンドボックス

Claude Code のサンドボックスは、各シェルコマンドを OS レベルで分離します。そのため、例外が承認されない限り、コマンドはプロジェクトフォルダ内のファイルしか変更できず、許可リストにあるサイトにしか接続できません。

![ローカルサンドボックスの図：コマンドはプロジェクトフォルダを変更でき、保護されたファイルはロックされたまま、新しい Web サイトへのアクセスはチェックポイントを通り、コンピューター上のそれ以外のものは変更できない。](https://assets.claude.com/aabbaac0e88f3064fc95654d2bc63f5577613fb3.png)

コマンドはプロジェクトを変更できます。それ以外のものには、壁かチェックポイントが立ちはだかります。

デフォルトでは、開発者または auto モードの分類器が安全だと判断すれば、エージェントがサンドボックスの外で動作したり、許可リストにないサイトにアクセスしたりすることを承認できます。

[マネージド設定](https://code.claude.com/docs/en/managed-settings)（詳しくは次章で説明します）を使えば、管理者はローカルサンドボックスの利用を必須にし、エージェントのコマンドをそのサンドボックス内に封じ込め、エージェントが[一元的に承認されたサイトのみにアクセス](https://code.claude.com/docs/en/sandboxing#network-isolation)できるようにすることができます。

エージェントをサンドボックスに封じ込めたら、プロジェクト外のファイルを読み取って認証情報にアクセスすることで抜け出されないようにしたいところです。認証情報の漏洩に対抗するため、管理者は組織の認証情報のパスに対する Read deny ルールを追加し、さらに[認証情報のマスキング](https://code.claude.com/docs/en/sandboxing#mask-credentials)を設定できます。これにより、コマンドは実際の値を一切保持することなくサインインできます。

#### クラウドセッション

[**Claude Code のクラウドセッション**](https://claude.dev/blog/claude-code-in-the-cloud/)は、Anthropic が管理する環境上で実行され、タスクごとに専用の VM が割り当てられます。これにより Claude が実行できる場所が封じ込められるだけでなく、GitHub の認証情報も VM の外に保たれます。

クラウドセッションは、信頼できないコンテンツを読み込む作業や、無人で実行される作業に適しています。デフォルトで開発者のマシンや社内ネットワークから分離されており、VM はいつでも破棄できるからです。

![Claude Code のクラウドセッションの構造：各セッションはリポジトリのクローンを持つ新しい VM で実行され、GitHub プロキシとセキュリティプロキシは VM の外側に置かれる。](https://assets.claude.com/44050228876da8e6828dcf77a83330fc9966e677.png)

クラウドセッションの構造：各セッションは新しい VM で実行され、GitHub の認証情報は VM の外に保たれます。

開発者が新しいクラウド環境を作成すると、Claude は限られた[プリインストールツールと許可ドメイン](https://code.claude.com/docs/en/cloud-environments#default-allowed-domains)のセットで起動しますが、開発者は例外を追加できます。開発者は、毎回のセッションでクローンするリポジトリを選択する必要があります。

![クラウド環境の設定ダイアログの例。ネットワークアクセス、ネットワークシークレット、セットアップスクリプト、環境変数の項目がある。](https://assets.claude.com/eaa627f67288a6d195be2c3f194138f6766064d9.png)

クラウド環境の設定画面の例。

組織のオーナーは、デフォルト環境を設定し、個々の開発者が変更できない設定を持つ共有環境を公開できます。

開発者は引き続き新しい環境を作成し、その環境設定を変更できます。これをロックする必要がある組織は、自社で立ち上げて運用するインフラ上で Claude Code を実行し、セッションを自らホストすることで、それらのセッションのポリシーを管理します。

なお、ゼロデータリテンション、HIPAA 構成、またはカスタマー管理の暗号化キーを利用している組織では、クラウドセッションは利用できないことにご注意ください。

## 05 ポリシーを強制する

一元設定の概要 · どの設定が適用されるか

これまでの章ではデフォルト設定を取り上げました。以下の表では、さらに 2 つの構成を取り上げます。

1 つは **baseline（ベースライン）** と名付けたもので、代替のデフォルト、つまり個々の開発者が追加していける出発点を作りたいときに選ぶものです。

もう 1 つは **locked（ロック）** と名付けたもので、開発者レベルでは変更できないルールのセットを管理者が固定する方法です。設定をロックすることで、文書化されたポリシーが、強制されるセキュリティ制御へと変わります。

これは設定を網羅したリストではなく、エージェントのリスクに上限を設けるうえで鍵となる観点に絞ったものです。

### 一元設定の概要

|  | **ローカルセッション**マネージド設定で設定 | **クラウドセッション**claude.ai の管理者設定で設定 |
| --- | --- | --- |
| **利用を許可するか？** | デスクトップアプリでは無効化できる（`disableDesktopLocalSessions`）が、ターミナルでは不可 | 組織単位のクラウドセッションのトグル |
| **どの程度封じ込めるか？** | **Baseline:** すべてのローカルセッションでサンドボックスを有効化（`sandbox.enabled`）**Locked:** サンドボックスなしでの実行やサンドボックス外での再試行を禁止（`failIfUnavailable`、`allowUnsandboxedCommands: false`） | **Baseline:** オーナーが Cloud environments ページでメンバーが変更できない設定を持つ共有環境を作成し、その 1 つを組織のデフォルト環境に指定**Locked:** 自社で運用するインフラ上で Claude Code を実行する。Anthropic がホストする環境では、開発者は引き続き独自の設定で個人用環境を作成できる |
| **どこに接続できるか？** | **Baseline:** 開発者が追加できる、承認済みサイトの管理リスト（`sandbox.network.allowedDomains`）**Locked:** 管理側のリストのみを有効にする（`allowManagedDomainsOnly`）。このリストはシェルコマンドに適用されるため、WebFetch ツールは専用の権限ルールで制限する | **Baseline:** デフォルトでは Anthropic の信頼済みリスト（パッケージレジストリ、GitHub、クラウド SDK）、またはオーナーが各共有環境に設定したネットワークアクセス（コネクタ、GitHub、Anthropic API のトラフィックはこの設定では制限されない）**Locked:** [セルフホスト環境](https://code.claude.com/docs/en/self-hosted-environments)（パブリックベータ）を使用し、自社のネットワーク境界で接続を制限する。Anthropic がホストする環境には組織全体の許可リストはない |
| **何を読み取れるか？** | **Baseline:** 機密パスに対する Read deny ルール（`permissions.deny`）**Locked:** ファイルツールの読み取りをプロジェクト内に制限し、指定パスをブロック（`permissions.blockReadsOutsideWorkingDirectories`、`sandbox.filesystem.denyRead`） | **Baseline:** 同じ Read deny ルール**Locked:** 完全なロックはない。Claude GitHub App を承認済みリポジトリに限定し、セッションがクローン・プッシュできる対象を制御する。開発者は引き続きターミナルからローカルリポジトリをアップロードできる。 |
| **どの認証情報を使えるか？** | Read deny ルールで認証情報ファイルをブロックし、認証情報のマスキングを設定（`sandbox.credentials`） | オーナーはキーを共有環境の Network secrets として保存し、決して環境変数には置かない。 |

### どの設定が適用されるか

マネージド設定がセッションに届く経路は 3 つあります。Claude 管理コンソールからのサーバー管理設定、MDM または OS レベルのポリシー、そしてマネージド設定ファイルです。Anthropic がホストするクラウドセッションに届くのは、サーバー管理設定のみです。

![マネージド設定のソースを優先順位順に示した図：サーバー管理設定、MDM または OS ポリシー、マネージド設定ファイル、そして HKCU レジストリ。いくつかのキーはすべての管理ソースから読み取られる。](https://assets.claude.com/e35ee53fc465db82afbb8f031f5b30e98be5bf5f.png)

デフォルトでは、Claude Code はポリシーキーを持つ最初のソースを使用します。managedSourcesBehavior を "merge" に設定すると、管理ソースが統合されます。

デフォルトでは、[Claude Code はこの順序で最も優先順位の高いソースのみを適用し、それ以外は警告なしに無視します](https://code.claude.com/docs/en/managed-settings#how-claude-code-combines-managed-sources)。MDM プロファイルでサンドボックスを有効にし、マネージド設定ファイルにエグレス許可リストを置いている場合、その許可リストは適用されません。

## 06 はじめに

本ガイドで紹介した制御はレイヤーとして機能し、それぞれが他のレイヤーの見落としをカバーします。1 つのリポジトリでパイロットを実施すれば、展開を広げる前に、自社の環境でレイヤーがどのように機能するかを確認できます。

パイロットのチェックリスト

**リポジトリを階層化し、ベンダーレビューを実施します。** エージェントが触れるリポジトリを機密度でランク付けし、第 1 章の要件に照らしてプロバイダーを確認します。

**最も低い階層からリポジトリを 1 つ選びます。** たとえば、活発に開発中の社内ツールなどです。実際のセッションが十分に発生する程度に活発で、見落としがあってもコストが小さい程度にリスクの低いものを選びましょう。

**一元的なポリシーのベースラインを展開します。** サンドボックスを strict モードで有効化し、認証情報のパスへの deny ルール、認証情報のマスキング、エグレス許可リスト、auto モードを設定します。デフォルトのクラウド環境を設定・構成します。`security-guidance` プラグインと、譲れないルールを強制するためのフックを追加します。

**記録を有効にします。** ツールの内容を含む OpenTelemetry エクスポート（ベータ）を有効にし、サンドボックスとエグレスのログが保持されていることを確認します。

**ポリシーを変更せずに 2 週間運用します。** そうすることで、すべての結果を 1 つの構成にさかのぼって追跡できます。

**各レイヤーが何をしたかを振り返ります。** 分類器による拒否、サンドボックスによるブロック、サンドボックス外での再試行の試み、拒否されたエグレスを確認します。それぞれが、制御が役割を果たした結果か、ベースラインが想定していなかった正当なニーズのどちらかです。deny ルールを緩めるのではなく、作業に必要だった許可リストのエントリを追加しましょう。

**2 つ目のチームへ展開を広げる前に、**第 1 章の 5 つの質問に照らしてパイロットを評価します。

正しく実施すれば、このセキュアなフレームワークは、コーディングエージェントを最大限のスピードで活用するチームの力を、妨げるのではなく加速させるでしょう。
