# Datadog はどのように Claude Code のための「万能工作機械」を作ったか

エージェント化、機械化、そして工業化

Datadog のエンジニア全員が本番コードに AI コーディングツールを使っており、そのうち少なくとも 3 分の2 は Claude Code が担っています。Datadog では Claude Code を使い、ソフトウェア開発ライフサイクルの中で 4 つの異なるカテゴリに沿ったパーソナライズされたフローを生み出しています。

- **的を絞った変更**: 厄介なバグ修正、パフォーマンス最適化、既存サービスへの橋渡しを何十件も。
- **大規模なリファクタリング**: カスタムの protobuf パーサーを 3 日でリファクタリングしたり、メトリクス制御を FoundationDB から Postgres へ 3 か月足らずで書き換えたり。
- **大部分の置き換え**: 新しいシャーディングアルゴリズムやオートスケーリングの再設計。
- **システム全体の構築**: MongoDB を Postgres へ置き換える、BYOC のコントロールプレーン、ゼロから作るインジェスションパイプラインなど。

しかし、この地図の上を作業が流れていくにつれ、一方の軸では生成がより複雑になり、もう一方の軸では検証がより曖昧になっていくことが分かってきました。

## フローの問題

エンジニアにとって、フローとはかつて意図とコードの間の直接的な関係を意味していました。問題を理解し、コードを書き、テストし、レビューし、出荷し、運用し、それを繰り返す。しかしエージェントの登場によって、その抽象化は急速に変わりつつあります。

「もうコードを書いているのではなく、作業を形作っているのです。エージェントに何を見せるべきか、どんなツールを持たせるべきか、成功とは何か、失敗をどう検知すべきかを決めている。まるで全員がマネジメントチェーンを 3 段階も昇進させられたようなものです。エンジニアとしてはそんなこと望んでいなかったのに」と Datadog のエンジニアリング担当 VP、Sesh Nalla 氏は語ります。

[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) のようなアプローチにより、Datadog のセッションはより長く、時には数日間にわたって実行されます。それぞれのエージェントが独自のツール、独自のグルーコード、独自の慣習を発明します。エージェントはずっと有用になる一方で、エージェントの実行と人間向けに設計されたツールとの間のギャップを埋めるには人間の手が必要になります。

工作機械とは、製造業で見かける治具、固定具、ゲージ、フライス盤のことです。これらは精密で再現性のある部品を生み出し、それをエンジン、航空機、原子炉、月面着陸船といった、より大きく複雑な機械へと組み立てていきます。工作機械は工業化のブレークスルーであり、それによって部品が組み合わせ可能で、検査可能で、交換可能なものになりました。

Temper は、Sesh 氏が「エージェント型システムのための万能工作機械」を Datadog なりに試みたものだと表現するプロジェクトです。言い換えれば、エージェントが安全かつ精密に必要なものを構築するために必要な、最小限のカーネルです。

「もっと構造的な何かが必要だと感じた瞬間でした」と Sesh 氏は言います。「エージェントが私たちのシステムの大部分、つまりミッションクリティカルなデータベースを構築し運用していくのであれば、この工作機械という概念に相当するものが必要です。Temper は Datadog にとってのその工作機械なのです。」

## Temper への道のり

機械化とは、エージェントがより多くの作業を担うようになることを意味します。そして工業化とは、作業が反復可能で、検証可能で、制御可能で、スケール可能になることを意味します。Datadog では、これは一度に起きたわけではありません。Temper に至る道のりは、Courier、BitsEvolve、Helix という 3 つの別プロジェクトを経てきました。それぞれのプロジェクトが次のボトルネックを露わにし、彼らの野心を大きくしていったのです。

2024 年、彼らは分散キューイングシステムである [**Courier**](https://www.datadoghq.com/blog/engineering/formal-modeling-and-simulation/) を導入しました。ゼロから完全に手作業で構築するのに 1 年かかりました。

「難しかったのは部品を作ることではなく、部品同士の相互作用を観測可能、テスト可能、検証可能にすることでした」と Sesh 氏は言います。「そのため、フォーマルモデリングとシミュレーションを厳密に行い……ミスが高くつく、あるいは元に戻すのが難しい部分を特定して、そこの厳密さを引き上げました。」

2025 年 9 月、彼らはクローズドループの進化的最適化ハーネスである [**BitsEvolve**](https://www.datadoghq.com/blog/engineering/self-optimizing-system/) を構築しました。モデルの合議体がコードのバリエーションを生成します。[ベンチマーク](https://www.datadoghq.com/blog/ai/production-grounded-code-optimization/)、テスト、本番環境の可観測性の連鎖が、何が生き残るかを決めます。

「これは私にとって、ソフトウェアの一部が生物のように育てられるのだという初めての気づきでした。変異とフィードバック、適応を通じて成長していくのです」と Sesh 氏は言います。

問題は、進化は適応する環境次第でしか良くならないということであり、BitsEvolve のボトルネックはこのフィードバックループでした。そこで彼らは、Kafka に匹敵するストリーミングサービスである [**Helix**](https://www.datadoghq.com/blog/ai/fully-autonomous-optimization/) を構築しました。構築のほとんどを Claude Code が担い、人間は 1 人が舵取りをしただけでした。

「信じられないことに、数日で完全に機能する Kafka 相当のシステムができあがりました」と Sesh 氏は言います。「構築はあっという間で、シャドーイングを始めてみると、コストを 2 倍から 5 倍削減できる可能性が見えてきました。」

しかし本番投入にはさらに多くの走行距離が必要でした。運用面の堅牢化は、時間をかけて、複数の人手によって初めて得られるものであり、これは今もなお展開の途上にあります。

「ボトルネックは再び移動しました。エージェントはシステムの大部分を構築できるようになった……しかし人間は依然として、人間向けに作られたツールや仕組みを通じて本番へと出荷するために調整をしなければなりません」と Sesh 氏は言います。

Datadog に必要だったのは、検証済みでポリシー駆動型のランタイム環境の中で、エージェントが自らのツールを構築できる方法でした。そのランタイムが [**Temper**](https://github.com/nerdsane/temper) です。

## Temper

エージェントはどんなチームが手作業でレビューするよりも速くコードを生み出せますが、間違いも犯します。

Sesh 氏にとって、エージェントが生成するものと検証を通過するものとの間のギャップこそ、失敗モードが積み上がる場所です。しかし、従来のコードベースにエージェントを単純に組み合わせるだけでは、それをスループットの問題として扱うことになり、検証のギャップそのものは埋まりません。

Temper はこの等式を逆転させます。アプリケーションコードを生成する代わりに、エージェントは仕様を生成します。カーネルは各仕様を読み込み、4 層の分析を通じて検証し、その仕様が記述するとおりに動くシステムをデプロイします。仕様が証明の対象であると同時に実行の対象でもあるため、検証された内容と実際に動いている内容との間にズレが生じません。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a5f892116fdac8cb7ef2661_17085ded.png)

「Temper はシステムの*中心*を変えます。エージェントはもはや、ローカルな必要に応じてつながりのないツールを発明し続ける必要がありません。代わりに、意図と問題領域の仕様として、精密な記述を生成します。それは治具や CNC マシンと同じ意味での工作機械です。ネジ山がどうあるべきかの仕様を与えれば、非常に再現性の高い動きをします。それを使って航空機のような複雑なものすら構築できるのです」と Sesh 氏は言います。

つまりこの場合、エージェントは毎回その場で最終的な仕組みを即興で作るわけではありません。精密な記述を生成し、Temper（あるいは Temper のような仕組み)と共に反復して、まずは動くものを作り、それを後から反復可能で、チェック可能で、再利用可能なものへと変えていくことができます。そうすることで、実際にコードベースの周りにソフトウェアファクトリーを構築できるようになるのです。

それぞれのケイパビリティは 3 つの契約によって記述されます。

- **振る舞い (Behavior)**: 状態、遷移、事前条件、そして満たされなければならない安全性の性質。
- **データ契約 (Data contract)**: エンティティの型、そのプロパティ、そして各型がサポートするアクション。これらは機械可読な形式で公開されるため、エージェントはドキュメントなしで API の全体像を発見できます。
- **認可 (Authorization)**: デフォルト拒否、スコープベースの承認。拒否は保留中の判断として記録され、人間が承認してポリシーエンジンにホットロードできます。

すべての仕様は、カーネルが読み込む前に 4 つの独立した層を通過します。シンボリック推論は、各ガードが充足可能であり、各不変条件が帰納的であることを証明します。網羅的な状態探索はすべての到達可能な状態を巡ります。

決定論的シミュレーションは、シードを与えた障害注入(ドロップ、遅延、順序の入れ替え、クラッシュ)を伴って実際の本番コードパスを実行するため、同じシードの下で障害を正確に再現できます。

ランダム化されたプロパティテストは、約 1,000 個の疑似ランダムなアクション列を実行し、違反があればそれを最小限の反例へと縮小します。小さな仕様であれば、このカスケード全体が 1 秒足らずで完了します。

## Helix のためのダークファクトリー

Simon Willison 氏は「ダークファクトリー」という言葉を広めました。これは、仮想の工場フロアで人間なしにエージェントが働き続けるソフトウェアプロセスのことです。Helix のダークファクトリーにおいて、Temper は 3 つの役割を果たします。

Temper は managed agents のための**エージェント制御プレーン**です。セッション、ロール、作業キュー、ライフサイクルを司ります。また、エージェントが SDLC のツール群(Git、CI、デプロイ)と小さな Temper アプリとを橋渡しする**ツールビルダー**層でもあります。そして、ワークロードを稼働させるデータプレーンを取り巻くライフサイクル面である **Helix 制御 API** でもあります。

「驚いたのは、これがエージェントインフラよりもずっと汎用的なものに感じられ始めたことです。よく見れば、多くのソフトウェアはデータベース API の周りの制御ロジックにすぎません。状態、変更に関するポリシー、ライフサイクルの遷移、外部システムとの連携。Temper は、私が説明したような形をしたあらゆるソフトウェアに適用できるという意味で、普遍的なものになり得るのです」と Sesh 氏は言います。

## なぜ単に CRUD アプリを作らないのか

「Claude Code は [TypeScript や Python で CRUD アプリを構築する] のがとても得意です。ただ、通常の CRUD アプリでは、制御ロジックはルート、データベースの制約、サービスコード、バックグラウンドジョブ、ドキュメントに散らばっています。良いテストとカバレッジがあったとしても、一般的には状態マシンの形を取る運用モードは、コードベースの中に暗黙的に埋め込まれたままです」と Sesh 氏は言います。

「Temper はその状態マシンを明示的にします。エージェントは任意のコードではなく、精密な記述を生成します。コンパイルのステップは LLM の外側にあります。ちょうど Rust のコードを Rust コンパイラに渡すのと同じです。遷移テーブルはデータであって、サービスメソッドの中に埋め込まれたスパゲッティな制御フローではありません。エージェントは安全にそれを動的に変更し、CI を経由せずにホットリロードできます」と彼は説明します。

## この先にあるもの

Temper の背後にある発想は、それぞれの成果物は人間の頭の中に収まるくらい小さくあるべきだ、というものです。航空や金融システムのような高保証ソフトウェアは何十年もこのやり方で構築されてきましたが、人間の手でその厳密さを実現するコストは、エージェントが登場するまでは一般的なソフトウェアにとって高すぎました。

産業革命が可能になったのは、工作機械によって部品が組み合わせ可能で、検査可能で、交換可能になり、それによってどんどん大きく複雑な機械を構築できるようになったからです。

「もしエージェントがこの種の規律をもって、ファクトリーの中で自律的にソフトウェアを構築できるなら、私たちはダークファクトリーで立ち止まる必要すらないかもしれません。このように構築されたソフトウェアは、フィードバック、選択、適応を通じて育て、耕し、進化させていける有機体のように感じられ始めます」と Sesh 氏は言います。
