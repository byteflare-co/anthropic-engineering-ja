# 本番環境で auto mode を運用する
- 執筆者

  Molly Vorwerck

[auto mode は Claude Code のデフォルト設定](http://claude.com/blog/auto-mode-default-in-claude-code) になりました。エージェントが実行しようとするコマンドを一つひとつ承認してもらう代わりに、分類器が各アクションを評価し、有害と思われるものをブロックします。

auto mode の設計は、エージェント型コーディングにおける「速度か安全性か」というよくあるトレードオフを解決します。すべてのコマンドをレビューすれば人間をループに残せますが、セッションが数時間に及んだり並行して増えたりすると、その監視自体がボトルネックになります。かといって権限チェックを完全にスキップすれば速くはなりますが、プロンプトインジェクションやスコープの逸脱、時には本番リソースの誤削除がすり抜けてしまう原因にもなります。

auto mode はそのギャップの大部分を埋めます。社内評価では、この分類器は開発者が権限プロンプトを手作業でクリックしていたときよりも多くの危険なアクションを検知し、その性能はサードパーティによるレッドチーミングでも維持されました。そしてセッションの中断が減ることで、Claude Code 全体の利用において、以前のデフォルト設定と比べて中断なく作業できる時間が 9 倍に伸びています。

auto mode が本番環境でどのように機能しているかを見るため、私たちは Nuro、Gusto、Garner Health のチームに話を聞き、本番環境で速度と安全性のバランスを取るために、彼らがどのように、そしてなぜ auto mode を日常のツールとして使っているのかを尋ねました。

### Nuro における長時間稼働の自律エージェントの強化

普遍的なレベル 4 の自動運転技術を開発する物理 AI 企業 Nuro は、2025 年末に Claude Code を導入し、3 月までには社内で最も人気のあるエージェント型コーディングツールになりました。

auto mode がリリースされる前、スタッフソフトウェアエンジニアの Kai Zhou 氏はすでに社内向けの代替案をプロトタイピングしていました。保留中のアクションをそれぞれ小さなモデルに送り、日常的な作業の 90% は自動承認し、機微なものは人間がレビューできるよう Slack に回す、というフックです。このプロトタイプは実際の緊張関係に応えるものでした。エンジニアたちは承認プロンプトの子守りをするのを嫌がっていましたが、会社のセキュリティ・法務の観点からは、権限チェックを完全にスキップすることは危険すぎて認められなかったのです。auto mode がリリースされると、Kai 氏はこのサイドプロジェクトを棚上げしました。

現在、Kai 氏は自分が書くすべてのコードで auto mode を使っています。

「いちいち承認をクリックするために座っていたくないんです」と Kai 氏は語ります。「コーディング作業の 100% で auto mode を使っています。たいていは 3、4 個のセッションを auto mode で並行して開き、必要なときだけ確認しています。」

例外は、他のチームに関わる作業です。例えば Claude Code が代理で Pull Request をレビューするときは、Kai 氏はインタラクティブモードに切り替え、公開前に一つひとつ確認します。

auto mode も無制限に動作するわけではありません。Nuro は [スキル](https://agentskills.io/home) を多用しており、再帰的な削除のような最も危険なコマンドは、設定でエンジニアが完全に拒否しています。分類器はそのガードレールの内側で判断を下しています。

しかし、auto mode がもたらした最大のブレークスルーは、エンジニアがその日の作業を終えた後も動き続けるタスクを開始できるようになったことです。具体的には、Kai 氏のチームは auto mode を使って、自動運転スタックの背後にある評価指標を地道に改善し続ける長時間稼働のリサーチエージェントを動かしています。これは、エージェントが自律的に反復できる明確で測定可能なシグナルを持つタスクです。

一晩の間に、エージェントは評価スイートが検出した偽陰性を調べ、提案を起草し、実験を実行し、結果に基づいて反復を続けることができます。このアプローチは、明確な評価方法を持つあらゆるタスクに応用できます——Nuro の別のチームは特定のバイナリのメモリフットプリントを縮小するために使っています——なぜなら指標自体が、改善しているのか後退しているのかをエージェントに教えてくれるからです。

「先日、夜の 10 時にエージェントを起動したら、朝の 5 時まで動き続けて、朝には 3 つの PR を仕上げてくれていました」と Kai 氏は言います。「かなり印象的だと思います。こういう働き方を可能にするのは auto mode だけです。」

### Gusto における PR の高速かつ安全な出荷

中小企業向けテクノロジー企業のリーディングカンパニーである Gusto では、auto mode への移行は積極的なセキュリティ強化として始まりました。

同社の AI Dev Tools チームで働く Martin Emde 氏は、権限疲れがチームの速度を落としているのを見てきました。auto mode は制御やセキュリティを犠牲にすることなく同じ速度を実現し、エンジニアリング組織全体に導入が浸透して以来、権限に関する全体的な負担は明らかに減少しています。

Martin 氏は 12 月以降、auto mode を日常のツールとして 2,425 件の Claude Code セッションを起動してきました。かつてはフォルダアクセスの承認で止まっていたリポジトリ横断の作業も、今では中断なく実行できます。また、GitHub、Slack、Jira からデイリーノートをまとめるといった無人ジョブも自律的に実行されています。同氏のチーム自身の分析によると、2026 年 5 月中旬以降のセッショントランスクリプトの約 10% に auto mode による拒否が含まれており、分類器が正当なタスクの足を引っ張ることなく実際に機能している証拠だとしています。

「auto mode のおかげで、速度と制御の間でより安全なバランスが取れるようになりました」と Martin 氏は言います。「繰り返しのプロンプトを取り除き、安全性を損なうことなく生産性を高めることができました。auto mode が適切なタイミングでブロックしてくれることが分かるので、自信を持ってスピーディーに動けます。」

Gusto の AIT Cloud Engineering チームのメンバーである Chad Kunsman 氏も、別の角度から同じ結論にたどり着きました。彼の仕事——エンドポイント調査、ログ監査、コネクタ管理、MCP サーバー群にまたがるドキュメントの取り込み——は、一晩がかりのマラソンではなく、20 分程度の短いバーストで進められます。彼が求めていたのはより長時間の実行ではなく、悪意あるプロンプトやプロンプトインジェクションがすり抜けてしまうリスクを負うことなく、bypass permissions と同じ手離れの良さを得ることでした。

「プロンプトインジェクションに対する保護があり、自分がやっていることが本当に頼んだことと合致しているかをチェックしてくれる点で、bypass permissions よりも良い選択肢であり、権限プロンプトよりもはるかに速いです」と Chad 氏は言います。

分類器が実際に介入してくる稀なケースについても、Chad 氏はそれが的を射ていると言います。「止められたとき、それには納得できましたし、なぜ止めたのかも説明してくれました。もともと頼んだこととズレていて、確認を求めてきたんです。的外れなことは全くありませんでした。」

それでも Chad 氏は、最も機微な作業では auto mode を外します。セッションが本番インフラ——Terraform、AWS、稼働中の API への直接の POST リクエスト——に踏み込むときは、accept edits に切り替え、ツール呼び出しを一つひとつ手作業で検証します。「節約できる時間と、それが合理的に犯しうるミス、そしてそのミスがどれほど破滅的になりうるかを天秤にかける必要があります」と彼は言います。「結局のところ、何が起きるかについてはあなた自身が責任を負うのです。」

こうした判断は、より広範な多層防御の仕組みの中で機能しています。Gusto は MCP トラフィックを、ツールガードとプロンプト検査を備えたガバナンス付きプロキシ層経由でルーティングしており、auto mode が判断を下す前の時点で、エージェントはすでに厳格に制限された権限で動作しています。

### Garner Health におけるソフトウェア開発ライフサイクル(SDLC)の加速

ヘルスケアテクノロジー企業の Garner Health は、2 月にすべての職能にまたがる 550 名の従業員全員に Claude Code を導入しました。このツールは Salesforce、Zendesk、Snowflake を含むすべての基幹システムに組み込まれており、従業員は自分の仕事の中で最も反復的な部分を自動化するために、週に約 2 時間を費やすよう推奨されています。

auto mode 以前、この規模には運用オーバーヘッドが伴っていました。Garner のプラットフォームエンジニアリングマネージャーである Evan Magnussen 氏は、承認済みコマンドのリストを手作業で整備し、パイプで連結されたコマンドが拒否されるのを見守るという、退屈な繰り返し作業として権限管理を表現しています。

現在、Evan 氏とその同僚のほとんどは、コードベースの調査から MCP 経由での外部連携管理まで、あらゆるセッションで auto mode を使っています。

「auto mode があってはじめて実現できたことですが、エンジニアリング組織全体のために標準化されたソフトウェア開発ライフサイクルを構築しました」と Evan 氏は言います。「従業員はそれを肩の荷が下りたことだと捉えています。もう何時間もエージェントを監視し続ける必要がなくなったのです。」

そのライフサイクルは、標準化されたスキルのプラグインとして動作します。エージェントはタスクを引き受け、アクセスできるコンテキストを調査し、コンテキストファイルをリポジトリにコミットし、Evan 氏が「敵対的リサーチ」と呼ぶ、自らの前提を検証するプロセスを実行してから実装に進みます——人間が介入するのは、自力では見つけられないコンテキストが必要になったときだけです。Evan 氏によれば、このリサーチ主体の段階は auto mode 以前には実現できなかったものです。

分類器はそのままの状態でもほとんど調整が必要ありませんでした。Evan 氏が行った唯一の調整は、Nuro の Kai 氏と同じ発想です。Slack メッセージやメールの送信など、他者とのコミュニケーションを伴うアクションは承認しないよう auto mode を設定しました。

「自分が誰かとコミュニケーションを取っているときに、Claude が勝手に代理として動くのは個人的に好きではありません」と同氏は言います。中核的な知的財産に関わるチーム——auto mode 以前は権限チェックのスキップに最も懐疑的だった人たち——は、自分たちの作業に合わせて分類器に注入するプロンプトをより厳格にしたり緩くしたりする調整の仕方を身につけました。

他の企業が auto mode を導入する際のアドバイスは何かと聞くと、こう答えました。前のめりになり、エンジニアの力を引き出しつつ安全な展開を確保できるような、適切な統制を構築することだと言います。「もし『みんな自分でワークフローを作ってください、テレメトリはありません』と言っていたら、それは非常に危険だったでしょう」と Evan 氏は言います。「テレメトリがあり、比較的標準化されたワークフローを構築してきたからこそ、私たちははるかに大きな自信を持てているのです。」

***[***auto mode***](https://code.claude.com/docs/en/auto-mode-config) を Claude Code で使ってみましょう。***
