この 1 年、私たちは小売、マーケットプレイス、旅行、エンターテインメント、通信事業者など、コマース業界全体のチームと協力し、Claude を使ったコマースエージェントを構築してきました。

**01**

## アーキテクチャ

長い裾野を skills でカバーし、すでに運用しているシステムを呼び出すツールを備えた、標準的なエージェントループの中の 1 つのモデル。これは一度決めれば済むことです。

### **コマースエージェントとは何か**

私たちは、コマースエージェントを「オンラインカタログ全体にわたる売買を簡素化するエージェント」と定義しています。

消費者と向き合うエージェントもあります。検索し、比較し、代替品を提案し、注文を組み立てます。それは小売のカート、旅行の旅程、モバイルプランの変更、あるいは公演の座席の確保かもしれません。ビジネス側と向き合うエージェントもあります。売上に関する質問に答え、プロモーションやキャンペーンを実行し、在庫や価格を管理します。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a97121e31e08caa3a0e6679_02653800.png)

中核となるアーキテクチャは、[標準的なエージェントループ](https://www.anthropic.com/engineering/building-effective-agents)の中の 1 つのモデルです。ゴールについて推論し、コンテキストを探索し、ツールを通じて行動を起こし、skills を通じて手順を学び、明確化のための質問をし、ゴールが達成されるまで結果を観察します。

その手前で会話をセグメント分けするインテントルーターもなければ、その後ろにドメインごとのエージェント群を控えさせることもありません。

### **エンジニアリング上のコンテキスト**

#### **サブエージェントではなく skills を使う**

コマースエージェントは多くのカテゴリーにまたがる幅広い能力をカバーする必要があるため、ドメインごとにサブエージェントを 1 つずつ作りたくなります。

しかし実際には、これは最適ではないことが分かっています。なぜなら、コマースの会話は複数のインテントとターンにまたがる、密結合な 1 つのセッションであり、大きな共有コンテキストを必要とするからです。

サブエージェント型のアーキテクチャでは、オーケストレーターがカートや保留中の変更、ユーザーの好み、そして会話履歴を保持します。

サブエージェントへのハンドオフは、そのたびに状態の一部が失われる操作であり、サブエージェントの応答の品質、ひいては全体の応答の品質に影響することが多くあります。それに加えて、ハンドオフ 1 回あたり、トークン消費が何倍にも膨らみ、レイテンシも数秒単位で増加します。

ドメインはそもそもきれいには分離できないことがほとんどです。返品フローには注文履歴、現在のカート、商品カタログが必要になることがあり、これはドメインごとにサブエージェントを分ける方式では、そのアクセス権をあらゆる場所で重複させるか、タスクの途中でハンドオフするしかないことを意味します。

モデルが賢くなるにつれ、より長いコンテキスト、より多くの skills、より多くのツールを扱えるようになるため、今日の配置ルールの背後にある制約も、モデル世代が進むごとに緩んでいきます。

その代わりに、[agent skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) を使えば、ハンドオフのコストをかけることなく、ドメインごとのモジュール性とコンテキスト制御を得られます。skill の指示は、すでに全履歴を保持しているメインエージェントの中に読み込まれるからです。

複数のエンタープライズ展開にわたる私たちの比較では、skills を備えた単一エージェントが、「1 つのプロンプトですべてをこなす」設計とサブエージェント設計の両方を品質面で一貫して上回り、しかもタスクあたりのコストとレイテンシが低くなることが多いという結果が出ています。

サブエージェントが真価を発揮するのは、オーケストレーターが、専用のコンテキストウィンドウを持つことで恩恵を受けられるような、狭い範囲の自己完結型タスクのためにサブエージェントをツールとして呼び出す場合です。

よくある本番の例は、ディープリサーチ用のサブエージェントです。サブエージェントがドキュメントを検索・読解し、コードを書いて実行し、データモデルを辿り、行き止まりに突き当たります。作業はすべて 1 つ以上のサブエージェントの中で完結し、オーケストレーターに戻ってくるのはコンパクトな回答だけです。

もう 1 つの例外は、すでにそのドメイン専用に作られたエージェントが存在する場合です。もし薬局や金融サービスの体験が、独自のコンプライアンス面を持つ専用エージェントによって動いているのなら、適切な選択はハンドオフであり、そのエージェントがタスクを引き継ぎ、自身のループを通じてタスクが完了するまでユーザーと直接やり取りします。

この違いは会話の所有権にあります。ハンドオフはドメインエージェントをユーザーのカウンターパートにするのに対し、委譲はオーケストレーターが所有権を保持したまま、1 ターンの中でドメインエージェントを出し入れし、やり取りのたびに劣化させていきます。

#### **システムプロンプトか skill か: 頻度で決める**

一連の指示をシステムプロンプトに入れるか skill に入れるかを決める主な要因は、エージェントがそれをどのくらいの頻度で必要とするかです。skill の読み込みにはモデルのターンが 1 つ余分にかかるため、ほとんどのターンでエージェントが必要とするものは、基本的にシステムプロンプトに入れます。

ただしこれは、トラフィックの分布や、evals が示すエージェントの挙動にも左右されます。良い出発点は、ローンチ前に想定していたか本番で観測されたかを問わず、トラフィックの 3 分の 1 以上に関係するものはシステムプロンプトに入れ、残りは skills に入れる、というものです。

skill がすでに持っているシグナル (ユーザーがどのページから来たかなど) から予測可能であれば、最初のモデル呼び出しの前にハーネス側から注入し、skill を読み込むための余分なターンを省くことをお勧めします。

安全性や法務上のルール、ブランド上の制約、アレルギーなど重要なユーザーの事実といった重要な指示は、常にシステムプロンプトに入れます。

コマースエージェントの場合、これはほぼすべてのセッションで商品検索に触れるため商品検索がプロンプトに入り、skills が機能の長い裾野を担うということを意味します。

[リファレンス実装](https://github.com/anthropics/commerce-agents)では、ショッピングエージェントのプロンプトがグラウンディング、カートとチェックアウトのセマンティクス、提示のルールを保持し、残りは以下の skills がカバーします: search-discovery、purchase-research、planning-goals、customer-care、memory-personalization。

マーチャントエージェントも同様の分割で、performance-insights、catalog-listings、inventory-operations、pricing-promotions、marketing-campaigns がそれぞれ 1 つの業務ドメインに対応する skills です。

**プロンプトの中**  *ショッピングエージェント*  グラウンディング、カートとチェックアウトのセマンティクス、提示のルール、商品検索。

**ショッピング skills**  *長い裾野*  search-discovery · purchase-research · planning-goals · customer-care · memory-personalization

**マーチャント skills**  *業務ドメインごとに 1 つ*  performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns

### **エージェントのツールを設計する**

[エージェント向けの効果的なツールの書き方](https://www.anthropic.com/engineering/writing-tools-for-agents)についての記事では、ツール設計全般を扱っています。コマースにおいてとりわけ重要だった点が 2 つあります。

**エージェントのツールは、既存の中核システムとロジックの上に構築する。**

コマース企業はすでに、検索とランキング、カート、好みとプロフィールのストア、在庫システム、プロモーション・キャンペーンエンジン、売上分析などを持っており、それぞれが何年もかけて調整されてきたロジックを備え、モデルが決して見ることのないシグナルを見ています。

エージェントのツールはこれらのシステムを呼び出すべきであり、再実装すべきではありません。ツールの境界とは、これらのロジックが終わり、モデルの判断が始まる場所です。

たとえば、エージェントが `search_products` を呼び出すとき、結果はすでにランク付けされた状態で返ってくるべきです。エージェントの仕事は、どの結果がユーザーのゴールに資するか、いくつ表示するか、どう提示するかを判断することです。

**ツールの結果はコンテキストである。**

モデルが推論に使うフィールドだけを返し、それ以外は落としましょう。検索結果の全行に画像 URL を付けるのは、よくある問題です。

必要に応じて、ツールの内部で生のレスポンスを整形し直しましょう。データからは明らかでない次のステップを追記することも含みます。

これはエラーのシナリオでとくに重要です。モデルはエラーコードよりも指示から恩恵を受けます。たとえば、汎用的な 403 の代わりに「在庫確認をクエリする際は商品 ID を含めてください」というエラー指示を追加するといった具合です。

#### **UI コンポーネントはツールである**

コマースエージェントの応答のほとんどは、商品カルーセル、旅程、座席マップ、チャートなど、散文ではなく UI コンポーネントです。つまりエージェントはテキストではなくスキーマを出力する必要があります。

チームは最初、モデルにカスタムタグを出力させ、クライアント側でパースするところから始めることがあります。しかしこれは、次の理由で表面が広がるにつれ立ち行かなくなります。

- モデルはツール呼び出しほどには独自のマークアップについて訓練されていないため、ネストしたコンポーネントが増えるほど信頼性が下がります。プロンプトだけで整形されたデータが保証されるわけではありません。
- タグの定義はシステムプロンプトの中に存在するため、新しいコンポーネントを追加するたびにコンテキストが肥大化し、編集のたびにプロンプトの他の部分で回帰が起きるリスクがあります。
- 過去の会話が、自前のパーサーでしか読めない形式で保存されることになります。履歴を読み込むには、生のメッセージをクライアント側でパースするか、モデル API にとってネイティブでない形式で二重にコピーを保持するかのどちらかが必要になります。

うまくいっているパターンは、各 UI コンポーネントをツールにすることです。モデルは `present_products`、`present_itinerary`、`present_plan_comparison` を型付きの引数で呼び出し、サーバーがその呼び出しを検証・拡充してイベントを発行し、クライアントがそれをレンダリングします。

これらのコンポーネントはツール呼び出しであるため、すでにメッセージ配列の中にネイティブな形式で存在しており、古い会話を読み込むときに再パースする必要がありません。提示用ツールの契約の例を下に示します (また[リファレンスリポジトリ](https://github.com/anthropics/commerce-agents)にもあります)。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a971accf6d9dcde640f87df_presentationtool.gif)

トレードオフはストリーミングの粒度です。ツール呼び出しの各トップレベル引数はサーバー側で検証のためにバッファされるため、ストリーミングを有効にしていても、提示用ツールのサブコンポーネントは段階的に到着します。これは体感レイテンシに影響します。

トークンレベルのストリームを得るには、ツール定義で `eager_input_streaming:` を true に設定します。これによりバッファリングがスキップされ、それとともにサーバー側のスキーマ保証もスキップされます。

私たちの evals では、Claude Sonnet クラス以上のモデルでスキーマ違反は非常に稀ですが、それがすり抜けるケースに備えて呼び出しをリトライでラップしてください。

提示用ツールは、画面上に何が表示されているかの記録もエージェントに残します。顧客が「最初のホテル」や「左下から 3 番目」と言ったとき、レイアウトはメッセージ配列の中、つまり直近の提示用呼び出しの引数の中にあります。

これを機能させるには、引数がレンダリングされたレイアウトを反映している必要があります。そのため、クライアントが並べ替えるフラットなリストではなく、UI が構造化されているのと同じように、順序付きの行やカルーセルとして構造化してください。

## 高速かつ低コストにする

エンドツーエンドと体感の両面からレイテンシを攻め、コストはキャッシングに任せましょう。そのどれもが、知性を犠牲にすべきではありません。

コマースにおいてレイテンシは重要であり、消費者向けの面はもっとも容赦がありません。しかし、エージェント型の面において、リテンション、エンゲージメント、カートサイズといった指標を一貫して動かしてきたのは成果の品質でした。

回答が的確だったか、タスクが実際に完了したかどうかは、わずかなレイテンシの改善よりもこれらの指標にとってはるかに重要でした。

そのため、レイテンシは 2 つの前線から攻めましょう。優れたエンジニアリングによってエンドツーエンドのレイテンシを最小化し、それと合わせて体感レイテンシを下げます (エージェントが作業している様子を見ている時間は、進捗として読み取られるためです)。

すべてのユーザーにはレイテンシの予算があり、以下の手法は、知性を犠牲にすることなくエージェントをその予算内に収めるためのものです。

### **タスク完了レイテンシを最小化する**

タスク完了レイテンシとは、モデルのターンごとの、最後のトークンまでの時間とツール処理時間の合計です。これは、取り組むべき 3 つのレバー、つまりターン数を減らす、ツールを高速化する、トークンを高速化する、を与えてくれます。これらのレバーは互いに競合することがあるため、最小化すべきなのはどれか 1 つではなく、その合計です。

**ターン数を減らす**  ありそうなコンテキストを事前に読み込み、モデルの知性を高め、独立したツールを並列に呼び出させる。

**ツールを高速化する**  ツール自体のバックエンドを最適化し、引数が揃い次第、ツールを即座にディスパッチする。

**トークンを高速化する**  eval スイートを掃引して、モデルとその設定を選ぶ。

#### **ターン数を減らす**

クエリの複雑さはターン数を増やしますが、これは概ねコントロールできません。モデルの知性と関連するコンテキストは、エージェントがより少ないターンでタスク完了に至るのを助けます。この領域での主な学びは以下の通りです。

- **ありそうなコンテキストを事前に読み込む。** ユーザーが商品ページからアシスタントを開いた場合や、マーチャントがキャンペーンダッシュボードから開いた場合は、そのページのデータをセッションコンテキストに入れておきます。会話はおそらくそれに関するものであり、コンテキストから答えれば追加のターンはかかりません。
- **モデルの知性を高める。** より賢いモデルは、エージェントがより効率的にプランを立ててツール呼び出しを発行できるため、タスク完了までの全体のターン数を減らせることがあります。これは、トークン生成が遅いことをしばしば上回るメリットです。クエリが複雑になりがちであったり、本番でタスクあたり 5 ターンを超える場合、より高速なモデルとは往々にしてより賢いモデルのことです。どちらがそれに該当するかはトラフィックに依存するため、後述の「モデルを選ぶ」の通り、掃引によって選んでください。
- **モデルに独立したツールを並列に呼び出させる。** コマースのユースケースでは、複数商品の検索、多数のポリシー文書へのクエリ、多くの売上データソースからのレコード取得など、多くの操作を並行して行う必要がしばしばあります。並列ツール呼び出しにより、複数の独立したクエリが余分なターンを消費しないようにできます。1 ターンの中で多くのツールを呼び出し、その結果を 1 つのユーザーメッセージにツール結果の配列として返すよう、モデルにプロンプトしてください ([並列ツール利用のドキュメント](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)を参照)。

#### **ツールを高速化する**

- **ツール自体のバックエンドを最適化する。** ツールが本当に扇状に広がることもあります。たとえば「今日のスナップショットを取得する」というクエリを持つマーチャントエージェントは、売上、在庫、キャンペーン状況を 3 つの独立した呼び出しで読み取ります。しかし、私たちがよく目にするのは、ツールの境界が、本来バックエンドにあるべきロジックの欠落を埋め合わせる場所になってしまっているケースです。たとえば、在庫確認がカタログから SKU を取得し、店舗ごとに在庫サービスを呼び出し、フルフィルメントサービスから締め切りを取得したうえで、代替ルールと店頭受け取りの可否をツール自身のコード内で適用してから答えを返す、といった具合です。このツールはドメイン知識を過剰に抱え込んでおり、ルールが変わるたびに正しさを保つのが難しくなり、本来は上流のシステムにあるべきロジックを抱えていることになります。ツールの中でこうしたロジックを書いていることに気づいたら、正しい修正はそれに答える 1 つのバックエンドのエンドポイントを作り、エージェントツールからそれを呼び出すことです。
- **ツールを即座にディスパッチする。** ツールの引数は他のトークンと同じようにモデルからストリームで出力されるため、ハーネスは各ツールの引数が揃い次第その呼び出しを実行し、モデルが他の並列ツールやコンテンツブロックをまだストリーミングしている間にそれを処理できます。私たちはこれによって数秒単位のギャップが数百ミリ秒にまで縮まるのを見てきました。[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) はデフォルトでこれを行います。レイテンシの改善を最大化するには、もっとも時間のかかる呼び出しを最初に出力するようモデルにプロンプトしてください。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a971b4ebf113390b39a25b2_eagerdispatch.gif)

### **体感レイテンシ**

体感レイテンシとは、ユーザーが画面上で何かが起きたと感じるまでの時間です。取引の摩擦がチェックアウト率と収益に直結する消費者向けのユースケースでは、これはとりわけ重要です。モデル自体に手を加えることなく体感レイテンシを縮める手法が 2 つあります。

- **形成されつつあるコンポーネントをストリーミングする。** レンダリングされたコマースの応答は通常 500〜700 出力トークンで、ストリーミングなしではスピナーが 5 秒以上表示されることになります。提示用ツールの各パラメーターがストリームされるたびにクライアントへ送り、ページを段階的にレンダリングしましょう。
- **作業の様子を見せる。** エージェントがコンテキストを収集している間、各ステップに対応する短い進捗行を平易な言葉でレンダリングします (たとえば「海沿いのホテルを探しています」)。これは、商品検索のクエリなど、ツールの既存の引数から組み立てることも、モデルにその行を書かせる追加の user_facing_message パラメーターを持つツールを追加することもできます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a971b28c43d0f061e80bc6c_perceivedlatency.gif)

*上の 2 つのパネルは、同じエージェント、同じツール、同じプロンプトで動作していますが、ハーネスだけが異なります。合計時間はほぼ同じですが、ユーザーが何かを目にするまでの時間はかなり違います。*

### **プロンプトキャッシング**

プロンプトキャッシングは最大のコスト削減候補であり、コマースのトラフィックはそれにうってつけです。キャッシュされた入力トークンの読み取りコストは新規読み取りの 10 分の 1 で、キャッシュ書き込みには約 1.25 倍のプレミアムがかかるものの、キャッシュされたプレフィックスは 2 回目の利用で元が取れます。トラフィックの多い消費者向けアプリケーションでは、もっとも安価なデフォルトの 5 分間のキャッシュ有効期限を使って、非常に高いキャッシュ率を達成できる独自の機会があります。

私たちが目にしたもっとも優れたコマース展開は 90〜99% のキャッシュヒット率で稼働しており、それが最初から設計すべき目標範囲です。私たちの経験では、キャッシュされたトークンの読み取りは約 10 万トークンで約 1.5〜2 倍高速になり、トークン数が増えるほどほぼ線形にスケールします。

キャッシングはプレフィックスベースです。リクエストは、以前のリクエストと異なる最初のバイトまでキャッシュから読み取るため、重要なのはコンテキストに何が含まれるかだけでなく、その順序です。リクエストを、変化する頻度でソートされた 3 つのセグメントとして考えてください。

- **グローバル**: システムプロンプトの大部分とツール定義で、すべてのセッションで同一です。これがもっとも「温まった」キャッシュであり、規模が大きくなれば期限切れにならない可能性が高くなります。ターンやセッションをまたいでバイト単位で同一に保ち、その末尾にキャッシュのブレークポイントを置きます。
- **セッション**: セッションごとのコンテキストと会話履歴で、セッション間では異なりますが、1 つのセッション内では安定しています。このセグメントはグローバルセグメントの後に続きます。
- **揮発性**: 現在時刻や現在のページなど、セッション内で変化するものです。これはリクエストの一番最後、最新のユーザーターンのタグ付きブロックとして、あるいは[会話の途中に挿入できるシステムメッセージ](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)をサポートするモデルではメッセージ配列に追加するシステムロールのメッセージとして置きます。私たちがもっともよく目にする間違いは、タイムスタンプや現在のページをシステムプロンプトの先頭に置いてしまい、リクエストのたびにキャッシュを黙って壊してしまうことです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a970f654fd654f0e7990b95_c63ca0e7.png)

ここで覚えておくべき実装上の詳細が 2 つあります。第一に、skills はシステムプロンプトに追記するのではなく、ツール結果として読み込むべきです。そうすれば skill の本文は会話のプレフィックスに乗り、それと一緒にキャッシュされます。

第二に、ブレークポイントは各ターンで前方に転がしてください。1 つのリクエストで許されるブレークポイントの数には上限があるため、最新のものを各ユーザーターンの末尾に移動させます。そうすれば、検索レスポンスのような長いツール結果を含む、蓄積された履歴を各ラウンドでキャッシュから読み取れます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a97109fd7957fb6e5b0facf_f48075ed.png)

### **モデルとその設定を選ぶ**

[モデルサイズとエフォート設定](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)は同じトレードオフ、つまり知性とレイテンシ・コストのトレードオフであり、両方とも測定によって選ぶべきです。

1. **指標と下限を決める。** ビジネスが依拠する品質指標 (タスク完了率、回答の的確さ、根拠のある正確さ) と、それを下回ってはいけない eval スコア、そして p50 と p99 のレイテンシおよびコストの予算を決めます。
2. **掃引する。** 検討対象の*すべての*モデルとエフォートレベルにわたって、eval スイート全体を実行します。私たちは、分析負荷の高いタスクを扱うマーチャントエージェントには Opus から、レイテンシがより重視される消費者向けエージェントには Sonnet から始めることをお勧めします。本番トラフィックがあれば、実際のクエリの構成比で結果を重み付けしてください。そのうえで、数字に決めさせましょう。カートを動かすタスクでの Opus 5 の伸びが、Sonnet とのコスト差を正当化することもあれば、そうでないこともあります。
3. **結果を注意深く読む。** チームを驚かせることが定期的に 2 つあります。1 つ目は、プロンプトはモデルに合わせてチューニングされるため、あるプロンプトで実行した掃引が、そのプロンプト向けに書かれていない他のモデルの性能を過小評価してしまうことがあるという点です。小さいモデルは通常、現行モデルが自力で推論できるような指示を必要とし、大きいモデルは、小さいモデルが無視していた指示にも忠実に従います。各候補の失敗ケースに対して数回イテレーションを回すことは、どれかを除外する前に踏むべき安価なステップです。2 つ目は、より知性の高い設定のほうが、トークン生成が遅いにもかかわらず (もっともよくあるのは p90 と p99 で) レイテンシで勝つことがあるという点です。これは、ツール呼び出しをより上手にプランニングし、もっとも複雑なリクエストでのラウンド数が少なくて済むためです。

モデル呼び出しごとではなく、完了したタスクごとにコストを測定してください。ターン数が多くなったり、失敗が増えたりする安価なモデルは、実は安くないからです。結果が僅差で、コストがタスクあたりの経済性とレイテンシに収まっているなら、知性を選びましょう。品質こそが採用とリテンションを牽引するものであり、モデルが今後 6 か月でより優れたものになっていく余地を作ってくれます。

## 本番環境で運用する

メモリ、安全性、evals、そして組織全体への展開。これらが、エージェントを本番環境に到達させ、そこに留まらせるものです。

最後に、エージェントを本番運用に乗せ、そこに留め続けるもの、すなわちメモリ、安全性、evals、そして組織全体での展開について話します。

### **セッションを超えて残るメモリ**

顧客との関係とやり取りは重要です。メモリとは、エージェントが何もない状態から始めるのではなく、前回の会話の続きから再開できるようにする仕組みです。3 月にナッツアレルギーについて話したショッパーが、6 月にそれを繰り返す必要はないはずですし、毎週月曜に同じ 3 つのキャンペーンを確認するマーチャントが、そのたびにキャンペーン名を挙げる必要もないはずです。長期メモリ、つまりセッションをまたいで残るべき事実は、あなたが構築するシステムであり、それには 3 つの要素があります。事実がどう保存されるか、どう書き込まれるか、どう読み出されるかです。

#### **メモリを保存する**

メモリはモデルの中ではなく、あなたのシステムの中に置くべきです。

プロフィールが小さく、エージェントだけがそれを読む場合は、フラットな markdown プロフィールでも機能します。ほとんどの本番のコマースエージェントはそれを超えて成長するため、実用的な置き換え先は、あなたがすでに運用しているデータベースです。1 つの事実は、小さな型付きレコードです。キー (shoe_size、default_store、preferred_report_cadence など)、短い値、カテゴリー、そしてそれが由来するセッションから成ります。一部のキーは事前に決めておき全ユーザーが持つものにし、残りは抽出器が発見します。データベースであれば、ストアが大きくなってもクエリ可能であり続け、特定の属性に対する決定論的な振る舞いを構築でき、すでに持っているユーザーデータと結合できます。

マーチャント向けエージェントでは、アカウント単位ではなく人単位でメモリをキーにしてください。マーチャントのログインはオペレーター間で共有されることが多いため、各オペレーターは自分自身のプロフィールを必要とし、読み取りはそのオペレーターの権限を尊重しなければなりません。店舗マネージャーのエージェントは、地区マネージャーが述べた事実を思い出すべきではありません。

コマースの領域では、エージェントのメモリは個人データを保持します。記憶しておく価値のある事実は、しばしばもっとも規制の厳しいものであり、法域ごとにルールも異なります。メモリを単なるストレージの問題ではなく、データ取扱いの設計上の問題として扱ってください。実務上、これは次の 4 つを意味します。

- **保持を許可するメモリの種類を決める。** これはプロンプトだけでなく、すべての保存操作が通るバリデーターによって書き込みパスで強制します。
- **保存されているものをユーザーが確認・修正・削除できる手段を用意する。** 削除をアカウント削除やデータ請求のフローに組み込みます。
- **保持期間を設定する。** 数年前の好みはすでに古くなっている可能性が高いため、保持期間はメモリの事実を新鮮に保つ助けになります。
- **メモリはデプロイメントごとに切り替えられるスイッチにする。** これにより、こうした義務を負えないリージョンでもメモリなしで運用できます。

#### **メモリを書き込む**

メモリは非同期に書き込んでください。各ターンの終わりに、あるいは長いセッションでは数ターンごとに、別のスレッドまたはプロセスにいるエージェントが会話を読み、ストア内の事実を作成・更新・削除します。これにより、セッションが進む間もエージェント自身の作業用コンテキストは保たれます。

これは会話のレイテンシに何も追加せず、私たちの社内コマースメモリ eval スイートでは事実の再現率が 13% 向上しました。

明白な代替案である、エージェントが事実を保存するために呼び出すツールは、レイテンシに敏感なコマースエージェントには不向きです。すべての保存操作はユーザー向けターンの中でのツール呼び出しとなり、ストア全体がコンテキストにない限り、保存には更新や重複排除のための読み取りがまず必要になり、それ自体が 1 ラウンドを消費します。

さらに、これは毎ターン、エージェントの前にもう 1 つ決定事項を突きつけることになり、私たちの evals ではその注意の奪い合いがメモリの取りこぼしという形で現れました。

抽出器を分離することで、それに正確なプロンプトを与えられるようにもなります。抽出器はユーザーとアシスタントのテキストのみを読み、ツール結果は決して読まないため、商品説明やレビューがユーザーに関する事実になってしまうことはありません。そのプロンプトは、何が事実としてカウントされるか (明示されたサイズ、食事制限、配送の好み、マーチャントがいつも見るマテリアライズドビューなど) と、何がそうではないか (商品一覧からの情報や一度きりの詳細など) を規定します。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a9713df298bf7d2c29e81e1_7480b230.png)

#### **メモリを読み出す**

メモリは 3 つの層で読み出します。

**常にコンテキストに含める**  ショッパーのデフォルトの店舗や配送の好み、オペレーターの店舗や役割など、ほぼすべてのリクエストが依存する少数の固定された事実は、毎ターンコンテキストに入れます。

**ターンごとに事前取得する**  現在のリクエストに関連する事実は、skill を事前読み込みするのと同じシグナルからターンごとに事前取得します。靴の検索であればサイズとブランドの好みを引き、キャンペーンに関する質問であればオペレーターがいつも見る指標を引きます。

**ルックアップツールの背後に置く**  それ以外のすべてはルックアップツールの背後に置きます。

メモリはユーザーごとのコンテキストであるため、そのすべてはグローバルなキャッシュのブレークポイントより下の、セッションセグメントに入ります。

### **安全性: 強制はハーネス側で行う**

安全な振る舞いはプロンプトから始まりますが、コマースにおいてそれを強制する場所にはなり得ません。失敗は金銭的であり、しばしば取り返しがつきません。プロンプトのルールは、1 回のインジェクションや 1 回の外れたサンプルでスキップされてしまいます。以下のすべてのルールは、消費者向けエージェントとマーチャントエージェントの両方で、コード側で強制されており、一度定義すればすべてのランタイムで共有されます。

#### **モデルはステージングし、実行するのは人かポリシーである**

モデルのツール呼び出しが、直接お金を動かしたりビジネスを変更したりすることはありません。注文の確定、支払い、返金、価格変更、キャンペーンの開始はすべて、モデルではなくハーネスが制御するアクションで終わります。

消費者側では、これは構造的に保証されています。チェックアウト用ツールは注文確定ボタン付きのカートをレンダリングするだけであり、エージェントが呼び出すバックエンドのインターフェースには課金メソッドがそもそも存在しません。

マーチャント側では、すべての書き込みツールがサーバー生成の ID を持つ保留中の変更を作成し、`apply_change` は、オペレーターのポータルのボタン、CLI での確認、あるいはエージェントが Managed Agents 上で動作している場合はプラットフォーム自身のツール承認プロンプトといった、実際の面を通じて承認された ID に対してのみ成功します。

ガードレールは、変更がステージングされた時点の上限ではなく、適用時点の現在の上限に照らして再チェックされます。どの面であっても形は同じです。モデルのもっとも危険なアクションは提案することであり、承認は、そのビジネスがその種の変更に対してすでに持っているメーカー・チェッカー型のフローを経由します。

#### **書き込みとレンダリングはサーバー発行の ID のみを受け付ける**

ハーネスは、サーバーがモデルに渡したすべての ID をセッションごとに記録しており、その記録だけが、あらゆる書き込みやレンダリングが受け付ける唯一の鍵です。

カートはこのセッションでサーバーが返した商品 ID のみを受け付け、マーチャントツールはエージェントが実際に読み取った出品・キャンペーンの ID のみを受け付けます。それ以外の方法で到着した ID (幻覚によるもの、ユーザーが貼り付けたもの、レビューに仕込まれたものなど) は、バックエンドに到達する前に拒否されます。

同じルールが UI にも適用されます。提示用ツールは ID を受け取り、サーバー自身が商品・注文・変更のレコードを埋め込むため、カードはサーバー自身が埋めたレコードだけをレンダリングします。

これは委譲先にも及びます。マーチャント分析用のサブエージェントはデータを読み取りますが、エージェントが書き込める ID の集合に何かを追加することはありません。

手数料、開示事項、その他の規制対象コンテンツについては、モデルはどの商品を開示するかを選び、サーバーが承認済みのコピーからすべての文言を供給します。同じ手数料フィールドはマーチャントエージェント側の保護リストにも入っているため、どちら側もそれを変更したり言い換えたりできず、evals はレンダリングされた文字列をバイト単位でチェックします。

#### **上限のある取引は、繰り返しのリクエストに対しても保たれなければならない**

ほとんどのコマースの面には、チケットの割り当て、プロモーション価格、不正防止などのために、1 ユーザーが購入できる数量の上限があります。エージェントは、人間がボタンをクリックするのとは違う形でリトライし、言い換え、並列化します。

そのため、上限は書き込み後の状態としてラインごとに強制され、2 回目の「あと 2 つ追加」がそれを超えて積み重なることはありません。また、1 セッションのカート書き込みはシリアライズされ、1 ターン内の並列ツール呼び出しが組み合わさって上限を超えることもありません。

マーチャント側の変更も同様にチェックされ、価格変動、値引き幅、再入荷数量、キャンペーン予算の上限、そしてどの変更も触れてはならない保護フィールドのリストに照らされます。このルールは一般化できます。すべての上限はリクエストではなく結果として生じる状態に対して強制し、書き込みはセッションごとにシリアライズすることです。

#### **サードパーティのコンテンツはサニタイズされる**

コマースでは、コンテキストの大半があなた以外の人 (販売者、レビュアー、競合など) によって書かれているため、バックエンドからのすべての読み取りは信頼できない入力として扱われ、1 つのサニタイザーを通ります。

出品情報、レビュー、ポリシー、販売者からのメッセージ、保存されたメモリなど、サードパーティが作成したすべてのツール結果は、モデルに見せる前にサニタイズされ、固定のラベル付きフェンスで囲まれます。

サニタイザーは制御文字と双方向テキスト制御文字を取り除き、フェンスマーカーを模倣するものを除去し、会話のターンやツール呼び出しを模倣するテキストを無力化し、サイズに上限を設けます。これは、悪意のある出品情報がシステムになりすましたり、コンテキストを埋め尽くしたりするのを防ぐために設計されています。

プロンプト側は、この契約のもう半分を担います。フェンスで囲まれたテキストは報告すべき材料であって、決して行動の根拠にしてはならないというものです。

### **Evals: 非決定的なシステムを出荷する**

小さなプロンプトの変更から新しいツールに至るまで、あらゆるものが予測しづらい形でエージェントの振る舞いを変える可能性があり、出荷しようとしている変更自体は、しばしば回帰の原因にはなりません。Evals は、デプロイする前にそれを見つけるための手段です。[エージェント向け evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) についての以前の記事では、一般的な実践を扱っています。このセクションでは、コマースエージェントに特有の点を扱います。

**会話ではなくスナップショットを評価する**

モデルの API はステートレスなので、エージェントの出力はシステムプロンプト、ツール、メッセージ配列の関数です。つまり、コマースの会話が到達しうるあらゆる状態は、直接構築できます。したがって、eval ケースを作るとは、テスト用の状態を構築し、テスト用のユーザーメッセージを追加し、そこからエージェントを実行させることを意味します。

そのうえで、結果を採点します。最終的な状態と、レンダリングされた応答 (直近の書き込みの引数を含む) です。ほとんどの場合、エージェントがそこに至った経路を採点することはお勧めしません。そのようなテストケースは壊れやすく、制約が強すぎるためです。

第 2 のモデルがユーザーを演じ、ジャッジが会話全体を採点する、シミュレートユーザー型の evals は、測定手段としては貧弱です。2 つの非決定的なシステムが相互作用すると、より大きなサンプルサイズが必要になり、トライアルあたりのコストも高く、判定も難しく、原因の特定が困難な失敗が生じます。これらはカバレッジのギャップを見つけたり、エージェントの全体的な「感触」を確認したりするのには有用なので、ケースを発見するために使い、その後は各ケースをスナップショットとして書き起こしましょう。

#### **厳しい条件下での振る舞いを評価する**

ほとんどのチームは、注入された状態を正しくテストできていません。ケースは、タスクだけでなく失敗の前提条件もエンコードするべきです。ある振る舞いが、いくつものツール呼び出しを含む立て込んだ最初のターンの後や、セッション前半での矛盾の後にしか現れない場合、クリーンな状態から始まるケースはどの設定でも通過してしまい、有意義なデータを何も提供しません。

私たちの観察では、ほとんどのスイートはこうしたクリーンな状態のケースに偏っています。長く、雑然とした、あるいは矛盾を含む履歴から始まるケースを一定の割合で含めるようにしてください。

##### **コマースエージェント evals のさまざまな種類をカバーする**

効果的な評価には、望ましい振る舞いと望ましくない振る舞いの両方をテストする必要があります。

すべての肯定的なケースには、対応する否定的なケースを書きましょう。すべての「拒否すべき」に対して「対応すべき」を、すべての「確認すべき」に対して「そのまま実行すべき」を用意します。否定的なケースの欠落は、私たちがスイートの中でもっともよく見つけるギャップです。

以下について評価してください。

- **中核的なリクエスト**: トラフィックの大半を占めるもので、ここでの失敗はほとんどのセッションに影響します。単純な検索、複数制約のリクエスト、商品やプランに関する質問、複数インテントのメッセージなどが含まれます。質問については、価格・在庫・属性のすべてが返されたデータに遡って裏付けられていること、そしてデータが欠けている場合にエージェントがそれを捏造せずにそう伝えることを確認してください。
- **文脈依存のリクエスト**: 画面上のものへの言及、以前のターンから持ち越された制約、既存のカートに対する書き込みなどです。メモリの評価もこのカテゴリーに含まれます。メモリが抽出され、取得され、答えに反映されたことを確認してください。
- **安全性とブランドに関するケース**: 失敗が金銭やユーザーの信頼のコストになるケースです。インジェクションの試み、他ユーザーのデータを読もうとする試み、バイト単位でチェックされる規制対象言語などが含まれます。インジェクションは 2 種類に分けてください。指示がユーザー自身のメッセージから来るユーザー由来のインジェクションと、商品名やレビュー、ツール結果経由で届く Web スニペットに仕込まれたデータ面のインジェクションです。
- **インターフェースの評価**: 適切なコンポーネントがレンダリングされているか、アイテムの上限が守られているか、ユーザー向けテキストに内部識別子が漏れていないかを確認します。タイムアウトと空の結果も忘れずにテストしてください。
- **複数の能力に同時にまたがるリクエスト。** あるオペレーターが「これを 15% 値下げしたら、需要をまかなうだけの在庫は足りている?」と尋ねたとします。これは価格の質問であり在庫の質問でもあります。正しい答えは、在庫予測を添えた値下げをステージングすることです。誤った答えは、どちらか片方だけを行い、もう片方を飛ばすことです。能力ごとに書かれた evals では、それぞれが自分の半分しか採点しないため、これを捉えられません。隣接する 2 つの能力を同時に必要とするリクエストのケースを書き、答えの両方の半分を採点してください。

##### **SME と共に evals を書き、実際のインシデントを活用する**

Product、Legal、Merchant Ops、Customer Care、Category Management のチームメンバーなど、失敗を実際に目にする主題専門家(SME) と協力してテストケースを設計してください。実際の失敗は最良の evals になり、ユーザーフローあたり 50〜100 の eval ケースが良い出発点です。

前述の通り、さまざまな種類のケースを用意するようにしてください。本番のトランスクリプトは、とくに扱いにくいものを含む新しいケースを見つける上で優れた情報源です。コーディングエージェントは、追加のケースや敵対的なバリエーションを生成するのが得意です。[リファレンスリポジトリ](https://github.com/anthropics/commerce-agents)には、私たちが推奨するアプローチで構築された eval 作成用 skill を備えた Claude Code プラグインが含まれています。

#### **大規模な組織での展開**

コマースのエンタープライズでは、エージェントは多くのエンジニアリングチームによって構築されます。検索、チェックアウト、価格、マーケティングテック、カスタマーケア、カタログプラットフォームは、それぞれエージェントが依存するシステムを所有し、それぞれ独自のペースで出荷し、それぞれがツールや skill、プロンプトルールを追加・変更したがります。

サービスとは異なり、エージェントには他を保護する厳密なモジュール境界がありません。プライシングチームによる変更が、チェックアウトとコンテキストウィンドウを共有しているのです。

魅力的に見える解決策は、ビジネスユニットごとに 1 つずつ、システムを多数のサブエージェントに分割することです。Part 1 で議論した通り、私たちは品質上の理由からこれには反対です。代わりに、複数チームでのコラボレーションのリスクを減らすためのプロセスを以下に示します。

- **所有権はシステムに従う。** すべての skill とツールには単一の所有チームがあります。たとえば、プライシングチームはプロモーション用ツールと pricing skill を所有し、ケアチームは注文・返品用ツールと customer-care skill を所有します。共有プロンプトには、共通部分を担当するプラットフォームレベルの単一の所有者と、ドメイン固有部分を担当するドメイン所有者がいます。
- **変更はケースとともに出荷され、CI はそれに応じて選ばれたセットを実行する。** skill を提供するチームは、否定的なケースや隣接する skills との境界ケースを含む、そのケース群も提供します。すべての pull request でスイート全体を実行するのは遅すぎコストがかかりすぎて現実的ではないため、そこから CI 用のセットを構築します。このセットは、トラフィックの多いリクエストとすべての安全性ケースからなる中核セットで構成されます。それに加えて、その変更が触れた範囲のケースを実行します。skill であれば、その skill 自身のケースと隣接する skills の境界ケースです。ツールであれば、それを呼び出すすべてのケースです。共有プロンプトであれば、すべてがシステムプロンプトを読むため eval スイート全体です。複数回の試行にわたる合格率、キャッシュヒット率、ターンあたりのコストでゲートすることをお勧めします。スイート全体を毎晩、そして各リリース前に実行するのも良い習慣です。チームをまたぐ回帰はこれらの実行で捕捉されます。
- **エージェントもリリースカレンダーに組み込まれるべきである。** これは 1 つのデプロイ単位であり、悪い変更はすべてのユーザーに一度に届いてしまいます。プロンプトや skill の変更はまずカナリアコホートに展開し、デプロイなしで 1 つの skill をオフにできるスイッチを持ち、他のシステムをピーク期間の前に凍結するのと同じように、エージェントもピーク期間の前には凍結してください。

こうした取り組みの人間側の側面については、[効果的なヒューマン・エージェントチームを構築する](https://claude.com/blog/building-effective-human-agent-teams)をご覧ください。

## **今後の展望**

本稿で説明していることの大半は、モデルそのものについてではありません。ツールはすでに運用しているシステムを呼び出し、skills はすでに従っている手順をエンコードし、evals はプロダクト要件をテストとして書き起こしたものであり、ハーネスはどんなクライアントに対しても強制するであろうポリシーを強制します。モデルは今後も改善し続け、より良いモデルが出荷されたときには、ここで説明したアーキテクチャは、eval の掃引を伴う設定変更としてそれを取り込みます。それ以外の部分は動き続けます。

プロダクトの面のロードマップについて考えることも重要です。このアーキテクチャはチャットパネルより長く生き残るでしょう。同じエージェントは音声上でも動作でき、ユーザーが尋ねる前に運賃の値下がりに先回りして対応することもできます。すでに evals とツールを持つチームにとって、それらはプレゼンテーション層のプロジェクトです。さらに先を見れば、あなたのストアフロントへのトラフィックの一部は、ユーザーに代わって買い物をするエージェントから来るようになるでしょう。自分のエージェントを範囲内に留めているのと同じ来歴、ステージング、承認のルールこそが、そうしたエージェントに対してあなたのツールを安全に開放することを可能にするものです。

コマースは常に、購買プロセスをできる限りスムーズにすることに報いてきました。エージェントはそれをずっと容易にします。小売、旅行、通信、エンターテインメント向けの、消費者向けとマーチャント向けの両方のエージェントと実行可能なサンプルを備えた、[完全なリファレンス実装](https://github.com/anthropics/commerce-agents)をぜひご覧ください。
