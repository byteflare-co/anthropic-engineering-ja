# AI駆動のコードモダナイゼーション・プロジェクトに備える方法
- 著者

  Jonah Ezekiel

  Lexie Tonelli

*「Notes from the Field」シリーズでは、Anthropic のフォワード・デプロイド・エンジニアが実際の顧客導入から得たベストプラクティスを紹介します。今回は、大規模なコードモダナイゼーション・プロジェクトを管理してきた経験を共有します。*

かつては複数年・全社体制の取り組みとして見積もられていた[コードモダナイゼーション](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)は、いまや数か月([数週間](https://claude.com/blog/ai-code-migration))で完了できるようになりましたが、その両側にある組織的な作業は依然として変わりません。

たとえば、重要な銀行システムへのあらゆる変更は、チェンジマネジメント、レビュー、承認を経なければなりません。これは規制当局や監査人、事業側が求める、堅牢なプロセスです。

こうしたプロセスがあるからこそ重要システムは信頼できるものになっており、それは「各変更は人間が書き、各差分は人間がレビューする」という前提の上に構築されてきました。エージェントが変更の作成を加速させると、ボトルネックは「変更を生み出すこと」から「その変更をめぐって組織を動かすこと」へと移ります。

この記事では、モダナイゼーションに着手する前に企業がすべき作業を扱います。「完了」とは何を意味するのか、変更にはどのような証拠が必要か、認定された変更はどのようにして本番環境に到達するのか、そして実行を開始するために何を準備しておく必要があるのか、といった点です。

このプロセスを6つのステップに分解します。

1. **ターゲットを定義する:** モダナイズ後のコードが備えるべき技術スタックと振る舞い。
2. **証明書を作成する:** 変更がターゲット状態において正しいと見なされるために満たすべき条件。
3. **昇格ポリシーを設定する:** 認定された変更が生成される速度で本番環境に届くための経路。
4. **前提条件を整える:** 環境、CI/CD、レビュー体制、承認プロセス。
5. **エージェント型ワークフローを構築・改良する:** モダナイゼーションを、変更を生み出す多数の小さな並列サブエージェント作業ストリームに分散させる、カスタムの Claude Code [ダイナミックワークフロー](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)。これはターゲット、証明書、昇格ポリシーを軸に構築します。
6. **モダナイゼーションを実行する:** コードベースの小さな一部でワークフローを最初から最後まで検証し、そのうえでスケールさせる。

## **ステップ1: ターゲットを定義する**

**ターゲット**とは、モダナイゼーションの最終状態です。望ましい最終状態によって、以下の表に示す3種類のモダナイゼーションのどれに当たるかが決まります。

### **モダナイゼーションのタイプを見極める**

| タイプ | 内容 | 選ぶべき場面 | ターゲット |
| --- | --- | --- | --- |
| **アップリフト** | 同一スタック内でのバージョンアップ(例: C++11 → C++20)。 | スタック自体には問題がないが、バージョンが遅れている場合: サポート終了したランタイム、未パッチの脆弱性、これ以上アップグレードできない依存関係など。 | ランタイムのバージョンとパッケージ群。 |
| **トランスフォーム** | 振る舞いを固定したままスタックを跨いで書き換える(例: COBOL → Java)。 | スタックそのものが解決すべき問題であり、振る舞いは信頼できる場合。 | アップリフトに必要なものすべてに加え、新しいコードが従うべき言語、フレームワーク、アーキテクチャの規約。 |
| **リイマジン** | 新しいアーキテクチャ上での振る舞いも変更したグリーンフィールドの再構築。 | 振る舞いをコードと合わせて変更する必要がある場合。 | トランスフォームに必要なものすべてに加え、新システムの振る舞いを記した仕様書。 |

どのタイプのモダナイゼーションを行うかは、組織内でしばしば議論の的になります。私たちの経験では、本番運用に最も近い人々は、リスクを抑えるためにスタックだけを入れ替え振る舞いは一定に保ちたいと考えます(トランスフォーム型モダナイゼーション)。一方、そのコードベースと長く付き合ってきたエンジニアたちは、モダナイゼーションを技術的負債の返済の機会にしたいと考え、加えて他の事業側のステークホルダーは、この機会に新しい要件を打ち出したいと考えることが多いです(リイマジン型モダナイゼーション)。

どちらの立場も理にかなっていますが、この問いを未解決のまま残すと、後になって「ある変更が『正しい』かどうか」をめぐる議論として再燃します。どちらの道を進むかについて合意形成することは、初期の摩擦を増やしますが、プロジェクト全体としては流れをスムーズにします。

### **コードベースをマッピングし、振る舞い仕様を作成する**

現行システムを理解することは、ターゲットを定義するための良い最初のステップであることが多いです。旧コードが実際に何をしているかを抽出し、現在の振る舞いの一覧を作成すれば、どの部分を変更または削除すべきか、したがってこのモダナイゼーションがトランスフォームなのかリイマジンなのかを判断しやすくなります。これによって、誰も把握していなかった業務ロジックやエッジケースが明らかになることも少なくありません。

Claude はこうした発見作業の多くを、[誰も構築した覚えのない依存関係をマッピングし、ワークフローを文書化する](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)ことで担えます。[code modernization プラグイン](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)の *assess*、*map*、*extract-rules* コマンドは、ソースの引用付きで業務ルールを掘り起こし、エンジニアがそれをレビューできるようにします。

とはいえ、Claude による発見だけでは、レガシーシステムの振る舞いを完全には捉えきれない場合があります。業務担当者や開発者へのインタビュー、社内ドキュメントがそのギャップを埋めます。コンテキスト収集には最初にある程度の時間がかかりますが、そのコンテキストの質が、その後ワークフローが下すあらゆる判断を左右します。

リイマジンの場合、ターゲットの定義にはさらなる作業が必要です。詳細な振る舞い仕様を書き起こし、ユーザーグループと合意する必要があります。

### **プロジェクトの正当性と目標を定める**

ターゲットの定義と並行して、組織はそもそもなぜこのモダナイゼーションに取り組む価値があるのかを検討すべきです。レガシーシステムのモダナイズは継続的な保守・運用コストを削減しえますが、私たちの経験では、コスト削減がほとんどのモダナイゼーション・プロジェクトの主動機になることはありません。

> リスク低減が、モダナイゼーションの最も重要な便益であることが多いです。プロジェクトを行うかどうかを議論する際は、モダナイズしなかった場合のリスクを考慮してください。

たとえば、未パッチの脆弱性を抱えたシステムは、サイバー侵害や、事業そのものを危険に晒すほど深刻な障害につながりかねません。サポート切れのランタイムや、そのシステムを理解しているエンジニアの減少は、このリスクをさらに悪化させます。

Claude Code のようなエージェント型コーディングツールはモダナイゼーションの所要期間を短縮してきましたが、それでも予算の見積もりは依然として難しく、それが現状維持への傾きを生みます。私たちはいくつかの[大規模なモダナイゼーション](https://claude.com/blog/ai-code-migration)のコストを公開しており、[他社](https://claude.com/customers/lg-cns)も同様に公開しています。これらは大まかな基準として使え、予算見積もりに関する追加のガイダンスをこのガイドの末尾に用意しています。

こうしたプロジェクトを始める際の主な難所は、通常、そのシステムを所有するチームと、それに依存するチームからの社内合意とコミットメントを取り付けることです。多くの場合リーダーシップレベルでビジネスケースを構築し、プロジェクトの目標を定めておくことで、このプロセスは楽になります。これは、後に続く証明書と昇格ポリシーにおけるトレードオフの基準にもなります。ステークホルダー間で、ある変更がどれだけのリスクを許容できるかについて意見が割れたとき、モダナイズしないことのリスクがその重しになります。

## **ステップ2: 証明書を定義する**

**証明書**とは、すべてのモダナイゼーション変更が満たすべき条件やテストの集合です。その変更がターゲットに対して正しいという最も強い累積的証拠を与える条件を選びます。

各条件は人間の介在なしにチェックできるものであるべきです。そうすることで、エージェント型ワークフローは変更が証明書を満たすまで反復し、満たせない場合は人間によるレビューへとフラグを立てられます。

証明書に何を含めるかはターゲットに依存しますが、通常は以下のリストから選びます。

- 元のテストスイートが通る
- モダナイゼーション中に Claude が書いたテストがすべて通る
- テストカバレッジが合意した閾値を満たす
- パフォーマンスベンチマークが合意した範囲内に収まる
- Claude による独立したアドバーサリアルレビュー(それぞれ新しいコンテキストウィンドウで実施)がブロッカーとなる問題を検出しない
- ユーザーインターフェースについては、Claude によるコンピュータ操作でリグレッションが検出されない
- 現行版とターゲット版が、同じ入力に対して同じ出力を生成する(入力はライブ、記録済み、または Claude が生成したもののいずれでもよい)
- 永続化された状態とワイヤーフォーマットが、現行版とターゲット版の間でラウンドトリップできる
- 変更がステージング環境で合意された期間稼働し、エラー率、レイテンシ、アラートにリグレッションがない
- 静的解析とセキュリティスキャンで新たな指摘が出ない
- コンパイル対象の場合、ビルドがクリーンで型チェックが通る

> **証明書は、レビューと昇格を担う人々と一緒に作成してください。** 証明書とエージェント型ワークフローがまだ設計段階にあるうちに、現在そのコードベースに依存している開発者、ユーザーグループ、事業側のリードを巻き込みます。

彼らの専門知識が、証明書が何を測定するかを形作り、早い段階での関与が、変更がレビューに到達したときの信頼獲得につながります。完成した証明書に対する良いチェックは、彼らがその証拠だけでマージすることに納得できるかどうかです。証明書に自分たち自身の基準が反映されていると感じられれば、ステップ3の昇格ポリシーはより軽くできます。

証明書が何を基準にどう照合するかは、モダナイゼーションのタイプによって異なります。

- **アップリフト型モダナイゼーションの場合**、パリティは元のコードベースに対するものであり、元のテストスイートが証明書の中核になり得ます。
- **トランスフォーム型モダナイゼーションの場合**、パリティも元のコードベースに対するものですが、元のテストスイートが新しいスタック上でそのまま動くことはまれです。代わりに、本番トラフィックのリプレイ、新旧間の差分テスト、本番並行デプロイが作業の大半を担います。
- **リイマジン型モダナイゼーションの場合**、証明書は振る舞い仕様に基づきます。これが最も難しいケースです。仕様は既存システムとの差分照合ほど客観的ではないため、モデルの判断がより多く関与し、結果のばらつきも大きくなりがちです。ここでは、仕様から書き起こされたテスト、各変更を仕様と照合する Claude による独立したアドバーサリアルレビュー、新システムが旧システムの振る舞いを保っているかを見る差分チェックに証明書は依拠します。仕様が明確化されるにつれて証明書を改訂することになると想定してください。仕様の抜け穴はまずここに現れます。

古いシステムはテストカバレッジが薄く、テストが不安定で、テレメトリもほとんどないことが多いです。証明書を定義する作業の一部は、こうしたギャップを特定することです。強力な証明書を支えるのが難しそうな場合、このステップで最も有用なことの一つは、Claude を使って不足している証拠を作ることです。本番並行環境を立ち上げる、リプレイハーネスを構築する、テストをさらに書く、といったことです。

## **ステップ3: 昇格ポリシーを設定する**

エージェントは、どんな人間のチームが差分ごとにレビューできるよりもはるかに速く変更を生み出します。昇格ポリシーとは、変更のレビューの深さを規定する、事前に書き起こされ合意された段階的なレビュー経路であり、これによってモダナイゼーションを許容できる期間内に終わらせられます。

証明書と同様、このステップもレビュー担当者と一緒に取り組み、可能な限り組織の既存のチェンジマネジメント・プロセスに組み込んでください。詳細は組織や直面するリスクのトレードオフによって異なりますが、どこでも成り立つルールがいくつかあります。

- **変更の影響範囲とエージェントの確信度によって階層を分ける。** 組織自身の変更・リスク分類があればそれを使います。クリティカルパスについては人間による完全なレビューを維持します。
- **繰り返し出てくる指摘は根本原因で直します。** フラグの立った変更を時系列でグループ化・分析します。同じ種類の指摘が繰り返し出てくる場合は、その都度レビューするのではなく、エージェント型ワークフローや証明書側で原因を修正します。
- **出力フォーマットはレビュー担当者と一緒に設計する。** どのような情報とフォーマットがレビューを最も速くするか、どのシグナルがより高い確信を与えるかについて合意します。ステップ5では、初期のサンプル出力を彼らにレビューしてもらいます。
- **SME(専門家)の時間を効果的に配分する。** SME は最終的な差分をすべて読むわけではありませんが、その判断は依然として希少な入力です。大きな差分をかき分けなくても、最もリスクの高い階層の変更、そしてその中でフラグが立ったエージェントの判断に直接たどり着けるようにします。そうすれば、少数の専門家の工数で、最もリスクの大きい変更をカバーできます。

これらのルールの多くは、プロジェクトの早い段階で SME を関与させることで、その工数を前倒しします。彼らのフィードバックが、本格的なモダナイゼーションが始まる前に証明書とエージェント型ワークフローを調整します。

サンプルに対する彼らの承認は、確信度が高い箇所についてより軽いレビュー経路を取ることのさらなる正当化にもなります。これは、レビューが最後に行われる従来の非エージェント型パターンとは逆の流れです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6ab3ce6a62d56528c6b6e01f_878b06f2.png)

*生成から本番環境に至るまでの、ある変更の経路。*

昇格ポリシーは、そのモダナイゼーションが「速度」と「レビューの深さ」というスペクトル上のどこに位置するかも反映すべきです。サポート終了が迫るランタイムのような厳しい締め切りに向かって進むモダナイゼーションでは、より速いポリシー、つまり人間によるレビューを軽くし、変更ごとのリスクをより多く受け入れるという明示的な合意が必要です。

より長い時間軸のモダナイゼーションであれば、より深い人間によるレビューとより緩やかな切り替えの余裕があります。ステークホルダーはリスク許容度や制約に応じてこのスペクトル上の異なる地点に落ち着くため、作業が始まる前にそれを固めておく価値があります。

規制の厳しい環境では、どんな変更であれ軽い人間レビューの経路を取ることに、実質的な抵抗が生じます。個々の承認者は、悪い変更が生じた場合のリスクを自分が背負うことになるため署名をためらう一方、リーダーシップは老朽化したシステムというより大きなリスクを背負っています。

私たちの経験では、昇格ポリシーの方針は組織のトップから出すのが最善です。また、事前に合意しておくことで、本番環境に到達したバグの責任が特定の承認者一人に押し付けられるのではなく、共有されるようになります。

> **これらすべては、実際の証拠として機能するだけの詳細さを備えた証明書と、Claude がどのようにしてその変更にたどり着いたかを十分理解し、信頼できるレビュー担当者の存在を前提としています。**

## **ステップ4: 前提条件を整える**

このステップの多くは、モダナイゼーション・チームの外側にあるチームを通じて進みます。ホストのためのプラットフォームやインフラ、テスト体制のための QA やリリースエンジニアリング、承認のためのセキュリティやコンプライアンスなどです。これらのチームにはそれぞれ独自のバックログや承認プロセスがあることが多いため、要件が判明し次第、ステップ1〜3がまだ進行中であっても早めに会話を始めてください。

### **環境**

- コードベースや Claude が参照すべき他の関連ソースにアクセスできる、ワークフロー実行専用のリモートホスト
- 証明書が要求するテスト体制
- 証明書を強化するもの全般: 本番テレメトリ、本番並行環境、リプレイ用の本番データ

### **コードベースと CI/CD**

- ビルド・コンパイルログ、インポート解析、あるいはランタイムトレースに基づいた、コードベースの依存関係マップ。注: プラグインの *map* コマンドは良い出発点になりますが、コードベースの規模や年数によっては、より広範な事前作業が必要になる場合があります
- ターゲット定義の一部として、依存関係やパッケージの扱いに関する計画
- 必要であれば、CI/CD に組み込める互換性チェック
- 既存コードベース上でモダナイズする場合の、合意されたコードフリーズ方針
- コードフリーズや新しい互換性要件について、現役の開発者に向けたコミュニケーション計画

### **チームとレビュー**

- そのコードベースに依存する他のチームから、証明書への署名やプロモーションポリシーに基づくレビューなど、どのように関与するかについての合意(レビュー担当者の時間確保を含む)

### **セキュリティとコンプライアンス**

- ソースコードへのアクセスが承認された、Claude Code 用のモデルアクセス経路
- エージェント型ワークフローに対する最小権限アクセス: モダナイゼーション用ブランチへの書き込みのみとし、本番環境の認証情報は与えない
- モダナイゼーション用ブランチから機密情報や個人情報を除去またはマスキング
- すべての変更を追跡可能にし、PR をエージェントのトランスクリプトと証明書の証拠にリンクさせる
- 新しい依存関係に対するライセンス・脆弱性チェック

## **ステップ5: エージェント型ワークフローを構築・改良する**

Claude Code を使って、コードベースをモダナイズするためのカスタム[ダイナミックワークフロー](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)を開発します。

まずは[code modernization プラグイン](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)から始め、ワークフローが必要とするあらゆるものをファイルシステム上、あるいは MCP 経由で Claude が参照できる場所に置くことをお勧めします。これには、ターゲット、証明書、昇格ポリシー、コードベース、ドキュメント、そして証明書が要求するデータソースやツール類が含まれます。この記事自体を Claude にコンテキストとして与えることもできます。これがプロジェクトの中心的なナレッジベースを形成します。

これが整えば、[モダナイゼーション・ワークフローの構築](https://claude.com/blog/ai-code-migration)自体は容易な部分です。SME には、下流の何かがそれに依存する前に、コードベース固有のスキルや抽出されたルールを含め、Claude の作業を必要に応じてレビューしてもらいます。

構築したものをコードベースの小さな部分に適用し、SME にその変更内容、エージェントのプロセス、証明書を満たしたことの証拠をレビューしてもらいながら改良していきます。

> 問題が表面化したときに修正すべきなのは個々の変更ではなく、ワークフローそのものです。目指すのは、スケールさせたときにほぼすべての変更が証明書を満たし、レビュー担当者が昇格ポリシーの下で安心してマージできるという確信です。

## **ステップ6: モダナイゼーションを実行する**

まず、コードベースの小さな一部分について、昇格ポリシーを通じた変更のレビューと反映を含め、モダナイゼーションを最初から最後まで完了させます。まだコストが低いうちにうまくいかない点を直し、確信が持てるまでこのプロセスを繰り返してから、コードベース全体にスケールさせます。

トランスフォーム型とリイマジン型のモダナイゼーションでは、既存システムと並行してターゲットを構築し、完成後に切り替えますが、アップリフトにはもう一つの選択肢があります。開発を続けながら、稼働中のコードベースをその場でモダナイズする方法です。

これは、システムを停止できない場合や、コードベースの変化が速すぎて別途モダナイズ済みのコピーを最新に保つのが難しい場合によく選ばれます。このケースでうまくいくと私たちが見てきたのは、コードベースを葉(依存の末端)から内側に向かって論理的なパーティションに分割し、一度に1つのパーティションをフリーズしてモダナイズし、パーティションが一度モダナイズされたら新しいコミットがそれを元に戻せないよう CI/CD をゲートすることです。

## **コストについての補足**

このようなモダナイゼーションがトークンでどれくらいのコストになるのか、とよく聞かれます。モダナイゼーションごとに事情は異なりますが、主なコスト要因には以下があります。

- コードベースのうち、変更する量に対して読み込む量がどれくらいか
- 証明書がどれだけ複雑か(規制の厳しい環境では、変更を書くことよりも検証のほうがコストの大きな割合を占めることが多い)
- 証明書が要求する新規テストの作成・修復がどれだけ必要か
- 実行が進行中に他のチームがまわりでマージしてくることから生じる調整作業がどれだけあるか

> コードベースの小さな一部でモダナイゼーションを完了させる際は、トークン使用量を計測し、それを残りの実行分に外挿してください。稼働中のコードベース上での調整作業のように、パイロットでは見えなかったものは未知数として扱います。こうすることで、モダナイゼーション全体のコストの下限を見積もれます。

パイロットからの計測結果は、エージェント型ワークフローのどこをコスト最適化すべきかも示してくれます。ワークフローの中で最もトークンを消費した部分を見つけ、どうすればより効率化できるかを検討してください。計算コストの高い検証シグナルは、より安価なチェックが通った後にのみ実行されるように、後段に配置します。

証明書が完全にチェックする機械的で大量の作業には、Sonnet のようなコストと能力のバランスが取れたモデルの使用を検討してください。難しい変換作業や、正しさを検証するアドバーサリアルレビューには、より高性能なモデルを取っておきます。

安価なモデルが証明書を満たせなかった場合により高価なモデルにエスカレートすることもできますが、パイロット段階ではリトライ率を注意深く分析してください。安価な試行を何度も重ねると、高価な試行を1回行うより高くつく場合があるからです。ワークフローとパイロットデータの両方に Claude をアクセスさせれば、こうした分析の多くを一緒に行うことができます。

## **モダナイゼーションのその先へ**

モダナイズされたコードベースは、成果物の一つにすぎません。他の成果物には、それを生み出したワークフロー、何が正しいかを定めた文書化された証明書、あなたの組織のチェンジマネジメント・プロセスがすでに受け入れている昇格ポリシー、そして反映されたすべての変更の証跡があります。このプレイブックを再利用可能な資産としてコード化しておけば、次のアップグレードや書き換えのためのパターンがすでに用意されていることになります。
