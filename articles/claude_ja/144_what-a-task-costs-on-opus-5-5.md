# Opus 5.5 で1つのタスクにかかるコスト
- 著者

  Addy Osmani

## タスクのコストと、やり直しのコスト

あなたは何百万トークンも買おうとして作業を始めるわけではありません。機能を作り、移行を終わらせ、あるいはタスクを1つ片付けようとしているだけです。トークン数は、そこにたどり着くためにモデルが必要とした量にすぎません。

トークン単価が同じ2つのモデルでも、同じタスクにかかる金額は大きく異なることがあります。片方はコードを1回読みます。もう片方はコードを読み、修正を試み、また読み直します。それぞれのステップは1ターンであり、各ターンはこれまでの会話全体を再送します。だから、より多くのターンを必要とするモデルは、単価が同じでもより高くつきます。

この記事を読み終える頃には、自分自身の作業について次の3つの質問に答えられるようになっているはずです。

- 自分の典型的なタスクは Opus 5.5 でいくらかかるのか?
- どの設定がそれをどれだけ変えるのか?
- 自分のセッション使用量をどう確認すればよいのか?

先に共有しておきたいトレードオフは、トークン消費を減らすあらゆる方法が、タスクの完遂そのものを犠牲にしうるということです。effort を下げる、小さいモデルを使う、コンテキストを減らす――どれも確かにトークンを節約できます。しかしやり直しは、その節約分より高くつきます。この記事では、それぞれのトレードオフに値段をつけてみます。

ここに載せている数字の一部はリスト価格そのもの、一部はそこから組み立てた例示です。図はインタラクティブになっているので、読みながら入力値を変えてみてください。これらはあくまでベストエフォートの例示であり、必ず私たちのドキュメントとご自身の計算で確認してください。

## タスクのコストとは何か

Claude Code におけるタスクとはループです。モデルは会話を読み、ツールを呼び出し、結果を読み、完了するまでこれを繰り返します。ループを1周するごとに1つのリクエストが発生します。このループのコストを決めるのは4つの要素です。

**ターン数。** 各ターンはそれまでの会話全体を再送します。ターン数が少なければ、処理される入力も少なくなります。

**キャッシュ読み取り。** あるターンが再送する内容の大部分は、前のターンでモデルがすでに見たテキストです。これはキャッシュ読み取りとして課金され、入力価格のごく一部で済みます。

**出力トークンの種類。** 最も高価なトークンで、入力価格の5倍です。[thinking(思考)](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)は出力として課金されるため、答えにたどり着くまでの推論が少ないモデルほどコストは低くなります。

**モデル。** 各モデルには価格ページに掲載された固有の価格があり、選ぶモデルがすべてのトークンの単価を決めます。

以下の例では、Opus 5.5 の API リスト価格――入力100万トークンあたり4ドル、出力100万トークンあたり20ドル、キャッシュ読み取り100万トークンあたり0.20ドル――を使用しています。この先に出てくる計算機と同様、この例ではキャッシュされた入力を読み取り価格で、それ以外はすべて入力価格で課金し、キャッシュ書き込みは考慮に入れていません。トークン数はあくまで例示です。

### ターン数

あるタスクが2万トークンのコンテキストから始まり、モデルがファイルやツールの結果を読み進めるうちに12万トークンまで膨らんだとしましょう。40ターンでは、平均的な1ターンが約7万トークンを送信することになります。会話自体は12万トークンを超えて膨らんでいないにもかかわらず、タスク全体では約280万入力トークンに達します。90%がキャッシュから読み込まれるとすると、入力コストは約1.62ドルです。同じタスクを25ターンで終えれば、処理されるのは約175万トークンで、入力コストは約1.02ドルになります。

1ターンのコストは、それが追加する分のトークン以上にかかります。それより前のすべてを再送するからです。だから、一番安いターンとは、必要としないターンのことです。

ターン数を減らせる習慣の1つは、モデルに自分の作業を確認する手段を与えることです。たとえば、実行できるテスト、ビルド、あるいはエンドポイントを呼び出すスクリプトなどです。自分の作業を確認できるモデルは、より早く自分の間違いに気づきます。

必要なものを1回で集め、ツール呼び出しをまとめて行うモデルも、再送の回数を減らせます。

### キャッシュ読み取り

同じ280万入力トークンでも、まったくキャッシュから読み込まれなければ11.20ドルかかります。ヒット率90%なら1.62ドル、96%なら約0.99ドルです。他のどの設定も、これほど入力コストを動かすことはありません。安定したセッションは、放っておいても高いヒット率を保ちます。キャッシュを壊さないための工夫については、この記事の後半で取り上げます。

### 出力トークン

Opus 5.5 では、出力トークン1つがキャッシュ読み取りの100倍のコストです。典型的なタスクの6万出力トークンは1.20ドルかかり、これはキャッシュから600万トークンを読むのと同じ金額です。出力には thinking が含まれます。Claude Code が要約しか表示しない場合でも、そのすべてに対して料金を支払うことになります。だからこそ、主にモデルがどれだけ考えるかを変える effort は、これほど請求額を動かすのです。

### モデル

キャッシュ読み取りが安いモデルは主に長いセッションで有利になります。出力が安いモデルは主に多くの推論を必要とするタスクで有利になります。

## Opus 5.5 で変わったこと

変わったのは2つです。価格と、モデルがこなす作業量です。

**すべての価格行が下がりました。** 入力トークンと出力トークンは Opus 5 より20%安くなりました。キャッシュ読み取りは60%安くなっています。入力価格が下がったことで読み取り価格も下がり、入力価格の10分の1から20分の1になりました。図Aは、両モデルの100万トークンあたりの価格を比較したものです。これらは API リスト価格です。Pro、Max、Team プランでは、Opus 5.5 の低価格がキャッシュされたコンテキストを含む利用上限に反映されるため、Opus 5 のときよりも約25%長く使えるようになります。キャッシュ読み取りの追加値下げは API 価格の変更です。

API キーで利用する場合、キャッシュ読み取りの値下げが最も効いてくるのは Claude Code です。長時間のエージェント的セッションは、入力の大部分をキャッシュ読み取りに費やします。下の図Bで価格を計算したセッションでは、キャッシュの行が1.00ドルから0.40ドルまで下がり、レシート上で最大の下落となっています。

どれだけ節約できるかは、あなたの作業の形次第です。ほとんどがキャッシュ読み取りであるセッションなら、入力コストを最大60%節約できます。キャッシュなしの短い質問と長い回答の組み合わせなら、出力がコストを支配するため最大20%の節約です。ほとんどの Claude Code タスクはこの中間に位置します。下の計算機で、あなた自身の位置を確認できます。

Opus 5.5 は回答に使うトークンを増やせます。常に返答の前に thinking を行うためです。私たちは Opus 5.5 でより多くのことをこなせるようになると見込んでいますが、これはタスクによって変わるため、ご自身の作業で測定してください。図Cは両モデルのタスクあたりのコストを比較したものです。この部分は価格よりもはるかに、あなた自身の作業内容に左右されます。

スコープがきちんと定まったタスクでは、両モデルともほぼ同じターン数で完了するため、得られるのは価格の値下げ分だけです。差が最も大きくなるのはオープンエンドなタスクで、モデルが間違った方向に多くのターンを費やしうる場面です。すべてのコードベースに当てはまる単一の数字はないので、実際に測定してください(最後のセクションを参照)。

**長時間の実行はレポートで締めくくられます。** Opus 5.5 は長時間の実行を、何を変更し、何を発見し、あなたから何を必要としているかというレポートで締めくくります。これは節約にもつながります。何が起きたか把握できるので、セッションを再実行する頻度が減るからです。

## セッションの価値を最大化するためのヒント

Opus 5.5 の値下げにより、トークン1つあたりのコストは下がります。しかしセッションの進め方次第で、使用するトークン数そのものが変わります。以下のステップが役立ちます。

### **モデルを変える前に effort を上げる**

effort は、モデルが各ターンにどれだけのトークンを費やすか――thinking、書き出すテキスト、ツール呼び出し――という全般的な傾向を設定するものです。effort が低いと、ツール呼び出しの回数が減り、それも短くなります。Opus 5.5 には4段階(low、medium、high、xhigh)に加え、1セッション限りの max があります。以下からレベルを選んで、いつ使うべきか、それを設定するコマンドを確認してください。

Medium:スコープの定まった日常業務向け

明確なスコープのある日々の作業。high よりも各ターンで考える量が少ないため、1ターンあたりのコストは低くなります。

タスクのスコープが定まっているなら、まずここから始めてください。

各レベルは、思考量が少ない順から多い順に並んでいます。

`/effort medium`

`/effort status`

`/model`

`/usage`

Claude Code はモデルごとにデフォルトのレベルを設定しており、`/effort status` で自分の設定を確認できます。スコープの定まった日常業務には **medium** を試してください。medium で行き詰まったら **high** を試します。medium より多く、しかしより大きなモデルに切り替えるよりは少なく費やします。リネームや、既知のパターンを複数ファイルに適用するような機械的な作業には **low** を使ってください。

effort の価格感を大まかにつかむ方法として、high がタスク全体で2万 thinking トークンを追加すると仮定してみましょう。Opus 5.5 ではそれは0.40ドルです。キャッシュされた10万トークンのコンテキストで10ターンのやり直しループが発生し、出力トークンが合計1万トークンになるケースも、ほぼ同じコストです。つまり high は、1回のやり直しを防げるタスクではそれだけで元が取れます。medium で最初から終わっていたはずのタスクでは、無駄になるということです。

#### **medium が1つの層だけを直すとき**

effort をもっと上げるべき最もわかりやすいサインは、修正が1つの層で止まってしまうことです。

API ハンドラー内でフィールド名がリネームされたとしましょう。medium では、モデルはハンドラーを更新し、ハンドラーのテストは通り、しかしクライアントは古いフィールド名を送り続けます。頼まれたことはやりました。ただ、もう一段先の呼び出し元まで読み進めなかっただけです。high では、書き始める前に呼び出し元をより多くのターンをかけて読み、両方の層を1回で変更します。

同じバグはチェックでも捕まえられます。クライアントを経由するテストをモデルが実行できるなら、古いフィールド名は medium のまま、書かれたそのターンでテストに落ちます。だから effort を上げる前に、モデルが自分の作業を確認する手段を持っているかを確認してください。テストの実行にかかるのは1ターンとその出力だけです。effort を上げると、すべてのターンに thinking が追加されます。

effort を上げてチェックを追加しても効果がない場合は、より大きなモデルに切り替えてください。

#### **セッション途中で effort を変更する**

Claude Code では、`/effort` にレベルを付けて実行します。たとえば `/effort high` のように。`/effort status` で現在のレベルを表示できます。タスクの途中で変更することもでき、新しいレベルは次のリクエストから適用されます。

effort や thinking の設定を変更すると、キャッシュされた会話がクリアされます。これらの設定はプロンプトの一部としてキャッシュのマッチングに使われるためです。次のリクエストは、会話全体に対してキャッシュ書き込み価格を支払うことになります。

### **作業に合ったモデルを選ぶ**

モデル選択はセッション内のすべてのトークンの価格を決めるため、effort よりも請求額を大きく動かします。しかもその影響はさらに広範囲に及びます。メインモデルを継承するすべてのサブエージェントは、その価格も継承するからです。ほとんどの日は3つのモデルで足ります。ルックアップ用の小さなモデル、綿密に監督する作業用の Opus 5.5、そして最も難しいタスク用のより大きなモデルです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6ab2b335fc4bd44bfd949d5e_fig-model-ladder.png)

#### **日常のドライバーとしての Opus 5.5**

Opus 5.5 は、あなたが監督する作業――数ファイルにまたがる機能開発、デバッグ、フォローアップの編集を伴うコードレビュー――に使ってください。何をしているかを読み、逸れたら介入するので、ループは短く保たれます。Fable 5.1 への切り替え

**結果が単価より重要なときは Fable 5.1 に切り替えてください。**たとえば、監督しない長時間の実行、コードベースに既存のパターンがない問題、多数のサブエージェントを調整する大規模な変更です。3回目の失敗を待つ必要はありません。Opus 5.5 の high が同じ問題に2回ぶつかったら切り替え、解決したら元に戻してください。インタラクティブな作業では、レイテンシが低くコストも安い Opus 5.5 の方が向いています。

Fable 5.1 のリスト価格は入力100万トークンあたり10ドル、出力100万トークンあたり50ドルで、Opus 5.5 の2.5倍です。キャッシュ読み取りは100万トークンあたり0.25ドルで、Opus 5.5 の1.25倍にとどまります。これは入力価格の0.025倍で課金されるためです。つまりこの価格差は、長くキャッシュ主体の実行で最も小さく、書き込みの多いタスクで最も大きくなります。

自然な区切りで切り替えてください。キャッシュは前のモデルに属するものなので、新しいモデルでの最初のターンは会話全体に対して書き込み価格を支払うことになります。先に `/compact` を実行するか、短い計画を書いたうえで新しいセッションを始めれば、そのターンを小さく抑えられます。エイリアスまたはモデル名を指定して `/model` を実行すれば切り替えられます。`/model` は選択内容を新しいセッションのデフォルトとしても保存するため、難所を越えたら元に戻してください。

#### **ルックアップ用に下げる**

**ルックアップ用には Sonnet や Haiku に下げてください。ただしコードを書く作業には使わないでください。**検索・要約を行うサブエージェント、ログやテスト出力の読み取り、「これはどこで定義されているか」といった質問などです。多数のファイルにまたがる機械的な編集には、Opus 5.5 を保ったまま effort を low に設定してください。編集は残りのコードを書いているモデルの上で行われたまま、1ターンあたりのコストだけが下がります。

[サブエージェント](https://code.claude.com/docs/en/sub-agents)を小さいモデルに割り当てるには、その定義で `model: haiku` や `model: sonnet` を設定します。すべてのサブエージェントを1つのモデルにするには、`CLAUDE_CODE_SUBAGENT_MODEL` 環境変数を設定してください。サブエージェントの定義内で指定されたモデルは、この変数より優先されます。モデル設定のないサブエージェントは、変数が設定されていない限りメインモデル上で動作します。

各サブエージェントは自分自身のコンテキストウィンドウで動作し、要約を返すため、そのファイル読み取りはメインの会話には残りません。それでも自分のトークン分の料金は発生するため、モデル設定がそのコストを決めます。

トレードオフはこうです。検索結果を読み違える小さいモデルは、メインモデルを間違ったファイルへと向かわせ、その回り道の代金をメインモデルが支払うことになります。小さいモデルには、間違いを見つけるコストが低い作業――ファイル探し、テストの実行、ログの読み取りなど――を任せてください。

判断を要する仕事はメインモデルに残してください。`opusplan` エイリアスは作業を別の分け方で分担します。Opus が plan mode で計画を立て、Sonnet がその計画を実行します。これは上記の助言とは逆に、コード編集を Sonnet 側に置くやり方です。デフォルトにする前に、自分のタスクで測定してください。

### **移行時にはプロンプトを確認する**

古いモデル向けに書かれた指示は、Opus 5.5 に必要以上に書かせたり、ツール呼び出しを繰り返させたりすることがあります。Claude Code で `/claude-api prompt-audit` を実行すれば、スキルや CLAUDE.md ファイルなど、Claude Code の設定にこうした[プロンプティングのアンチパターン](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)がないかをチェックできます。Claude Platform 上に構築するアプリのコードもチェック対象です。

これは、こうしたパターンをいくつも含んだプロンプトを持つ44件のチケットからなる社内のカスタマーサポートベンチマークを使い、Opus 4.8 から Opus 5.5 への移行でテストしました。低 effort での Opus 5.5 への移行だけで、ベンチマークのコストは約18%下がりました。さらに prompt-audit を実行すると、そこからさらに9%下がり、Opus 4.8 の出発点から約25%下がった水準になりました。この監査は、モデルに余計な文章を書かせたりツール呼び出しを繰り返させたりしていた儀式的な指示――必須の6ステップ手順、スクラッチパッドのルール、2回検証するルール、互いに矛盾する指示――を取り除いたものです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6ab2b2c575f4bb6ac9f4d52a_fig-d-prompt-audit_2.png)

### **キャッシュと圧縮(compaction)**

Claude Code はキャッシュと圧縮をあなたに代わって処理します。セッションの進め方が、そこからどれだけ節約できるかを左右します。

#### **キャッシュの仕組み**

Claude Code は、システムプロンプト、ツール定義、これまでの会話など、リクエストの中で繰り返される部分をキャッシュします。

Opus 5.5 では、キャッシュされた読み取りは新規入力トークンの5%のコストです。キャッシュへの書き込みは新規読み取りより高く、現在の価格では5分間キャッシュで入力価格の1.25倍、1時間キャッシュで2倍です。各ヒットは無料で寿命をリセットします。

Claude Code での寿命は、支払い方法によって変わります。Claude サブスクリプションでは1時間、API キーやクラウドプロバイダー経由ではデフォルトで5分です。サブスクリプションも、使用クレジットに切り替わると5分になります。

12万トークンのコンテキストでは、Opus 5.5 での5分間キャッシュの書き込みは約0.60ドル、読み取りは約0.02ドルです。1回の書き込みは25回の読み取り分に相当します。API キーを使っている場合、6分間のコーヒーブレイクが、次の0.02ドルの読み取りを0.60ドルの書き込みに変えてしまいます。同じサイズでの1時間キャッシュの書き込みは約0.96ドルで、API 上ではこの割増分を支払うことで1日の作業の合間を埋められます。

#### **セッションの形とヒット率**

キャッシュはプレフィックスを保存するため、リクエストの先頭から前回と一致する部分だけを再利用できます。

安定したセッションは毎ターン会話の末尾に追記していくため、ヒット率を高く保てます。リクエストの前の方を変えるものは何であれ、ヒット率を下げます。ツール定義を変更するとキャッシュ全体がクリアされ、システムプロンプトを変更すると、その時点以降――つまりほぼすべて――がクリアされます。

実際には、次のような場合にキャッシュ書き込みが発生すると考えてください。

- キャッシュの寿命より長く一時停止したとき
- effort や thinking の設定を変更したとき(effort のセクション参照)。キャッシュされた会話がクリアされることがあります
- MCP サーバーを接続または切断したとき。各リクエストの冒頭で読み込まれる内容が変わることがあります
- モデルを切り替えたとき。新しいモデルは空のキャッシュから始まります
- 会話が圧縮されたとき。キャッシュが一致していた履歴が書き換えられます

だから、これらはセッションの開始時に整えておき、作業中はそのままにしておいてください。

#### **なぜ長いセッションほど1ターンあたりのコストが上がるのか**

各ターンはコンテキスト全体を再送するため、キャッシュが温まっていても、コンテキストが大きくなるほど1ターンのコストは上がります。コンテキストが2万トークンなら、Opus 5.5 での1ターンのキャッシュ読み取りは約0.004ドルです。15万トークンなら約0.03ドルで、そのサイズで30ターン実行すると読み取りだけで0.90ドルかかります。同じ30ターンを2万トークンで行えば約0.12ドルです。Claude 4.6 以降のモデルでは、コンテキストウィンドウが大きくなってもトークンあたりの価格は変わらないため、このコストはすべて会話を再送すること自体から来ています。

そのコンテキストの多くは、1時間前のスタックトレース、すでに用済みのファイル、修正済みのテスト実行結果など、以前の作業の残骸です。それでも毎ターン送信され続けます。

#### **圧縮、/compact と /clear**

セッションがコンテキスト上限に近づくと、Claude Code は古い履歴を要約し、以降のターンで送信する量を減らします。`/autocompact` にトークン数を指定すれば、これが発生するまでにコンテキストをどれだけ埋めるかを変更できます。

自分で行うための2つのコマンドがあります。`/clear` は会話を空にし、コストはかかりません。無関係な作業に移るときに使ってください。`/compact` は継続性を保ちますが、1回分のリクエストのコストがかかります。要約対象の会話を読み込み、何を残すかを指定できます。たとえば `/compact keep the failing test names and the schema change` のように。

15万トークンでの圧縮のおおよその価格は約0.25ドルです。これは読み取り分、数千出力トークンの要約、そして短くなったコンテキストへの新しいキャッシュ書き込みの合計です。それ以降の各ターンは読み取りで約0.025ドル節約できるため、圧縮は約10ターンで元が取れます。終わる直前の圧縮は、節約分より高くつきます。

要約は詳細も失います。デバッグセッションの途中での圧縮は、重要だったログの1行を落としてしまうことがあります。自然な区切りで圧縮を行い、次のステップが特定の何かに依存している場合は、`/compact` の指示の中でそう伝えてください。

#### **入力する前に読み込まれるもの**

[CLAUDE.md ファイル](https://code.claude.com/docs/en/memory)はセッション開始時にコンテキストへ読み込まれるため、そこに書かれた各行は、すべてのターンが再送する内容の一部になります。[コストのドキュメント](https://code.claude.com/docs/en/costs)では、200行以内に収めることを勧めています。MCP のツール定義は遅延読み込みされます。開始時に読み込まれるのはツール名とサーバーの指示だけで、完全な定義はそのツールが使われた時点で読み込まれます。`/mcp` を実行して接続中のサーバーを確認し、使っていないものはオフにしてください。

## 自分で測定する

この記事の図はすべて例示です。あなたのコードベース、プロンプト、習慣は異なるので、自分自身のタスクでコストを測定してください。確認方法は次のとおりです。

1. **セッション内で** [**/usage**](https://code.claude.com/docs/en/costs) **を実行する。** `/cost` も同じことをします。Session ブロックには、トークン使用量とリスト価格での推定金額が表示されます。プロンプトキャッシュの行では、入力のうちどれだけがキャッシュから来たかがわかります。Pro、Max、Team、Enterprise プランでは、同じ画面にプラン使用状況のバーも表示されます。金額はお使いのマシン上でリスト価格をもとに計算されるため、サブスクリプションではそれは請求額ではなく、どれだけの作業をこなしたかの目安です。
2. **同じタスクを2回実行する。** バックログから何かを選んでください。トイ・サンプルではなく実際のタスクです。`/model` で Opus 5 と Opus 5.5 を切り替えます。それぞれの実行についてターン数、出力トークン数、コストを記録してください。結論を出す前に、3〜4個のタスクで試してください。
3. **チームであれば、利用状況・コストレポートを使う。** [Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api) はユーザーごとの推定コストを提供します。[Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) は、モデル別、キャッシュされたトークンとされていないトークン別に支出を内訳できます。
4. **effort のはしごを試す。** 難しいタスクを1つ、medium と high の両方で実行してみてください。機械的なタスクを1つ、low で実行してみてください。

### セッションの読み方

タスクの最後に /usage で3つのことを確認してください。

- **キャッシュの割合。** 長いセッションであれば高いはずです。低い場合は、長い一時停止、effort やモデルの変更、あるいは途中で接続された MCP サーバーがなかったか確認してください。
- **入力に対する出力の量。** 小さな変更に対して出力が多い場合、たいてい effort のレベルがタスクに対して高すぎるか、モデルがやり直しを繰り返しています。
- **会話のサイズに対する入力の合計。** 合計が会話のサイズの何倍にもなっている場合、そのセッションは多くのターンを要しており、ループがどこで繰り返されたのかを見つけるために会話を読み返す価値があります。

基準として、Claude Code のコストに関するドキュメントでは、エンタープライズ導入全体の平均が開発者・稼働日あたり約13ドルで、ユーザーの90%が稼働日あたり30ドル未満だとしています。自分の通常の水準を大きく上回るセッションは、見直す価値があります。

## 心に留めておくこと

- スコープの定まった日常業務には medium effort を使う。
- モデルに自分の作業を確認する手段を与え、複数ファイルにまたがる変更は plan mode で始める。
- medium で行き詰まったら high に上げる。変更はキャッシュ書き込みのコストがかかりうるので、区切りのタイミングで行う。
- high が同じ問題に2回ぶつかったら Fable 5.1 に切り替える。解決したら元に戻す。
- 検索やログ読み取りのサブエージェントは Sonnet や Haiku に置く。コード編集は Opus 5.5 に残す。
- 長いセッションは動かし続け、キャッシュを温かく保つ。
- 無関係なタスクの間は /clear を使い、区切りでは何を残すかをメモしたうえで /compact を使う。
- **最も重要なこと:** 各モデルで実際のタスクを1つ実行し、/usage が示す結果を比較する。信頼すべきは自分自身の数字です。
