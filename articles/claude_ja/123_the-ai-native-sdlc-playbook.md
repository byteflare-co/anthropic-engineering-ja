- 執筆者

## コードはもはやボトルネックではない

各組織は、1 年前には考えられなかったスピードで AI を使ってコードを書き始めていますが、コードを取り巻くプロセスは同じペースでは変化していません。

多くのエンジニアリングチームは依然として同じ承認ゲート、レビュー、引き継ぎ、ポリシーを抱えたままで、[Claude Code](https://claude.com/product/claude-code) のようなエージェント型コーディングソリューションを使うことで得られる生産性向上を頭打ちにしています。

ソフトウェア開発ライフサイクル（SDLC）とは、ソフトウェアをアイデアから本番稼働へと導くプロセスです。ほとんどの組織は、計画、設計、構築、テスト、デプロイ、保守という同じ 6 つの段階の何らかのバージョンを運用しています。従来、各段階は異なる役割が担当する個別のフェーズでした。プロダクトマネージャーが要件を書き、テクニカルアーキテクトがそれを設計に落とし込み、エンジニアが設計を構築し、規制産業の企業では QA チームがそれを検証し、リリースチームが出荷し、運用チームが稼働中のものを監視します。作業はドキュメント、チケット、承認を通じて各フェーズ間を移動します。

従来の SDLC は、各ステップで説明責任と統制を確保するためにプロセス重視になっています。しかし、従来の SDLC は、コードを書いて実装する段階が最も時間とコストのかかる段階だった時代に効率を最大化するために設計されたものであり、それはもはや現実ではありません。PRD、見積もりの儀式、プロダクトセキュリティレビューはいずれも、数週間、数か月、あるいは四半期にも及びうる開発作業の中で足並みを揃えるために存在していました。

従来の SDLC には、すべてのステップが人間によって実行されることを前提とした統制も組み込まれています。最も大きな価値を生み出している組織は、人間をループに残しつつ、エージェント型 AI が今できることを中心にプロセスを再構築しています。本ガイドでは、私たちの Applied AI チームが、SDLC の各段階に Claude を社内統合して開発を加速し、プロセスをより速く回すためのベストプラクティスのいくつかを、顧客との協働から得た知見をもとに紹介します。

コードがもはやボトルネックではなくなり、構築フェーズが従来の SDLC が許容する以上のスピードで進むようになると、次の 3 つのことが真実になります。

- ボトルネックが構築フェーズの前後のステップに移動します。主に計画、レビュー・テスト、デプロイであり、これらは依然として人間の速度で動いています。
- 統制が現実と噛み合わなくなり、扱いきれなくなります。人が書いたコードを1行ずつレビューすることには意味がありましたが、エージェントが差分の大半を書くようになるとそれには追いつけなくなります。
- ガバナンスのコストが増加します。例外は依然として毎週あるいは毎月開かれる会議や委員会を経由してルーティングされるためです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8739a1b934ffe55bfc9715_44592f18.png)

構築はもはや制約ではなく、その前後にある人間速度のステップこそが制約です。人間速度の段階は長さを保ったまま、構築だけが数時間に短縮されます。

セキュリティのボトルネックを例に考えてみましょう。セキュリティチームは人間のアウトプットを前提に人員配置されているため、エージェントがコードの出力を何倍にも増やすと、レビューキューが積み上がるか、コードが十分にレビューされないまま出荷されるかのいずれかになります。規制対象の組織はどちらの結果も受け入れられないため、セキュリティとポリシーのチェックはエージェントのペースについていく必要があります。

エージェント型 AI の生産性向上をより良く実現し、それを安全に運用するためには、従来の SDLC ライフサイクル全体が、実装フェーズが経験したのと同じレベルの変革を必要としています。

### AI ネイティブ SDLC とは何か

AI ネイティブ SDLC とは、従来の統制目標を新しい実施方法と組み合わせて再構築したプロセスです。線形の流れではなく、プロセスがループになり、AI が各ポイントに組み込まれます。AI ネイティブ SDLC は自動化された引き継ぎと後続のプレイのトリガーを促進し、従来の SDLC の各フェーズ間の引き継ぎが手作業で不格好だったという課題に対処します。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8858c2eccce183e7553cf2_53b010df.png)

### 変化点

下の表は、Claude によって支えられる従来の SDLC と AI ネイティブ SDLC のスペクトラムの両端を示しています。ほとんどの組織はこの 2 つの列のどこかに位置しています。

| 段階 | 従来の SDLC | AI ネイティブ SDLC |
| --- | --- | --- |
| 計画 | 委員会によって要件が集められ、ワークショップと承認を通じて練り上げられ、手作業で書き起こされる | Claude がソースから直接ペインポイントを合成し、人間にも読め機械的にも扱える `intent.md` にまとめる |
| 設計 | アナリストが仕様を書き、デザイナーがそれを解釈する | 要件と設計が 1 つの作業セッションでエージェントとともに圧縮され、スキルとしてコード化された標準に導かれ、git でバージョン管理される |
| 構築 | テストとコードは手書きされ、ドキュメントは主要な開発が終わった後に書かれる | テストとコードは AI によって生成され、組織的知識はバージョン管理された機械可読な `CLAUDE.md` ファイルとスキルとして維持される |
| テスト | 段階の境界での QA ゲート | 実装を通じて継続的に織り込まれる評価（eval） |
| デプロイ | 人間がコードのすべての行をレビューし、ガバナンスはレビューサイクルの中で行われるが、しばしば一貫性を欠く | エージェントによる多層のレビューが行われ、人間によるレビューは規制対象・重要なコードに限定される。ガバナンスは AI が行動する中で実施され、承認ゲートとしてフックが機能する |
| 保守 | 人間が本番環境をバグの有無について監視する | エージェントが稼働中のデプロイを監視する。統制帯を逸脱したものは診断され、新しい `intent.md` としてループに書き戻される |

右列を貫く共通のテーマは、コミットされる成果物です。各段階は、（`intent.md`、`spec.md`、`plan.md`、差分とそのテスト、レビュー結果を伴う PR、インシデント記録などを含む）成果物をバージョン管理にコミットすることで終わり、次の段階はそれを読むことから始まります。初期の段階では、プロダクトオーナーとエージェントの双方が同じファイルを読んで行動できるため、.md ファイルが主要な成果物になります。構築以降は、成果物はコードとその記録になります。コミットの連鎖は、誰が何を求め、エージェントが何を作り、誰が承認したかという監査証跡でもあります。

判断を要するすべての決定について、人間が引き続き説明責任を負います。エージェント化された SDLC の世界では、レビューされるべき成果物とともに、人間の注意の向け先も変化します。

各段階は、次の段階が読める成果物をコミットします。意図、仕様、計画、差分、そしてレビュー結果を合わせたものが監査証跡です。

## プレイ

プレイはこのプレイブックの中核であり、6 つの非線形な段階（計画、設計、構築、テスト、デプロイ、保守）にグループ化され、それらを合わせるとライフサイクル全体をカバーします。

各プレイは次をカバーします。

- 何が変わるか
- はじめ方
- 実装のための具体的なステップ
- ガバナンス上の考慮事項
- 効果を測定する方法

これらのステップはモジュール式であり、組織は独自のニーズに応じて、異なる段階の変革を異なるタイミングで優先することを選べます。各プレイは「前提条件」の下にその依存関係を示しており、依存関係グラフがそれをさらに図解しています。

段階は成果物をコミットすることで終わり、そのコミットが次の段階を開始します。受理された `intent.md` は要件・設計パスをトリガーし、承認された `spec.md` はプランモードをトリガーし、マージされた PR はパイプラインをトリガーし、本番環境で統制帯が逸脱すると次の `intent.md` が書かれ、こうしてループが続きます。

まず、各ステップを手作業でプロンプトすることから始め、最終的には受理された各成果物が次のゲートを発火させるループになることを目指します。人間の注意はゲートに集中し、各段階をゼロから始めるのではなく、エージェントがフラグを立てたものをレビューすることになります。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8855c75344623fc81efcb8_5d5a3c05.png)

プレイは段階とともに一覧化されており、矢印は採用すべき順序を示しています。この2つは同じではありません。まずはどのプレイから始めても構いません。矢印が入っていないプレイには何も先に必要ないからです。それ以外のプレイについては、そこに入る矢印が先に採用すべきプレイです。

## 計画

アイデアはもはや、誰かがそれを書き起こしてくれるのを待つ必要がありません。意図は発案者自身の言葉で一度だけ取り込まれ、次の段階が行動に移せるバージョン管理された成果物になります。

### intent.md として取り込む

ソフトウェア開発プロセスを起動する `intent.md` は、異なる経路から入ってくることがあります。人がアイデアを思いつく、チケットが起票される、あるいはアラートを通じてインシデントが表面化する（段階6：保守を参照）などです。

人がアイデアを思いついたとき、その人は Claude とブレインストーミングを行い、markdown のプロトスペックを作成します。従来の SDLC では、同じ人物がプロダクトチームのメンバーを説得して、そのアイデアを一緒に、あるいは代わりに書き起こしてもらう必要があります。

Claude によって生成されたプロトスペックは、人間にも読め、バージョン管理され、次の段階が即座に消費できます。このプロトスペックは `intent.md` として保存されます。

意図がイベントトリガーから生まれたものであれエージェントから生まれたものであれ、同じステップが適用されます。プロダクトオーナーが、コミットする前にエージェントが書いた `intent.md` をレビューし修正します。

**従来** アイデアは、誰かがそれに基づいて行動できるようになるまで、バックログエントリ、ユーザーストーリー、ストーリーポイント、リファインメントミーティングを経由します。所有権は各引き継ぎのたびに移り、エンジニアリングに届く頃には発案者が意図したものから何段階も離れてしまいます。

**AI ネイティブ** 発案者は Claude とブレインストーミングし、その結果を発案者自身の言葉によるプロトスペックである `intent.md` として書き留めます。この成果物には、何が求められているか、なぜか、どのような制約のもとでかが含まれます。反復的なプロセスはスキルによってコード化されます。

はじめ方

**前提条件**

なし。

**インフラ**

エンジニアではない人向けの Claude アクセス（claude.ai または [Cowork](https://claude.com/product/cowork)）。合意された `intent.md` テンプレート。プロダクトオーナーが監視する、共有されたバージョン管理された意図の置き場所。単一プロダクトの場合、最もシンプルな置き場所はプロダクトリポジトリ内の `intent/` フォルダです。この設定により、成果物の連鎖がそこから派生したコードのすぐそばに保たれます。専用の intent リポジトリは、意図が多数のリポジトリにまたがる場合にのみ、そのオーバーヘッドに見合う価値があります。モノレポの場合はそれが単なるディレクトリになります。段階3：構築のサイドバーでは、この置き場所が、すでにレコードを保持している Jira や要件管理ツールとどう関係するかを扱います。

これを整えるのはプラットフォームチームまたはエンジニアリングチームが一度だけ行うタスクです。組織全体から多くの貢献者が来ることになるため、技術的なチームメンバーが intent の置き場所を立ち上げ、誰が書き込めるかを決める必要があります。

リポジトリさえ存在すれば、git の経験がない貢献者は直接 git を使う必要はありません。代わりに、バージョン管理システム（GitHub など）へのコネクタを使えば、Claude が claude.ai や Cowork から代わりに markdown ファイルをコミットできます。

#### 実行方法

1. 発案者は自分の言葉で問題を Claude に説明します。発案者は、今日できないこと、誰が影響を受けるか、より良い状態とは何か、範囲外のことは何かを説明できます。決まった言い回しは必要ありません。
2. アイデアが具体的になるまでブレインストーミングします。Claude はアナリストが尋ねるような質問、つまり範囲、ユーザー、制約、成功の定義を尋ねます。
3. Claude に、組織のテンプレートを使って `intent.md` として結果を書くよう依頼します。このテンプレートは、技術的なチームメンバーがセットアップしリードが承認するスキルとしてコード化できます。これには問題、提案された成果、影響を受けるユーザーとシステム、制約、未解決の質問を含められます。
4. 発案者は、Claude が誤解した点を修正します。
5. `intent.md` を共有の置き場所にコミットします。作成者とタイムスタンプが記録に加わり、そこからプロダクトオーナーがアイデアを引き継ぎます。

```
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?
```

#### ガバナンス上の考慮事項

証跡は、作成者、タイムスタンプ、全リビジョン履歴を含む、コミットされた `intent.md` です。それは意図の置き場所の git 履歴に記録されます。プロダクトオーナーが承認し、意図を段階2：設計に進めるかどうかの受理・却下の決定は、マージまたはクローズされたレビューとして記録されます。

測定方法

**先行指標**

最初の会話からコミットされた `intent.md` までの時間。これは、作成者とタイムスタンプを記録する意図の置き場所の git 履歴から読み取ります。数週間かかっていた聞き取り・練り上げのサイクルが数時間に短縮されることが期待されます。

**遅行指標**

生存率、つまりプロダクトオーナーが段階2：設計へ受理する `intent.md` ファイルの割合（クローズされたものに対して）。受理・却下の決定は、成果物のマージまたはクローズされたレビューとして記録されます。加えて、同じ変更について最初の `spec.md` コミット後に `intent.md` に加えられた変更の回数も指標になります。

**02**

## 設計

要件と設計が 1 つのセッションに収束します。ポリシーは何週間も後のレビューで発見されるのではなく、仕様を書いている最中に適用されます。

### 要件と設計

プロダクトオーナーによって承認されると、Claude は受理された `intent.md` を受け取り、要件・設計仕様を作成します。これはブランド、セキュリティ、コンプライアンス、UX に関する組織の[スキル](https://code.claude.com/docs/en/skills)によって導かれます。

プロダクトオーナーはその仕様をレビューしますが、書くことはありません。このプロセスの目標は、エンジニアリングチームが計画を立てられる仕様を、懸念事項にフラグを立てた状態で作ることです。

フロントエンドの作業はその最も分かりやすい例です。`intent.md` が受理されると、プロダクトオーナーは [Claude Design](https://claude.com/product/design)（ベータ版）で `intent.md` からデザインをモックアップし、そのモックを反復し、それを Claude Code に書き出して構築します。

**従来** 要件と設計は別々のチームが運用する別々のフェーズです。アナリストがアイデアを要件として形式化し、デザイナーがそれを解釈してデザインに戻します。この分離は説明責任のために存在しますが、遅く、情報の欠落を招きます。

**AI ネイティブ** 両方のフェーズが 1 回のプロンプトされたセッションの中で起こります。Claude は `intent.md` を受け取り、組織のスキルによって制約された要件・設計仕様を、懸念事項にフラグを立てた状態で作成します。

はじめ方

**前提条件**

`intent.md` ファイルの作成、そしてブランド、セキュリティ、コンプライアンス、UX のポリシーがスキルとして書かれていること。

**インフラ**

Claude にアクセスできるプロダクトオーナー。エンジニアリングのスキルは不要です。

#### 実行方法

1. プロダクトオーナーは、組織のスキルが利用可能な状態でセッションを開き、`intent.md` を添付します。
2. プロダクトオーナーのプロンプトは `intent.md` を指し示し、制約に名前を付け、フラグを立てるべき懸念事項を求めます。まずは手作業で実行し、それから組織レベルのスラッシュコマンドとしてコード化します。そこから、意図の置き場所での `intent.md` の受理をトリガーとし、マージ時に発火する非対話型ジョブを用意して、組織のスキルを読み込んだ状態でこのパスを実行し、`spec.md` をプルリクエストとしてコミットします（配線については段階5：デプロイの CI/CD プレイで扱います）。この時点から、プロダクトオーナーの最初の関与はレビューになります。
3. 同じプロダクトオーナーが、仕様をアイデアと照らし合わせてレビューします。仕様は述べられた問題を解決しているか、`intent.md` の未解決の質問は答えられているか、あるいは引き継がれているか。
4. まずフラグの立った懸念事項に取り組みます。これらはアナリストならエスカレーションしていたであろう論点だからです。プロダクトオーナーは、エンジニアリングが仕様を見る前に、それぞれをポリシーオーナーとともに解決します。
5. `intent.md` と並べて `spec.md` をコミットします。このファイルのペアは、何が求められ、何が決定されたかを記録します。
6. プロダクトオーナーは、仕様と意図を構築に進めるかどうかを決定し、組織が高リスクと分類するものについてはテクニカルリードに相談します。この判断は常に人間のチームメイトが行い、仕様を受理することが段階3：構築のプランモードプレイを開始させます。

#### 実際の見た目（プロンプト）

```
Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.
```

#### ガバナンス上の考慮事項

何週間も後のレビューで発見されるのではなく、生きたポリシーが仕様の作成中に読み込まれ適用されます。組織のスキルは仕様に対する制約として適用されます。仕様、それを生成したプロンプト、有効だったスキルのバージョンはすべてバージョン管理に記録されます。プロダクトオーナーが仕様に署名し、フラグの立った懸念事項を指定されたポリシーオーナーにルーティングします。

測定方法

**先行指標**

同じ変更について、`intent.md` コミットから `spec.md` コミットまでの経過時間（2つの git タイムスタンプ）。従来の要件・設計サイクルと比較します。

**遅行指標**

構築開始後の要件の手戻り。同じ変更について、最初の `plan.md` コミットより後の日付を持つ `spec.md` コミットの数を数えます。git ログから直接得られます。

**03**

## 構築

承認された計画なしには何も実装されません。組織的知識はエージェントが読むファイルになり、ガードレールは習慣ではなくコードとして動作します。

### デフォルトの起点としての Claude Code プランモード

エンジニアは [プランモード](https://code.claude.com/docs/en/permission-modes) で Claude Code のセッションを開始し、段階2：設計で承認された `spec.md` を Claude に渡し、エンジニアが計画に満足するまでインタビューさせながら反復させます。

**従来** エンジニアは設計を読み、コードを書き始めます。変更をどう行うか、どのファイルとどのテストを扱うかまで、それはエンジニアの頭の中、良くてもチケットのコメントに留まります。他の誰もそれをレビューできません。レビュアーが最初に目にするのは完成した差分であり、その時点では手戻りが遅くなります。

**AI ネイティブ** 作業は、Claude がプランモードで作成する書面の計画から始まります。この段階では Claude は何も変更せずにコードベースを読めます。コードが書かれる前にエンジニアが計画を修正し、承認済みのバージョンは後続の段階が照合できるよう `plan.md` としてコミットされます。

はじめ方

**前提条件**

（存在する場合は）意図の成果物（`intent.md` または `spec.md`）。`CLAUDE.md` ファイルがあると役立ちます。

**インフラ**

リポジトリへのアクセス権を持つ Claude Code。

#### 実行方法

1. エンジニアは Claude とのセッションをプランモードで開始します。
2. エンジニアは `intent.md` と `spec.md` を Claude に渡し、変更するファイル、作業の順序、それを証明するテストを名指しした実装計画を求めます。
3. その変更が何を壊しうるか、どのステップが最もリスクが高いか、Claude が選ばなかった他の選択肢は何かを尋ねて計画を問い詰めます。
4. この会話を見たことがないエンジニアでも計画だけから変更を実装できるようになるまで反復します。
5. 承認された計画を `plan.md` としてコミットします。この計画は監査証跡に加わり、PR レビュープレイ（段階5：デプロイ）で最終的な差分と照合されます。
6. 計画を承認し、Claude に実装させます。しっかりした計画があれば、実装は 1 回のパスで済むことが多いです。
7. 実装が計画から逸脱する場合は、同じコミットで `plan.md` を更新します。フックを使って両者の同期を強制することも検討してください。

#### 実際の見た目（plan.md）

```
# Plan: claims status self-service (from intent.md 2026-06-02)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.

## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.
```

#### ガバナンス上の考慮事項

設計レビューは、コードが生成される前、進路変更がまだドキュメントの編集で済む段階で行われます。プランモード自体がこれを強制しており、エンジニアが計画を承認するまで Claude はファイルを編集できません。計画とその改訂、そして誰がそれを承認したかが記録されます。定型的な変更はエンジニアが承認し、組織が高リスクと分類するものはテクニカルリードやアーキテクトに回されます。

測定方法

**先行指標**

最初の実装パスからマージされる変更の割合、および計画承認からマージ済み PR までの時間（PR のメタデータに必要なデータとともに）。

**遅行指標**

PR のメタデータから得られる変更あたりの手戻り回数、そしてマージされた差分がコミット済みの `plan.md` とどれだけ一致し続けているか。

### 自動モードでの Claude Code

Claude Code は自動モードでも実行でき、この場合エンジニアは計画を承認し、満足して反復を終えたら、Claude は一つひとつの編集ごとにプロンプトを出すことなく各変更を適用します。後続のプレイで整備されるガードレール（チューニングされた `CLAUDE.md`、ポリシーをコード化したスキル、安全でない操作をブロックするフック、Claude が実行できるテストスイート）が成熟するにつれ、定型的な作業では自動承認がデフォルトになっていきます。引き締まった `spec.md`、影響範囲の小さな変更、既存のテストがカバーしているコードが揃った場合です。

この変化は、ユーザーがエージェントの編集を見守りアクションをレビューするあり方から、長時間の自律セッション後に成果物をレビューするあり方への移行です。自動承認モードは、ワークツリーと組み合わせることで個人・チーム間の並列性をさらに高め、段階6：保守で説明する、SDLC を自律的に実行しループを閉じることの基盤となります。

サイドバー

### レガシーシステムと信頼できる情報源

*このプロセスが生み出すすべての成果物に当てはまります。*

既存の SDLC プロセスはすでに、markdown ファイルという形ではないにせよ成果物を追跡している可能性が高いです。作業項目は Jira に、要件は規制トレーサビリティを組み込んだツールに、デザインは Figma に、変更承認は変更管理委員会にあるかもしれません。これらのシステムは、監査人や規制当局がすでにそれを受け入れており、他のチームがそれに依存しているため置き換えが難しく、AI ネイティブ SDLC は既存のものに合わせて構築する必要があります。

AI ネイティブ SDLC へ移行する際は、プロセスが生み出す各成果物について、1 つのシステムを信頼できる情報源として指定し、それ以外はコピーまたは元へのリンクを保持するようにします。以下の構成は、成果物ごとに 1 つの信頼できる情報源を設定するために選べる選択肢です。

**リポジトリを信頼できる情報源とする。** markdown の成果物が正式な記録となり、レガシーシステムはコミット内のファイルを参照します。これはエンジニアリング主導の組織にとって最もクリーンな構成の 1 つになり得ます。すべての記録が 1 つのツールに、1 つのタイムスタンプ機関のもとで存在するためです。

**レガシーシステムを信頼できる情報源とする。** Jira、ServiceNow、または要件管理ツールが正式な記録を保持し、markdown の成果物は作業用のコピーになります。Claude はセッションの開始時に記録を読み、仕様や計画を生成したのと同じセッション内で [MCP](https://code.claude.com/docs/en/mcp) コネクタを通じて結果を書き戻します。

**最低限のリンク付け。** すべての成果物がレコード ID を記載し、すべてのレガシーレコードが markdown ファイルのコミット SHA を含みます。リンク付けは、2 つの信頼できる情報源が存在することを受け入れつつ、AI ネイティブ SDLC への移行を始める良い出発点です。

レガシーシステムと markdown ファースト方式は、両者の間にリンクがあるか、どちらかが信頼できる情報源として宣言されている限り、共存できます。

### CLAUDE.md

[`CLAUDE.md`](https://code.claude.com/docs/en/memory) は、新しく加わったメンバーが必要とするであろうコンテキスト、つまり規約、コマンド、アーキテクチャ、チームが最も頻繁に目にする間違いを Claude に与えます。かつては人々の頭の中や wiki にあった知識が、すべてのセッション開始時にエージェントが読み込むファイルになり、チーム全体で保守され、ミスが発生するたびに反復更新されます。

はじめ方

**前提条件**

なし。

**インフラ**

リポジトリ、Claude Code のインストール、そしてコードベースをよく知るエンジニア 1 名。

#### 実行方法

1. リポジトリで `/init` を実行します。Claude が見つけたものから初期の `CLAUDE.md` を生成します。
2. 生成されたファイルを、初日に新しいメンバーが必要とするものに絞り込みます。ビルド、テスト、リントのコマンド、重要な規約、そして Claude が繰り返し間違えることを残します。
3. `CLAUDE.md` をリポジトリのルートで git に登録し、チーム全体が 1 つのバージョンを共有し、変更がコードと同じようにレビューされるようにします。
4. ここで役立つ経験則があります。Claude が同じ間違いを 2 回犯したら、その修正を `CLAUDE.md` に加えます。
5. 1 ページ未満に収めます。Claude はセッション開始時にすべてを読み込むため、古くなった内容は何の利益もなくコンテキストを消費するだけだからです。

#### 実際の見た目（CLAUDE.md）

```
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.
```

#### ガバナンス上の考慮事項

`CLAUDE.md` はバージョン管理されているため、エージェントが従う指示はレビューでき、監査可能です。チームの規約はこのファイルを通じて適用され、変更は git 履歴に記録され、コードオーナーが PR レビューでその変更を承認します。

測定方法

**先行指標**

Claude が `CLAUDE.md` で防げたはずの間違いをどれだけ繰り返すか。`CLAUDE.md` への修正・変更は git 履歴の中で追跡されるべきです。

**遅行指標**

PR 履歴から得られる、チームの新しいメンバーが最初の PR をマージするまでの時間。

### 組織的知識としてのスキル

スキルは、組織が自らの組織的知識を運用可能にする方法です。指示は明示的で、バージョン管理され、幅広く適用され、ポリシーが変わったときには中央で更新されます。経験則としては、一貫して適用されるべき組織的知識にはスキルを書き、`CLAUDE.md` やプロンプトに収まるようなものにはスキルを書かないことです。

はじめ方

**前提条件**

必須のものはありません。`CLAUDE.md` があると、エージェントの作業知識がリポジトリ内に保たれるため役立ちますが、スキルはそれに依存しません。

**インフラ**

指定されたオーナーと、書面による信頼できる情報源を持つ 1 つのポリシー。

#### 実行方法

1. 今日一貫性なく実施されている知識を 1 つ選びます。セキュリティ標準、API 設計の規約、ブランドルールなどが考えられます。
2. それをスキルとして書きます。スキルは、いつ発火するかをフロントマターに記し、本文に何をすべきかを記した `SKILL.md` を含むフォルダです。エンジニアが、ポリシーオーナーの信頼できる情報源をもとに、Claude の助けを借りて書きます。
3. スキルをリポジトリの `.claude/skills/<name>/` に置いてコードとともに出荷するか、[プラグイン](https://code.claude.com/docs/en/plugin-marketplaces) を通じて組織全体に配布します。
4. スキルが発火することをテストします。関連するタスクを異なる方法で Claude に依頼し、毎回スキルが読み込まれることを確認します。
5. ポリシーが変わったら、スキルを変更し、ポリシーオーナーにその変更を承認してもらいます。
6. エンジニアは次のセッションで自動的に新しいバージョンを受け取ります。

#### 実際の見た目（.claude/skills/secure-api-review/SKILL.md）

```
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review

When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run scripts/check-endpoints.sh and include its output in your summary.
```

#### ガバナンス上の考慮事項

スキルは統制ですが、あくまで助言的なものです。ポリシーがコードの記述中に適用される可能性を高めますが、セッションがそれに従うことを強制するものは何もありません。常に成り立つ必要のあるポリシーには、スキルの背後にある決定論的な何か、たとえば操作をブロックするフックや、PR でポリシーを再チェックするレビューパスが必要です。スキルは違反をまれにし、フックはそれをほぼ不可能にします。スキルの呼び出しはセッショントレースに記録され、ポリシーオーナーがスキルの変更をコードのようにレビューします。

測定方法

**先行指標**

ポリシーオーナーがポリシー変更を承認してから、更新されたスキルがマージされるまでの時間。スキルフォルダの PR から取得します。

**遅行指標**

ポリシーを引用する PR レビューの指摘。スキルがコードの記述中にポリシーを適用するようになれば、これはゼロに向かって減っていくはずです。ゼロに向かわない場合、スキルが発火していないか、その文言が公式ポリシーからずれてしまっています。

### ビルド時ガードレールとしてのフック

スキルが助言的な統制であるのに対し、[フック](https://code.claude.com/docs/en/hooks) はその背後にある決定論的な層です。Claude のアクションの大半は実装中のファイル編集とシェルコマンドであるため、構築フェーズはフックが最も頻繁に発火することになる場所です。

構築フェーズのフックは次のことができます。

- 生成されたクラスや凍結されたパッケージなど、保護されたパスへの編集をブロックする
- ファイル編集後にフォーマッタとリンタを実行し、乱れが蓄積しないようにする
- 認証情報が差分に含まれないようにする

例外なく維持されるべきポリシーを持つスキルの背後には必ずフックを置きます。フックは一致するアクションのたびに実行されるため、構築フェーズのフックは高速で、変更されたファイルに限定されるべきです。テストスイート全体のような重いチェックはコミットや PR の段階に属します。

人間の承認を求めるフックは段階5：デプロイのゲートに属します。構築中の承認プロンプトは、並行して走っているすべてのセッションのクリティカルパスに人を戻してしまうからです。

### 並行セッションとサブエージェント

1 人のエンジニアが複数の作業ストリームを同時に進められます。

並行セッションとは、独立した git [ワークツリー](https://code.claude.com/docs/en/worktrees) で別のタスクに取り組んでいる、もう 1 つの完全な Claude Code インスタンスです。各独立セッションは互いについて何も知らず、それらを操縦しているエンジニアだけが共通しています。

[サブエージェント](https://code.claude.com/docs/en/sub-agents) は、1 つのセッション内で独自のコンテキストウィンドウとツール制限を持つスコープ限定のヘルパーとして動作し、アプリが期待通り動いているかを確認するなど、複数のタスクで繰り返し発生する作業に向いています。

並行セッションはエンジニアが同時に抱えられるタスクの数を増やし、サブエージェントは各セッションを自身のタスクに集中させたままにします。エンジニアの仕事は、それらすべてを操縦しレビューすることです。

**従来** 1 人のエンジニアは一度に 1 つのタスクに取り組み、1 日または 1 週間のかなりの部分をビルド、テスト、レビュー待ちに費やします。待っている間に別のタスクへ切り替えることは可能ですが、そのコンテキストスイッチは疲れるものなので、それを選ぶ人は多くありません。

**AI ネイティブ** 1 人のエンジニアが、それぞれ独自のワークツリーで独自のタスクに取り組む複数の Claude セッションを同時に走らせます。繰り返し発生する仕事は、独自のコンテキストとツール制限を持つサブエージェントになります。エンジニアの仕事はオーケストレーションへ、そして最終的にはループを構築し監視することへとシフトします。

はじめ方

**前提条件**

すべてのセッションがこのファイルを読むため `CLAUDE.md`。段階4：テストのフィードバックループもここで役立ちます。セッションが自分の作業を検証できると、エンジニアからの監督が少なくて済むためです。

**インフラ**

分離がワークツリーから得られるため git リポジトリ。組織が安全とみなすコマンドの承認プロンプトでセッションが待たされないようにチューニングされた権限設定。

#### 実行方法

1. エンジニアは、段階3：構築のプランモードプレイの計画を使って作業が独立している箇所を見極め、異なるファイルに触れるタスクに作業を分割します。同じファイルを共有するタスクは 1 つのセッションで順番に実行します。
2. 各並行タスクは独自のワークツリーを持ちます。たとえば、あるターミナルで `claude --worktree feature-auth`、別のターミナルで `claude --worktree fix-rate-limit` のように。ワークツリーは独自のブランチを持つ独立したチェックアウトであり、セッション同士がファイルで衝突するのを防ぎます。
3. 2〜3 セッションが妥当な出発点です。実質的な上限は 1 人が適切にレビューできるストリームの数なので、レビューが追いついている間だけセッションを追加します。
4. 繰り返し発生する仕事は、`.claude/agents/` 内の markdown ファイルで定義されたサブエージェントにします。それぞれに名前、いつ使うかの説明、触れられるツールを持たせます。例としては、メインエージェントが終わった後に不要な複雑さを取り除くコードシンプリファイア、アプリを実行して動作を確認するベリファイア、メインのコンテキストを圧迫せずにコードベースを探索して報告するリサーチャーなどがあります。チーム全体で共有できるよう定義を git に登録します。

#### 実際の見た目（.claude/agents/verifier.md）

```
---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.
```

#### ガバナンス上の考慮事項

セッションが増えるほど出力も増えるため、統制はリポジトリ内の設定から来る必要があります。そこにあるフックと権限設定はすべてのセッションに適用され、あるセッションが何をしたかは記録され、それを実行したエンジニアに紐づけられます。

測定方法

**先行指標**

レビュー品質を保ったままの、エンジニア 1 人あたりの同時セッション数（OpenTelemetry のエクスポートから数える）。そして、待機ではなく操縦に費やされた 1 日の割合。

**遅行指標**

PR 履歴から求められる、エンジニア 1 人・週あたりのマージ数と、それに合わせた手戻り率。

### Claude にフィードバックループを与える

テスト、ビルド、スクリーンショット差分など、Claude が自分の作業を検証できる方法を必ず与えます。セッションは、エンジニアがそれを目にする前に、自分の作業を確認し自分の間違いを修正します。

このフィードバックループは、段階3：構築のベリファイアサブエージェントと混同してはいけません。フィードバックループはタスク全体を通して作業回数だけ実行されます。一方でベリファイアサブエージェントは、セッションが作業完了と判断した後、新しいコンテキストウィンドウで最終チェックを 1 回実行する形でパッケージ化する方法の 1 つです。こうすることで、コードを作った際の前提に左右されない判定が得られます。

**従来** コードが動くというシグナルは遅れて届きます。CI は数分後、テスターは数日後、本番環境は数週間後です。エージェントがコードを作る場合、シグナルが遅れると、人がその出力すべてを確認しなければならなくなり、その人がボトルネックになります。

**AI ネイティブ** セッションには、人がそれを見る前に自分の作業を確認する方法が与えられます。テストを実行し、ビルドを実行し、スクリーンショットを撮ります。Claude はチェックが通るまで反復するので、エンジニアに届く頃にはすでにそのチェックを通過しています。ループを設定するのはそのセッションを実行しているエンジニアの役目であり、以下のステップはそのエンジニア向けに書かれています。

はじめ方

**前提条件**

なし。

**インフラ**

それぞれ 1 つのコマンドでローカルに実行できるテストスイートとビルド。UI の作業には、ブラウザツールか MCP 経由で組み込んだスクリーンショットユーティリティなど、Claude が結果を見る手段が不可欠です。

#### 実行方法

1. 今日、作業の確認に一連のコマンドと環境知識が必要な場合は、それを "make test" や "npm test" のような、失敗時に非ゼロで終了する 1 つのターゲットにまとめます。
2. `CLAUDE.md` の Commands セクションに、健全な出力の例とともに各コマンドを記載します。
3. Claude があなたに尋ねなくても作業を確認できるよう、目標を状態し定量化可能にします。たとえば「test_status.py のすべてのテストが通る」「スクリーンショットが添付のモックと一致する」「エンドポイントが新しいフィールドとともに 200 を返す」などです。
4. バグ修正の場合は、まず失敗するテストを書きます。Claude にバグをテストとして再現させ、実行させ、期待通りの理由で失敗することを確認させます。そのテストをコミットします。その後にのみ、テストを編集せずにそれを通すよう Claude に依頼し、最終ステップのテストファイルフックでその制約を強制します。修正前から存在し、エージェントが書き換えられなかったテストは、バグが消えたことの証明になります。
5. UI の作業では、視覚的なチェックでループを閉じます。Claude にブラウザまたはスクリーンショットツールとモックを与え、反復させます。実装し、スクリーンショットを撮り、比較し、調整します。2〜3 ラウンドが普通で、結果は回を重ねるごとに改善するはずです。
6. 検証を「完了」の一部にします。指示は `CLAUDE.md` に書きます。タスク完了を報告する前にテストを実行させ、その出力を示させます。
7. 最後に、ループ自体を保護する必要があります。コードを修正するエージェントが、そのコードに対するチェックを弱めることができてはいけないからです。修正タスク中にテストファイルへの編集をブロックするフックがこれを実現します。代替策として、レビューで差分を確認し、テストに触れる変更はすべて却下することもできます。

#### 実際の見た目（CLAUDE.md の検証ブロック）

```
## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
```

ガバナンス上の考慮事項

**何が強制されるか**

タスクを完了と報告する前の検証、そして修正タスク中にエージェントがテストファイルを編集することのブロック。いずれも、組織が保証を求める場合はフックとして実装されます。

**証跡は何か**

"make test" の生の出力、ビルドログ、または Claude が実行し貼り付けたスクリーンショット差分。証跡はツールチェーン自体から生まれます。

**どこに記録されるか**

セッションのトランスクリプトに記録され、OpenTelemetry のエクスポートが組織のオブザーバビリティスタックに転送します。また、PR のチェック実行にも記録され、レビュアーや後の監査人もそれを見られます。

**誰が承認するか**

PR をレビューするコードオーナーです。機械的な証跡はすでに添付されているため、意図とリスクに集中できます。

測定方法

**先行指標**

エージェントが書いた変更の初回パス CI 成功率。これは CI システムがすでにサポートしています。

**遅行指標**

PR あたりのレビュー時間（PR のメタデータから）。テストがかつてレビュアーが見つけていたものを捕捉するようになれば下がるはずです。そしてインシデントトラッカーから得られる変更失敗率。

### CI における継続的評価

評価（eval）は、段階ゲート方式の QA に相当する AI ネイティブなものです。実際には、エージェントの設定が変わるたびに実行されるスイートを意味します。新しいモデルが導入されたときやプロンプトが書き換えられたとき、評価スイートはエージェントが同じ水準で作業をこなせているかどうかを示します。

評価は生きたスイートとして扱うべきです。モデルが向上するにつれ、かつて識別力を持っていたケースが機能しなくなり、継続的な監視から生まれる新しいケースを追加しなければなりません。

ユースケースによっては、すべての変更ごとではなく、決まった頻度でオフラインでこれらの評価を実行することを好むチームもあるでしょう。以下のステップは継続的な評価を対象としています。

はじめ方

**前提条件**

`CLAUDE.md` とフィードバックループ（段階4：テスト）。

**インフラ**

Claude Code を非対話的に実行できる CI、そして評価実行のための予算を持つ API キー。

#### 実行方法

1. プラットフォームエンジニアは、最近の作業から期待される・受理された結果とともに 20〜50 個の実際のタスクを集めます。
2. 各タスクを評価として書きます。つまりプロンプトと、何が合格かを定義するチェック（テストが通る、リントがクリーン、動作が変わらない、ポリシーに従っている）です。
3. このスイートは、スケジュールに従って、また `CLAUDE.md`、スキル、フックへの変更のたびに CI 上で非対話的に実行されます。これらの設定はエージェントを操縦するものであり、コードが受けるのと同じ回帰テストに値するからです。
4. 設定変更を結果でゲートします。合格率を下げるスキル変更は、マージ前にレビューされます。
5. 各本番インシデントはそのインシデントを担当したチームによって評価として書かれ、回帰テストとしてスイートに残ります。

#### 実際の見た目（.github/workflows/agent-evals.yml）

```
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

#### ガバナンス上の考慮事項

評価は、エージェントの出力に追いつくゲートを QA に与えます。合格率のしきい値はマージチェックとして強制され、実行結果は記録され時間の経過とともに比較でき、設定変更を所有するチームがそれを承認します。

測定方法

**先行指標**

すべての実行でスイートが報告する評価の合格率の推移、そして本番インシデントが恒久的な評価になるまでの時間。

**遅行指標**

CI で捕捉された回帰と本番で発見された回帰の比較（インシデントトラッカーから得られる）。

**05**

## デプロイ

レビューは両方向に流れ、ガバナンスはエージェントが行動する中で実施されます。エージェントは本番ゲートの手前まですべてを行い、それを越えては何もしません。

### PR レビューループの中の AI

Claude はレビューを与えもし受けもします。組織のポリシーに照らして受信 PR をレビューし、自分自身の PR に対するレビューコメントに自ら対応します。これによりエンジニアは、意図とリスクを判断することに帰着する行動面のレビューに集中できます。

**従来** レビューのキャパシティは人間のアウトプットを前提に計画されていました。PR はレビュアーがすべてを読むのを待ち、レビューの質はレビュアーの負荷によって変わり、著者は督促を続け、バックログは膨らんでいきます。

**AI ネイティブ** すべての PR が、重大度でランク付けされた指摘とともに、同一のレビューパス一式を受けます。人間の注意は 1 段階上、つまり変更が計画の意図通りかどうか、リスクが許容できるかどうかへ移ります。

はじめ方

**前提条件**

段階3：構築で更新された `CLAUDE.md` ファイル。レビューパスが書面のポリシーを強制する場合はスキル。定義済みのサブエージェント。

**インフラ**

Claude 統合をインストールしたリポジトリ。管理者が有効化するマネージド [Code Review](https://code.claude.com/docs/en/code-review)（リサーチプレビュー）サービスか、自前の CI で動かす [claude-code-action](https://code.claude.com/docs/en/github-actions)（必要に応じて AWS Bedrock、Google Vertex、Microsoft Foundry 経由でのモデル呼び出し。CI/CD プレイでデプロイの選択肢を扱います）。コードオーナーの承認を必須とするブランチ保護ポリシーも有効です。

#### 実行方法

1. マネージドの Code Review サービスが最速の出発点です。管理者がそれを有効化し、対象リポジトリを選びます。パイプラインを制御したい場合や、自社のクラウド契約を通じてモデル呼び出しをルーティングしたい場合は、自前の CI で claude-code-action を使ってレビューを実行します（その配線は CI/CD プレイで扱います）。
2. テクニカルリードは、リポジトリのルートに `REVIEW.md` としてレビューポリシーを書き、組織が重視するパス、つまりバグと論理エラー、セキュリティと脆弱性、（要件パスの `spec.md`、プランモードプレイの `plan.md`、設計原則に照らした）仕様準拠に分けます。`REVIEW.md` はまた、何が Nit ではなく Important に当たるか、そして何をスキップすべきかも定義します。
3. テクニカルリードは人間側のしきい値を設定します。指摘だけで PR が承認・ブロックされることはなく、ブランチ保護は引き続きコードオーナーの承認を要求します。指摘に基づいてマージをゲートしたいプラットフォームエンジニアは、チェック実行が公開する機械可読な重大度別集計を読めます。
4. レビュアーまたは著者がレビューコメントで `@claude` にタグ付けすると、Claude はそのコメントに対応し修正をプッシュします。PR スレッドには依頼と変更の両方が記録されます。この修正ループは claude-code-action を通じて動きます。マネージドサービスでは、`@claude review` とコメントすることで代わりに新しいレビューを要求します。Claude が開いた PR については、さらに一歩進めて Claude にマージまでの世話をさせられます。チームは、PR 上の未解決のレビューコメントと失敗しているチェックを一掃し、それらに対応して修正をプッシュし、PR がグリーンになりコードオーナーの承認だけを待つ状態になるまで続けるカスタムスラッシュコマンドにこのループをラップします。
5. レビューの指摘は `CLAUDE.md` にフィードバックされます。レビューが 2 回目のミスにフラグを立てたとき、その修正はそのレビューの一部として `CLAUDE.md` に加えられ、レビューが `CLAUDE.md` を読むため、次の PR 以降そのミスは捕捉されます。レビューはまた、変更によって `CLAUDE.md` が古くなった場合にもフラグを立てます。
6. 月に一度、テクニカルリードは指摘を評価してレビュアーを改善し、`REVIEW.md` で Nit の量に上限を設けることでセットアップを調整します。生成されたパスや CI がすでに強制しているものは除外されます。

#### 実際の見た目（REVIEW.md）

```
# Review instructions

## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.

## Cap the nits
Report at most five nits per review; summarize the rest as a count.

## Do not report
Generated files under src/gen/ and anything CI already enforces.
```

#### ガバナンス上の考慮事項

コードを書いたエージェントにはそれを承認する手段がないため、職務分掌は保たれます。`REVIEW.md` のレビューポリシーはすべての PR に適用され、指摘、修正、評価、承認は PR 履歴に記録されるため、PR が監査記録になります。承認は指摘に基づき、ブランチ保護を通じて人間から得られます。

測定方法

**先行指標**

数分に短縮されるはずの最初のレビューまでの時間、そして Git に直接保存されたデータをもとにした、人がブランチに触れることなく解決されたレビューコメントの割合。

**遅行指標**

マージ前に捕捉された欠陥・脆弱性と、本番に漏れ出したものとの比較（PR 履歴とインシデントトラッカーから）。

### 承認ゲートとしてのフック

構築フェーズではフックをガードレールとして使い、人を介さずにアクションを許可・ブロックしていました（段階3：構築）。フックは「尋ねる」こともでき、特定の人物が承認するまでアクションを一時停止できます。これはリリースゲーティングが必要とするものです。

このプレイが段階5：デプロイに位置づけられているのは、リリースゲートが最も分かりやすい事例だからですが、フックはデプロイ専用ではなく、Claude が行動するあらゆる場所で動きます。たとえば、フックは段階3：構築で変更チケットのないマイグレーションやインフラへの編集をブロックしたり、段階4：テストで修正タスク中にエージェントがテストファイルを編集するのを止めたりできます。

はじめ方

**前提条件**

なし。

**インフラ**

変更プロセスが要求する承認の書面リスト。

#### 実行方法

1. エンジニアリングのリーダーシップは、変更管理・コンプライアンスとともに、変更管理の承認、リリース認可、保護されたパスへの編集など、存続させるべき人間の承認ゲートをリストアップします。
2. プラットフォームエンジニアは各ゲートを、Claude が行動する前に実行され、許可・確認・ブロックのいずれかを行うスクリプトであるフックとして表現します。
3. チームのフックは git 上の `.claude/settings.json` に置き、譲れないフックは、個々のエンジニアがオフにできないプラットフォームや IT 管理者が所有するマネージド設定に置きます。
4. ブロックは自身を説明すべきです。フックがアクションを止めたとき、その理由と承認へのルートが Claude の出力に表示されるようにします。

#### 実際の見た目（.claude/settings.json）

```
{
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [
            { "type": "command",
              "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
          ]
        }
      ]
    }
}
```

#### そしてゲート自体（.claude/hooks/production-gate.sh）

```
#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
   if [ -z "$RELEASE_APPROVAL" ]; then
     echo "Production deploys need a release authorization." >&2
     exit 2 # exit 2 blocks the action; the message goes to Claude
   fi
fi
exit 0
```

#### ガバナンス上の考慮事項

フックが承認ゲートです。ゲートの条件は、誰に対しても毎回強制されます。許可・ブロックの判断はタイムスタンプ付きで記録されます。ゲートはまた、承認とは何を意味するか、たとえば承認済みの変更チケットなのかリリースマネージャーの署名なのかも定義します。

各行が統制の観点で何を買っているか

`permissions.deny` はエージェントのコンテキストからシークレットを排除し、ツール経由の任意のネットワーク送出をブロックします。`permissions.allow` は安全な内側のループを事前承認しておくことで、拒否リストがプロンプト疲れに変わらないようにします。

`disableBypassPermissionsMode` と `allowManagedPermissionRulesOnly` を組み合わせることで、どのエンジニア、プロジェクトファイル、コマンドラインフラグもルールを広げられなくなります。

`sandbox` は権限だけでは埋められないギャップを塞ぎます。WebFetch へのツールレベルの拒否は、シェルコマンドがネットワークに到達するのを止めません。OS レベルのドメイン許可リストが送出そのものをブロックします。

`failIfUnavailable` と `allowUnsandboxedCommands` はサンドボックスをゲートにします。サンドボックスが初期化できない場合 Claude Code は起動を拒否し、サンドボックス内で失敗したコマンドをその外で再試行することはできません。

`credentials` は拒否ルールが残していたギャップを塞ぎます。`permissions.deny` は Claude のファイルツールを管理しますが、サンドボックス化されたシェルコマンドはデフォルトでは依然として `~/.ssh` や `~/.aws/credentials` を読める可能性があります。このブロックはその読み取りを拒否し、サンドボックス化されたすべてのコマンドの環境から指定したシークレットを取り除きます。

`allowManagedHooksOnly` は、このプレイの承認ゲートだけが実行されることを意味します。ローカルの何かがそれに追加したり置き換えたりすることはできません。

`disableSideloadFlags` と `strictKnownMarketplaces` は、エンジニアのマシン上のすべてのスキル、エージェント、フック、MCP サーバーが、ホームディレクトリからではなく、組織が承認したプラグインマーケットプレイスを経由して届いたことを意味します。

`allowManagedMcpServersOnly` は、エージェントのツールサーフェスをプラットフォームチームが所有する許可リストにします。

`requiredMinimumVersion` は、承認された下限を下回るバージョンでの起動を拒否するため、統制は組織が実際に評価済みのビルドによって強制されます。

上記はコピーすべき推奨事項というより、調整するための出発点と考えてください。すべての拒否は能力とトレードオフの関係にあり、適切なバランスはリポジトリのデータ分類次第です。設定リファレンスは、マネージド専用のキーも含め、すべてのキーを文書化しています。[code.claude.com/docs/en/settings](https://code.claude.com/docs/en/settings)

測定方法（フック自体について）

**先行指標**

各承認ゲートで待たされた時間。すべてのフックの判断はタイムスタンプと許可・ブロックの判定とともに OpenTelemetry のエクスポートに書き込まれるため、ゲートごとの待ち時間が可視化されます。

**遅行指標**

フック導入前後で本番に到達したゲート違反（インシデントトラッカーから）。

### CI/CD 統合とデプロイ

Claude Code を CI/CD パイプライン内で非対話的に実行し、長時間動くエージェントが安全に動作するよう実行をサンドボックス化し、MCP 統合を通じてデプロイを公開し、エージェントが実際にそれを必要とする前にロールバック経路をリハーサルします。

**従来** パイプラインは決定論的なスクリプトを実行し、判断が必要なものはすべて人間を待ちます。たとえば、不安定なテストのトリアージ、変更履歴の作成、ビルドが壊れた理由の調査などです。デプロイとロールバックは、人がプレッシャーの中で従うランブックです。

**AI ネイティブ** Claude はパイプライン内で判断を要するステップのために非対話的に実行され、スコープを限定した認証情報とともにサンドボックス内で動きます。デプロイツールは MCP を通じてエージェントに公開されるため、変更を書きテストしたワークフローがそれを出荷しロールバックすることもでき、これは組織が環境ごとに定義するゲートの内側で行われます。

はじめ方

**前提条件**

PR レビューループの中の Claude、そして承認ゲートとしてのフック。ゲートはそれらを通じて自動化を加速させる前に存在している必要があるためです。

**インフラ**

claude-code-action をインストールした CI プラットフォーム、または `claude -p` を呼び出せる任意のランナー。API、あるいはトラフィックを組織のクラウド契約内に留める必要がある場合は Bedrock、Foundry、Vertex 経由でのモデルアクセス。デプロイ対象向けの MCP サーバー。本番の常設認証情報を持たないエージェントジョブ用のサンドボックスプロファイル。

#### 実行方法

1. プラットフォームエンジニアは、読み取り専用の判断ステップから始めます。パイプラインのジョブで `claude -p` を使い、失敗したビルドをトリアージしたり、不安定なテストを要約したり、変更履歴を下書きしたりします。
2. リントの修正、生成ドキュメントの更新、`@claude` メンション経由のレビューコメント対応など、既存のゲートの内側で書き込みステップを追加します。エージェントが書くものはすべてブランチ保護を経由して PR として届き、エージェントには main へ直接プッシュする経路がありません。
3. 実行はサンドボックス化されます。エージェントのジョブは、短命でスコープを限定したトークンとともにネットワークポリシー下のコンテナで実行され、デフォルトでは本番の認証情報を保持しません。
4. MCP を通じてデプロイを公開します。デプロイ、ステータス確認、ロールバックは環境ごとにスコープされたツールになり、エージェントのデプロイ権限は、認証情報を持つシェルスクリプトではなく許可リストになります。
5. 環境ごとに自律性の段階を設けます。開発環境ではエージェントが自由にデプロイします。本番環境では、エージェントがリリースを準備し、リリースマネージャーがそれを認可し、フックが本番ゲートを強制します。ステージングはその中間に位置します。
6. ロールバックはパイプラインの中で最もリハーサルされたパスであるべきで、エージェントが実行でき、ステージングで定期的に演習される単一のコマンドにします。段階6：保守で扱うループを閉じるプレイは、統制帯が逸脱したときにこのロールバックを呼び出すため、事前に実証されている必要があります。

#### 実際の見た目（パイプラインステップ）

```
- name: Triage failed build
  if: failure()
  run: >
    claude -p "Read the build log at out/build.log. Identify the most
    likely cause, say whether the failure looks flaky or real, and write a
    three-line summary for the PR thread." >> triage.md
```

#### ガバナンス上の考慮事項

支配的な原則は、エージェントは本番ゲートまでは行動でき、それを越えることはできないというものです。以下の統制がこの原則を強制します。

- ブランチ保護により、エージェントが書くものはすべて PR になり、main への直接経路はありません。
- 本番デプロイフックは、指名されたリリースマネージャーが認可するまでリリースをブロックします。非対話型の各実行はエージェント自身のアイデンティティのもとで動作するため、パイプラインのログはエージェントが行ったことと、それをトリガーしたエンジニアが行ったことを区別します。
- 環境ごとの権限階層が、ゲートに至るまでにエージェントがどれだけのことをできるかを設定します。

測定方法

**先行指標**

人を呼び出すことなくトリアージされたパイプライン障害の割合（CI/CD パイプラインのログから）。

**遅行指標**

CI システムとデプロイツールがすでに出力している DevOps Research and Assessment（DORA）指標。

## 保守

ループが閉じます。人が呼び出しの経路に入ることなくトリガーが Claude を呼び出し、見つかったものは `intent.md` として再びパイプラインに入ります。

### 保守とループを閉じること

ここまでは、SDLC プロセスの各段階に Claude をどう加えるかを扱ってきました。それぞれの段階は最初のステップを起動するために人間を必要とします。しかしこの段階では、焦点はループを閉じるための Claude の自律的な実行へと移ります。

たとえば、常時稼働する監視エージェントは、バグチケットが起票されたことを受けて `intent.md` を作成し、要件、計画、構築、テスト、レビューの各フェーズを流れていくことができます。段階6：保守はヘッドレスで動作し、各段階の間に独立した信頼度ゲート、つまり決定論的なチェックやアドバーサリアルにレビューするエージェントが、前段階の出力を続行させるか人間にエスカレーションするかを決めます。

**従来** 保守は受動的なフェーズです。すべてのチケットやインシデントは、誰かがそれに対応してプロセスを再開させるのを待ちます。アラートが午前3時に鳴っても見逃されることがあり、チケットは誰かが拾い上げるまでバックログに眠り続けることがあり、ポストモーテムのアクション項目は別の火事が起きればコードベースに反映されないまま終わることもあります。

**AI ネイティブ** 統制帯の逸脱、チケット、チャンネルメッセージ、スケジュールといったトリガーが、人を経路に入れることなく Claude を呼び出します。Claude は診断し、ゲート付きの経路を通じてのみ行動し、見つけたことを `intent.md` として書き、それが上記で説明した各段階を経ていきます。人はその作業をトリアージしレビューしますが、もはやそれを開始する必要はありません。

### ループを閉じる

決定論的なスクリプトが本番環境を監視し、統制帯が逸脱したときに Claude を呼び出します。逸脱の監視は、ループを自律的に走らせるパターンの分かりやすい例です。段階の最後にある [Claude Tag](https://claude.com/product/tag)（パブリックベータ）のセクションでは、異なるチャンネルから届く作業を扱います。

はじめ方

**前提条件**

ループに構造化された出力を与え再起動させる `Intent.md`。Claude による PR レビューの加速、境界としてのフック、そして（最も自律性の高い段階が呼び出す）CI/CD のロールバック経路。

**インフラ**

検知スクリプトが問い合わせられるメトリクスストア（Prometheus、CI システムの API など）。リポジトリへの読み取りアクセス。Claude Code を CI で非対話的に実行する手段、あるいは Webhook を受け取るサービス向けの [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)。

#### 実行方法

1. サービスオーナーまたはプラットフォームエンジニアは、CI のテスト失敗率、デプロイ後の 5xx 率、PR サイクルタイムなど、安定したローリングベースラインを持つメトリクスを 1 つ選びます。
2. 検知スクリプトを書きます。通常は、緩やかなドリフトもスパイクも捉えるルール（Western Electric ルールなど）を伴う、ローリングウィンドウ上の平均と標準偏差です。このスクリプトはバージョン管理され単体テストされており、検知は完全に決定論的で、モデルは一切関与しません。
3. 応答段階はバージョン管理された設定（下記の `bands.yaml`）で定義されます。1σ ではスクリプトはログを記録するだけ、2σ では Claude を読み取り専用で呼び出して診断させ、3σ では Claude が行動できますが、それはレビューゲートへの PR を開く、あるいは事前承認済みのランブックをトリガーすることに限られます。
4. トリガー層は、GitHub や GitLab のスケジュール済みワークフロー、既存の監視スタックからの Webhook、ネットワーク内の Cron ジョブのいずれでもかまいません。Claude はステートレスに動作し、CI ランナー上の非対話型ステップとして、あるいはサンドボックス化されたコンテナ内の Agent SDK サービスとして実行されます（デプロイとモデルアクセスの選択肢は CI/CD プレイで扱います）。実行はステートレスかつ非対話的であるため、誰も起動していないところでループが始まり終わることができます。
5. エージェントは、異常とその証拠、提案する成果、影響を受けるシステム、未解決の質問をカバーする、段階1：計画のフォーマットで診断を `intent.md` として書きます。そこから、その発見は他のものと同じようにパイプラインを進みます。
6. サービスオーナーまたはオンコールエンジニアはキューをトリアージし、プロダクト向けの発見をプロダクトオーナーにルーティングします。今すぐ修正する、スケジュールする、却下するのいずれかです。却下はバンドを調整しノイズを減らすのに役立ちます。
7. 修正が出荷されたら、そのインシデント向けの評価を追加し（継続的評価プレイ）、今後同様の問題が起きないよう保護します。

#### 実際の見た目（CI のテスト失敗率を監視する bands.yaml の例）

```
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

#### ガバナンス上の考慮事項

段階の境界はバージョン管理された設定によって強制され、権限とマネージド設定は本番アクセスを拒否します。呼び出し、発見、トリアージの決定はタイムスタンプとともに記録されます。サービスオーナーが発見をトリアージし承認し、結果として生じる変更は通常の PR レビューゲートを通過し、エージェントがトリガーできるランブックは事前に承認されています。

測定方法

**先行指標**

バンド逸脱から `intent.md` がトリアージキューに入るまでの時間。従来のインシデント発生からポストモーテムのアクションまでの時間と比較します。検知スクリプトのログには逸脱のタイムスタンプとインシデントの段階が記録されています。

**遅行指標**

発見がマージ済みの修正になる割合（トリアージキューと実際の PR 履歴を照合）、そして同種のインシデントの再発は、修正が評価スイートにケースを追加していくにつれて減っていくはずです。

#### 例

- CI のテスト失敗率が 3σ を逸脱すると、エージェントは不安定なテストを隔離するか、リバート PR を開き、レビューゲートが判断します。
- デプロイの時間帯を含めてデプロイ後の 5xx 率が 3σ を逸脱すると、エージェントは既存のロールバックパイプラインをトリガーします。
- PR サイクルタイムがドリフトルールに引っかかると、エージェントはエンジニアリングのリーダーシップ向けにレポートを書き、この仕組みが本番指標だけでなくプロセス指標にも機能することを示します。

検知は決定論的なまま保たれます。Claude はバンドが逸脱した時点で呼び出され、その段階が何をできるかを設定します。

### Claude Tag によるオンコール対応の Claude

インシデントは Slack や Teams のような業務用コミュニケーションアプリなど、他の経路からも届くことがあります。インシデントチャンネルでの緊急修正を求める午後10時の Slack メッセージのようなものも、今ではすぐに行動に移せます。Claude Tag（現在 Slack でパブリックベータ提供中）は Claude を独自のアイデンティティのもとでそれらのチャンネルのメンバーにするため、新しいインシデントごとに最初の対応者が付き、対応そのものが将来のインシデントに向けたループとメモリの一部になります。

会話と組織的知識はチャンネルに残り、チャンネル内の誰もが対応を導き行動できます。誰でもチームメンバーが仮説を検証し、新しい選択肢を探り、リアルタイムで調査でき、チャンネル履歴が監査可能性を高めます。MCP へのアクセスを通じて Claude はメトリクスがベースラインに戻ったことを検証し、スレッドでそれを確認し、将来の調査が読めるバージョン管理されたレッスンファイルにポストモーテムを書きます。

Claude Tag が引き受けるのはインシデントだけではありません。MCP 経由でチケットにタグ付けされたり、チャンネルで尋ねられたりすると、Claude は同じ方法でその作業をトリアージします。小さく十分に範囲が定まった修正はレビューゲートを通じて PR として届き、それより大きなものは段階1：計画向けの `intent.md` として書き起こされ、その時点でループが自らを養い始めます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8760aded54a2a8319cd5b9_fe6d780d.png)

チャンネルが監査証跡です。依頼、診断、人間による認可、修正はすべて、インシデントが対応された場所に残ります。

## 結びに

モデルとハーネスはより高度になり、組織はコードの作り方だけでなく、ソフトウェア開発ライフサイクル全体を変革できるようになりました。

この変革は、人間の判断をプロセスの中心に据え続けたまま、大企業のガバナンスと規制の要件を考慮しています。

本ガイドは、私たちの Applied AI チームが日々顧客のために実践している、実際のベストプラクティスの多くを集約したものであり、実践的で行動可能なリソースとなれば幸いです。

ループは走り続けます。人間の判断はその上に留まり続けます。
