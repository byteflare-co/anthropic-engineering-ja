# Claude Fable フィールドガイド: 自分の未知を見つける

Claude Code と一緒に作業していると、地図と現地の違いをよく思い出させられます。

地図とは、これから行う作業を表現したもの、つまり私が Claude に与えるプロンプト、skill、コンテキストです。現地とは、その作業が実際に行われる場所、つまりコードベースであり、現実世界であり、そこに存在する具体的な制約です。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec1c_94358c3c.png)

地図と現地の差分こそが、私が *未知* と呼んでいるものです。Claude が未知に突き当たったとき、Claude は私が何を望んでいるかを推測して意思決定を下す必要があります。作業量が増えれば増えるほど、Claude が突き当たる未知の数も増えていきます。

Claude Fable は、私にとって初めて「自分が未知をどれだけ明らかにできるか」で作業品質のボトルネックが決まると感じるモデルです。

重要なのは、事前に計画しておくだけでは十分でないことがあるという点です。未知は実装の深い部分から見つかることもありますし、未知が浮上したことで「本来はまったく別のやり方で問題を解くべきだった」と気づかされることもあります。

私が Fable と作業していて実感するのは、実装の前・最中・後を通じて自分の未知を発見していく、反復的なプロセスだということです。

## 自分の未知を知る

そもそも、自分の未知とは何でしょうか? 私は Claude に問題を持ち込むとき、次の 4 つに分けて考える傾向があります。

- **既知の既知 (Known Knowns):** これは要するに私のプロンプトに書かれている内容です。エージェントに何をしてほしいと伝えているか。
- **既知の未知 (Known Unknowns):** まだ答えは出ていないけれど、自分でも「まだわかっていない」と自覚していること。
- **未知の既知 (Unknown Knowns):** 当たり前すぎてわざわざ書き出しはしないけれど、目にすれば「これだ」とわかること。
- **未知の未知 (Unknown Unknowns):** そもそもまったく考えていなかったこと。自分が気づいていない知識。どこまで良くできるのかすら知らない状態。

最も優れたエージェント志向のコーダーは、未知が比較的少ないものです。[Boris](https://www.linkedin.com/in/bcherny) や [Jarred](https://www.linkedin.com/in/jarred-sumner-a8772425) のような人がプロンプトを書いている様子を見ていると、彼らは自分が何を求めているかを細部までわかっていることが一目でわかります。コードベースにもモデルの振る舞いにも、深く同期しているのです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec52_cc0ee2de.png)

ただし、彼らも未知の存在を前提にしています。未知を減らすこと、そして未知を織り込んで計画することは、多くの意味でエージェント志向のコーディングにおける **スキル** そのものです。幸いなことに、これは Claude と作業を重ねることで伸ばしていけるスキルでもあります。

## Claude が助けてくれるように仕向ける

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec55_c4646783.png)

Claude への指示は繊細なバランスの上に成り立っています。指示が具体的すぎると、Claude は方向転換したほうがよさそうな場面でもあなたの指示に忠実に従い続けます。逆に曖昧すぎると、Claude はしばしば業界のベストプラクティスに基づいた選択や仮定をするため、あなたのタスクには合わないこともあります。

未知を織り込まないと、この両方向で失敗してしまいます。どこで道が障害物だらけになるかもわからないし、どこで道がきれいに空いているのに、それでも Claude に舵を切ってほしいのかもわかりません。

Claude はあなたが自分の未知を発見するのを助けてくれます。あなたのコードベースやインターネットを非常に高速に検索できますし、平均的なトピックについてはあなたよりずっと多くを知っています。失敗を糧に素早く反復することも得意です。

このプロセスで一番大事なのは、自分の出発点についてのコンテキストを Claude に与えることです。たとえば、自分が思考のどの段階にいるのかを伝える。問題やコードベースに対する自分の経験を明かす。Claude を思考のパートナーのように扱って一緒に作業する。こうしたことが大切です。

本稿では、これらの未知を掘り起こすために私が使っているパターンをいくつか紹介します。

## 実装前

### ブラインドスポットパス

作業を始めるときに最も有用なことの一つは、自分の盲点を把握することです。たとえばコードベースの新しい領域で機能を書いているときや、デザインを反復するといった不慣れな作業を Claude に手伝ってもらっているときは、**未知の未知** をたくさん抱えている可能性が高いはずです。

どんな質問をすべきか、良い状態とはどんなものか、これまでにどんな作業がなされてきたか、避けるべき落とし穴はどこか、といったことがわかっていないかもしれません。

そうした状況では、Claude に自分の未知の未知を見つけて説明してもらうよう頼むことができます。私はあえて「ブラインドスポットパス」「未知の未知」という言葉をそのまま使うようにしています。あなたが何者で、何を知っているのかというコンテキストを与えることは、Claude があなたと最適な形で協業するうえで通常とても重要になります。

**プロンプト例**:

- 「新しい認証プロバイダーを追加しようとしているのですが、このコードベースの認証モジュールについては何も知りません。ブラインドスポットパスを行って、私が知るべき未知の未知を洗い出し、私がもっと良いプロンプトを書けるように手伝ってもらえますか。」

- 「私はカラーグレーディングが何なのかわかっていないのですが、この動画をグレーディングする必要があります。カラーグレーディングについての私の未知の未知を教えてもらって、もっと良いプロンプトを書けるようにしてもらえますか?」

### ブレインストームとプロトタイプ

**未知の既知** が多い領域、つまり見て初めて基準を定義できるような領域で作業しているときは、Claude にブレインストームとプロトタイピングを一緒にやってもらうのが好みです。

プロトタイピングの早い段階で未知の既知を洗い出して言語化することは非常に価値があります。実装中にそれらが判明すると (相対的に) コストが高くつくからです。機能や仕様のちょっとした変更が、コード上ではまったく異なる実装を引き起こすことがありますし、あなたのエージェントにとってはそれまでの変更を巻き戻すのがかえって難しくなることもあります。

たとえば、バックエンドのルートを配線したりフロントエンドで追加の状態を保持したりせずに、フレームに追加したボタンがどう見えるかをただ確認したい、といった場合です。

もう一つの例はビジュアルデザインです。私にとってビジュアルデザインは言語化しづらいのですが、目にすれば何が欲しいかがわかるものです。こうした場合は、成果物に対して複数のデザインアプローチを頼むようにしています。

私はまた、コーディングセッションのほぼ毎回を探索やブレインストーミングのフェーズから始めています。これは、プロジェクトのスコープを意図をもって定義するための出発点になります。Claude は私が見落としていたであろう価値の高いアプローチを見つけてくれることが多い一方、木を見て森を見ないこともあります。ブレインストーミングは、スコープが狭すぎたり広すぎたりするのを防いでくれます。

**プロンプト例:**

- 「このデータのためのダッシュボードが欲しいのですが、私にはビジュアルのセンスがなく、何が可能なのかもわかりません。まったく違う方向性のデザインを 4 つ載せた HTML ページを作ってくれませんか。それに対して反応します。」

- 「何かを配線する前に、新しいエディタツールバーをダミーデータでモックした 1 つの HTML ファイルを作ってください。実アプリに触れる前にレイアウトに反応したいです。」

- 「大まかな問題はこれです: ユーザーがオンボーディング後に離脱してしまいます。コードベースを検索して、介入できそうな場所を安価なものから野心的なものまで 10 個ブレインストームしてください。どれが響くか、私が伝えます。」

### インタビュー

十分にブレインストーミングを終えても、おそらくまだ未知は残っています。

その場合、私は Claude に、あらゆる未知や曖昧さについて自分にインタビューしてもらうよう頼みます。Claude にインタビューを頼むときは、質問を導くために問題のコンテキストを与えるようにしてください。

**プロンプト例:**

- 「一問ずつ、曖昧な点について私にインタビューしてください。私の回答次第でアーキテクチャが変わるような質問を優先してください。」

### リファレンス

自分が欲しいものを細部まで説明できないこともあります。たとえばそれを表現する語彙を持っていなかったり、細部まで書き下すには途方もない時間がかかりそうだったりします。

そうした場合、最良のアプローチはリファレンスを示すことです。図表・ドキュメント・画像なども含められますが、絶対的に最良のリファレンスは *ソースコード* です。

もし特定の方法で何かを実装したライブラリや、自分が本当に気に入っているデザインコンポーネントがあれば、Fable にそのフォルダを指し示して、たとえ言語が違っていても「これに注目して」と伝えるだけで十分です。これはスクリーンショットなどと比べて、マークアップや構造まわりのはるかに豊かな情報を Claude に与えます。

**プロンプト例:**

- 「vendor/rate-limiter にある Rust クレートが、私が欲しいバックオフの挙動をちょうど実装しています。これを読んで、同じセマンティクスを私たちの TypeScript API クライアントで再実装してください。」

### 実装プラン

いよいよ実装できる、と思ったタイミングで、私は Claude に実装プランをまとめてもらって、それを自分がレビューする形をとる傾向があります。プランはデータモデル、型インターフェース、UX フローなど、最も変わりそうな部分にフォーカスしたものにします。こうすることで、実は自分が変えるべきだったポイントを Claude が浮かび上がらせてくれます。

**プロンプト例:**

- 「実装プランを HTML で書いてください。ただし、私が微調整する可能性の高い判断 (データモデルの変更、新しい型インターフェース、ユーザーに見えるあらゆる要素) を先頭に持ってきてください。機械的なリファクタリングは末尾に埋めてください。そこはあなたに任せます。」

## 実装中

### 実装ノート

自分のプランに納得したら、新しいセッションを立ち上げて、あらゆる成果物をプロンプトに渡します。これで Claude には、フレッシュなコンテキストウィンドウを持ちながらも、プランニング段階でまとめた情報のすべてを持たせることができます。たとえば、仕様ファイルとプロトタイプを渡し、それを実装するようエージェントに依頼する、といった形です。

とはいえ、どれだけ計画しても、未知の未知は必ずどこかに潜んでいるのが実情です。エージェントは作業を進める中で、コードから見つけたエッジケースのために別のアプローチをとる必要が出てくることもあります。

私は Claude Code に、自分が下した意思決定を追跡するための一時的な「implementation-notes.md」(あるいは .html) ファイルを作らせて、次回の試みに向けて学べるようにしています。

**プロンプト例:**

- 「implementation-notes.md ファイルを作ってください。プランから逸脱せざるを得ないエッジケースに当たったら、保守的な選択肢を選び、それを『Deviations』の下に記録して、そのまま進めてください。」

## 実装後

### ピッチと説明資料

何かを出荷するうえで最も重要な部分の一つは、賛同と承認を得ることです。ピッチや説明資料を最終ドキュメントとして仕上げておくと、次のような効果があります。

- レビュアーが、あなたと同じ未知からスタートするときの理解を加速する
- エキスパートが「彼らが予期したであろう未知や典型的な失敗ポイントに配慮しているか」を確認したいときの承認を加速する

**プロンプト例:**

- 「プロトタイプ、仕様、実装ノートを 1 つのドキュメントにまとめて、Slack に貼って賛同を得られるようにしてください。デモの GIF を先頭に置いてください。」

### クイズ

長い作業セッションの後、Claude が私の想像以上に多くのことを成し遂げていることがあります。コードの diff を読むだけでは、既存のコードパスに依存する挙動が多いため、その全体像を軽くしか把握できません。

たっぷりコンテキストを与えたうえで、変更内容についてのクイズを Claude に出してもらうと、そこで何が起きているのかを理解するのに役立ちます。私は、クイズに完璧に合格するまでマージしないようにしています。

**プロンプト例:**

- 「この変更で起きたことをすべて理解したいです。変更点について、コンテキスト・直感・何が行われたかなどをふまえて私が読んで理解できる HTML レポートを出し、末尾に必ず合格しなければならないクイズを付けてください。」

## これがどのようにまとまるか: Fable のローンチ

[Fable のローンチ動画](https://x.com/ClaudeDevs/status/2064399512664526853) は、エンドツーエンドで Claude Code を使って編集されました。これは私にとって新しい領域で、決してエキスパートではありません。

そこで、私は自分が知っていることから始めました。Claude がコードを使って動画を編集したり、文字起こしをしたりできることは知っていましたが、それが十分に正確なのかどうかはわかりませんでした。そこで Claude に Whisper のような文字起こしがどう動くのか、そして「えっと」や長い間を ffmpeg で正確に切り出せるのかを説明してもらいました。

私は自分が話す言葉に合わせて動く UI を Claude に作ってほしかったのですが、それが可能なのかがわかりませんでした。そこで、Remotion と文字起こしを使ってプロトタイプ動画を作り、それでうまくいきそうかを確認するよう Claude に依頼しました。

最後に、動画そのものが少しくすんで見えました。それがカラーグレーディングの結果だとは知っていましたが、カラーグレーディングそのものが何かはよくわかっていませんでした。最初は Claude にいくつかバリエーションを出してもらって選ぼうとしたのですが、カラーグレーディングの「良い」がどういうものかを自分がわかっていない、と気づきました。そこで代わりに、自分の未知を発見するために、Claude にカラーグレーディングについて教えてもらうことにしたのです。

## 地図と現地を一致させる

モデルが良くなればなるほど、正しいアプローチで達成できることは増えていきます。長期的なタスクが誤った結果で返ってきたなら、自分の未知を定義することにもっと時間を割くか、あなたと Claude がその未知に沿って適応していけるような実装プランを作る必要があるでしょう。

説明資料、ブレインストーム、インタビュー、プロトタイプ、リファレンス、そのどれもが、修正コストが高くなる前に「自分が知らなかったこと」を発見するための、安価な手段です。

だから次のプロジェクトはぜひ、Claude に自分の未知を見つけるのを手伝ってもらうところから始めてみてください。
