# AI ネイティブなエンジニアリング組織を運営する

長年にわたり、アプリケーションを作るうえで高くついていたのはエンジニアリングのバンド幅でした。ソフトウェアの計画と出荷にまつわるプロセスは、ウォーターフォールも、その後のアジャイルも、すべてその「コスト」を中心に組み立てられていたのです。

私のキャリアは 2000 年代初頭、Visual Studio に携わるところから始まりました。当時、ソフトウェアは CD-ROM に焼いて出荷するもので、製造の締め切りはハードなものでした。オンラインで配布できるようになってからは、継続的にアップデートを出荷する方向へと舵を切っていきました。そして今、私たちはまた働き方を変えようとしています。今度は、ソフトウェアを書くのにかかる時間と人数についてです。

Claude Code チームでは、コードを書くこと、テストを書くこと、リファクタリングをすることが、もはや私たちの足を引っ張ることはほとんどありません。とはいえ、エージェントによるコーディングが「実際にコードを打ち込む必要」を取り去ったからといって、ボトルネックがなくなったわけではありません。代わりに台頭してきたのが、検証（verification）、コードレビュー、そしてセキュリティです。

私たちはみな、いまや大量のコードを驚くほどの速さで生成できるようになりました。しかしそれと同時に、新しい問いも立ち上がってきています。このコードは正しいのか？ どう保守していくのか？ そして、私が他のエンジニアリングリーダーから最もよく受ける質問のひとつが、「コードレビューをそのやり方で回していて、人間側はどうついていけているのか？」というものです。

## いつのまにか機能しなくなっていたプロセス

私たちがプロセスを置くのは、いつだって理由があります。ある隙間を埋めるため、あるいは何かをうまく動かすためです。しかし、その隙間がもはや存在しなくなり、プロセスが時代遅れになっても、そういうプロセスがひとりでに消えてくれることは滅多にありません。Claude Code チームがエージェントによるコーディングをデフォルトの働き方として使い始めると、既存のプロセスの多くが機能しなくなりました。ここでは、私たちが書き換えた規範と、その理由を紹介します。

### 計画: ロードマップをジャストインタイムに

かつての規範は、コーディング時間が高くつくので、事前の計画にもっと多くの時間を費やすというものでした。Claude Code チームに加わったとき、私たちはなかなか良い 6 ヶ月ロードマップを書き上げました。ところが *Claude Code 自身のせいで* 物事が次々と変わり、3 ヶ月目にはもう古くなっていたのです。

エンジニアリングのスピードとスループットがいまや別物である以上、スプリントの計画の仕方も変わりました。私はそれをジャストインタイム（JIT）計画と呼んでいます。ちょうど JIT コンパイルのように、「ちょうど良いタイミングで、ちょうど良い量だけ」どうやるか、というわけです。私たちの計画の儀式は、設計ドキュメントから、PR やプロトタイプ上の議論へとシフトしました。この領域は動きが速いので、プロダクトレビューはあまりやりません。今の私たちのプロセスは、まずプロトタイプを作り、社内ユーザーをたくさん乗せ、そのフィードバックに沿って動き始める、というかたちです。

### コンテキスト集め: コードを書いた人ではなく Claude に聞く

エンジニアがコードを書いていたころは、たいていの問いの答えを得る第一歩は「そのコードを書いた人を見つけること」でした。ところが今、私たちの PR はすべて Claude が手伝っているので、「この変更を入れたのは誰？」だけではもう十分ではありません。新しい規範は、もう一段深く踏み込むこと、つまり「あなたが本当に知りたいのは何なのか」を問うことです。例: リグレッションを起こした犯人を探しているのか？ 顧客の質問に答えてくれる専門家を探しているのか？ それとも、ある意思決定の背景情報を探しているのか？ その問いを Claude に投げ、Claude がより多くのデータや文脈とともに直接答えられるかどうかを考えるのです。

Claude Code チームでは、その問いが何であれ、私たちのプロセスにはもうひとつ「自動化する方法はあるか？」という問いがついて回ります。たとえば、毎朝、顧客フィードバックチャンネルを Claude に要約させる、というのは、以前はコーヒー片手に私が手作業でやっていた儀式でしたが、いまやバックグラウンドで自動的に走っているものになっています。

### コードレビュー: 信頼しつつ検証する

私たちは [Code Review](https://code.claude.com/docs/en/code-review) をかなりヘビーに使っています。スタイルや lint、PR でのフィードバック対応、フルコミット前のバグ捕捉と修正、テスト追加——これらはすべて Claude が引き受けます。それでもなお人間に居てほしい場所が、専門性（expertise）です。

新しい規範は、「人間によるレビューを、本当に意味のあるところに置く」ということ。たとえば法務レビューでは、リスク許容度の判断には必ず法務パートナーに入ってもらいます。信頼境界（trust boundaries）やセキュリティに敏感なコードについては、その領域の専門家に入ってもらいたい。プロダクトマネージャーやデザイナーも、プロダクト感覚やセンスの面では絡んでもらう必要があります。

ただし、ここは継続的に評価していくことが重要です。なぜなら、「信頼するか／検証するか」の正しいバランスは、モデルの改善とともに動き続けるからです。今日、人間が必要な場所は、次のモデルでは違って見えるかもしれません。

### チーム構成: 役割の境界がぼやけていく

Claude と AI は、チーム全体の役割の形を変えました。私たちの PM はいまや結構コードを書いていて、それを見るのは楽しいものです。Claude のおかげで、これまで伝統的にコードを書いてこなかった人たちがより多くのエンジニアリングをこなせるようになり、エンジニア側もコンテンツやデザインといった、従来は「技術側」とされてこなかった仕事を引き受けられるようになっています。

Claude Code のエンジニアリングチームでは、私は 2 つのプロフィールに大きくインデックスしています。ひとつは、プロダクト感覚を持ったクリエイティブなビルダー——問題を解くプロダクトを世に出すことに深く好奇心と情熱を持つ「夢想家」たちです。もうひとつは、システムに深い専門性を持つエンジニアです。たとえば、私がチームに加わったとき、私たちにはシステムバックグラウンドの専門家が足りておらず、それは [Claude Code on the Web](https://www.anthropic.com/news/claude-code-on-the-web) を構築するときに必要になるものでした。Claude をどこでも動かせるようにするためです。

逆に、私があまり重視していないのは、生のスループットです。そこはモデルが引き受けてくれます。それよりも大事な問いは、「どこに依然として人間の専門性が必要なのか」であり、私であればそこにフォーカスします。

## 新しい規範をどう浸透させたか

これらの規範が変わっていく中で、ある側面はチームの原則として強制し、ほかの側面は小さなサブチーム（pod）に自分たちで考えてもらう、というかたちにしました。Claude Code のコアチームには、絶対に外せない「これだけはやる」原則のセットがあります。

- **自分たちのプロダクトを徹底的にドッグフーディングする:** Claude Code のチームメンバーは全員、職能横断のパートナーも含めて、Claude Code（そして Claude Cowork）を使っています。私たちはつねに、Claude にもっと速く、もっと効率よく仕事を手伝わせる方法を考えています。
- **チームをできるだけフラットに保つ。** 私が Claude Code に加わったとき、すべてのマネージャーには、まず IC として始めてもらい、出荷を通じてチームで効果的なエンジニアになる術を学び、Anthropic のエンジニアとして何が起きているのかを身をもって理解してもらいたいと考えていました。Claude Code と Claude Cowork には、ひとつの全体ミッションがあります。マネージャーは「pod」と呼ぶ仕事の単位を支えつつ、チームを機敏に保ち、人が仕事のあるところへ動けるようにします。
- **機能しなくなったプロセスを殺すのをためらわない:** 最後に、私たちは「なぜそのやり方でやっているのか」を執拗に問い続けます。何かが意味をなさなくなったとき、メンバーには古いプロセスを問い直し、葬る明示的な許可があります。

これらわずかなルールの内側では、各 pod に大きな裁量があります。トリアージに Claude をどう使うか、どんな計画の儀式やスタンドアップを走らせるか、どのワークフローを最初に「Claude 化（Claudified）」するか——どれも pod に委ねられているのです。

## 新しいプロセスが定着しているかをどう知るか

エンジニアリングリーダーが変化をロールアウトするうえで、いま追い始めるべき数字を 3 つ紹介します。

- **オンボーディングのランプ時間が下がる:** エンジニアでも、デザイナーでも、PM でも、どれくらい早く効果を出せるようになるか。私たちのチームでは、1 年前と比べてこれは大きく速くなっていて、エンジニアは初週のうちに本番コードを出荷しています。
- **PR のサイクルタイムが下がる:** これは深掘りしてみると興味深い指標です。なぜなら、自分たちのパイプラインが、どこでスケールに苦しんでいるかを浮かび上がらせてくれるからです。これだけ多くのコードを生成していると、ビルドシステムや継続的インテグレーション（CI）の側がついていけなくなることがあります。
- **Claude 支援コミットが上がる:** 私たちのところでは、デフォルトであらゆるコミットが Claude 支援です。直近 4 ヶ月、Claude が関わっていないコミットを見た記憶がないくらいです。

3 つ目の点については、スループットと成功を取り違えないことが重要です。スループットはあくまでひとつの指標であり、本当の指標は「自分が解こうとしている対象」を測ることです。正しい狙いのアラインメントさえあれば、スループットは問題をより速く解くのに役立ちます。

## まずやってみる

ひとつだけお土産を持って帰ってもらえるとしたら、こうお伝えしたいです。**いちばん騒がしいワークフローを 1 つ選んでください。** いちばんコストがかかっているもの、あなたが密かに気が重いと思っているもの、チームが楽しみにしていないもの、どれでもかまいません。そして問うのです。「これはまだ目的を果たしているのか？」もしまだ果たしているなら、「自動化できるか？」と。

私はかつて、ある高くつく週次レビューを持つチームにいました。たくさんの人が会議室に集まるものでした。気づいたのは、自分の番でステータスを報告するとき以外、みんなノートパソコンに向き合っているということでした。順番が来ると顔を上げ、ステータスを言い、またノートパソコンに戻る。私はシンプルな問いをひとつ投げました。「なぜこのミーティングをまたやっているんでしょう？ 私たちの時間の使い方として高くついているように見えるんですが」。その問いひとつで、全員が「これは要らないな」と気づいたのです。だから、私たちはそのミーティングをキャンセルしました。

ですので、ご自身にも問うてみてください。あなたのエンジニアリングワークフローのうち、自動化を検討する、あるいは思い切ってやめてしまうことを検討してもよさそうな 1 つはなんでしょうか？
