# フロンティアを守る: JetBrains が Claude Fable 5 を評価し導入する方法

JetBrains は、IntelliJ IDEA や PyCharm から Kotlin プログラミング言語まで、世界中の開発者が使うツールを構築しており、1,250 万人以上のアクティブユーザーと Fortune Global 100 のうち 88 社にサービスを提供しています。JetBrains の CTO である Vladislav Tankov 氏が Anthropic と対談し、同氏のチームが新しいモデルをどう評価するか、Claude Fable 5 をいつ使うかをどう判断するか、そしてフロンティアモデルを扱う際のデータ保持と安全対策についてどう考えているかを語りました。

**2026 年、JetBrains にとってフロンティア AI はどう変わりましたか?**

私は JetBrains に 10 年在籍しており、私たちは LLM プロバイダーの最初期の顧客の一社でした。この 1 年で、顧客の中にも社内にも AI 懐疑派がいる状態から、AI がこれからも定着し続けるものだと見なす状態へと移り変わりました。これはテクノロジー業界にとって大きく根本的な変化です。社内の懐疑派は文字通り全員、考えを変えました。

**新しいモデルをどのように評価し、いつ使うかをどう判断していますか?**

私たちはコーディングの会社ですので、大規模な評価パイプラインを持っています。プライベートリポジトリ(モノレポも含む)を使った大規模な eval セットです。モデルが実際の作業でもベンチマークスコアどおりの性能を発揮するかどうかを注意深く見ています。一部のモデルは公開ベンチマークで高いスコアを出すように調整されていますが、実際のタスクではうまくいきません。プライベートリポジトリを使えば、それをずっと簡単に確認できます。また、最高品質、タスクあたりの最低コスト、最速のモデルという観点でそれぞれリーダーボードを維持しています。Claude Fable 5 はトークンあたりのコストは高いのですが、特により複雑で長時間にわたる作業では、タスクあたりのコストが低くなる場合があります。

**Claude Fable 5 は、これまでのモデルと比べて eval でどのようなスコアでしたか?**

Claude Fable 5 は、これまでのモデルよりも高精度かつ高効率です。私たちのスイートで最高の Python 合格率を記録し、Opus 4.8 の 28.2% に対して 44.3%、実に 16 ポイントの向上でした。Opus 4.8 と直接比較すると、Claude Fable 5 は Opus 4.8 が解けなかった Python タスクを 18 件解決した一方、逆に負けたのはわずか 2 件でした。その回答もより信頼できるものです。コードが実行された場合、いずれの Opus モデルよりもはるかに高い割合で私たちのテストに合格しました。これは重要な点です。なぜなら、実行はできても誤った答えを出すコードこそ、発見するのに最もコストのかかる種類の失敗だからです。

効率性についても同様に興味深い結果が出ています。Claude Fable 5 は Opus 4.8 よりも約 22% 少ないステップ数で解答にたどり着けるため、試行錯誤を減らして動くコードに行き着けます。また、労力を適切な場所に注いでもいます。Java のタスクでは、Opus 4.8 は私たちの環境ではほとんど役に立たない外部リソースを繰り返し取り込もうとしましたが、Claude Fable 5 はそれを完全に省略し、目の前のコードだけで作業を進めました。全体としてより優れたエンジニアリングの習慣が見られます。

**他のモデルではなく Claude Fable 5 を使うのはどのようなときですか?**

Opus は働き者と見なされています。作業をやり遂げてくれることを非常に確信できるモデルです。本当に優れた推論が必要なとき、ほとんどパートナーが必要なとき、そして自分自身どうすればよいか分からないときには Claude Fable 5 に頼ります。例えば、私たちのテックリードの一人が、これまで何年もかけて何度か挑戦してきたリッチテキストエディタコンポーネントの実装を決断したのですが、Claude Fable 5 はほぼ一発でそれを実現しました。

もう一つよく使われる Claude Fable 5 のユースケースは、長時間にわたるエージェント型コーディングの実験です。私たちは、Claude Fable 5 を動かすエージェントにテキストと画像の形で仕様書を与え、洗練された IDE 的アプリケーションを実装させています。ここで興味深いのは、この仕様書自体もエージェントが既存のアプリをもとに生成できるという点です。この 2 つの要素を組み合わせることで、あるランタイム、フレームワーク、言語から別のものへと、ほぼブラックボックスに近い形でアプリを書き換えることができます。

**今日のフロンティアモデルにおける安全性とデータ保持について、どのように考えていますか?**

私たちは、自分たちで最も安全なモデルを作ろうとしている会社ではありません。Anthropic 側で行われているレッドチーミングやその他の取り組みが、モデルの安全性を信頼するのに十分だと考えています。その上で、私たちは安全性を保証できる形で、体系的なデプロイのアプローチを取っています。つまり、モデル自体を調整するのではなく、モデルとハーネスを取り囲むインフラと安全策を構築するということです。

セキュリティも、私たちにとって Claude Fable 5 の最大の用途の一つです。私たちは自社製品に対してホワイトボックステストを実施し、脆弱性を見つけています。そして私たちのセキュリティチームは、モデルを使っているのは私たちだけではなく、社外の人々も Claude Fable 5 やそれに類するモデルを使って、私たちのすべての製品にわたる脆弱性を探ろうとしている、という事実に備えています。私たちは規制業界の大企業にサービスを提供しているため、こうした事態への備えが重要です。Claude Fable 5 は私たちの業務を妨げるのではなく、後押ししてくれます。

つまり、これは微妙なバランスの上に成り立っています。あなた側の分類器の判定が緩ければ緩いほど、私たちの製品の中に、これまで誰も知らなかったものも含めて、より多くの脆弱性を誰かに見つけられてしまうことになります。

そして隠すつもりはありません。私たちは本音では、ゼロ・データ・リテンションを望んでいます。しかし、何が尋ねられ、分類器がどこで誤動作した可能性があるかを理解する方法は、それ以外にないと思います。レビューが、フラグの立った最も深刻なケースの調査のみに限定されている限り、私はそれで構わないと考えています。フロンティアの知能へのアクセスと引き換えに、チームが最高の仕事をできるようになるのですから、これは公正なトレードオフだと思います。

**JetBrains の今後の AI ロードマップは?**

LLM プロバイダーが構築する基盤モデルは、これからも能力を高め続けると私たちは見込んでいます。今重要なのは、ソフトウェア開発のためのいわば「コックピット」です。エージェントと人が協働し、人が開発プロセスを管理できる空間です。

JetBrains にとって、これは大きな変革です。私たちは、そのコックピットを支えるエージェント型ソフトウェア開発ライフサイクル全体にわたって、次世代の製品を構築する機会があると考えています。開発者はエージェントとともに、より多くのより良いコードを出荷できるようになり、非技術職の役割はソフトウェア制作においてより大きな役割を担うようになり、そして組織は投資対効果に関して必要なガバナンスと明確さを手にすることになるでしょう。
