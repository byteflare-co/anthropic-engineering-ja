# すべてのタスクにハーネスを: Claude Code の動的ワークフロー

先週、Claude Code で [dynamic workflows](https://code.claude.com/docs/en/workflows)（動的ワークフロー）をリリースしました。Claude はその場で、目の前のタスクに合わせて作り込んだ自前の [harness](https://code.claude.com/docs/en/glossary#agentic-harness)（ハーネス）を書けるようになったのです。

Claude Code のデフォルトのハーネスはコーディング向けに作られていますが、結局のところ多くのタスクはコーディングタスクに似ているので、ほかの種類の仕事にも幅広く役立ちます。一方で、ピーク性能を引き出すために Claude Code の上に独自のハーネスを組み上げてきた領域もあります。たとえば [Research](https://support.claude.com/en/articles/11088861-using-research-on-claude)、[security analysis](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)、[agent teams](https://code.claude.com/docs/en/agent-teams)、[Code Review](https://code.claude.com/docs/en/code-review) などです。

ワークフローを使うと、Claude Code の上に動的にハーネスを組み立てられるようになり、Claude がこれらの問題をよりネイティブに解けるようになります。作ったワークフローは他の人と共有・再利用することもできます。

この記事では、ワークフローを最大限に活用してもらえるよう、私自身が最初に得た体験と学びを紹介します。なお、ベストプラクティスはまだ発展途上です。動的ワークフローはトークン消費が多くなりがちで、複雑で価値の高いタスクに向いていることを覚えておいてください。

## プロンプトの例

技術的な詳細に入る前に、ワークフローでどんなことができるかをイメージしてもらうために、いくつかのプロンプト例から始めたいと思います。

「このテストはだいたい 50 回に 1 回くらい落ちる。これを再現するためのワークフローを組んで。レース条件について競合する仮説をいくつか立てて、証拠に耐えるものが 1 つ残るまで止めないで。」

「ワークフローを使って、私の直近 50 セッションを掘り、私が繰り返し直しているコレクションを抽出して。繰り返し出てくるものは `CLAUDE.md` のルールにして。」

「ワークフローを使って、過去 6 ヶ月の Slack の #incidents を掘り、誰もチケットを切っていない繰り返しの根本原因を見つけて。」

「私のビジネスプランを、投資家、顧客、競合のそれぞれの視点から別々のエージェントに引きちぎってもらうワークフローを走らせて。」

「ここに 80 通の履歴書フォルダがある。ワークフローを使ってバックエンド職向けにランク付けし、上位 10 通をダブルチェックして。AskUserQuestion ツールを使って私にインタビューしながらルーブリックを作って。」

「この CLI ツールに名前が欲しい。ワークフローを使ってたくさん候補をブレインストームし、トーナメントで上位 3 つを選んで。」

「私たちの User モデルをすべての場所で Account にリネームするワークフローを使って。」

「私のブログ記事のドラフトを通して、すべての技術的な主張をコードベースに対してワークフローで検証して。間違った内容のまま出したくないんだ。」

## 動的ワークフローのしくみ

動的ワークフローは、[subagents](https://code.claude.com/docs/en/sub-agents) をスポーンして協調させるためのいくつかの特別な関数を備えた JavaScript ファイルを実行します。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f1684f559cc83ff4b465b_image1.png)

動的ワークフローには、データ処理を助けるために、JSON、Math、Array といった標準的な JavaScript の関数も含まれています。

特に押さえておきたいのは、動的ワークフローではエージェントが使うモデルや、サブエージェントを独自の worktree で走らせるかを決められるという点です。これにより、Claude は必要なインテリジェンスのレベルと隔離のしかたを選べます。

ワークフローが、ユーザー操作やターミナル終了などで中断されても、セッションを再開するとそこから続きを実行できます。

## なぜ動的ワークフローなのか

デフォルトの Claude Code ハーネスにタスクを頼むと、計画と実行を同じコンテキストウィンドウの中でこなす必要があります。多くのコーディングタスクではこれは非常に効果的ですが、長時間にわたるもの、大規模に並列なもの、高度に構造化されたもの、あるいは敵対的なタスクでは破綻しがちです。

これは、Claude が単一のコンテキストウィンドウの中で複雑なタスクに長時間取り組むほど、いくつか特有の失敗モードに陥りやすくなるからです。

- **Agentic laziness（エージェントの怠惰）** は、特に複雑で多パートのタスクを終え切る前に Claude が止まってしまい、部分的な進捗で「完了」と宣言してしまう現象を指します。たとえばセキュリティレビューの 50 項目のうち 35 項目を片付けたところで終わらせてしまう、といったケースです。
- **Self-preferential bias（自己優先バイアス）** は、Claude が自分自身の結果や発見を、特にそれをルーブリックに照らして検証・判定するよう求められたときに、好んでしまう傾向を指します。
- **Goal drift（目的のドリフト）** は、多くのターンを経るにつれて、特に圧縮（compaction）の後に、元々の目的に対する忠実度が徐々に失われていくことを指します。要約のステップは情報損失をともない、エッジケースの要件や「X はしないで」という制約のようなディテールが失われやすいのです。

ワークフローを作ると、それぞれが独自のコンテキストウィンドウと、フォーカスされ隔離されたゴールを持つ別々の Claude サブエージェントを束ねることができ、これらの失敗モードに対抗できます。

## 動的ワークフロー vs 静的ワークフロー

これまでにも、Claude Agent SDK や `claude -p` を使って、複数の Claude Code インスタンスを連携させる静的なワークフローを作ってきた人もいるかもしれません。

しかし、静的なワークフローはあらゆるエッジケースに対応する必要があるため、どうしても汎用的なものになりがちです。[Claude Opus 4.8](https://www.anthropic.com/news/claude-opus-4-8) と動的ワークフローによって、Claude はあなたのユースケースに合わせて作り込んだ独自のハーネスを書けるくらいに賢くなりました。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f3a0e17e2844bed86f22a_image9.png)

## 動的ワークフローを使うときに役立つパターン

動的ワークフローは、Claude にワークフローを作って、とお願いするだけで使い始められます。あるいは、トリガーワード「`ultracode`」を使うことで、Claude Code がワークフローを作るように仕向けることもできます。

ただし、動的ワークフローがどう動くかのメンタルモデルを作っておくと、いつ使うべきか、そしてプロンプトで Claude をどう促すかが分かりやすくなります。

Claude がワークフローを組み立てるときによく使う、そして組み合わせるいくつかの一般的なパターンを紹介します。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f16d86247e586b929a407_image10.png)

### Classify-and-act（分類して動く）

分類エージェントを使ってタスクの種類を判断し、その結果に応じて別のエージェントや振る舞いにルーティングします。あるいは、最後に分類エージェントを使って出力を決める使い方もあります。

### Fan-out-and-synthesize（ファンアウトして統合する）

タスクを多くの小さなステップに分割し、それぞれにエージェントを走らせ、結果を統合します。これは小さなステップが大量にある場合や、各ステップがクリーンなコンテキストウィンドウを持つことで互いに干渉・交差汚染しないようにしたい場合に特に有用です。統合のステップはバリアになっており、ファンアウトしたエージェントすべてを待ってから、それらの構造化出力を 1 つの結果にマージします。

### Adversarial verification（敵対的検証）

スポーンしたエージェントごとに、その出力をルーブリックや基準に対して敵対的に検証する別のエージェントをスポーンします。

### Generate-and-filter（生成してフィルタする）

あるトピックについてアイデアを多数生成し、ルーブリックや検証でフィルタし、重複を取り除き、最も質が高く検証済みのアイデアだけを返します。

### Tournament（トーナメント）

作業を分割するのではなく、エージェント同士を競わせます。それぞれ異なるアプローチで同じタスクに挑む N 体のエージェントをスポーンし、結果はプロンプトまたはモデルが、判定エージェントを使ってペアワイズで判定していき、勝者が決まるまで続けます。

### Loop until done（終わるまでループ）

作業量が事前に分からないタスクでは、固定回数のパスではなく、停止条件（新しい発見がない、ログにこれ以上のエラーがない、など）が満たされるまでエージェントをスポーンし続けます。

## ユースケース

Claude Code にいつどのように動的ワークフローを作らせるか、創造的に考えてみてください。私自身の経験では、ワークフローは技術以外の作業にとってさらに有用なことすらあります。

### マイグレーションとリファクタ

[Bun](https://bun.com/) はワークフローを使って Zig から Rust に書き直されました。詳しいやり方は [Jarred の X スレッド](https://x.com/jarredsumner/status/2060050578026189172) で読めます。

ポイントは、タスクを処理すべきステップ群（呼び出し箇所、落ちているテスト、モジュールなど）に分解することです。修正ごとに worktree でサブエージェントをスピンオフして修正させ、別のエージェントに敵対的にレビューさせ、マージします。マシンのリソースを使い切らずに最大限並列化できるよう、エージェントにはリソース集約的なコマンドを使わないように指示することも検討してみてください。

### Deep research（ディープリサーチ）

私たちは Claude Code 内に動的ワークフローを使った deep research スキル（`/deep-research`）を公開しました。具体的には、ウェブ検索をファンアウトし、ソースを取得し、その主張を敵対的に検証し、引用つきのレポートを統合します。

ただし、こうした調査はウェブ検索だけのものではありません。たとえば、Slack のコンテキストからステータスレポートを作るよう Claude にお願いしたり、コードベースを深掘りしてある機能の仕組みをリサーチしてもらうこともできます。

### Deep verification（深い検証）

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f1721824a27cf13da87f4_image2.png)

逆に、参照している事実主張を一つひとつチェックして裏取りしたいレポートがあるなら、まず 1 体のエージェントにすべての事実主張を特定させ、それぞれについて詳しくチェックするサブエージェントをスピンオフする、というワークフローを作るとよいでしょう。さらに、ソース担当のサブエージェントが質の高いソースを使っているかを確認する検証エージェントを置くこともできます。

### Sorting（ソート）

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f173ce727a972001584cc_image3.png)

Claude Code がうまく評価できそうな質的な尺度で並べたいアイテムのリストがあるとします。たとえば、バグの深刻度でソートしたいサポートチケットなどです。しかし、1000 行以上を 1 つのプロンプトでソートしようとすると、品質が落ちますし、そもそもコンテキストに収まりません。そこで、トーナメント、ペアワイズ比較エージェントのパイプライン（絶対スコアより比較判断のほうが信頼できます）、あるいは並列でバケットランク付けしてからマージする、といった方法を使います。各比較はそれ自体が独立したエージェントなので、決定的なループがブラケットを保持し、コンテキストにはランニングオーダーだけが残ります。

### メモリとルール遵守

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f17517076bb59050d90bb_image8.png)

`CLAUDE.md` に入れても Claude が見落としたり苦戦したりするルール群があるなら、チェックすべきルールのリストを持つワークフローを作り、ルールごとに検証エージェントを 1 体ずつ用意してください。そのルール自体が妥当かを確認する懐疑派ペルソナのサブエージェントを別に用意しておくと、偽陽性が増えすぎるのを防げます。

逆方向にも有効です。最近のセッションやコードレビューコメントから自分が繰り返し行っている修正を掘り出し、並列エージェントでクラスタリングし、それぞれの候補を敵対的に検証し（このルールがあれば本当のミスを防げただろうか？）、生き残ったものを `CLAUDE.md` に蒸留して戻すのです。

### Root-cause investigation（根本原因の調査）

デバッグは、独立した複数の仮説を立てて検証するのが一番うまくいきますが、1 つのコンテキストウィンドウしか使っていないと、Claude は自己優先バイアスに陥りがちです。

ワークフローは、分離した証拠（たとえばログ、ファイル、データそれぞれ別のエージェント）から仮説を生成するエージェントをスピンアップすることで、これを構造的に防げます。それぞれの仮説は、検証側と反論側のエージェントのパネルに直面することになります。

これはコードだけの話ではありません。ワークフローは営業（なぜ 3 月に売上が落ちたのか？）、データエンジニアリング（なぜこのパイプラインが落ちたのか？）、その他のポストモーテム的な作業にも使えます。

### Triaging at scale（大規模なトリアージ）

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f1778dc00d34cca70819d_image6.png)

どのチームにも、人間だけでは捌き切れないサポートキュー、バグレポート、その他のバックログがあるはずです。

トリアージワークフローは、各アイテムを分類し、すでに追跡されているものとの重複を排除し、アクションを取ります。アクションは、修正に挑むか、人間のユーザーにエスカレーションするか、といった内容です。

トリアージワークフローで役に立つパターンが quarantine（隔離）です。これは、信頼できない公開コンテンツを読むエージェントが高権限のアクションを取らないようにし、代わりに情報をもとに行動する側のエージェントがそれを担う、というものです。

トリアージワークフローを /loop と組み合わせれば、Claude にこれを継続的にやらせることができます。

### 探索とテイスト

ワークフローは、デザインや命名のようにテイストに依存し、ルーブリックがあると助かる、いろいろなアプローチを試したいときにも役立ちます。

Claude に複数の解を探させ、レビューエージェントには「良い解とはどのようなものか」のルーブリックを渡してみてください。レビューエージェントが基準を満たしたと感じた時点でタスク完了です。ルーブリックに基づいてトーナメントで解を並べたり選んだりすることもできます。

### Evals（評価）

特定タスクの軽量な評価を、worktree で別エージェントをスピンオフし、それぞれの出力をルーブリックに対して比較・採点する比較エージェントを別にスピンオフすることで、走らせることができます。たとえば、自分が作ったスキルを特定の基準に対して評価し、リファインしていく、といった使い方です。

### モデル・インテリジェンスのルーティング

自分のタスクに合わせてチューニングした分類エージェントを作り、どのモデルを使うかを決めさせます。タスクが多くのツールコールを伴い、実行前にリサーチを行うことでそのジョブにベストなモデルを特定できるような場合に、これは役立ちます。

たとえば、「auth モジュールがどう動くかを説明する」というタスクのベストなモデルは、auth モジュールにファイルがいくつあるか、コードベースの形がどうなっているかに依存します。分類エージェントがこのリサーチを行い、想定される複雑さに応じて Sonnet や Opus にルーティングする、ということができます。

## 動的ワークフローを使うべきでないとき

ワークフローは新しい仕組みです。大きな成果を生むユースケースは数多くありますが、すべてのタスクに必要なわけではなく、トークンを大幅に多く使ってしまうこともあります。

ワークフローは、これまでに試したことのない方向に Claude Code を押し広げるために、創造的に使うのがベストです。通常のコーディングタスクでは、「これは本当に追加の計算が必要なのか？」と自問してみてください。たとえば、ほとんどの伝統的なコーディングタスクには、5 人のレビューアのパネルは要りません。

## 動的ワークフローを組み立てるコツ

### プロンプティング

動的ワークフローでは、上で説明したような具体的なテクニックを使った、詳細なプロンプティングが最良の結果を生みます。

ワークフローは大きなタスクだけのものではありません。モデルに「クイックなワークフロー」を使うよう指示することもできます。たとえば、ある前提に対するクイックな敵対的レビューを作ることもできます。

### `/goal` と `/loop` との組み合わせ

たとえばトリアージ、リサーチ、検証のように繰り返せるワークフローを使うときは、`/loop` と組み合わせて一定間隔で走らせ、`/goal` で完了の確固たる要件を設定するとよいでしょう。

### トークン使用バジェット

動的ワークフローには、タスクが使うトークン数を制限する明示的なトークン使用バジェットを設定できます。「10k トークン使って」のようにプロンプトすれば、上限を設定できます。

### 動的ワークフローの保存と共有

ワークフローはワークフローメニューで「s」キーを押すことで保存できます。これを `~/.claude/workflows` にチェックインしたり、skill 経由で配布したりできます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f17b1ca20533e666c867c_image4.png)

skill 経由で共有する場合は、JavaScript のワークフローファイルを skill とフォルダに置き、[SKILL.MD](http://skill.md) から参照します。柔軟性を高めるには、Claude に、skill 内のワークフローを「そのまま実行するスクリプト」ではなく「テンプレート」として捉えるようプロンプトするとよいでしょう。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a1f17cb835cf4f9fd5da921_image7.png)

## 発見のための新たな出発点

ワークフローは、Claude Code を拡張する助けになる新しい方法です。これを出発点と捉え、自分のタスクをこなすのに Claude を使う新しいやり方を探ってみてください。最もうまく使う方法については、まだまだ発見の余地があります。あなたの発見をぜひ教えてください。
