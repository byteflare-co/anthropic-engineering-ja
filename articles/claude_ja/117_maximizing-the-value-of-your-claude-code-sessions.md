# Claude Code セッションの価値を最大化する
- 執筆者

  Lydia Hallie

## TL;DR

- **タスクの合間に `/clear` を実行する。** これにより、前のタスクの無関係なコンテキストがモデルに送り返されるのを防ぎ、トークン使用量を削減できます。
- **開始前にモデルとエフォートレベルを設定する。** 会話の途中でどちらかを変更するとプロンプトキャッシュが壊れ、トークンコストが増加する可能性があります。
- **ファイル名をタイプするのではなく @ メンションする。** ファイルがメッセージに直接添付されるため、Read 呼び出しや、Claude がファイルを探すための検索を省けます。
- **出力が多いコマンドには静音化フラグを付けるか、サブエージェントで実行する。** コマンドの出力はファイルと同じように会話に追加され、セッションが続く限りそこに残り続けます。
- **新しいセッションで一度だけ `/context` を実行する。** 何が読み込まれているか（`CLAUDE.md`、MCP ツール定義など）が表示されるので、不要なものを削減できます。
- **キーボードから離れる前に `/compact` する。** プロンプトキャッシュは 1 時間で失効しますが、会話がまだキャッシュされているうちに要約する方がずっと安価です。

## 価値を最大化する

つい最近まで、コードを書くツールは定額（あるいは無料）でした。エディタは、その日の午後にテストを 1 つ直そうが 50 個直そうが同じ料金だったので、個々のタスクにはそれ自体の値段というものが実質的にありませんでした。

Claude Code のようなエージェント型コーディングツールでは、そうではありません。同じ完了済みタスクでも、使い方次第で異なるコストがかかります。

あるセッションでは、Claude はテストとそれがカバーするファイルを読み、編集を行い、わずか数ターンで完了します。別のセッションでは、まずリポジトリ全体を grep で調べ回り、同じ 2 つのファイルにたどり着くまでに十数個のファイルを読み、それ以降のすべてのターンが今朝からずっと会話に読み込まれてきたそれ以外のすべてを引きずっていくことになります。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1946bc7cd69c4c8919db_be236b0d.png)

同じ修正なのに、費やしたトークン数は異なり、しかもその間ずっと、モデルは不要な 10 個のファイルについても考えなければなりませんでした。

トークンを効率的に使うということは、全体として使う量を減らすことではありません。使うトークンが、実際に頼んだことのために使われるようにするということです。

そこで、まずトークンの価格を決めるものを見て、次に 1 つのセッションが送るトークン数を決めるものを見て、その過程で、それがセッションの進め方にとって何を意味するのかを見ていきましょう。

## **トークンの価格を決めるもの**

課金はトークン単位ですが、実際に支払っているのは推論、つまり GPU（あるいは TPU、そのモデルが動いているものが何であれ）がトークンに対してモデルを実行するのにかかる時間です。

そのトークンにどれだけの時間がかかるかを決める要因は 3 つあります。どのモデルを実行しているか、それが入力トークン（入っていくもの）か出力トークン（出てくるもの）か、そしてキャッシュされていたかどうかです。

### モデル

大きなモデルは入力トークンにも出力トークンにも、より多くの計算を行います。どの作業にどのモデルが見合うかはそれ自体が独立したトピックであり、[*Claude Code でのモデルとエフォートレベルの選び方*](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)で取り上げました。

この記事にとって重要なのは、これから説明することすべてがモデルの価格によって倍率がかかるという点だけです。問題が本当に難しかったり曖昧だったりするときは大きなモデルを使い、作業がルーチンなものであれば小さなモデルを使いましょう。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1946bc7cd69c4c8919de_da980737.png)

*曲線はあくまで説明のためのものであり、実際のベンチマークデータを表すものではありません。*

まず、プリフィル（prefill）の段階で、モデルはリクエストとコンテキスト、つまりシステムプロンプト、`CLAUDE.md`、あなたのメッセージ、そしてそれ以降に会話に追加されたすべて（Claude が読んだファイルや実行したコマンドの出力）を読み込みます。これらが入力トークンです。

次に、デコード（decode）の段階で、出力トークンを書き出します。思考、実行するツール呼び出し、そして表示されるテキストです。これは 1 トークンずつ行われます。200 トークンのレスポンスは、モデルを 200 回連続で実行することに相当します。トークンあたりで見ると、デコードの方が GPU をはるかに長く占有するため、出力は入力のおよそ 5 倍の価格になっています。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1947bc7cd69c4c891a0f_c69dbb11.png)

1 つのセッションにおける出力トークンの多くは思考トークンであり、1 ターンあたりにモデルがどれだけ思考するかを制御しているのがエフォートレベルです。モデルと同様に、`/effort` で選んだレベルも次のセッションのデフォルトとして引き継がれます。

> **ヒント:** 新しいセッションで一度 `/model` と `/effort` を実行して、実際に何を使っているか確認しましょう。どちらも前回選んだ設定を覚えているので、その選択は意図的なものにしたいところです。

> **ヒント:** そのセッションが単純作業になるとあらかじめわかっている場合、`MAX_THINKING_TOKENS=0 claude` でそのセッションだけ思考をオフにできます（Fable 5 を除く）。これは `/effort` low よりさらに一段階下です。

### プロンプトキャッシュ

あるリクエストが、サーバーがちょうど見たばかりのリクエストとまったく同じトークン列で始まっている場合、その共有された冒頭部分の状態は前回と同じ結果になるため、サーバーはそれを前回のまま保持しておき、その後に続く部分だけをプリフィルすればよくなります。これがプロンプトキャッシュです。

キャッシュからの読み込みは入力価格の 0.1 倍で済みます。サーバーが状態を計算し直すのではなく読み込むだけだからです。キャッシュへの書き込みは通常の入力より少し高く、最大 2 倍かかります。サーバーはその後もその状態を保持し続ける必要があるためです。しかし書き込みが発生するのはトークンごとに一度だけであり、0.1 倍での読み込みはそれ以降のすべてのターンで発生します。

Claude Code はすべてのリクエストでプロンプトキャッシュを管理しており、オンにする設定などはありません。ただし壊してしまうことはあり得るので、こうしたコストの急増をどう避けるかを知っておくことが重要です。

たとえば「`utils.test.ts` の失敗しているテストを直して」と入力したとしましょう。Claude Code はこれに対して次のように送信します。

1. Claude Code はシステムプロンプト（ツール定義を含む）、あなたの `CLAUDE.md`、そしてあなたのメッセージから最初のリクエストを組み立て、送信します（入力トークン）。まだ何もキャッシュされていないため、すべてがプリフィルされ、キャッシュに書き込まれます。

2. モデルは見ていないテストを直すことはできないので、少し考えてから `utils.test.ts` に対する Read 呼び出しで応答します（出力トークン）。Claude Code はファイルを読み、会話に追加し、全体を再送します（入力トークン）。今回はリクエスト 1 のすべてがキャッシュから 10 分の 1 の価格で読み出され、フルプライスでプリフィルされるのは新しく追加された部分、つまり Read 呼び出しとファイルだけです。

3. 次にモデルはテスト対象のファイルを要求します（出力）。もう 1 回の Read、もう 1 回の追加、そして全体が再送されます。リクエスト 1 と 2 はキャッシュから、2 つ目のファイルはフルプライス（入力）で送られます。

4. モデルが Edit で応答します（出力)。Claude Code がそれを適用し、結果を追加し、全体を再送します。同じ話です。Edit とその結果が新しく、それより前はすべてキャッシュからの読み込みです。

5. モデルが `npm test` を実行します（出力）。Claude Code がテスト出力を追加し、全体を再送します。テスト出力だけが新しい部分です（入力）。

6. テストが通り、モデルは短い要約で応答します（出力）。ツール呼び出しがないため追加するものがなく、リクエスト 6 は発生しません。ここで終わりです。

これでちょっとした修正 1 つに対して 5 回のリクエストが発生し、そのそれぞれがそれまでの会話全体を含んでいました。1 ターンの内訳は非対称です。数万トークンが入っていくのに対し、出てくるのは数百トークン程度です。しかし、そのターンで新しくフルプライスでプリフィルされるのは新しい部分だけです。

これが 1 ターンあたりの請求のすべてです。履歴に対するキャッシュ読み込み、新しい部分に対するフル入力価格、そしてレスポンスに対する出力価格です。

> これはサブスクリプションでも同様に適用されます。この価格が直接見えるわけではありませんが、あなたの利用上限を減らしているのは同じリクエストです。

キャッシュはリクエストの冒頭からずっと一致していなければならず、リクエストは常に同じ順序で送られます。ツール定義、システムプロンプト、そして会話（先頭に `CLAUDE.md` が付いたもの）の順です。

そのプレフィックスのどこかが変わると、それより後ろのすべてが再びプリフィルされます。会話の末尾に追加されたツール結果は理想的なケースです。その後ろには何もないからです。キャッシュを台無しにするのは、そのプレフィックスの前方に近い部分を変えること、あるいはキャッシュのキーとなっているもの自体を変えることです。

- **`/model`**: モデルごとに専用のキャッシュがあるため、次のターンでは会話全体がフルプライスで再びプリフィルされます（opusplan も含まれます。plan mode に出入りするたびにモデルが切り替わるためです）。
- **`/effort`:** エフォートレベルもキャッシュのキーの一部なので、同じことが起こります。`/model` も `/effort` も、会話の途中で切り替えると確認を求めてくるのはこのためです。
- **Fast mode**: これもキーの一部であり、再プリフィルは fast mode の価格で行われます。オンにするなら、セッションの最初にオンにしましょう（オフに戻すのはキャッシュの観点では無料です）。
- **`/compact`**: 会話がより短いものに置き換わるため、その中身は何一つ一致しなくなります（その前にあるシステムプロンプトは生き残ります）。要約自体を書く処理は、古い会話がまだキャッシュに残っている限り安価なので、長い休憩の前に行う方が、休憩の後に行うよりずっと安くなります。
- **時間:** ターンが発生するたびに時計はリセットされますが、キャッシュはサブスクリプションでは 1 時間、API キーでは 5 分で失効します（`ENABLE_PROMPT_CACHING_1H=1` にすると 1 時間になります）。それより後に戻ってくると、次のターンで会話全体が再びプリフィルされます。古いセッションを再開する場合もほぼ必ず同様です。その頃にはたいていキャッシュは消えていますし、システムプロンプトも起動時にどのみち再構築されます。

だからといって、モデルやエフォートを絶対に切り替えるべきでないというわけではありません。それを切り替えるのに安く済むタイミング（セッションの開始時や `/clear` の直後）と、高くつくタイミング（長い会話の途中）があるということです。

> **ヒント:** 直近の数ターンが望まない方向に進んでしまった場合、`/compact` を実行する代わりに、その直前まで `/rewind` しましょう。Rewind はそれらのターンを末尾から切り落とすだけなので、それより前はすべてキャッシュされたままで、コストは一切かかりません。Compact は会話全体を書き直すため、必ず何らかのコストがかかります。

## **1 つのセッションが送るトークン数を決めるもの**

ここで知っておくべき最も重要な点は、何も一度だけ送られるわけではないということです。会話に一度でも入ったもの（Claude が読んだファイルや実行したコマンドの出力）は、それ以降のすべてのターンで、セッションが続く限り繰り返し送られ続けます。

キャッシュされているのでその再送のそれぞれは安価ですが、安価であってもゼロではありませんし、それは毎ターン、モデルが思考を巡らせなければならないコンテキストの中でも場所を占め続けます。

これこそが、1 つのセッションのコストモデルのすべてです。いくつのトークンがコンテキストに入るか、それらが何ターンそこに留まるか、そしていくつのコンテキストを同時に走らせているか。

### **コンテキストに入るもの**

コンテキストの一部は、何かをタイプする前からすでにそこにあります。ツール定義、システムプロンプト、`CLAUDE.md`、そして起動時に読み込まれるその他もろもろです。

> **ヒント**: 新しいセッションで `/context` を実行し、まだ何もタイプしていない時点で何が入っているかを確認しましょう。`CLAUDE.md` は具体的な指示に絞り、ワークフロー固有の指示はスキルに移しましょう。スキルは使われたときにだけ読み込まれます。そのセッションで不要な MCP サーバーがあれば、`/mcp` でオフにしましょう。

セッション中に追加されるもののほぼすべてはツール結果、つまり Claude が読んだファイルと、実行したコマンドの出力です。

Claude がどれだけ読むかは、ほとんどの場合、Claude が自力でどれだけ調べなければならないかで決まります。「テストが失敗している」とだけ伝えると、まずどのテストなのかを突き止めなければなりません。grep を 1、2 回、関連しそうなファイルをいくつか開いて確認し、それらの結果はすべて、役に立たなくなってからもずっとコンテキストに残り続けます。

「`utils.test.ts` の失敗しているテストを直して」であれば、その探索を省いて 1 回の Read 呼び出しで済みますし、「`@utils.test.ts` の失敗しているテストを直して」であればその Read 呼び出しすら発生しません。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1b213f60488b546224d4_cab63270.png)

> **ヒント:** ファイルについて言及するときは、パスを入力する代わりに @ メンションを使いましょう。Claude Code は何かが送信される前にファイルをメッセージに添付するため、それは最初のリクエストの時点ですでにそこにあり、そのための Read 呼び出しは発生しません。ファイル自体がコンテキスト内で占める場所はどちらの方法でも同じなので、1 つの会話の中では 1 回だけ言及すれば十分です。それはそこに残り続けますし、後のターンで再び @ メンションすると、通常はもう 1 つコピーが添付されることになります。

コンテキストを埋めるもう 1 つの要因は、Claude が実行するコマンドの出力です。テストを実行するたび、ビルドするたび、`git log` を実行するたびに、その出力は Claude が読んだファイルと同じように会話に追加され、同じ数のターンだけそこに残り続けます。

本当に大きな出力についてはむしろ問題ありません。30,000 文字を超えると、Claude Code はその出力をファイルに書き出し、会話には短いプレビューとパスだけを載せます（変更したい場合は `BASH_MAX_OUTPUT_LENGTH`）。

問題はそれ未満のものすべてです。400 件のテストが通ったことを 1 行ずつ出力するテストランナーはこの上限を下回っており、その 400 行は残りのすべてのターンの一部になります。

Claude はフラグや `tail` を使ってこれをうまく処理してくれることも多いですし、それを Claude 任せにしたくない場合は、うるさいコマンドを実行前に書き換え、重要な行だけが返ってくるようにする小さなフックがドキュメントにあります。

> **ヒント**: 1 日中実行しているコマンド 2、3 個は、自分で打つときと同じように静音化フラグ込みで `CLAUDE.md` に書いておきましょう（「単一のテストファイルを `npx vitest run <file> --reporter=dot` で実行する」のように）。ちょっとした追加ですが、それ以降のすべてのセッションで 1 ターンと数百行の出力を節約できます。

### 何ターンそこに残り続けるか

1 つの長いセッションは、同じ作業をいくつかの短いセッションに分けた場合よりコストがかかります。しかも思っている以上にです。40 ターン目は、それより前の 39 ターン分も一緒に読み直しているからです。セッションのコンテキストは短く、関連性の高いものにしておきたいものです。1 つのタスクのコンテキストを次のタスクに持ち越さないようにしましょう。新しいことを始めるときは `/clear` を、同じタスクの前半部分が終わったときは `/compact` を使います。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1cdb7fb1ad2229b0afa5_92ab0ee2.png)

> **ヒント**: 後でそのセッションに戻ってきたいなら、`/clear` する前に `/rename` しましょう。`/compact` するときは何を残すべきかを伝えましょう。いつも同じことを伝えているなら、「Compact instructions」セクションを `CLAUDE.md` に書いておくとよいでしょう。1M モデルを使っていて、autocompact のセーフティネットを以前の位置に戻したい場合は、`/autocompact 200k` で元に戻せます（Claude Code v2.1.221 以降が必要です）。

自分がタイプしていないときに発生するターンにも注意しましょう。`/loop` は、それを設定したセッションの中で 1 つの完全なターンとして発火し、そのたびにその会話全体を一緒に運びます。しかも前回のターンから 1 時間以上経っていれば、その上さらにキャッシュミスにもなります。ループは別のターミナルで新しいセッションを立ち上げて、そこから実行しましょう。

### サブエージェント

何かをコンテキストの外に出しておくもう 1 つの方法は、それを別のコンテキストで行うことです。それがサブエージェントの役割です。サブエージェントは、自分専用のシステムプロンプトとツール、そして `CLAUDE.md` を持った独自のコンテキストウィンドウを得ますが、あなたの会話は持ちません。サブエージェントは自分自身のターンを実行し、メインセッションに戻ってくるのはその答えだけです。それ以外はすべて、完了した時点で破棄されます。

自分の会話を持たないことの欠点は、サブエージェントがときにメインセッションがすでに持っていたものを読み直さなければならず、そうしている間の自分のターン分の料金も発生するということです。小さな作業であれば、それは単なるオーバーヘッドです。

これが報われるのは、ログを読み進めるような、保持しておく必要のない大量の出力を生み出す作業のときです。そういった作業には Claude が自ら判断してサブエージェントを使うことも多いですし、Claude がそうしないときには「ログをサブエージェントで確認して」のように直接依頼することもできます。メインセッションに戻ってくるのは、サブエージェントが報告することを選んだものだけだという点は覚えておいてください。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7f1cdb7fb1ad2229b0afaa_a653b369.png)

> **ヒント**: 何度も繰り返し任せているうるさい作業があるなら、それ専用に `model: haiku`（または `sonnet`）を指定したサブエージェント定義を作りましょう。そうしなければ、メインセッションが使っているものと同じモデルで実行されます。
