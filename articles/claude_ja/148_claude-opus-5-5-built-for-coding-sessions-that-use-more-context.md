# コーディングセッションは長くなり、より多くのコンテキストを使うようになっています。Claude Opus 5.5 はそれを踏まえて作られています。
- 著者

  Michael Segner

トークン課金の典型的なワークロードにおいて、Claude Opus 5.5 は Opus 5 と比べて[実行コストが約40%低い](https://www.anthropic.com/claude-opus-5-5)と見積もっています。開発者にとっては、その節約が具体的に*どのように*積み上がるのかが重要です。

トークン単位で支払っている場合、コストの差が最も大きく出るのは、より長時間実行され、より高いコンテキストを使うセッションです。そしてこれはまさに、この半年で増えてきたタイプの Claude Code セッションです。

この記事では、今日(そしておそらく明日も)開発者がコーディングしている方法において、何が Opus 5.5 を費用対効果の高いものにしているのか、その仕組みを掘り下げます。

## **Claude Code の利用傾向**

私たちは、2026年3月から9月にかけて開発者が Claude Code をどう使ってきたかについての集計データを収集しました。モデルの能力が向上するにつれ、開発者はますます高度な方法でエージェントを展開するようになっています。1セッションあたりのプロンプト数は横ばいでしたが、いくつか興味深い振る舞いが見つかりました。

- Claude は1プロンプトあたり3.3倍長く働くようになり、プロンプトあたりのモデル呼び出しは40%以上増えています。中断は68%減少しました。
- 開発者がツールサーバーを接続していたり、スキルを使っている割合はおよそ2倍になり、プロンプトにテキストを貼り付ける割合は3分の1減っています。
- リクエストあたりのコンテキストは2.6倍に増加しました。入力対出力のトークン比率は189対1から324対1に変化しています。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6ab54d371474ec5e28cb0912_0dfedac7.png)

これらはすべて、開発者がより力強く働き、より多くの情報を持った Claude を、より大きく、よりオープンエンドなタスクに向けようとしていることを示しています。この種のセッションでは、コンテキストエンジニアリングの経済的な影響が積み重なります。

つまり、Claude はより多くのトークンを読むことになります。[提供しているコンテキストがすべて本当に必要かどうか](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)を確認し、[そのコンテキストのできるだけ多くがキャッシュから読み取られるようにする](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions)必要があります。

## **長時間・高コンテキストなセッションで Opus 5.5 が費用対効果に優れる理由**

長時間実行され、コンテキストの多いセッションをより費用対効果の高いものにする変更は3つあります。価格、モデルの振る舞い、そして Claude Code のハーネスです。それぞれ見ていきましょう。

### **キャッシュは安い**

トークン課金の利用について、入力トークンと出力トークンの価格を20%引き下げ、*キャッシュされたトークンを読み取る価格は60%引き下げました*。後者の引き下げが重要なのは、キャッシュ読み取りがエージェント的な作業やコーディング作業のコストの大部分を占めているからです。

そして先ほど述べたように、リクエストあたりのコンテキストはこの半年でおよそ2.6倍に増加しており、節約は正しい方向に向かっています。トークン課金ユーザーにとって同じ価格変更でも、今日の Claude Code のトラフィックの方が、6か月前よりも多くを節約できます。請求額のより多くの部分が、再読み込みされるコンテキストになっているからです。

この記事の公開時点で、Opus 5.5 上のキャッシュされたトークンは、競合モデルより優れた性能を発揮しながら、それらと比べて5分の1のコストで済みます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6ab54d381474ec5e28cb0920_7df87a60.png)

### **Claude Code はキャッシュの使い方がうまくなった**

これは Opus 5.5 に固有というよりも、この半年で私たちが追加してきた多くの Claude Code の機能の成果です。先ほどのコーディングセッションの傾向を踏まえると、キャッシュミス率が上がっていてもおかしくありませんが、実際は逆です。**キャッシュミスする入力は50%以上減少しました。**

例えば、ログインの再取得のような小さな「紙一枚の切り傷」的な操作で意図せずキャッシュを壊してしまうことを難しくしました。会話の途中で指示を追加したり、ツールをオンデマンドで読み込んだりといった、より大きなアクションでも壊れにくくしました。Opus 5.5 や Fable 5.1 のような新しいモデルでは、キャッシュをリセットすることなくセッション中に effort レベルを変更できるようになりました。

より長時間実行されるセッションや委譲されたセッションでも、キャッシュをより有用にしました。API キーおよびクラウドプロバイダーの開発者は(サブスクリプションではすでにできていたように)1時間のキャッシュ寿命を設定できるようになり、フォークされたサブエージェントは親のキャッシュから開始するため、同じコンテキストに対して再度料金を払う必要がなくなりました。

### **同じタスクを、より少ないターンで**

Opus 5.5 は、他のモデルよりも少ないターン数で同じタスクを達成できることがあります。Zeta Labs では、Opus 5 と比べてタスクあたりのターン数とツール呼び出し数が減った一方で、コストはほぼ半分になり、最も難しいタスクの完遂数は2倍になりました。

これはすべてのタスクに当てはまるわけではありません。[Opus 5.5 で1つのタスクにかかるコスト](https://claude.com/blog/what-a-task-costs-on-opus-5-5)の中で、Addy はこう書いています。「スコープがきちんと定まったタスクでは、両モデルともほぼ同じターン数で完了するため、得られるのは価格の値下げ分だけです。差が最も大きくなるのはオープンエンドなタスクで、モデルが間違った方向に多くのターンを費やしうる場面です。すべてのコードベースに当てはまる単一の数字はないので、実際に測定してください」

言い換えれば、単純で短く機械的なタスクは同じターン数で終わりますが、長く難しいタスクほど、Opus 5.5 が誤ったアプローチにトークンを浪費せずに済む可能性が高くなります。減らせたターンは、キャッシュされたトークンよりもさらにコスト効率が良いのです。

もう一つ触れておく価値があるのは、Claude が監督なしで、あるいは中断されることなくより長く働くようになるにつれて重要になる点です。Opus 5.5 は Opus 5 より30%以上速く出力を生成します。これはキャッシュヒット率を上げたりトークン使用量を減らしたりするものではありませんが、長時間の実行での待ち時間を減らしてくれます。

## **キャッシュ読み取りを守る**

エージェント的なコーディングが成熟するにつれ、各組織は「何としてでもスケールする」よう開発者に求める段階から、「効率よくスケールする」よう求める段階へと移ってきました。Claude Code で /usage を実行して、自分の利用量のうちどれだけがキャッシュ読み取りかを確認してください。そして、その数字を守りましょう。

- セッションの途中で切り替えるのではなく、開始時点でモデルを選ぶ、
- 離席した後ではなく、離席する前に圧縮(compact)する、
- API キーやクラウドプロバイダーを使っている場合は、長いセッション向けに[1時間のキャッシュ寿命](https://code.claude.com/docs/en/prompt-caching#choose-the-ttl-yourself)を設定する。

こうした習慣が積み重なるオープンエンドでコンテキストの多い作業に Opus 5.5 を向け、実際の数値については[Opus 5.5 で1つのタスクにかかるコスト](https://claude.com/blog/what-a-task-costs-on-opus-5-5)をご覧ください。
