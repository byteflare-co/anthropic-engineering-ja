## フロンティアで働く AI ネイティブたち

仕事の未来を少し覗いてみたいなら、スタートアップに「今どう働いているか」を聞いてみるのが一番です。そこで実際に聞いてみました。

私たちは急成長中のスタートアップ十数社に、エージェント型のコーディングツールをどのように使って製品を作り、会社を拡大しているかを聞きました。これらのスタートアップは、誰が「作る」側に立てるのか、何を切り捨てるべきか、そして作り方と作るものの間にどうやってフライホイールを生み出すかという、これまでのルールを変えつつあります。

そして彼らは、自社の 10 倍の規模の組織のような速さで出荷しています。

ClickHouse**30%**多くの機能を出荷

Omni**2〜3 倍**のエンジニアリング生産性

Clay**バグトリアージの 100%**を自動化

Artemis Security**週 6,000 件以上**の PR

このガイドでは、これらの組織ならではの導入事例を掘り下げ、彼らが高速に出荷し続け、競争優位を維持するために従っているルールを学びます。

そしてその過程で、「もしある組織が製品開発ライフサイクルをゼロから Claude Code を前提に構築したら、どんな姿になるか」という問いへの答えも見えてきます。

**01**

## 誰もが出荷する

エージェント型コーディングは参入障壁を下げるので、問題を理解している人が最初の修正版を出荷できます。

エージェント型コーディングは、非技術系の従業員が製品を作るための参入障壁を下げます。Claude Code を使えば、コーディング言語や IDE の使い方に精通していなくても機能する機能を作れます。

![Mads Lunau Liechti](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb96afe3f55f3c73f16_1716034051392.jpeg)
> 「エンジニアがはるかに多くを出荷するようになっただけでなく、（私のような）非技術系の人間も、突然 UI の変更やその他の製品改善を出荷するようになりました。」**[Mads Lunau Liechti](https://www.linkedin.com/in/mads-lunau-liechti/)** · 共同創業者、[Parahelp](https://www.parahelp.com/)

スタートアップの創業者にとって、これには明らかな利点があります。まず、大企業の競合ほどの人員を抱えていないため、「総動員」体制になります。しかし創業者が求めているのは単なる生の作業量だけではありません。こうした非技術系のチームメンバーは、ドメイン知識ももたらしてくれるのです。

![Ryan Daniels](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb9a794cf3b05d104b2_1759928398629.jpeg)
> 「Claude Code は Crosby で弁護士であることの意味を変えました。弁護士こそが最も優れた製品への洞察を持っています。なぜなら彼らこそがユーザーだからです。彼らが腕を振るうのを見るのは実に痛快でした。」**[Ryan Daniels](https://www.linkedin.com/in/crosbyryan/)** · 共同創業者 兼 CEO、[Crosby](https://crosby.ai/)

[Heidi](#) の共同創業者 兼 CEO である Dr. Thomas Kelly からも同様の話を聞きました。

![Dr. Thomas Kelly](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a860761e110c43cd72b4b36_thomas-kelly.jpg)
> 「私たちにとって、Claude Code は伝言ゲーム問題を解決してくれました。従来、新しいアイデアがチームの中を伝わっていく方法は、アイデアを持つ人が PM に伝え、PM がデザイナーに伝え、デザイナーがエンジニアに伝える……というものでした。そしてこのチェーンの中で、アイデアの本質は必然的に失われていきます。何かが出荷される頃には、当初思い描いていたものとはまったく似ても似つかないものになっていることが多く、しかも何週間もかかっていました。Claude Code はこのチェーンを一気に短縮します。問題を実際に理解している人が PR を出荷でき、専門性が必要な部分だけデザイナーやエンジニアを巻き込めるのです。」**[Dr. Thomas Kelly](https://www.linkedin.com/in/tomkeykong/)** · 共同創業者 兼 CEO、[Heidi](https://www.heidihealth.com/)

「誰もが出荷する」と言えば LinkedIn の投稿としては映えますが、実際にはどう機能しているのでしょうか。マーケティングチームがプルリクエストを承認しているのでしょうか。法務チームがフレーキーテストの二分探索の細部に取り組んでいるのでしょうか。

私たちが得た答えは、依然として分業は存在するというものでした。マーケターは引き続きマーケティングに集中し、開発者は引き続き開発に集中します。ただし、アイデアを動くプロトタイプへと変える最初の重要な一歩、つまり 0 から 1 を生み出す部分は、誰にでも開かれています。

また最も効果的なスタートアップは、こうした貢献を偶然や個人の意欲任せにするのではなく、仕組みとして組み込むメカニズムを作り出していることも分かりました。

### つながりを作る

従業員に AI を使うことを期待するのと、実際に Claude Code や必要なツールへのアクセスを与えるのとは別のことです。

![Kareem Amin](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85f1033623355a8a430864_Kareem-clay.webp)
> 「私たちは実際には（非技術系の従業員が貢献すること）から逃げているのではなく、むしろそこに向かって進んでいます。私たちの考え方では、あらゆる職種がエンジニアリング職になりつつあります。なぜならその職種のためのソフトウェアを作れるようになるからです……だから私たちは、いじり回すのが好きで、作ることに関心がある人を採用します」**[Kareem Amin](https://www.linkedin.com/in/kareemamin/)** · 共同創業者 兼 CEO、[Clay](https://www.clay.com/)

Crosby では、チームは弁護士を Claude Code のもとへ連れて行くのではなく、弁護士が日々慣れ親しんで使っているツールや業務システムに Claude Code を接続することで、Claude Code を弁護士のもとへ連れて行きました。

**ヒント:** Claude は見えないものを理解できません。Claude の価値を広げる最も効果的な方法の一つは、信頼できる情報源とチームが日々使っているツールに接続することです。

[MCP](https://code.claude.com/docs/en/mcp) は、Claude Code にツール、データベース、API へのアクセスを与える AI とツールの統合のためのオープンソース標準です。チームがツールから Claude へ情報をコピー&ペーストしていることに気づいたら、こうした接続の追加を検討してください。

成熟したコマンドラインツールがすでに存在する場合（`gh`、`kubectl`、`bq`、`psql` など）、CLI 経由で接続する方がトークン効率が良く、エンジニアと同じ一次情報に対して Claude を働かせられます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a85f6614d1e747fe4f0b524_fca89ab9.png)

Claude Code デスクトップ版の MCP コネクタディレクトリ。

### スタンドアップでの発表

あるところまで来ると、アイデアには優先順位付けの機会が与えられ、組織のリソースをその市場投入に振り向けられるようになる必要があります。プロダクトマネージャーにとってその道筋は明確です — それが彼らの仕事なのですから — しかし非技術系の従業員にとってはそれほど明確ではありません。

Clay は四半期ごとのレビューを設け、プロトタイプを検討し、正式なロードマップに組み込めるようにしています。これが、Clay の go-to-market チームのメンバーが、あなたのウェブサイトを訪れてリード獲得フォームに入力し、応答にかかる時間を計測し、体験を評価し、パフォーマンスレポートを生成する自律型エージェントを構築した経緯です。

Omni には、シニアな技術スタッフを含む全員が貢献する、Claude が生成したプロトタイプのための専用 Slack チャンネルがあります。彼らはまた、「誰もが出荷する」の系である「誰もが顧客と話す」も実践しています。

### スキルを共有する

「誰もが出荷する」と「バラバラ」の間の境界線は薄いものです。機能のプロトタイプは、誰が作ったものであれ、一つのまとまりある製品に統合される必要があります。ここで役立つのが、チームの基準や文脈をエンコードした再利用可能な指示ファイルであるスキルです。開発プロセスがますます民主化されていく中でも、開発の一貫性を保つ助けになります。

「チームの誰もが、私たちのデザインシステムを参照として、Claude Code から製品コンポーネント、マーケティング資料、デッキ資料の草案を作れます。製品に触れる AI は、より高い基準をクリアしなければなりませんが、Claude Code はより高い精度でその基準を満たす助けになってくれます」と Heidi の Dr. Thomas Kelly は語りました。

スキルはまた、新しい開発者や非技術系の従業員をすばやくオンボーディングし、稼働状態に持っていくのにも役立ちます。

![Mukund Jha](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb78347c9db82e1a2f7_1769085036393.png)
> 「……私たちには Claude Code スキルの GitHub リポジトリもあり、既知の Emergent の詳細（データベース〔とデータウェアハウスの〕場所、いくつかのスキーマ〔情報〕、会社全体の文脈など）を使って Claude Code セッションをすばやく立ち上げるための共有ナレッジベースとして機能しています……ここで完璧を目指そうとするのではなく、コンテキストファイルが多少古くなっていても、エージェントがすばやく検証して軌道修正できる限りは問題ないという考え方です。」**[Mukund Jha](https://www.linkedin.com/in/mukund-jha-a1596413/)** · 共同創業者 兼 CEO、[Emergent](https://emergent.sh/)

![Jack O'Hara](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb9f09c093edabf6943_1733849104342.jpeg)
> 「私たちのエンジニアは Claude Code を使って、役割ごとに整理された社内向け専門エージェントのマーケットプレイスを立ち上げています。おかげでエンジニアリング、デリバリー、セールスの各チームが、それぞれの実際の働き方に合わせて作られたツールを手にできます。」**[Jack O'Hara](https://www.linkedin.com/in/jack-o-hara-/)** · 創業者 兼 CEO、[Translucent](https://www.translucent.co/)

**ヒント:** スキルは[ディレクトリを使って会社全体で共有できる](https://code.claude.com/docs/en/plugin-marketplaces)ため、一人の従業員のベストプラクティスを即座に別の従業員へ伝えられます。リポジトリの各サブディレクトリには、そのサブディレクトリ固有で常に適用されるコーディング規約のために `CLAUDE.md` ファイルを使ってください。オンデマンドの手順的なワークフローにはスキルを使ってください。詳しくは、[Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) をお読みください。

**02**

## 面倒な作業を自動化する

エージェントがライフサイクルの機械的な 80% を担うことで、エンジニアは本当に判断が必要な事案に時間を使えます。

産業革命の黎明期以来、あらゆる企業がテクノロジーによる効率化を追求してきましたが、これらのスタートアップは導入のスピードと深さで頭一つ抜きん出ていました。

これらの創業者たちは、AI が自分たちのミッションに欠かせない要素だと考えています。多くが、エージェントが機械的な作業の 80% を担い、エンジニアは本当に判断が必要な事案に時間を使うのだと明言しています。

![Shachar Hirshberg](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb924b99c1b701066b9_1783109987447.png)
> 「誰もが AI 製品を作ろうと競い合っています。しかし、自社の運営そのものを作り直している企業ははるかに少ない。後者こそが、より大きなブレークスルーです。Artemis Security は、たまたま AI を使っている会社ではなく、AI ネイティブな会社として運営されています。これが私たちの速度を飛躍的に高め、顧客がマシンスピードで攻撃を止める助けになっています。」**[Shachar Hirshberg](https://www.linkedin.com/in/shachar-hirshberg/)** · 共同創業者 兼 CEO、[Artemis Security](https://artemissecurity.com/)

具体的には、他社に比べて AI が SDLC の各段階により密接に統合されており、繰り返し発生するタスクをエンドツーエンドで担う専用エージェントもより多く見られました。両方の例をいくつか見てみましょう。

### AI ネイティブな SDLC

これらの注目スタートアップの多くは、チームのエージェント型コーディングプロセスへのオンボーディングを加速する手段を導入しています。例えば Emergent では、Mukund が「入社初日に、新入社員は適切な Markdown ファイルを Claude に指し示すだけで、開発環境全体をブートストラップします。オンボーディング中に Claude が何か壊れていたり古くなっていたりするものに遭遇したら、そのファイルを更新します」と語ってくれました。

**ヒント:** [Code Review](https://code.claude.com/docs/en/code-review)（リサーチプレビュー）は、Claude Code 上のマネージド型マルチエージェントサービスです。有効化したリポジトリの PR に対して自動レビューを実行します。指摘事項は手動で修正してプッシュすることも、指摘に `@Claude` とコメントする（GitHub Actions を設定・構成済みの場合）ことでループを閉じることもできます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a85fadd2e4ee0c9bc09260c_f0ed4c96.png)

Code Review は各指摘事項に重要度レベルのタグを付けます。

これらのチームは高速に出荷するため、エンジニアをすばやくオンボーディングする必要があります。

![Tanay Tandon](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efba858ba52aeb268f5b_1765628872241.png)
> 「ここのエンジニアは、エージェントの艦隊をオーケストレーションし、本番データの問題への修正を発見した当日中に出荷し、複数の PR を同時並行で動かしています。あるエンジニアは、約 13 件のチケットからなる取り組みを Claude のサブエージェントを並列で使って進め、各サブエージェントが一つのチケットとその PR を担当しました。」**[Tanay Tandon](https://www.linkedin.com/in/tanaytandon/)** · CEO 兼 創業者、[Commure](https://www.commure.com/)

これらの組織では、Claude Code はコードを生成するだけでなく、レビューも行います。「私たちは、検証済みの技術・コンプライアンスフレームワークに照らして自動コードレビューを実行し、重大な問題にフラグを立て、何かが出荷される前に適切なレビュアーへ提案された変更をルーティングしています」と Heidi の Dr. Kelly は語りました。

これらの組織の一部は、コードレビュー、テスト、CI のためのカスタムエージェントも構築しています。これらのスタートアップは、単にコードをデプロイするだけでなく、[ループを構築すること](https://claude.com/blog/getting-started-with-loops)に相当な注意を払っています。

「私のお気に入りは『Translucent コードレビュアー』です。変更全体にわたって展開し、複数の角度からレビューし、シニアエンジニアの一人がやるのと同じように、しかし誰か一人よりも速く結果を統合してくれます」と Translucent の創業者 Jack は語りました。

Clay は「……ファーストパスから修正のためのコード変更の提案まで、バグトリアージを処理するエージェントを構築しました」と Kareem は語りました。

**ヒント:** ここ数か月、[Claude Tag](https://claude.com/product/tag) は Anthropic における CI/CD 障害の一次対応者を務めています。Claude は最近発生したすべてのインシデントで、状況報告書のドラフトの第一稿を書き上げており、多くの場合 15 分以内に最初の分析を公開しています。

[Claude Tag には専用のサービスアカウント](https://claude.com/blog/agent-identity-access-model)があり、Anthropic の CI エンジニアが必要とするツール（Datadog や Grafana など）へのアクセス権を持っています。標準の指示は、GitHub リポジトリにコミットされたスキルとして Markdown ファイルにまとめられています。これにより、複数のチームメンバーが指示を反復改善でき、コードと同じように変更を管理できます。

Claude Tag は Slack でオンコールのスレッドを引き継ぎ、チャンネル内で進捗を報告します。

> これが最も顕著だったのが [ClickHouse](https://clickhouse.com/) で、**共同創業者 兼 CTO の Alexey Milovidov が報告した**ところによると、このデータベース企業はほぼすべての SDLC の段階を自律型のループへと変えていました。フレーキーテストの修正とテストカバレッジの欠落発見のために作られた 2 つの専用エージェントは、現在 ClickHouse リポジトリへのコントリビューション数で 2 位と 3 位を占めています。別のエージェント群がオペレーションを担当しており、チームはこれらのエージェント自体の構築と反復改善にも Claude Code を使っています。

### エージェントによるプロセスの加速

もう一つ一貫して見られたパターンは、これらのスタートアップが Claude Code のエージェント型ループを開発の加速だけに使うのではなく、繰り返し発生する面倒なプロセスを加速するためのエージェントも作っていたことです。

こうした作業はしばしばルーティンワークであり、それを自動化することで、競争優位、顧客関係、トップライン成長により多くの注意を向けられるようになります。私たちが見た中で最も多かった、Claude によって加速されるプロセスの一つがセルフサービス型のデータ分析でした。

これらの企業のほぼすべてに、非構造化データを含む新鮮なデータですばやく意思決定できる何らかの仕組みが備わっており、スタートアップの人生において不可欠なピボットを支えていました。

例えば Clay は社内向けの分析エージェントを構築し、Heidi は Claude Code を使って顧客と臨床医のフィードバックを利用状況データとともに分類し、製品への洞察に重要なシグナルを浮かび上がらせています。

ClickHouse と Omni はいずれも、この種の AI データ分析を組み込んだ製品を出荷しており、いずれも Claude によって支えられています。

その他の例としては、サブエージェントを使った数千件の法律文書の要約（Crosby）、複数拠点にまたがる保険金請求データの異常のフラグ付け（Commure)、どのアナリストチームも間に合わないほどのスピードで病院の財務データを継続的に監視し警告サインを見つけ出すこと（Translucent）などがあります。

**ヒント:** [Dynamic workflows](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) は、大量のデータを並列で分析するために複数のサブエージェントを展開したり、別のエージェントの作業を敵対的にレビューしたりするために使えます。Claude Opus や Claude Fable のようなモデルを使う場合は、「複数のサブエージェントに展開して」あるいは「ワークフローを使って」と伝えてください。

## 信頼はするが、検証もする

結果を監視・検証する信頼できる手段がなければ、プロセスを自動化することはできません。

このルールは、ルール 2「面倒な作業を自動化する」の必然的な帰結です。結果を監視・検証する信頼できる手段がなければ、プロセスを自動化することはできません。

![Dan Shiebler](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a86fc9ddbdb6a1fb6d61375_dan-shiebler.jpg)
> Artemis Security 共同創業者の Dan Shiebler は、自分たちのデプロイ速度の向上が機能しているのは……「テストインフラ、コードベースの構成、エージェントがエンドツーエンドで出荷できるようにするチームのナレッジシステムに深く投資してきたからです。これが私たちが Claude と共に築いたフライホイールです。コードベース、ナレッジベース、チームを正しい形に構造化すれば、あらゆる貢献が複利で積み上がっていきます。」**[Dan Shiebler](https://www.linkedin.com/in/dan-shiebler-10219b42/)** · 共同創業者、[Artemis Security](https://artemissecurity.com/)

![Victor Hunt](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85f1ef3623355a8a439148_Victor%20Hunt.jpg)
> 「初期の頃、私たちは Claude に完全な自律性を与え、AI がやるべきことをやりました。もっともらしいコードを高速に出荷したのです。問題は、見た目は正しいのに実際には違う形で私たちのアーキテクチャから逸脱していたことでした。そこで私たちは……すべての不変条件を書き出しました。私たちが問題をどう捉えるか。何があっても真でなければならないこと。自信に満ちた答えを鵜呑みにするのではなく、何かが機能することをどう証明するか。このチームの考え方の 567 行分です。」**[Victor Hunt](https://www.linkedin.com/in/victor-c-hunt)** · 共同創業者 兼 CEO、[Zingage](https://zingage.com/)

**ヒント:** 変えてはならないことをリポジトリのルートにある `CLAUDE.md` に書いてください。Claude はすべてのセッションの開始時にこれを読み込むため、あなたのアーキテクチャルール、セキュリティ境界、譲れない原則がすべてのセッションに引き継がれます。

念のため言っておくと、これらのスタートアップのどこも、エージェントを main にマージさせてうまくいくことを祈っているわけではありません。多くは高度に規制された業界で事業を営んでおり、強固なガバナンスフレームワークを必要とします。Cainex は、決定論的なチェックとエージェントを組み合わせて医療記録を読み取り、病院の請求を左右するコードを生成する、特に示唆に富む例です。

![Uriah Israel](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85e97524b99c1b700c5b18_uriah.webp)
> 「医療コーディングにおいて、間違ったコードは単なるタイプミスではありません。それは請求とコンプライアンスに関わる事案です。この一事が、私たちの構築のすべてを支配しています。」**[Uriah Israel](https://www.linkedin.com/in/uriah-israel/)** · 共同創業者 兼 CTO、[Cainex](https://www.cainex.com/)

「これが Claude Code が私たちのために回しているループです。エージェントでバッチを処理し、社内アプリで監査担当者が出力をレビューします。彼らはコードを見るだけでなく、モデルの推論も確認し、両方にコメントします……すべてがバージョン管理され、監査可能です」と同氏は語りました。

「そこから Claude Code が引き継ぎます。データベースから直接、元の予測結果とすべての修正・コメントを読み取ります。各修正は関わるコードの種類でタグ付けされているため、Claude Code は診断の問題なのか、処置の問題なのか、それとも別のカテゴリの問題なのかを把握でき、その特定の種類のコーディングを支配するガイダンスへ直接たどり着けます。

そこから、エージェントの指示のうちミスを引き起こした部分を見つけて修正するか、まったく新しいケースの場合は新しいガイダンスを書きます。すべての変更は、バージョン管理された指示セットに対して行われ、失敗した記録に対してテストされます。私たちが徹底しているルールは、事例ではなく原則を修正するということです」と同氏は続けました。

「そしてバックテストです。一つの記録に複数の妥当なコーディングがあり得るため、これは単純な文字列一致ではありません。このチェックは、承認済みセットに対するセマンティックマッチングと、『これは本当のエラーなのか、それとも単に別の妥当な経路なのか』を問う判定器を組み合わせており、Claude Code もその上に独自の比較を追加します。

ゴールデンセットとランダムサンプルの両方に対して候補となる変更を実行し、何かが出荷される前に回帰がないかを洗い出します。返ってくるのは短いリストです。提案された修正、解決できなかった記録、そして答えを求めている質問。エンジニアは機械的な 80% ではなく、本当に難しいケースに時間を使えます」と同氏は語りました。

この医療請求特有のワークフローから、創業者が汲み取れる一般化可能な教訓は数多くあります。

例えば Cainex は、Claude の推論を定期的にレビューし導く専門家を活用し、そのガイダンスが自己改善ループの一部となるようにしています。しかし、それらの専門家は事例ごとに個別に修正するためにいるのではなく、そのガイダンスは自己改善ループの一部として使われます。Uriah の言葉を借りれば「事例ではなく原則を修正する」のです。

**ヒント:** ループとは、停止条件を満たすまで作業サイクルを繰り返すエージェントです。より自律的、あるいはより長時間にわたる作業に Claude Code を使う効果的な方法になり得ます。[エージェントが満たすべき基準をスキルで定義し](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)（明確に定義されているほど良い）、目標に達するまでエージェントに反復させることができます。

例えば、多くの組織はフレーキーテスト用のエージェント、すなわちループを作っています。停止条件が明確かつ自己完結的だからです。エージェントはテストを再実行し続けて、パスするまで自分の修正を検証できます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a43eb603762e725a739d98f_c6fa9ae5.png)

ループは停止条件を満たすまで作業サイクルを繰り返します。

‍

もう一つの教訓は、チームがエージェントの精度を検証するために使う、検証済みの質問と回答のペア群である評価用「ゴールデンセット」の維持に払われている入念さです。すべてのスタートアップは、主要なユースケースについて複数の評価セットを維持し、定期的に更新することで、ドリフトを防ぎ将来のモデルを評価できるようにすべきです。

![Alex Mashrabov](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85f11c728d6a4b5ce8da6d_alexhiggsfield.webp)
> 「〔Claude Code は〕モデルの入れ替わりの速さに私たちがどう対応するかも変えました。新しい動画・画像モデルは絶えず登場します。それぞれがデプロイ前に新しいスキル、評価、ルーティングロジック、本番テストを必要とします。Claude Code はそのサイクルを数日から数時間へと圧縮し、本番環境で問題を特定し、同じセッション内で修正をデプロイできるようになりました……人員数が 10 倍の企業と競争しているとき、そのようなレバレッジはすべてを変えます。」**[Alex Mashrabov](https://www.linkedin.com/in/amashrabov)** · 共同創業者 兼 CEO、[Higgsfield](https://higgsfield.ai/)

**ヒント:** チームが初めてエージェントを構築する際、手動テスト、ドッグフーディング、そして勘の組み合わせだけで驚くほど遠くまで進めることがあります。転機が訪れるのは、ユーザーが変更後にエージェントの調子が悪くなったと報告し、チームが検証手段を持たずに「手探り」状態になり、推測と確認しかできなくなったときです。チームは本当の回帰とノイズを区別できず、変更を出荷する前に何百ものシナリオに対して自動的にテストすることも、改善を測定することもできません。詳しくは [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) をお読みください。

Uriah が挙げる最後のポイントは、このプロセスにはある程度の手間がかかるということです。「最初からこんなにきれいだったわけではありません。最初のバージョンは過剰適合していました。特定の事例をそのままエンコードすることで『修正』してしまい、賢くなるどころかパッチを積み上げているだけでした。私たちはアプローチを変え、一般原則を強制し、一度の変更に入れられる個別事例の数に上限を設けました。」

**ヒント:** AI エージェントは決定論的ではありませんが、高度に規制された作業の多くは、毎回同じ手順で行われることを必要とします。Claude Code には、フロンティアの知性と決定論的なプロセスを組み合わせる助けになる機能があります。

[Hooks](https://code.claude.com/docs/en/hooks) は、Claude Code のライフサイクルの決まったタイミングで発火するユーザー定義のコマンドで、ハードゲートとして機能します。モデルがどう判断しようと毎回必ず実行されます。例えば、lint に失敗する書き込みをブロックしたり、コミット前にテストのパスを必須にしたり、サンドボックスから何かが出る前にシークレットを除去したりするのに使えます。

[Dynamic workflows](https://code.claude.com/docs/en/workflows#orchestrate-subagents-at-scale-with-dynamic-workflows) は、決定論的なシーケンス、独立したコンテキストウィンドウ、焦点を絞った目標でサブエージェントをオーケストレーションします。`/goal` は、Claude が作業を時期尚早に完了とみなしたり、レビュー時に自分自身の発見結果を優先したり、当初の目標からドリフトしたりしがちな、長く複雑なタスクに役立ちます。

**04**

## 作り直しを前提に作る

モデルの能力はこれらのチームの足元で絶えず変化し続けているため、永続的なものとして扱われるものはほとんどありません。

これらの AI ネイティブなスタートアップの多くは、絶え間ない再発明の状態にあります。

AI は、彼らが何を作るかだけでなく、どう作るかの中心にもあることが多いです。モデルの能力が絶えず進化し続けるため、画期的な機能や重要な足場も、サンクコストになった瞬間に捨てられます。多くの組織は、この絶え間ない作り直しを自分たちの競争優位の一部と捉えていました。

「Clay で私たちがやっているのは、作って、また作り直して、そしてまた作り直すということです。そして 4 回目に作るときには、必要なものがすべて分かっているので、正しく仕上げられます。だから私たちは、必ずしも物を捨てているわけではありません。作り直しているだけです。ただし今回はより明確な理解を持って」と Kareem は語りました。

「作り直しは、新しい経路が出荷された時点では終わりません。古い経路が消えて初めて終わります。取り壊しはこれまで常に優先順位付けの争いに負けてきました。地味で、機能を何も出荷しないからです」と Commure の共同創業者 Tanay は語りました。「今では Commure のエンジニアの一人が、『すでに全員にリリース済みのフィーチャーフラグごとに、それとそれに紐づくコードを削除する PR を開いて』という要領で Claude スキルを呼び出すだけで、あとはエンジニアが返ってきたものをレビューします。以前は開発サイクルの多くを食いつぶしていたマイグレーションが、今では計画と展開だけで数時間で終わります。」

**ヒント:** 現行バージョンをそのままにしながら、リポジトリの独立したコピーで作り直しを行うには [git worktree](https://code.claude.com/docs/en/worktrees) を使ってください。Claude Code が代わりに一つ立ち上げてくれます。v1 の隣で v2 が動く状態になり、両方に対して評価を実行し、新しい方が勝った場合にのみマージできます。これが「4 回作り直す」ことを安上がりにする仕組みです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a86014c09a6e237c1ac273c_ccb97885.png)

一つのリポジトリ、一つのオブジェクトストア — 同時に作業できる 3 つのチェックアウト。

各リンクされた worktree は、それぞれ独自のチェックアウト済みブランチを持つ通常のディレクトリです。3 つすべてが acme-web 内の単一の .git オブジェクトストアを共有します。

Kareem はまた、Clay の堀の一部が、絶え間なく作り直し、進化し、自己改善ループを生み出す能力にあると説明しました。

「今のところ、どの企業にとっても堀となるのは自己改善する能力だと思います。だから Clay は自己学習型のレベニューエンジンです。使えば使うほど、私たちはあなたの最良の顧客が誰か、何を言うべきか、何がうまくいって何がうまくいかなかったかを把握でき、それは時間とともに変化していきます」と同氏は語りました。「本当のレースは、誰が最も速く配荷にたどり着けるか……そうすることで、各顧客を助けながら自己改善もできるようになります。」

[2026 年 5 月の Code with Claude イベント](https://www.youtube.com/live/OFDm3T7pVlc?si=Z_RENcJSqm8H79aj)で、Harvey の Head of Applied AI である Niko Grupen は、モデル能力の新しい波（創発的推論、エージェント型の自動化、計画とオーケストレーション）のそれぞれが、プラットフォームの全面的な再アーキテクチャを必要としたことについて話しました。

![Niko Grupen](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85f137a1aa7f601c74989a_1b877ceecea22945f9acd75a60692d9c7b488058-1600x1600.webp)
> 「もし半年前に私たちのアーキテクチャがどんな姿かと聞かれたら、今日とはまったく違う答えをしていたでしょう。もし私たちが『これを捨てて、エージェントネイティブに向かおう』と言う覚悟がなければ、今こうしたこの機能をプラットフォームに持てていなかったはずです。」**[Niko Grupen](https://www.linkedin.com/in/nikogrupen)** · Head of Applied AI、[Harvey](https://www.harvey.ai/)

同じイベントで、Cognition の共同創業者 Walden Yan はこう語りました。

![Walden Yan](https://cdn.prod.website-files.com/6889473510b50328dbb70ae6/6a85efb993c65fad88a4e0b3_1699725986976.jpeg)
> 「今 AI を構築するという生き方は、今日作ったものが半年から 1 年後には捨てられる可能性が非常に高いということを受け入れることです……〔Devin は〕2 年前に私たちが持っていたモデル群では到底実現できないものでした。〔しかし賭けたのは〕今日はうまくいかないかもしれないが、いずれうまくいくだろうということでした。」**[Walden Yan](https://www.linkedin.com/in/waldenyan)** · 共同創業者、[Cognition](https://cognition.ai/)

**ヒント:** 些細ではない書き直しには、[プランモード](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)（`--plan` または Shift+Tab）で Claude Code を起動してください。Claude はコードを一切書く前にコードベースを探索し、作り直しのアプローチを提案します。それを承認するか、方向修正するかはあなた次第です。これは、作り直しがアーキテクチャからドリフトしそうになるのを捉えるのに最も安上がりな場所です。

**05**

## プロトタイプ、ドッグフーディング、プロダクション化

AI で作ることが、これらのスタートアップが AI を使って破壊的な製品を作る助けになっています — これが彼らのプロセスの中心にあるフライホイールです。

これらのスタートアップの多くには、開発プロセスの中心に重要なフライホイールがあります。AI で作ることが、彼らが AI を使って破壊的な製品を作る助けになっているのです。

開発者がエージェント型コーディングの実践を進化させると、モデルの能力についてより強い理解を持ち、フロンティアでハーネス設計がどう進化していくかについての洞察を得られます。そして彼らはこのインスピレーションを、自分たち自身のエージェントや製品に活かせます。

「私たちは〔Anthropic の〕ファイル方式と埋め込み方式の使い分けからヒントを得て、自分たちの製品でもシンプルさを保つ勇気を得ました。RAG パイプラインから生じていたであろう多くの複雑さを避けられました」と Omni の Chris は語りました。「また、Claude Code のハーネスがどのようにユーザーの並列作業を可能にしているかを見て、その概念の一部を自分たちの UI に取り入れました。」

これはまた、自社の製品パフォーマンスに敏感であり続ける助けにもなっています。

「私たちのアプリビルダーも裏側で Anthropic のモデルを使っているため、自社製品で何らかの挙動を目にしたときに……Claude Code を使ってローカルですばやくデバッグし、それがモデルの挙動なのかハーネスの問題なのかを見分けられます。これはトリアージのサイクルを大幅に改善する助けになっています」と Emergent の Mukund は語りました。

繰り返し耳にしたパターンは、Claude Code で社内向けエージェントを構築し、社内で使い(ドッグフーディング)、その反応次第で、多くの場合 Claude API、SDK、あるいは Claude Managed Agents を使って顧客向け製品へと昇格させるというものでした。

「私たちは〔製品内で〕チームが直接やり取りする独自の AI エージェントを構築しました。SQL コンソール内のエージェントや AI SRE などです。これらのエージェント自体の構築と反復改善には Claude Code を使っています。顧客の AI 体験を支えるツールは、一部が AI によって作られているのです」と ClickHouse の Alexey は語りました。

## チェックリスト

このガイドでは多くのことを取り上げました。ここに重要なヒントを 1 ページにまとめます。

#### 第 1 章: 誰もが出荷する

Claude は見えないものを理解できません。[MCP](https://code.claude.com/docs/en/mcp) または CLI 経由で、信頼できる情報源とチームが日々使っているツールに接続してください。[会社のプラグインマーケットプレイス](https://code.claude.com/docs/en/plugin-marketplaces)を作り、一人の従業員のベストプラクティスをスキルとして別の従業員へ即座に伝えられるようにしてください。リポジトリの各サブディレクトリには、そのサブディレクトリ固有で常に適用されるコーディング規約のために CLAUDE.md ファイルを使ってください。オンデマンドの手順的なワークフローにはスキルを使ってください。

#### 第 2 章: 面倒な作業の自動化

リポジトリに [Code Review](https://code.claude.com/docs/en/code-review)（リサーチプレビュー）を設定し、PR に対する自動レビューを実行してください。[Claude Tag](https://claude.com/product/tag)（パブリックベータ）を CI/CD のオンコール対応とバグトリアージの一部にしてください。[Dynamic workflows](https://code.claude.com/docs/en/workflows#orchestrate-subagents-at-scale-with-dynamic-workflows) は、大量のデータを並列で分析するために複数のサブエージェントを展開したり、別のエージェントの作業を敵対的にレビューしたりするために使えます。

#### 第 3 章: 信頼はするが、検証もする

変えてはならないことをリポジトリのルートにある CLAUDE.md に書いてください。より自律的、あるいはより長時間にわたる作業には、停止条件を満たすまで作業サイクルを繰り返すエージェントである[ループ](https://code.claude.com/docs/en/workflows)を使ってください。[エージェントの評価の作成と維持](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)のプロセスを確立してください。[Hooks](https://code.claude.com/docs/en/hooks) は、Claude Code のライフサイクルの決まったタイミングで発火するユーザー定義のコマンドで、ハードゲートとして機能します。作業の一部を決定論的にする必要がある場合に使ってください。

#### 第 4 章: 作り直しを前提に作る

現行バージョンをそのままにしながら、リポジトリの独立したコピーで作り直しを行うには [git worktree](https://code.claude.com/docs/en/worktrees) を使ってください。これが「4 回作り直す」ことを安上がりにする仕組みです。些細ではない書き直しには、プランモード(/plan または Shift+Tab)で Claude Code を起動してください。Claude はコードを一切書く前にコードベースを探索し、作り直しのアプローチを提案します。それを承認するか、方向修正するかはあなた次第です。これは、作り直しがアーキテクチャからドリフトしそうになるのを捉えるのに最も安上がりな場所です。
