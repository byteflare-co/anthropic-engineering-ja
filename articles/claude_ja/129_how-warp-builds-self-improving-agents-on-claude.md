# Warp が Claude 上に自己改善するエージェントを構築する方法
- 著者

  Michael Segner

*このシリーズでは、スタートアップが AI で業界をどう変革しているかを紹介しています。この記事では、Warp がステートレスなユーザーフィードバックを、エージェントのための自己改善ループへと転換した方法を共有します。*

| The quick pitch | |
| --- | --- |
| Name | Warp |
| Founded | 2020 |
| Founders | Zach Lloyd (CEO) |
| Stack | Rust、Golang、GitHub Actions、社内エージェントオーケストレーションプラットフォーム (Oz)、Claude Platform |
| Growth | 7,300 万ドルを調達。月間 80 万人の開発者が Warp 上で開発。フォーチュン 500 企業の 56% が Warp を利用。これまでに Warp 内で実行された Claude Code セッションは 1,000 万件、週あたり 40 万件以上。Warp Agent の会話は累計 4,000 万件。 |

エージェントは、繰り返し発生するタスクを確実かつ効果的に処理する必要があります。80% の精度で正解する最初のプロンプトは、ユーザーにとってノイズが多く不快な体験を生みかねません。Warp はこれを苦い経験から学び、それをプロダクト戦略に反映させ、世界中の 100 万人近い開発者にとってより良い体験を作り上げました。

AI を活用したターミナルであり、エージェント型の開発環境である Warp は、Claude Platform の上に構築されています。同チームは、社内のコードレビューエージェントでこの「ノイズの多い体験」という問題に直面しました。エンジニアからは、自分たちのエージェントが役に立たないコメントを付け、低品質な出力を生成しているという不満が寄せられていました。

チームは当初、観察されたコードレビューの失敗をもとにプロンプトを手作業で書き直すといった、その場しのぎの解決策を試みました。これによって出力の使い勝手は改善したものの、スケールしませんでした。AGENTS.md のようなコンテキストファイルを改善することも役に立ちましたが、完全な解決には程遠いものでした。

最終的に彼らが気づいたのは、目的が何であれエージェントへのフィードバックは通常セッション終了とともに消えてしまい、エージェントループから重要なコンテキストが失われているという、根本的な問題でした。彼らが出した答えは、フィードバックが時間とともに積み重なり、エージェントの出力を継続的に磨き上げていく、[Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) をベースにした自己改善エージェントのフレームワークでした。

このフレームワークを Claude Platform 上に skills を使ってどう構築したか、続けて見ていきましょう。

## **skills の上に構築された、エージェント自己改善ループ**

中心となる技術は、[**skills**](https://support.claude.com/en/articles/12512176-what-are-skills)(生のプロンプトから指示を切り離してファイルとして知識を符号化したもの)を使った自己改善ループです。Warp は、2 つの skill と、その間に挟まる人間のフィードバックからなる自己改善エージェントアーキテクチャを発展させました。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8f1a9a1b33f40618a9d59a_selfimprove-loop.jpg)

**内側(ベース)の skill** は、機能的なドメイン知識と指示を保持します。例えば、PR が開かれると、Warp のコードエージェントはこのベース skill とコンテキストを使ってレビューを生成します。

エージェントの出力に対する**人間のフィードバック**は、自己改善ループにとって不可欠な要素です。コードレビューの場合、これは単純な「いいね」のようなものでもかまいませんが、より具体的であるほど良いフィードバックになります。

「人間は『これは良い、役に立つコメントだった』と肯定することもできます」と Warp の創業者 Zach Lloyd は説明します。「しかし、そのコードレビューがなぜ良くなかったのかを詳細な理由とともに伝えることもできます。『この変数のリネームを提案していたが、私たちのコードベースの慣習では、この種のグローバル変数はこの特定の命名規則を使う』といった具体的な指摘は、エージェントに次回どうすれば正しくできるかを教えてくれます。」

**外側(改善役)の skill** は、タスクごとではなくスケジュールに沿って動くオブザーバーエージェントとして機能します。蓄積された人間のフィードバックを取り出し、エージェントが何を提案し人間がどう反応したかを比較し、ベース skill に対する小さく的を絞った編集を提案します。

skill は単なるファイルであるため、エージェントはそれらを更新するのが非常に得意です。これらの更新はレビュー可能・承認可能・マージ可能であり、通常の PR / コードレビューのワークフローに乗せることができます。マージされれば、次回のベース skill の実行にその改善が引き継がれます。

Warp は現在、このパターンをオープンソースリポジトリ全体で運用しており、仕様書作成・レビュー・トリアージの各エージェントがそれぞれ独自の自己改善ループを持っています。

「ファイルベースの skill は、プロンプトに直接知識を詰め込むのではなく、エージェントが作業の過程で単純に参照できるものとして知識を符号化する方法です」と Zach は語ります。「フレームワーク自体は実はとてもシンプルです。ドメイン固有のベース skill があり、そのドメイン固有の skill を磨き上げる改善役の skill がある。このシンプルさこそが、このアプローチの美点なのです。」

## **エージェントのための自己改善する skill の書き方**

以下は、エージェントループのための自己改善する skill を書く際に Warp チームが実践してきたコツです。

- **ルールではなく原則を書く。** 「コンピューターにプログラムを書くのではなく、賢い人に指示を出すつもりで skill を構成してください」と Zach は言います。「『重複したコードを探す』といった方向性を skill に含める方が、網羅的な変数命名ルールよりも良い指針になります。」
- **理由を説明する。** ルールの背後にある論拠を示すことで、エージェントは硬直的な指示に従うのではなく問題について推論できるようになり、より良い汎化が可能になります。
- **フィードバックを与える手間をゼロに近づける。** PR やイシューに直接コメントするなど、人がすでに作業している場所でフィードバックを取得しましょう。また、追加の提出ステップなしに、これが自動的に起きるようにしましょう。「摩擦の低さがシグナルの流れを保つ鍵です」と Zach は指摘します。「ハードルが高すぎればフィードバックは得られませんし、skill を改善することもできません。」
- **skill は小さく保ち、段階的開示 (progressive disclosure) を使う。** [良い skill](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) ファイルは大きくありません。すべてを一度にコンテキストへ詰め込むのではなく、リソースファイルやスクリプトを参照します。
- **フィードバックは量より質だが、量も助けになる。** シニアエンジニアからの少量だが詳細でドメイン固有のフィードバックは、単なる「いいね/よくないね」の二値評価よりも価値があります。二値評価では*なぜ*かが伝わらないからです。「他の方法では知り得なかったドメイン固有の知識について、人が非常に詳細なフィードバックをくれるなら、比較的小さいサンプルサイズでも本当に良いシグナルが得られます」と Zach は続けます。「とはいえ、質の高いシグナルのコーパスが大きければ大きいほど良いのも事実です。Warp では、オープンソースリポジトリ全体をこのループで管理しています。数百人が貢献しており、数千件のコードレビューを行っています。」
- **改善役の skill に特に力を入れる。** 改善役の skill(オブザーバーエージェント)の記述に力を注ぐことは、目の前のエージェントループを超えた見返りをもたらします。改善役の skill は、異なるユースケース間で非常に再利用しやすいからです。「ドメイン固有の知識の部分を除けば、これはかなり再利用可能な仕組みです。コードレビューエージェント用の改善役 skill は、他のどんなエージェント用の改善役 skill ともそれほど変わりません。」

## **実際のループ: Warp のイシュートリアージエージェント**

[Warp のイシュートリアージエージェント](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)は、この自己改善エージェント skill フレームワークを実例で示しています。このパターンは、誰かが新しい GitHub イシューをファイルするたびに起動します。GitHub Action がエージェントを発火させ、イシューの複雑さと実現可能性を分析し、ラベルを付け、修正の方向性を提案します。このトリアージエージェントは、各ラベルの意味とアクションを起こす前にコードベースをどう調べるべきかというドメイン知識を保持する、内側の skill ファイルに基づいて動作します。

あるサンプルイシューでは、第一段階の内側 skill はまずまずの仕事をしましたが、「ready to spec」というラベルを一つ見落としました。これは、コントリビューターがそのイシューに対してプロダクト仕様や技術仕様の作成を始められる、というシグナルです。Warp チームのあるメンテナーがこの見落としに気づき、まさに作業が行われていたその場、つまりイシュー上に直接フィードバックを残しました。重要なのは、彼が何を期待していたかだけでなく、なぜそう期待していたかも説明したことです。これにより、エージェントが後で吸収しやすい実行可能なフィードバックになりました。

外側の改善役 skill は、[Warp のエージェントオーケストレーションプラットフォームである Oz](https://docs.warp.dev/) 上で、スケジュールされた「update triage」エージェントとして動きます。このエージェントは GitHub に認証し、skill にバンドルされた Python スクリプトを実行してフィードバック付きの最近のイシューを取得し、それらを JSON ファイルにまとめ、それをコンテキストとして読み込み直しました。バンドルされたスクリプトを使うこと自体がベストプラクティスの一つです。skill は、実行のたびに新しいコードを書くのではなく、リソースファイルを参照できます。

そこからエージェントは、メンテナーのコメントに含まれる具体的なフィードバックシグナルを特定し、それらを捉える最小限の編集を提案しました。エージェントは、正確な UI や UX の形がまだ定まっていなくても、イシューが実際の問題を記述している場合には「ready to spec」ラベルを適用する、という内側 skill を編集する PR を開きました。

更新全体が skill ファイルであるため、これは通常のコードレビューのワークフローに乗って進みます。この PR には、どのシグナルが変更を促し、何を変更したのかを説明する説明文が添えられていました。人間がレビューし、承認し、マージすることで、次回のトリアージ skill の実行にその新しい知識が引き継がれます。この最後の人間によるステップがループを閉じ、実際に何が変わるのかを人間の管理下に保っています。

これは、Warp が現在オープンソースリポジトリ全体でスケールさせている仕組みと同じものであり、仕様書作成エージェント、レビューエージェント、トリアージエージェントがそれぞれ独自の自己改善ループを持っています。

タスクが何であれ、どんなエージェントも、人間のフィードバックシグナルを捉え、それを skill の更新に変換し、単発のヘルパーから組織全体で積み重なっていく有能なシステムへとエージェントを成長させるループを最初から組み込めば、時間とともに改善していきます。

| Warp チームのベストプラクティス | |
| --- | --- |
| skill とメモリを混同していないか? | skill は手続き的で安定しており、「X をどうやるか」を表し、実行間で変わらず、意図的に変更されるものです。メモリはエージェントが推論時に自動的に書き込むもので、常に変化し続けます。 |
| 改善ループはエージェントごとに 1 つ必要か、それとも 1 つで済むか? | 中間を取りましょう。テンプレート化されたベースループでエージェント間の重複部分を捉え、その上にドメイン固有の重み付けを重ねます。数個の改善役ならそれぞれが 1 つずつ持ち、100 個にもなれば共有すべきです。 |
| フィードバックが間違っていたらどうするか? | 間違っていることを前提にしましょう。エージェントにフィードバックを鵜呑みにさせてはいけません。妥当性を検証できるコンテキストを与え、誰の意見が採用されるかをフィルタリングし、フィルタリングか最終レビューのいずれかの段階で人間をループに残しましょう。 |
| あなたのドメインは検証可能か? | まず検証ハーネスを構築し、それに対してエージェントをチューニングさせましょう。参照コーパスを生成し、出力を参照と比較し、修正し、繰り返します。 |
| ドメインが検証可能でない場合はどうするか? | ゴールデン出力が存在する範囲では決定論的な評価に頼りましょう。人間のフィードバックを使わざるを得ない場合は、それをドメインエキスパートに限定し、誰でも投稿できる状態にはしないことです。 |
| システム全体が改善しているとどうやって分かるか? | 人間がすでに目視で確認しているグローバルな指標(マージまでの時間、コントリビューター数、コスト)を追跡し、それを改善役エージェントにフィードバックしましょう。デプロイは crawl-walk-run(徐々に段階を上げていく)方式で進めます。 |
