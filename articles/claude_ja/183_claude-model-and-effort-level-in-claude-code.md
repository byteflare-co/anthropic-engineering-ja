**要点**:

- Claude のモデル選択とは、固定された重みのセット、つまりモデル全体の能力の範囲を選ぶことです。モデルにはコンテキストを与えたり誘導（steering）したりできますが、モデルが持つ知識の基盤と能力そのものは固定されています。
- effort は単なる「考える時間」以上のものです。effort は、読み込むファイルの数、使用するツール、あなたに確認を求める前に進めるステップ数など、リクエストに対して Claude が行う作業量全体を制御します。
- 定型的なタスクには小さいモデルを、複雑なタスクや曖昧なタスクには大きいモデルを選びましょう。effort レベルはまず各モデルのデフォルトから始め、タスクごとではなく、自分が行う作業の種類に応じた全般的な好みとして調整します。
- Claude が必要なコンテキストをすべて持ち、明らかに努力したうえで、それでも間違えたなら、より高性能なモデルを選ぶべきサインです。ファイルを読み飛ばした、テストを実行しなかった、リファクタリングを途中で投げ出したといった理由で間違えたなら、より高い effort レベルを選びましょう。

## **Claude Code の effort レベルとモデル選択**

Claude Code には、「回答を良くする」ように見える設定が 2 つあります。モデル設定と effort レベルです。Claude Fable 5 のような大きいモデルは Claude Sonnet よりも賢い出力を返し、effort レベルを上げれば Claude は回答前により長く考える、と予想するかもしれません。

1 つ目の想定は正しいものです。業界標準のベンチマークによれば、私たちの最大のモデルほど高い能力を持っています。

しかし、effort は単なる「考える時間」以上のものです。effort レベルは、リクエストに対して Claude が行う作業量全体を制御します。これにはモデルが考える時間も含まれますが、それだけではありません。

- どれだけ多くのファイルを読むか
- どれだけ検証するか
- 複数ステップのタスクを、あなたに確認を求める前にどこまで進めるか

effort が高いほど、Claude はあなたに戻ってくる前に、こうしたアクション（たとえばファイルを読む、テストを実行する、ダブルチェックする）をより多く行います。effort が低いと、自力で何かを突き止めるためにトークンを費やすよりも、あなたに追加のコンテキストを求めることを選びます。

## **モデル選択の仕組み**

Enter キーを押すと、Claude Code はあなたのメッセージを、システムプロンプト、ツール定義、CLAUDE.md、会話履歴、コンテキスト内のファイルとまとめます。これらすべてが 1 つのリクエストとして API に送信されます。

![](https://assets.claude.com/8e646c17fd6a3737608c8cd46ac12c67997c3b68.png)

Claude Code が持つすべてが 1 つの API リクエストにまとめられます。サーバー側では、テキストはモデルに届く前にトークン化されます。

ただし、モデルがそれをプレーンテキストとして見ることはありません。サーバー上で最初に行われるのは**トークン化（tokenization）**です。テキストは断片に分割され、各断片はモデルの学習時に使われた固定の語彙の中の整数に対応づけられます。const は 1978 に、await は 4293 に対応するかもしれません。ここから先、あなたのプロンプトは整数の配列になります。

![](https://assets.claude.com/e12cb84c1cb631e9af20f00c3264b2ca12c4f814.png)

トークナイザーはテキストを断片に分割し、各断片を固定語彙内の整数に対応づけます。上段の各チャンクがトークン ID（下段）になります。ID は説明用の例です。

モデルの仕事は、その配列を受け取り、次にどのトークンが来るかを予測することです。これは、語彙内のすべてのトークンについて*確率*を計算し、上位から選ぶことで行われます。const x = await の後であれば、よく訓練されたモデルは fetch に高い確率（非常にありそう）を、banana にはほぼゼロの確率（まったくありそうにない）を割り当てます。

![](https://assets.claude.com/a449bfc1760f67e245fc11d0549341a4f41244d8.png)

モデルの予測は、語彙内のすべてのトークンに対する確率です。最上位の候補と無関係なトークンとの差は非常に大きくなります。

入力トークンをこれらの確率に変換するのが**重み（weights）**（*パラメータ*とも呼ばれます）です。これは大きな行列に整理された数十億個の数値です。1 つのトークンを予測するために、モデルは入力をこれらの行列に通し、長い行列積の連鎖を経て、最後に確率を読み取ります。モデルが「知っている」ことはすべて重みの中にあります。

**各モデルの重みは学習中に決まり、あなたがリクエストを送る時点では読み取り専用です。** プロンプトや CLAUDE.md、コンテキストのどれも重みを変えることはありません。（推論（inference）という言葉を聞いたことがあれば、それはまさにこのこと、つまり学習が終わって重みが固定された後にモデルを使うことを指しています。）

![](https://assets.claude.com/1810e1151d4fbf3a573c33608ff5393b1fbcae35.png)

プロンプトが入り、確率が出てきます。その間にある重みは変化しません。

TypeScript、人気のフレームワーク、慣用的な Go、その他一般的なプログラミング知識について Claude が知っていることはすべて、学習時にこれらの重みにエンコードされたものです。

プロンプトとコンテキストは予測を*誘導（steer）*することはできます（実際のコードを Claude に見せるのは*誘導*であり、非常に効果的です）が、重みそのものに何かを追加するわけではありません。

モデルの学習時に存在しなかったライブラリは、重みの中にありません。ドキュメントをコンテキストに入れれば Claude はそれを使いますが、それは*教える*ことではなく*誘導*です。Claude の応答が影響を受けるのはそのリクエストに対してだけで、基盤となるモデルがその情報を保持するわけではありません。

ですから、Claude が存在しない API を自信満々に呼び出すとき（ハルシネーション）、それは検索の失敗ではなく、学習時のパターンからもっともらしく*見える*トークン列を重みが生成しているのです。

では、モデルを変更すると実際には何が起きるのでしょうか。リクエストを処理する**凍結された重みのセット**が入れ替わるのです。

モデルは回答全体を一度に生成するわけではありません。1 つのトークンを予測し、それを系列に追加し、次のトークンを得るために計算全体をもう一度実行します。200 トークンの応答は、重みを 200 回別々に通過した結果です。このループが、待ち時間と出力コストの大部分の発生源です。

![](https://assets.claude.com/f33911c0e883b2b29728f07baf22aa467fecbb8a.png)

系列は 1 ステップごとにちょうど 1 トークンずつ伸びていきます。モデルは毎回配列全体を読み直して次に来るものを予測します。

つまり、**モデル設定**は、リクエストを*どの重み*が処理するかを決め、同時に出力トークン 1 つあたりのコストも決めます。

一方、モデル設定が決めないのは、生成されるトークンの数です。この数は、Claude がどれだけ作業をすると判断するかによって、同じプロンプトでも大きく変わることがあります。

これこそが **effort レベル**が制御するもの、つまり各ターンで Claude が*どれだけの作業*をすると判断するかです。

## **Claude Code の effort レベルの仕組み**

Claude Code がタスクに取り組んでいるとき、生成されるトークンはいくつかのカテゴリに分かれます。

- **Thinking**: アクションの前や合間にストリーミング表示される推論。
- **ツール呼び出し**: Read や Edit などのツール名とその引数を記した構造化ブロック。Claude Code がこれを解析して実行します。
- **あなたへのテキスト**: 計画、進捗の報告、最後のまとめ。

これらはすべて同じループから生成される通常の出力トークンであり、同じ料金で課金されます。たとえば、thinking トークンは他の出力トークンとまったく同じように生成され、そのターンの残りの間コンテキストに残ります。

Claude がコードを書く段階に進むと、それまでの推論は、読み込んだファイルと同じように入力の一部になります。

![](https://assets.claude.com/b65c64a00eb500a6112b4ac0ce81119a0ba16875.png)

Claude の出力はすべてトークンです。thinking、ツール呼び出し、あなたへのテキストは、すべて同じループから生成されます。

では、effort はこれらをどう変えるのでしょうか。effort レベルは、プロンプトと並んでリクエストの一部としてモデルに送られます。モデルは各 effort レベルでどう振る舞うべきかを学習しており、その学習された振る舞いは凍結された重みに組み込まれています。

リクエストが届くと、effort レベルは、プロンプトのテキストと同じように、モデルが反応するもう 1 つの入力となります。これによって、タスクが完了したと見なす前に Claude がどれだけ徹底し、どれだけ確信を持つ必要があるかという振る舞いが決まります。

**これは毎ターン考慮され**、より多くのトークンを使って、より確信度の高い回答を生み出します。

![](https://assets.claude.com/181600a66676825accdbc3ff497a457671061514.png)

同じプロンプトに 2 つの effort レベル。高 effort の経路では、より確信度の高い回答に到達するためにおよそ 7 倍のトークンが生成されています。

effort レベルが高いと、Claude は多くの場合まず計画を立てるところから始め、effort のレベルがその計画の深さと幅に影響します。ただし、計画は固定されたものではありません。Claude はアクションの結果を受け取るにつれて、どこまで進んだか、積み上げた結果にどれだけ確信があるかを更新していきます。

たとえば、3 つの仮説を立てたデバッグ計画のステップ 1 でバグが見つかれば、「仮説 2 と 3 を調査する」は不要なアクションになるかもしれません。Claude は通常、「最初のチェックで見つかったので、残りのチェックは不要です」と明示的に述べて先に進みます。Claude Code でタスクリストが実行途中で修正されるとき、これが起きているのを目にすることができます。

effort レベルが高いほど、Claude は追加の仮説をダブルチェックしたり正しさを検証したりする傾向が強くなりますが、一般に、単純なタスクで高い effort レベルだからといって使用量を人為的に膨らませることはありません。実際、私たちのチームはモデルの学習中に「考えすぎ（overthinking）」に細心の注意を払っています。考えすぎは有効性を損なうからです。

## **effort レベルを選ぶ**

私たちの推奨は、**ほとんどのタスクではモデルのデフォルトの effort レベルを使う**ことです。デフォルトは、Claude がタスクに対してほとんどの人が費やしたいと考える量に応じてトークン使用量を調整するレベルです。

effort は、Claude がどれだけ熱心に、どれだけ長く取り組むかを調整する手動のオーバーライドだと考えてください。自分の領域や作業の種類に基づいて、徹底性やスピードを強く重視したい場合に意図的に選びます。タスクごとの判断というより、全般的な好みとして考えましょう。

[Claude Opus 4.8 のリリース](https://www.anthropic.com/news/claude-opus-4-8)を受けて、参考になりそうな実践的な知見を 1 つ紹介します。私たちのテストでは、Opus 4.8 をデフォルトの effort 設定で使うと、同じタスクで Opus 4.7 をデフォルトの effort 設定で使った場合と比べて、ほぼ同じトークン数でより良い結果が得られました。

## **Claude が間違えたときに何を変えるか**

Claude が何かを間違えたとき、最初にすべきことはつまみを調整することではなく、与えたコンテキストを見直すことです。プロンプトが曖昧すぎないか。Claude は適切なツールに接続されているか。適切なスキルを備えているか。

本来必要ないはずのタスクで effort を上げているなら、解決策は多くの場合その上流、つまりコンテキストや CLAUDE.md、タスクのスコープの切り方にあります。

しかし、明確なコンテキストを与えたうえで Claude がそれでも間違えたなら、自問すべきは「十分に*努力*しなかったのか、それとも十分に*知らなかった*のか」です。

![](https://assets.claude.com/0128d65ec13f0c8696bc70e8932100418734c849.png)

2 つの問いと 1 つのフォールバック。このヒューリスティックは出発点を選ぶためのものであり、厳格なルールではありません。

### **モデル: 問題が難しすぎた**

問題が本当に難しいときは、大きいモデルを選びましょう。たとえば、微妙なバグ、なじみのない領域、アーキテクチャ上の判断といった問題です。どれだけコンテキストを与えても小さいモデルが自信満々に間違える状況では、大きいモデルが役立ちます。

また、大きいモデルは曖昧さへの対処にも優れています。一方、小さいモデルで成功するには、実行を方向づける具体的な指示を与えるのが効果的です。

作業が定型的なときは、小さいモデルを選びましょう。たとえば、正確に説明できる編集、機械的な変更、すでにコンテキストにあるコードについての質問などです。タスクに必要のない能力にお金を払う理由はありません。

Claude が必要なコンテキストをすべて持ち、明らかに努力したうえで、それでも間違えたなら、大きいモデルを選ぶべきサインです。大きいモデルを使っていて、しばらく定型的な作業が続いているなら、モデルを下げることで出力の品質を損なわずにスピードが上がり、通常はコストも下がります。

### **effort: Claude が十分に努力しなかった**

Claude がファイルを読み飛ばした、テストを実行しなかった、作業をダブルチェックしなかったといった理由で間違えたなら、より高い effort レベルを選びましょう。これは特に、モデルのデフォルトより低い effort レベルを選んでいた場合に当てはまります。

Fable vs. Opus vs. Sonnet: スペシャリスト、エキスパート、ジェネラリスト

2 つの設定の関係について、私が気に入っている考え方があります。Fable はほとんど誰も見たことのない問題を見てきたスペシャリスト、Opus はエキスパート、Sonnet は非常に優秀なジェネラリストです。そして effort レベルは、そのうちの誰であれ、あなたのタスクにどれだけの時間をかけるかを決めます。

**低 effort の Opus** は、あなたの問題に似た問題に深い経験を持つエキスパートに 5 分間だけ相談するようなものです。彼らはあなたのコードベースのどこにもない知識、つまり以前に見たパターン、確認すべき落とし穴、似た問題を数多く解いてきたからこそ得られるものをもたらしてくれます。ただし 5 分しか与えないということは、コードを丁寧に読むのではなく、ざっと目を通すだけになるということです。

**高 effort の Sonnet** は、非常に優秀なジェネラリストに午後いっぱいを与えるようなものです。すべてを読み、実行し、作業をダブルチェックし、最終的に*あなたの特定のコード*を徹底的に理解します。彼らがあまり持っていないのは、「まさにこれは前に見たことがある」という認識です。

**Fable は、低 effort でさえ**、他の誰もが行き詰まっている問題をスペシャリストがちらっと見て、他の誰も気づかない点を見抜くようなものです。その認識こそが最も高い対価を払っているものなので、本当にそれが必要なタスクのために取っておく価値があります。

どれかが普遍的に優れているわけではありません。モデル設定はおおよそ*どれだけ有能か*、effort 設定はおおよそ*どれだけ徹底的か*です。現実のタスクの多くは、その両方をある程度必要とします。

## **effort、モデル、トークン消費**

では、モデル選択、effort、トークン消費はどのように相互作用するのでしょうか。それはタスク次第です。

定型的な作業を同じ effort レベルで行う場合、一般にどちらのモデルも正しく処理できます。大きいモデルは追加の検証ステップでより多くのトークンを消費し、しかもトークンあたりの価格も高くなります。だからこそ、定型的な作業が続く間は小さいモデルに切り替えることで、品質を犠牲にせずに実際のコストを節約できるのです。

![](https://assets.claude.com/8352a1d61d466c02e601b9d3cb8012cb75a676fb.png)

曲線は説明用のものであり、両モデルがすぐに達成できる程度に単純な 1 つのタスクについて示しています。実際のベンチマークデータを表すものではありません。

より難しい複数ステップの作業では、計算が変わります。小さいモデルは自身の能力の限界に向かって反復を重ねながら粘り強く進まなければならない一方、大きいモデルはより少ないステップで同じ品質基準に到達します。

大きいモデルはトークンあたりの料金が高くなりますが、小さいモデルにとって本当に手に余るタスクでは、タスクあたりの総コストがむしろ低くなることがあります。そしてより重要なのは、大きいモデルは、小さいモデルが最高の effort 設定でも達成できないタスクを達成できるということです。

これが最も顕著なのが Fable です。長い複数ステップの作業で、Fable は最も大きく差をつけます。私たちのテストでは、Opus や Sonnet がどの effort レベルでも到達できない仕事を Fable は完了させました。一方で、トークンあたりのコストも最も高く、それが Fable を本当に必要な作業のために取っておくべきもう 1 つの理由です。

![](https://assets.claude.com/dfef391930320e0da39548b50d2b1e7b7ddfcd6c.png)

曲線は説明用のものであり、両モデルにとって手応えのある難しさの 1 つのタスクについて示しています。実際のベンチマークデータを表すものではありません。

上のグラフの要点は、effort レベルは Claude が曲線に沿って**どこまで進む意思があるか**を決めるものの、繰り返しになりますが、タスクを完了するために Claude が**そこまで進む必要がある**とは限らない、ということです。

もう 1 つの微妙な点として、effort はトークン消費を方向づけますが、制限はしません。システム内で唯一の厳格な上限は [max\_tokens](https://platform.claude.com/docs/en/build-with-claude/extended-thinking#max-tokens-and-context-window-size-with-extended-thinking) で、これに達すると応答がストリームの途中で打ち切られます。これは大ざっぱな手段であり、主に API 開発者に関係するものです。[task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets#task-budgets-are-advisory-not-enforced) やプロンプトで Claude に簡潔にするよう求めるといった、よりソフトな制御のほうが役に立ちます。これらは、ぶつかって止まる壁ではなく、モデルが従うよう学習しているガイダンスとして機能し、上限に近づくとモデルはタスクを締めくくろうとします。

## **まずはデフォルトから始め、それからダイヤルに手を伸ばす**

ほとんどの場合、どちらの設定についても考える必要はありません。結果が期待に届かなかったときに、「Claude は十分に知らなかったのか、それとも十分に努力しなかったのか」と問い、必要に応じて調整しましょう。
