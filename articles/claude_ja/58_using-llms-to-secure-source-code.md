# LLM を使ってソースコードをセキュアにする

モデルの能力は、急速に、そして不均一に進歩しています。私たちは、セキュリティチームが自社コードやオープンソースソフトウェアの脆弱性を発見・修正する取り組みに [協働してきました](https://www.anthropic.com/glasswing)。その経験から、モデルをソースコードのセキュリティ確保にどう使うかについて、より良い理解が得られました。**主な学びはこうです: 発見はもう簡単に並列化できるようになり、ボトルネックは検証・トリアージ・パッチ適用へと移った**ということです。

この差を示す一例として、私たちが [自ら行ったオープンソースソフトウェアのスキャン](https://www.anthropic.com/research/glasswing-initial-update) の結果、2026 年 5 月 22 日時点で 1,596 件の脆弱性を開示しました。私たちの知る限り、そのうちパッチが適用されたのは 97 件です。

このガイドでは、Claude Opus と一緒に脅威モデルを構築し、コードベース内の脆弱性を発見し、検証・トリアージ・パッチ適用までを行う方法を解説します。私たちもすべての答えを持っているわけではありませんが、各チームがどう発見をスケールさせたか、そして後段のフェーズで何が役に立ったかを共有します。*今日から始められるよう、対話的なワークフロー用 skill と自律スキャン用のデモハーネスを含む* [*付属リポジトリ*](https://github.com/anthropics/defending-code-reference-harness) *も用意しました。* 読み進める中で、各ステップを実装する skill を都度紹介していきます。

## **発見と修正のループ**

最も多くの脆弱性を発見・修正しているチームは、既存のベストプラクティスのバリエーションに収れんしてきました。私たちはそれを 6 つのステップに整理しました。

1. **脅威モデル:** スキャンを始める前に、何を脆弱性とみなすかを決める。
2. **サンドボックス:** エージェントを隔離しエクスプロイトを実証するためのサンドボックス環境を構築する。
3. **発見:** モデルにソースコード内の脆弱性を探させる。
4. **検証:** どの発見事項が実際にエクスプロイト可能なのかを独立に確認する。
5. **トリアージ:** 発見事項を重複排除し、深刻度を割り当て、修正の優先順位を付ける。
6. **パッチ適用:** 修正を適用し、脆弱性が無効化されたことを確認し、バリアントを探す。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a17340b26b22fa10e3ed68e_image1.png)

脅威モデリングとサンドボックスへの一度きりの投資が、防御側のループ——発見・検証・トリアージ・パッチ適用の繰り返しサイクル——を駆動します。ここでのボトルネックは、脆弱性を見つけることではなく、その後に続くすべてです。

最初の 2 ステップ——脅威モデル構築とサンドボックス構築——は、残りのループのためのセットアップです。これらは典型的にはコードベースごとに 1 回行い、基盤となるシステムが変わったときに見直します。続く 4 ステップが、ソースに対して回していくループ——発見・検証・トリアージ・パッチ適用——です。

コードベースに対する最初の実行は、通常もっとも多くの発見事項を生みます。その後の実行は、より少なく——ただし、より複雑な——脆弱性になりがちです。単純なものは過去の実行でパッチ適用済みだからです。とはいえ、*n* 回目の実行で新規の発見事項がゼロになると期待してはいけません。モデルは確率的であり、大規模なコードベースには、コードが変更されていなくてもじわじわと出てくる長い尾の脆弱性があり得ます。

コードベースに対する初回の反復では、ループを複数回回すべきです。停止のタイミングは、純粋に新規の発見事項の件数と、そのシステムに対するリスク許容度に基づいて判断します。初回の反復が終わったら、(1) 定期的に、または (2) コードが意味のある変更を受けたタイミングで、スキャンを続けます。

次に、各ステップを順に見ていきます。なぜ重要か、何を生み出すか、どう実装するかを説明します。

## **1. 脅威モデル: 何を脆弱性とみなすかを定義する**

偽陽性のもっとも一般的な原因は、モデルがあなたの信頼境界を十分に理解していないことです。モデルは、クライアントが壊れた値を送れる、あるいは攻撃者が config を制御できる、と仮定してコードを脆弱とフラグするかもしれません。たとえそれらの入力があなたの環境では*信頼された*ものであっても、です。逆に、インターネットに面したサービスを内部限定だと仮定し、真の脆弱性を過小報告することもあります。どちらの場合も、モデルが誤っているのはコードについてではなく、脅威モデルについてです。

> *あるチームは、自分たちの発見事項を横断する 1 つのパターンに気付きました: モデルは、脅威モデル・システム設計書・要件・制約がよくドキュメント化されているシステムに対してもっとも高い性能を発揮していたのです。脅威モデルがよく定義されているとき、モデルの発見事項は「90 パーセントの確率でエクスプロイト可能」だったといいます。*

Claude と一緒に脅威モデルを構築するには、2 段階のステップがあります。

**まず、コード・ドキュメント・脆弱性の履歴からブートストラップする。** 新人セキュリティエンジニアの初日に渡すような情報をモデルに与えましょう: アーキテクチャドキュメント、wiki、エントリーポイント、git の履歴、過去の脆弱性などです。これによって、コードだけからは暗黙の知識・トレードオフ・設計判断を推測しにくいという課題を乗り越えやすくなります。次に、システムコンテキスト・資産・エントリーポイント・信頼境界を含む脅威モデルの作成をモデルに依頼します。最後に、過去のバグをクラスタリングさせ、関連する脆弱性クラスを列挙させます。脅威モデルには、どんな脆弱性を気にする／気にしないのか、そしてその理由を記載するようにしてください。

> *あるチームは、数百件の過去 CVE およびセキュリティ修正コミットをレビューし、それらを「バグの形状（bug-shape）」のヒントとして蒸留し、モデルに 2 つの問いを投げかけました: 修正は完全だったか、そしてそれは他のすべての場所にも適用されていたか。彼らは 1 時間で 3 件のエクスプロイト可能な問題を発見しました。彼らの言葉を借りれば「『過去に何が悪用されてきたか』は、ときに『このコードベースの脆弱性を見つけてくれ』よりもはるかに簡単な成功への近道になる」のです。*

**次に、システムをよく知る人物に対してモデルにインタビューさせる。** [Shostack の 4 つの問い](https://github.com/adamshostack/4QuestionFrame) を参考にしてください: *私たちは何を構築しているのか? 何が間違い得るか? それに対して何をしているか? うまくできたか?* 先にブートストラップのステップを済ませておけば、インタビュー対象者はゼロから始めずに済みます。そうすれば、何時間もかけて調べ脅威モデルをゼロから組み立てるのではなく、ドラフトから始められるのです。インタビューのステップは任意ですが、コードやドキュメントからは得られないコンテキストを追加でき、脅威モデルを改善します。

いくつかのプラクティスは、大きな違いを生みます:

- **依存ライブラリのセキュリティポリシーを考慮する。** 多くのオープンソースプロジェクトはセキュリティポリシーを公開しています。たとえば、vLLM の [`security.md`](https://docs.vllm.ai/en/latest/usage/security.html)、SQLite の ["Defense Against the Dark Arts"](https://www.sqlite.org/security.html)、[ImageMagick のセキュリティポリシー](https://github.com/ImageMagick/ImageMagick/security/policy) などです。あなたの脅威モデルは、ポリシーをゼロから組み直すのではなく、これらを直接考慮に入れるべきです。
- **信頼されているものを明示する。** config ファイルや認証済みクライアントを信頼しているのであれば、脅威モデルにそう記載しましょう。これらの前提は、エクスプロイト不可能なバグと実際のエクスプロイトを切り分けるのに役立ちます。
- **`THREAT_MODEL.md` をコードと一緒に置く。** リポジトリ内に置き、コードの変更に合わせて更新します。発見エージェントは検索前にこれを読んで、既知の非問題をスキップできます。

脅威モデルは 2 か所で使います。発見では、スコープとして**:** コードを分割し、ターゲットの優先順位を付け、スコープ外をスキップします。これは、全体をスキャンしきれない大規模コードベースで役に立ちます。トリアージでは、フィルターとして: 広くスキャンした後で、脅威モデルを使って深刻度をあなたのシステムと環境に合わせて適切にキャリブレートします。

> *ある大規模プロジェクトをスキャンしたチームは偽陽性率が 40% にのぼり、その原因を掘り下げました。発見事項は再現可能で、PoC はエクスプロイト可能性を証明していました。しかし、そのコードを所有する開発チームは、それらを偽陽性として却下しました——バグがプロジェクトの脅威モデルに合わなかったからです。別のチームの CISO はそれを端的にこう表現しました:「[モデルは] コードのコンテキストは良く理解しているが、我々のことのコンテキストは良く理解していない」。*

**[`threat-model` skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/threat-model) を試してみてください。** これは本セクションで説明した 2 つのステップを通します——`bootstrap` がコード・CVE・git 履歴からドラフトを導き出し、interview がシステムオーナーに Shostack の 4 つの問いを通してそれを精緻化します。出力は `THREAT_MODEL.md` ファイルで、これは発見とトリアージのステップで使われます。

## **2. サンドボックス: エージェントを安全に動かし、エクスプロイト可能性を検証する**

**サンドボックスの目的のひとつは、自分のシステムを守ることです。** モデルを安全に自律的に動かすには、強い隔離レイヤーが必要です。これがなければ、エージェントが目標を超えて予想外のことをしてしまうかもしれません。

> *あるチームはモデルにネットワークアクセスがないと伝えていましたが——実際にはあったため——モデルはとにかく GitHub から fetch できると発見しました。別のチームは、スキャン途中で GitHub の issue にエージェントが回答しているのを目撃しました。どちらの行動も悪意のあるものではありませんでしたが、いずれも制約をコードと設定で強制する必要性を示しています。*

隔離は脅威モデルに合わせます。コードを読むだけの発見エージェントにはコンテナで十分ですが、ターゲットとその PoC は microVM (Firecracker のようなもの) または egress をロックダウンしたフル VM 内で動かし、本番システムには何も届かないようにします。そして、エージェントに認証情報 (`~/.aws`、`~/.ssh`、`.env`) を絶対に渡さないでください。

サンドボックスにネットワークアクセスを与えるのは、セットアップしている間だけです。依存関係を取得し、ビルドし、ツールをインストールし、ターゲットをデプロイし、既存テストを走らせて、すべてが動くことを確認します。その上で、環境をスナップショットし、ネットワークアクセスを取り除きます。スキャン中は、モデル API へのトラフィックのみ、ローカルプロキシ経由で許可します。各実行の冒頭でスナップショットを読み込み、すべてのスキャンが同じクリーンな状態から始まるようにします。

**サンドボックスのもうひとつの目的は、エクスプロイト可能性を証明することです。** 静的スキャン中、モデルはコードを読んで何が壊れ得るかを仮説立てしますが、経路が到達可能か、補償的なコントロールがあるかをテストすることはできません。その結果、モデルは、あなたが実際には気にしないようなエクスプロイト不可能なコード正しさのバグをフラグするかもしれません。エージェントがコードをコンパイルし、テストを走らせ、概念実証 (PoC) を起爆できるサンドボックスをチームが構築したところ、エクスプロイト不可能な発見事項は大きく減りました。

> *あるオフェンシブセキュリティチームは、エージェントにテストベッドを与えるハーネスを構築しました。検証ルールはシンプルです: エージェントが概念実証を構築してテストベッド上で実行できる場合のみ真陽性とみなす、というものです。6 週間後の彼らの評価は「最大の効率レバーは、モデルにテストベッド、稼働システム、そして PoC の実行を与えることだった」というものでした。*

サンドボックスを構築する際は、すべての実行が同じ環境で同じコードを使うように、できる限り固定しましょう: イメージタグ、コミット SHA、依存関係、ビルドコマンドなどです。ビルドがネットワークを必要としないようにローカルコピーをキャッシュし、コンテナは複数回のテストループでも読み込み直すだけで済むよう、耐久性のあるものを目指します。

> *あるチームのスキャンが脆弱性をフラグしたのですが、実際にはエージェントが実際にデプロイされているものではなく古いバージョンのライブラリをダウンロードしてしまったことの副産物でした。これは、トランスクリプトを読んでいたエンジニアが、別の依存関係がダウンロードされていることに気付いたことで発見されました。彼らは今では、本番に合わせて依存関係を pin した Docker コンテナを構築しています——発見エージェントと検証エージェントが、攻撃者が触れるのと同じアーティファクト上で動くようにするためです。*

サンドボックスは、本番環境に十分忠実であることが重要です。依存関係 (キューやデータストアなど) を除外すると、本番に存在しうるバグを過小報告することにつながります。逆に、本番側の防御 (WAF や認証ゲートウェイなど) を無視すると、本番環境では既に緩和されているエクスプロイト不可能な発見をモデルが報告することにつながります。

とはいえ、クラウド依存・データストア・その他の現実世界の複雑さのために代表的なサンドボックスの構築が現実的でない場合は、サンドボックスを後回しにして発見のステップ (後述) から始めても構いません。PoC をサンドボックスで実行する必要は必ずしもありません。フロンティアモデルは、ソースコードを分析するだけでも脆弱性を見つけるのが得意です。私たち自身を含むいくつかのチームが、これが有効であることを確認しています。トレードオフは検証フェーズにあります——稼働するターゲットがなければ、PoC で発見を証明できないので、検証により多くの時間を確保しましょう。発見事項のボリュームがサンドボックスを正当化できるようになってから、サンドボックスに投資するのも手です。

**リファレンスサンドボックスについては、[ハーネスの `README.md`](https://github.com/anthropics/defending-code-reference-harness/tree/main/harness) を参照してください。** この実装では、エージェントとターゲットは gVisor で隔離されたコンテナ内で動作し、egress はモデル API のみに制限されています。ターゲットは特定のコミットに pin された Dockerfile からビルドされ、[`setup_sandbox.sh`](https://github.com/anthropics/defending-code-reference-harness/blob/main/scripts/setup_sandbox.sh) がセットアップフェーズを担当します。

## **3. 発見: 豊富なコンテキスト、より短いプロンプト、有用なツールを与える**

発見エージェントには、脅威モデル、アーキテクチャドキュメント、過去のスキャン結果など、必要に応じて読み込めるコンテキストへのアクセスを与えましょう。エージェントが信頼境界やシステムの実際のデプロイ形態を理解していれば、そのシステム固有の脆弱性をよりよく特定できます。

私たちは、発見フェーズではフロンティアモデルがますますシンプルなプロンプトの恩恵を受けることを発見しました。直感に反するようですが、より処方的なプロンプトは発見を悪化させます——長いチェックリストは、モデルの創造性を減らし、新規バグの発見を減らしがちです。発見フェーズで役立ったプロンプティングのヒントをいくつか挙げます:

- **目標とコンテキストを与える。** 「なぜ」と「何を」——なぜスキャンしているのか、重要となる発見事項とはどんなものか、どのシステムをスキャンしているのか——を示し、「脆弱性をどうスキャンするか」はモデルに委ねます。フロンティアモデルはセキュリティタスクが上手くなってきており、過度に処方的にすると試す範囲が狭まってしまいます。
- **特定の脆弱性クラスを指定して頼んでみる。** 過去の CVE やコードベースの言語を踏まえて特定のタイプの脆弱性に絞り込みたい場合は、そう伝えましょう。脆弱性クラスとは何か、何をするか、どこに住みがちかを記述すれば、モデルがあなたのコードベース内でそれを認識できるようになります。
- **出力を定義する。** 事前定義したフィールドを持つ構造化レポートを依頼し、モデルの推論が各フィールドの上に積み上がるように順序付けます。フィールドの例には rationale、finding、impact、severity などがあります。弱い発見事項では早期に抜けられるよう、エスケープハッチも入れておきましょう。

モデルには、grep、glob などコードベースを検索・読み取るためのツールを与えます。また、チームが使うかもしれない SAST スキャナーやファザーといったセキュリティ専用ツールも使わせましょう。特定のタスクに必要なツールは何かをモデルに尋ね、それを利用可能にしてあげます。最後に、必要に応じてモデルにツールを構築させましょう: 最近のフロンティアモデルは、必要なツールを書くのがどんどん上手くなっています。

> *ソースコードに加えて、あるペネトレーションテストチームは、発見エージェントにリクエスト送信・レスポンス確認・トラフィックログのクエリのためのツールを与えました。その結果、エージェントは経路が到達可能かどうかを推測する必要がなくなり、進めながら稼働中のアプリケーションに対して各候補をテストできるようになり、真陽性率はほぼ 100 パーセントにまで改善しました。*

最初にモデルにシステム全体に対する 1 パスを実行させ、探索空間を分割します。たとえば攻撃面・エンドポイント・コンポーネントごとに区切ります。次に、それらの分割を並列の発見エージェントに渡し、同じ浅いバグに収れんしないようにします。最後に、システムレベルのパスを実行し、分割レベルの発見事項をコンテキストに取って脆弱性を探させます。

> *発見をブルートフォースで試したチームは、すぐに収穫逓減にぶつかりました。あるチームいわく「最初は単純に水平スケールしてエージェントを増やしてみたが、効果が頭打ちになるのを見た」。別のチームはフォーカス領域と並列エージェントを増やして「大量の issue」を得ましたが、ほとんどがお互いの重複でした。*

ターゲットを動かすサンドボックスがあるなら、発見エージェントに発見事項の PoC——スクリプト、クラッシュ入力、失敗するテストなど——を構築させましょう。PoC を作ることで、エージェントは反復しながら発見事項を絞り込めるようになり、できあがった成果物は検証エージェントに具体的な評価対象を与えます。とはいえ、エージェントが再現できなかった発見事項も、unproven のフラグを立てて報告すれば、再現率を高く保てます。

**この段階では [`vuln-scan` skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/vuln-scan) が役に立ちます。** これはあなたの `THREAT_MODEL.md` を読み、ターゲットをフォーカス領域に分割し、領域ごとに並列のレビューエージェントを fan-out します。出力は構造化された発見事項で、次のステップが直接消費できます。

## **4. 検証: エクスプロイト不可能な発見事項を除外する**

発見は再現率を最適化し、検証は*精度*を最適化します。言い換えれば、発見はできる限り多くの脆弱性を——可能性が低いものも含めて——見つけるべきであり、検証は実際にはエクスプロイト不可能な発見事項を除外すべきです。エージェントが*両方*を同じステップでやろうとすると、自己検閲してエクスプロイト可能な真陽性まで除外してしまいかねません。私たちはこれを苦い経験から学びました——発見エージェントに検証も頼んだ結果、別の検証ステップなら確認できたであろう真陽性をエージェントが除外してしまったのです。

検証エージェントは、発見エージェントから独立しているべきです。検証は、共有ファイルシステムも会話履歴もないまっさらなコンテナで実行します。検証エージェントが発見エージェントの推論にさらされてしまうと、主張をテストするのではなく単に同意してしまう可能性があります。そのため、検証エージェントには (1) 概念実証または書かれた発見事項と (2) コードベースだけを与え、発見者が見落とした緩和策 (たとえば上流のバリデーション、認証ゲート、型制約、到達不能コードなど) を探せるようにします。

検証パスが 1 回では、まだ多くのエクスプロイト不可能な発見事項が通り抜けてしまうなら、独立した複数の検証エージェントを走らせるとよいでしょう。違う角度から見たり、異なるモデルで動かしたりできます。そして多数決を取ります。発見エージェントと検証エージェントの結果を判定する別のジャッジを置くことも検討してください。

検証エージェントには、発見エージェントの発見事項を反証するようにプロンプトします。それぞれの発見事項が偽陽性だと仮定させ、その発見事項が誤りである理由を探させます。発見事項が真陽性かどうかを判定するのに使える明確な基準を含めます。発見エージェントの出力に PoC が含まれていない場合、これが特に重要になります。手動レビューの労力を減らすために、できるだけ多くのエクスプロイト不可能な発見事項を除外することを目指しましょう。

> *私たちが協働してきたチーム全体で、敵対的な検証エージェントを追加すると発見フェーズからのエクスプロイト不可能な発見事項の比率がおよそ半減しました。その検証エージェントにエクスプロイトを確認する概念実証の構築も要求すると、偽陽性率はほぼゼロにまで下がりました。これら 2 ステップを合わせることで、後段のトリアージとパッチ適用の負荷を大幅に下げることに繋がりました。*

本番環境をサンドボックスで十分に再現できるのであれば (ステップ 2 を参照)、検証エージェントには再現可能な概念実証 (PoC) を構築・実行するようプロンプトしましょう。PoC が動けば、その発見事項はエクスプロイト可能と結論できます。注意したいのは、その逆は成り立たないという点です——動く PoC を作れなかったことは、偽陽性であることの証明にはなりません。

> *オープンソースパッケージをスキャンするあるチームは、ループを閉じるのに役立つ検証ステップを構築しました: パッケージをスキャンし、概念実証を生成し、そのパッケージを利用するモックアプリケーションをデプロイして PoC をトリガーする、というものです。彼らの考えは「バリデーションが最大のボトルネックであり、PoC がそのバリデーションだ」というものでした。*

## **5. トリアージ: 根本原因で重複排除し、前提条件と影響でランク付けする**

検証が発見事項のエクスプロイト可能性を確認するのに対し、トリアージはパッチ適用の優先順位を評価します。以前は、発見により多くの労力がかかっていたため、バグを見つけたエンジニアがトリアージも行っていました。今ではモデルが昼休み前に 100 件もの候補を発見できるため、トリアージがボトルネックになっています。

適切なトリアージはアラート疲労を防ぐのに役立ちます。重複していたり深刻度が誇張されていたりするバグを大量に提出すると、プロダクトエンジニアはそれらを読まなくなってしまうかもしれません——たとえ即時のパッチ適用が必要なものであっても、です。オープンソースのメンテナは、トリアージされていない発見事項に圧倒されやすい立場にあります。彼らのソフトウェアに依存する多種多様なユーザーからレポートが届くからです。

> *複数のチームが同じ教訓を共有してくれました: 大半がエクスプロイト不可能な発見事項の山をプロダクトエンジニアに送れば、彼らはレポートへの信頼を失い、見るのをやめてしまうということです。彼らはまた、critical と high の発見事項を優先することで、下流のエンジニアを圧倒しないようにもしています。別のチームは、既存のバックログ——以前のスキャナー・以前のモデル・バグバウンティ受付からの未解決の発見事項——にモデルを向けることで成果を上げ、何百もの古い項目を数日でクリアしました。*

発見事項を重複排除するには、根本原因を考慮しましょう。スキャナーは 1 つのバグを複数のコールサイトでフラグしたり、単一の根本原因に対する複数の症状を報告したりすることがよくあります。実践的なアプローチはこうです: まず、安価な決定論的パスを使う——同じファイル、同じカテゴリ、脆弱性の行番号が互いに 10 行以内、というものです。続いて、残ったものに対してモデルに定性的なルールを適用させます:

- **重複として扱う**: 同じ根本原因が異なる言い回しで書かれている; 同じ脆弱性が複数のコールサイトで報告されている; 全体的な保護 (認証チェックなど) が欠如していることがエンドポイントごとに報告されている; 原因とその結果が同じ経路でフラグされている。
- **別物として扱う**: 同じファイル内の異なる脆弱性クラス; 異なる変数が異なるシンクに到達している; 1 つのヘルパー内に独立した 2 つのバグがある; 同じチェックが 2 つのエンドポイントで欠落していて、それぞれに独自の修正が必要。

ハーネスが発見事項ごとに PoC とパッチを生成するのであれば、ある発見事項に対するパッチが他の発見事項の PoC も無効化するかどうかを確認するのも、発見事項の重複排除のもうひとつのアプローチです。

重複排除の後は、以下に基づいて各発見事項の深刻度を評価します:

- **到達可能性。** 攻撃者は実際のエントリーポイントからこのコードに到達できるか、それとも内部コードやエンドポイントからしか到達できないか?
- **攻撃者の制御。** 信頼されていない入力が無傷でシンクに到達するか、それとも上流で何かがそれをサニタイズまたは制約するか?
- **前提条件。** バグをトリガーするために何が必要か: デフォルトでない設定、特定のフィーチャーフラグ、攻撃者が当てなければならない狭い時間枠?
- **認証。** 認証されていない攻撃者がトリガーできるか、それともログイン済みユーザーや管理者を必要とするか?
- **読み取り対 書き込み。** 攻撃者はデータを読めるだけか、それとも変更もできるか?
- **影響範囲。** PoC が発火したら、誰が影響を受けるか? 1 ユーザーか全ユーザーか、1 テナントかプラットフォーム全体か、ユーザーランドかカーネルか?

ルーブリックをスコアに変換するには、深刻度を割り当てる前に各問いへの回答をモデルに書き出させましょう。先に証拠を通すことで、モデルがバグクラス (「SQL インジェクションだから critical」) にアンカリングしてその深刻度に合わせて値を膨らませる、ということを防げます。出発点としては: 前提条件ゼロで認証なしのリモートアクセスは critical または high。1〜2 個の前提条件、または認証経路を要するものは medium。3 個以上、またはローカル限定は low。閾値はあなたのシステムに合わせて調整しましょう。

モデルはコンテキスト不足のために深刻度を誇張するかもしれません。攻撃者が実際にどの入力を制御しているのか分からなかったり、補償的なコントロールが見えなかったりするからです。前者の例として、SQL インジェクションは、認証されていないリクエストでトリガーされる場合は critical ですが、管理者専用の config ファイルでトリガーされる場合は問題になりません。後者については、エクスプロイトを防ぐ上流の WAF や認証は、ソースコード単体からは見えないかもしれません。

解決策は、トリアージ中に脅威モデルを与えて、システム内のどのタイプの脆弱性を気にする／気にしないのかをモデルに伝えることです。たとえば「私たちは認証済みクライアントを信頼する」と明示するだけで、critical の 1 クラスを丸ごと単純化または除去できる可能性があります。

> *あるチームは、モデルが何か検証するものに根ざしていないか、脅威モデルの一部として期待されているかどうかについてより多くのコンテキストがないと、しばしば自信過剰になることを発見しました。彼らの対処法は、発見エージェントと同じ脅威モデルをトリアージエージェントにも与えることでした。*

**[`triage` skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/triage) を試してみてください。** これは検証とトリアージの両方を行います: 発見事項ごとの多数決検証、実行をまたいだ重複排除、導出されたエクスプロイト可能性による再ランク付けです。出力は、生のダンプではなく、短くランク付けされ担当が割り当てられたリストになります。

## **6. パッチ適用: ループを閉じて、次のサイクルのためにコンテキストを改善する**

パッチ適用は、ループを閉じて脆弱性を修正する段階です。同時に、検証済みの発見事項に基づいて脅威モデルを改善する——信頼境界やより精査が必要なコンポーネントを更新する——のにも役立ち、過去の発見事項を次のスキャンのコンテキストに送り込みます。各サイクルがコードベースをより堅牢にし、次のスキャンをよりよく情報武装させてくれます。

パッチを当てる前に、既存のコードでは失敗する新しいテストを書きましょう。そして修正を実装し、同じテストが今度はパスし、他に何も壊していないことを確認します。(そうです、これはテスト駆動開発です)。テストを追加しないと、修正がひそかにリグレッションする可能性があり、そのバグが本物だったことを後から証明するのが難しくなることがあります。

> *あるペンテスターは、生成されるパッチに一貫性がない——良いものも悪いものもある——状態が続いたものの、パッチ適用後のコードに対して概念実証を再実行することでパッチを検証するようハーネスにモデルへ伝えさせたところ改善したと話します。モデルに反復するためのフィードバックを与えることで、パッチの品質が一気に向上し、人間レビューの時間を節約できました。*

モデルは、根本原因ではなく特定のコールサイトに対して狭く発見事項に対処してしまうことがあります。「根本原因を特定して修正してほしい」と単にプロンプトするだけで効果的です。そして、モデルにバリアントを 2 つのレベルで探させます: (1) 同じパターン——同じ不具合のあるコードの他のコールサイトやコピーが他にあるか、(2) 同じクラス——1 つの SQL インジェクション脆弱性を持つコードベースは、より多くの SQL インジェクション脆弱性を持っている傾向がある、というものです。検証済みの発見事項とパッチを脅威モデルに反映し、ループを閉じましょう。

パッチを出荷する前に、敵対的なチェックを実行しましょう。新しい発見エージェントに攻撃者としてパッチを探らせ、パッチが網羅的であることを確認します。次に、過剰に侵襲的なパッチに対処するために、生成されたパッチを単純化します。最小限のパッチはレビューが容易で、新たなバグを持ち込む可能性も低くなります。根本原因を修正する最小限の変更——リファクタリングなし、ついでのクリーンアップなし、再フォーマットなし——となるようプロンプトしましょう。

> *あるチームの最もよくあるパッチ失敗について: 「推奨されるパッチは、できる限り制限的になりがちで、他のサービスとの接続を壊してしまう点まで突き詰めてしまうことがあります。問題には対処できても、そもそもサービスが動くために必要な依存関係を壊してしまうのです」。*

各パッチは、安価なものから順にチェックのラダーで検証できます:

1. **ビルド。** パッチがコンパイルされ、新しいテストがパスする。
2. **再現を試みる。** 元の PoC が動かなくなっているはず。これは効果のないパッチを捕まえます。
3. **リグレッションをチェック。** 元のテストスイートが依然としてパスする。これは壊れているか過剰に制限的なパッチを捕まえます。
4. **再攻撃。** 新たな発見エージェントが敵対的なチェックを実行する。これは不完全なパッチを捕まえます。

最後に、モデルがパッチを書けるとはいえ、それを所有するのは依然として人間でなければなりません。生成されたパッチは予測可能な形で失敗し得ます——根本原因ではなく症状を修正する、正当な入力をブロックする、依存サービスへのアクセスを取り除く、などです。目標は、各パッチを可能な限り検証して、人間のレビューの労力を減らすことです。そして、変更受領・コードスタイルといったモデルが気付いていないかもしれないニュアンスに開発チームが集中できるようにし、パッチへの修正は最小限のレビューと更新で済むようにすることが狙いです。

**[`patch` skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/patch) を試してみてください。** これはトリアージの出力を消費し、発見事項ごとに候補となる diff を生成します。独立したレビュアーエージェントがそれぞれをチェックします。

## **始めるには**

まず、ループを自分で動かしてみてください。[`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness) をクローンし、Claude Code 内で `run /quickstart` を実行します。脅威モデリングからスキャン、トリアージまでを、デモターゲットに対する対話的なワークフローで案内します。このリポジトリには、自律ハーネスと、あなたの環境に合わせてハーネスを更新する /customize skill も含まれています。

そして、あなた自身のコードでそれを動かしてみてください。サービスやパッケージをひとつ選びましょう。コードとドキュメントから脅威モデルをブートストラップし、インタビューを行います。自分たちの環境のサンドボックス構築に投資します。スキャンします。発見事項を独立したエージェントで検証します。あなたの基準でトリアージし、high 以上にランク付けされたものをすべてレビューします。パッチを当てます。その後、定期的に再スキャンします。

最初のスキャンでは、想像以上に多くの発見事項が浮かび上がるはずです。そのほとんどは検証とトリアージを要します。スキャンの追加に予算を割く前に、スキャンの*後*のパイプラインに予算を割きましょう。

役に立つかもしれないリソース:

- [Claude Security](https://www.anthropic.com/product/security): Anthropic のエージェント的脆弱性検出とパッチ適用のためのマネージドプロダクト。
- [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness): 対話的ワークフロー用 skill と自律実行用のデモハーネスを含むコンパニオンリポジトリ。
- [`claude-code-security-review` action](https://github.com/anthropics/claude-code-security-review): すべてのプルリクエストで Claude をセキュリティレビュアーとして動かす Github Action。
- [Threat Intelligence Enrichment Agent](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent): 侵害指標を脅威インテリジェンスフィードと突き合わせて強化するエージェントを構築するためのクックブック。
- [Vulnerability Detection Agent](https://platform.claude.com/cookbook/claude-agent-sdk-06-the-vulnerability-detection-agent): 脅威モデルを構築し、脆弱性をスキャンし、発見事項を構造化レポートにトリアージするエージェントを構築するためのクックブック。

## **前に進む**

私たちは、モデルがコードの中の [脆弱性を発見し悪用する](https://red.anthropic.com/2026/exploit-evals) のはますます容易になっていると考えています。だからこそ、防御者としての私たちの仕事は、敵対者が悪用する前に自分たちのコード内の脆弱性を発見し修正することです。あるチームはハーネスをイベントに接続するところまで進んでいます——バグバウンティのレポートが自動的なバリアント解析をトリガーしたり、セキュリティレビューがスキャンをトリガーして候補となる発見事項を添付したり、検証済みの脆弱性が静的解析ツールを更新して将来同じことが起きないようにしたり、といった具合です。

この仕事は重要で、賭け金も高い。けれども、適切にやれば、それはより大きな、より希望に満ちたシフトの始まりです——攻撃者が悪用する前に脆弱性を発見し修正することが*できる*ようになる世界への、です。
