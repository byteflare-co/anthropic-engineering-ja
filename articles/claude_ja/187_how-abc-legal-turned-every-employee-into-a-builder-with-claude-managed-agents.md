# ABC Legal は Claude Managed Agents で全社員をビルダーに変えた

米国の法的文書送達企業 ABC Legal の CTO である Brandon Fuller が、今年初めに社員 1,100 人へ [Claude Enterprise](https://claude.com/solutions/enterprise) を展開したとき、すぐに手応えがありました。送達（service of process）、eFiling、出廷弁護士（appearance counsel）業務に加え、マーケティング、コンプライアンス、財務など、社内のあらゆるチームが、指示されたわけでもないのに自発的に自動化を構築し始めたのです。

「ユーザーが一気に飛びつきました」と Fuller は振り返ります。「コネクタやツールの使いやすさを目の当たりにして、組織中の人たちが、これまで一日の大半を奪っていた作業を自動化し始めたんです。」

これは、どの CTO も望むような定着ぶりでした。しかし Fuller は、さらに先へ進む機会を見出しました。ABC Legal が、バージョン管理され、観測可能で、常時稼働する AI エージェントの群れ（フリート）も運用できたらどうだろうか、と。

その構想の鍵はインフラでした。初期のエージェントは、作った人が置いた場所、つまり個人のデスクトップ上のスケジュールタスクとして存在していました。これを個人のマシンから移せば、無人で稼働させられるうえ、何が構築されたのか、いくらかかっているのか、昨夜ちゃんと動いたのかを Fuller が一元的に把握できるようになります。

そこで彼は [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) を導入しました。共通のデプロイ構造、共有ワークスペース、単一の監査・課金の窓口、そして個人のノート PC ではなくクラウド上で常時稼働するエージェントです。

2026 年 7 月時点で、Fuller と ABC Legal のチームは次の成果を記録しています。

- Managed Agents で構築され本番稼働しているエージェントが 50 以上
- 本格的な最適化の前の段階で、一部のエージェントが担う人手の作業のコストを最大約 50% 削減
- 全部門で約 310 人の社員が日常業務に Claude を利用

ここでは、彼らがどのようにしてそこに到達したのか、そしてその過程で何を学んだのかを紹介します。

## 熱意からエンジニアリングへ：すべてのエージェントをソフトウェアとして扱う

Claude Managed Agents を初めて導入したとき、Fuller はチームにすべてのエージェントをコードとして定義させました。彼は、それがエージェントにとって自然な形だと考えています。彼の説明によれば、「エージェントは結局のところ構造化されたテキスト、つまりプロンプトと設定にすぎません。テキストであるものなら何でもリポジトリに置けて、会社全体がそれを見て、レビューして、改善できるのです」。エージェントのプロンプト、ツール一覧、スケジュール、認証情報、メモリはすべて設定ファイルにまとめられ、会社のソフトウェアと同じ git リポジトリで管理されます。エージェントに対する変更は、誰かが承認したプルリクエストを通じてしか行われません。これにより、すべてのエージェントにバージョン履歴、コードレビュー、ロールバック、監査証跡が備わります。

彼は 1 週間かけて、2 つのテンプレートからなるスターターキットを作り、専用の git リポジトリに格納しました。1 つはイベント駆動型エージェント用で、新しい案件の到着や裁判所からの書類の返送など、何かが起きた瞬間に起動します。もう 1 つはスケジュール型エージェント用で、毎時・毎日・毎週といったタイマーで実行されます。各エージェントは標準構造を持つ独自のフォルダに置かれます。JSON の設定ファイル、Markdown で書かれたシステムプロンプト、デプロイスクリプト、運用ドキュメントです。main ブランチに変更をマージすると、エージェントが自動的にデプロイされます。ビルダーがソフトウェアを書く必要は一切ありません。リポジトリをクローンし、スターターテンプレートをコピーして、エージェントに何をさせたいかを Claude Code に伝えれば、設定、プロンプト、認証情報ストア、メモリといった、エージェントに必要なものがすべて手に入ります。

## 技術的な隔たりを埋める

Fuller は、財務、マーケティング、オペレーション、開発から集まった 15 人の運営委員会（ソフトウェア開発者は 1 人もいません）を招集し、リポジトリをクローンして Claude Code で Managed Agents を構築してもらいました。

目的は、非開発者でも本番用のエージェントを自分で構築できることを証明することでした。すべてのエージェントが開発チームを経由しなければならないなら、そのボトルネックが会社全体の動きの速さを制限してしまいます。これを安全にしたのは、彼らがソフトウェアを書いていたわけではないという点です。彼らは設定とプロンプトを埋めていただけで、ランタイムは Managed Agents が提供していました。

「PR が何なのかを説明しなければなりませんでした。[ソフトウェアエンジニアではない人たちの] 多くは、陸上の PR、つまり自己ベストのことだと思っていたんです」と彼は言います。「今では彼らがプルリクエストを作って、互いに送り合っています。」

1 週間以内に、15 人全員が動くエージェントを持つようになりました。そのビルダーたちは自分のチームに戻り、ほかのメンバーを指導しました。1 か月以内に、ABC Legal 全体でおよそ 50 以上のエージェントが稼働するようになりました。各エージェントには名前と担当者があり、担う仕事は 1 つだけです。

## 法的文書プロセスのほぼすべての段階にエージェントを

ABC Legal では現在、法的書類の提出プロセスとそれを取り巻く業務のほとんどの段階にエージェントが配置されています。

AI Code Reviewer は 4 つのコードベースにまたがるすべてのプルリクエストをレビューし、複数モデルによる分析を行って、セキュリティバグ、パフォーマンスの劣化、コミットされた認証情報を検出します。エンジニアは今では、マージする前にこのエージェントのレビューを待つようになっています。

EvidenceChain™ Delivery Agent は、アカウントマネージャーが手作業で行っていた毎週の雑務を引き継ぎました。ABC Legal は独自のサイト EvidenceChain.com を運営しており、裁判所、原告、被告は、現場で完了した送達の記録（送達担当者は誰か、いつ送達を試みたか、書類送達時の写真など）を参照できます。ある顧客が、そこから特定の記録を継続的に取り出したいと希望しました。現在はエージェントが、該当する案件のデータベースレポートを取得し、Managed Agent に組み込まれたブラウザで各 PDF を取得して、毎日顧客の FTP サーバーに届けています。これを設定したアカウントマネージャーは、それまで何かを自動化した経験がまったくありませんでしたが、Claude Code に内容を説明するだけで約 1 時間で構築しました。

eFiling Rejection Diagnoser は、裁判所が提出書類を却下すると自動的に起動し、案件の詳細を読み、裁判所の規則を確認して、約 1 分で診断結果を Slack に投稿します。以前は社員の一日のうち何時間も費やしていた作業です。案件検証エージェントは、新しく入ってくるすべての案件を裁判所の情報と照合します。ブラウザで裁判所のウェブサイトを操作し、審理や事件が適切に提出され、記載された日付に実際に行われることを確認したうえで、管轄区域、裁判所、出訴期限の時間枠にフラグを付けるなど、判明した内容に基づいて案件を調整します。

Attorney Coverage Agent は、弁護士のネットワークに働きかけて審理の担当を確保します。空き状況を確認し、弁護士にメールを送り、空き状況や料金についての返信を読み取って、コーディネーターが担当を確定できるようにします。

財務部門では、AR-remittance（売掛金入金）エージェントが入金通知メールを解析し、NetSuite の入金消込ファイルを作成して、ワンクリックで承認できるよう Slack に投稿し、その後インポートします。また毎日稼働するエージェントが、エンジニアリングの各チケットについて資産計上か費用処理かの判定を下しています。マーケティングでは Google Ads のアナリストエージェントが運用され、チャネル責任者向けに毎週推奨事項を投稿します。オペレーション部門では、Charvis というレビューエージェントが完了した送達案件をチェックしており、現在ではコンプライアンスチームの判断と約 98% 一致しています。

Service-Overdue-Nudger は、ABC Legal の業務バックログのティア 1 層、つまり本来なら人が行う反復的な一次対応を担い、段階に応じた毎日の連絡メッセージを下書きして人間の承認に回します。

## エージェントを賢くする：収集し、調整し、繰り返す

ABC Legal のエージェントは人間の監督下で動いています。実行した内容や推奨事項を Slack に投稿し、人々はスレッドで返信したり絵文字でリアクションしたりします。

![](https://assets.claude.com/8f900037eb2f484fefedada30cfe8e50e744453b.png)

社内のコードレビューエージェント Hank は、すべてのレビューを共有 Slack チャンネルに投稿します。各投稿には対象のプルリクエストと、そこから得られた件数が記載されるため、エージェントが何を判断したかの記録が公開され、検索可能になっています。

Fuller は、こうしたリアクションのデータを、無駄になっている学習シグナルだと捉えました。ただし、すべてのエージェントにそのシグナルが必要なわけではありません。フリートの大半は、誰も出力を採点しない単一タスクの実行役で、単独で動いています。採点されたフィードバックを集めるエージェントについては、ABC Legal は 3 つの役割からなるアーキテクチャを採用しています。1 つのワークスペース、環境、認証情報ボールトを共有しつつ、異なるスケジュールで動く別々のエージェントです。このパターンにより、Slack のメッセージが、バージョン管理され人間に承認されたエージェントへの変更へと変わります。

1. **Initial Agent** は実際の作業を行います。通常は案件が届いたときや書類が戻ってきたときにリアルタイムで動き、各アクションの監査証跡を記録します。
2. **Harvester** は毎時または毎日実行され、スレッドへの返信や絵文字リアクションとして Slack に寄せられた人間のフィードバックを収集します。それぞれがラベル付きのデータポイントになります。
3. **Tuner** は毎週実行され、すべてを一度に見渡して、モデルの重みではなくプロンプトや設定への変更を提案します。Tuner が行うのは下書きだけです。プルリクエストのレビューとマージは人間が行います。

![](https://assets.claude.com/be80e667d16bcafbeda2800fafdcc97e780547f2.png)

ABC Legal の自己改善型エージェントループでは、Initial Agent がリアルタイムで作業を行い、Harvester が毎時 Slack から人間のフィードバックを集め、毎週の Tuner がプロンプトと設定の変更をプルリクエストとして提案します。エージェントは、開発者がすでに使っているのと同じワークフローを通じて改善されていきます。

その一例が「deliveries-as-code」です。これは業務のルーティング方法を調整するための Fuller のエージェントシステムで、ABC Legal の 50 人規模の姉妹会社 Docketly で始まりました。Docketly は業務を「デリバリー」単位で整理しており、それぞれにルーティングと処理のための独自のルールセットがあります。約 145 のルールセットはすべて、管理画面上のレコードではなく git 上の単一の YAML ファイルとして管理されているため、デリバリーの調整はファイルを編集してプルリクエストを出すことを意味します。

このループは 4 つのエージェントで構成されています。1 つは毎週の判定を Slack に投稿し、Harvester は人間のフィードバックに基づいてリアクションをラベルに変換し、Tuner は YAML に対するプルリクエストを作成し、4 つ目のエージェントがマージされた設定を本番データベースに反映します。4 つ目のエージェントは、人間がすでにレビューし承認したものだけを実行します。実際には、誤ってルーティングされたデリバリーを指摘する絵文字リアクション 1 つが、その週のうちにそのデリバリーのルーティングルールへのマージ済み変更になることもあります。ループの中で手作業のステップはレビューだけです。

## なぜ Claude Managed Agents なのか

Fuller は、Claude Managed Agents を組織のエージェントハーネスとして採用する前に、複数のフレームワークを評価しました。彼の基準は具体的でした。バージョン管理、観測可能なセッション、ワークスペース単位の課金、モデル選択、メモリのプリミティブ、MCP 連携、そして何より、面倒を見続けなければならないインフラがないことです。

このプラットフォームの責任分担は、Fuller が望む運用の形にぴったり一致しています。Anthropic のマネージドインフラは、実行ループ、セッション、メモリ、コンソール、そしてモデルそのものといった、エージェントを動かすためのすべてを担います。ABC Legal は、プロンプト、ツール一覧、トリガーロジック、監査証跡、そして成果に対するフィードバックループを担います。

規模を拡大するうえで特に重要だった機能がいくつかあります。

- **バージョン管理:** プッシュのたびに楽観的ロック付きで新しいエージェントバージョンが作られます。ロールバックは造作もありません。
- **モデルの柔軟性:** ほとんどのエージェントのデフォルトは Claude Sonnet で、大量かつ高速なタスクには Claude Haiku、より深い推論がコストに見合う場合には Claude Opus を使います。モデルの切り替えは 1 行の変更で済みます。
- **MCP 連携と認証情報ボールト:** エージェントは ABC Legal 自身のプラットフォーム（100 以上のツールが利用可能）、レポーティング用の Metabase、ヒューマン・イン・ザ・ループのやり取りのための Slack、プロジェクト管理用の Atlassian に接続します。
- **スケジュールデプロイ:** 定期実行のエージェントは Bitbucket Pipelines を通じて cron スケジュールで動きます。Bitbucket Pipelines はすでにリポジトリへのアクセス、シークレット、課金を扱っています。

ABC Legal は AI への支出を 1 ドル単位で追跡し、ベンダー、ツール、チーム、ユースケースごとに分けて把握しています。春にかけてフリートが稼働していくにつれて支出は増加しましたが、7 月には利用が伸び続ける一方で支出が減少に転じました。これは後述する効率化の取り組みの成果で、多くのエージェントが担うタスクのコストは約 50% 削減され、全部門で約 310 人の社員が Claude を利用しています。

同社のコストへのアプローチは意図的なものです。リターンが測定可能な、業務特化型（バーティカル）のツールやエージェントに支出を寄せる一方で、汎用的（ホリゾンタル）なチャットやアイデア出しの利用は幅広く保ちつつコストを抑えています。ほとんどのエージェントはヒューマン・イン・ザ・ループの形で始まります。エージェントが案件やチケットを確認して推奨を出し、何かが実行される前に人がそれをレビューします。推奨は案件内に保存されてバナーとして表示され、担当者が業務の流れの中で承認または却下できるようになっているか、もしくは Slack チャンネルに投稿され、人々がスレッドで返信できるようになっています。こうした反応が良い判断と悪い判断のラベル付きデータセットを形づくり、それが Harvester と Tuner のループに供給されるとともに、チームが評価（eval）を書いて、フロンティアモデル間でエージェントをベンチマークすることを可能にします。特定のタスクにおいてエージェントが人間と同等以上であることが証明されると、自動化モードに移行して自律的に動くようになります。その後も同じ測定の枠組みの中にとどまり、パフォーマンスに変化がないかが監視されます。

ABC Legal が追跡している指標は効率比、つまりエージェントがもたらす価値を、その運用コストと比べたものです。各 Managed Agent は実行のたびに、自身の生み出した価値を時間とドルの単位でデータウェアハウスに報告します。エージェントは J カーブを描きます。導入当初は大きなモデルで動いているため赤字から始まることが多いものの、チームが eval を書き、より安価で高速なモデルに移行し、トークンを削減していくにつれて黒字に転じます。

## エージェントのフリートを展開するためのベストプラクティス

AI、特に Claude Managed Agents を展開してきた経験から、Fuller はこの技術を使ううえでのいくつかの実践的な原則にたどり着きました。

- **すべてをコードとして考える。** 「コードは構造化されたテキストにすぎません。LLM はテキストのエンジンです」と彼は言います。「ビジネスのより多くをリポジトリ内のテキストに変えられるほど、エージェントがもたらすレバレッジは大きくなります。」これは従来のソフトウェアだけでなく、プロンプト、スキーマ、ディスパッチルール、通知テンプレート、業務設定にも同じように当てはまります。
- **ヒューマン・イン・ザ・ループから始める。** すべてのエージェントは、人間のレビュー用に推奨を投稿するところから始まります。人間の判断と一貫して一致することを示して初めて、独立して行動する資格を得ます。「すべてのエージェントは、単独で動く前に信頼を勝ち取ります。最初からそうなっているわけではありません。」
- **PR をコントロールの手段にする。** 「ある判断にエージェントを関与させたいなら、その判断をプルリクエストのような形にしてください。」行単位のコメント、承認ワークフロー、改ざんできない監査証跡はバージョン管理によって無償で手に入り、AI によるレビューとも人間によるレビューとも自然に組み合わせられます。
- **フィードバックループに投資する。** Harvester と Tuner のパターンにより、エージェントは再学習なしで改善されます。Slack の返信や絵文字リアクションが構造化されたシグナルとなり、プロンプトや設定の変更へとフィードバックされます。そのすべてが、人間がすでに使っているのと同じプルリクエストのワークフローを通じて行われます。
- **スケジュールタスクの回り道はしない。** ABC Legal は Managed Agents に移行する前に、スケジュールタスクやローカルのルーティンの構築にかなりの時間を費やしました。主な理由は、当時 Managed Agents がベータ版として公開されたばかりだったからです。Fuller の今のアドバイスは、最初から Managed Agents を使うことです。
- **障壁は AI ではなく git だと心得る。** 難しかったのは AI そのものよりも、ビジネスユーザーにリポジトリのクローンや Git とプルリクエストでの作業に慣れてもらうことでした。結果的にうまくいき、しかも速かったものの、本当の障壁ではありました。Fuller は、ツール自体でこれがもっと簡単になることを望んでいます。
- **すべてのタスクにエージェントが必要なわけではない。** コストは現実のものなので、すべてのチームがコストに対する価値という観点で考えなければなりません。本当に時間を節約したり自動化を生み出したりする、扱いやすい課題を選び、あるタスクはエージェントに任せる価値がないと言える姿勢を持つことが求められます。

## 今後の展望

ABC Legal のエージェントフリートは成長を続けています。進行中のプロジェクトには、送達写真のレビュー担当、PagerDuty のトリアージエージェント、毎日の KPI ダイジェスト、既存エージェントへの Tuner ループの拡張などがあります。

チームはまた、さらなる「X-as-code」の候補も洗い出しています。通知テンプレート、イベントのルーティングルール、ディスパッチロジックなど、エージェントが読み取り、推論し、改善を提案できるようリポジトリに移せるものです。

Fuller はこう語ります。「私たちが目指しているのは、AI に支えられ、自走できるビジネスです。そして社員は、その舵取りに専念できるようになるのです。」
