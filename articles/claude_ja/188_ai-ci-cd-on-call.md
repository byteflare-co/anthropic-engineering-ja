# Claude on call: Claude Tag が Anthropic の CI/CD 障害の一次対応者を務める仕組み

*[セットアップキットを使って、あなた自身の Claude オンコールを構築しましょう](https://github.com/anthropics/oncall-kit)。*

## CI/CD のための AI インシデント対応: Anthropic における Claude のオンコール

数週間前、私がオンコール当番だったとき、夜 10 時に同僚から Slack でメッセージが届きました。新しいサービスで約 44 件のテストが実行されていない、という内容です。

以前であれば、私はしていたことを中断し、ノート PC の前に座り、うんざりとため息をついてから、1 時間がかりの調査と修正のプロセスに取りかかっていたでしょう。しかし今では、私のワークフローはまったく異なります。@Claude を呼び込み、何が見えるかを尋ねるのです。

このケースでは、Claude はその日の朝にある feature flag がオンになったタイミングでテストが消えたこと、そしてそれを元に戻しても安全であることを突き止めました。私は同僚にフラグを戻すよう頼みました。その 3 分後、Claude が Slack で私に連絡してきて、スキップルールが確かに削除され、エラー率がベースラインに戻ったことを確認してくれました。

![](https://assets.claude.com/f5b4aa5251da65b25186018374984cef9d44996d.png)

わかりやすさのため、実際のやり取りを再構成しています。

ここ数か月、Claude Tag は Anthropic における CI/CD 障害のオンコール一次対応者を務めてきました。これは私たちのプライベートな時間を守ってくれただけでなく、すべての CI インシデントに即座に対応する一次対応者をもたらしました。最近のインシデントのうち状況報告が作成されたものについては、そのすべてで Claude が最初の状況報告を書いており、**通常は 15 分以内に最初の分析を公開しています。**

本記事では、私たちが何を構築し、それがどのように機能するのかを順に説明します。あなた自身でも構築して、当番が回ってくることへの憂鬱から解放されるようにするためです。

## **私たちの Claude オンコール構成**

インシデント対応プロセスの各段階に入る前に、ここで構成の全体像を説明しておきます。詳細を埋めていく際に、全体像を念頭に置いていただけるようにするためです。

オンコールエージェントには、何が行われたかを覚えておくための**メモリ**、調査・理解・行動するための**接続とアクセス権**、いつ作業に戻るべきかを知るための**スケジュール**、そして何をすべきかを知るための**指示**が必要です。

[Claude Tag](https://claude.com/product/tag) は私たちのオンコールエージェントの基盤です。Claude Tag はオンコール用 Slack チャンネル全体にわたってメモリを保持し、インシデント対応中にターンごとの指示を与えるためのインターフェースを提供します。また Claude は、オンコールチャンネルやその他のチャンネルでのイベントにリアルタイムで反応します。ルーティン、つまり Claude が定期的に実行するアクションのスケジューリングもこのチャンネル上で行われ、「毎週月曜日の東部標準時 9:00 に CI の引き継ぎを実行して」のような自然言語のプロンプトで設定できます。

[Claude Tag は専用のサービスアカウントを持ち](https://claude.com/resources/articles/agent-identity-access-model)、Datadog や Grafana など Anthropic の CI エンジニアが必要とするツールへのアクセス権を持っています。これは管理者がチャンネルに対して一度設定しただけです（[設定方法はこちら](https://claude.com/docs/claude-tag/admins/setup-overview#choose-which-tools-to-connect)）。

オンコールチャンネルに加えて、同じく Claude Tag がメンバーになっている他の関連チャンネルも Claude が監視するように設定しました。これにより、サービスアラート、設定変更、PR の更新といった追加のコンテキストを得られます。

常設の指示は、スキルとして Markdown ファイルにまとめ、GitHub リポジトリにコミットしています。こうすることで、複数のチームメンバーが改善を重ねられ、変更をコードと同じように管理できます。そこには、ルーティングの指示、ポリシー、そして自己改善ループの一部として学んだ教訓のログといった重要な情報も含まれています。

この構成の構築にかかったのは数日ではなく数時間でした。同様のエージェントを始める助けとなる汎用的な[オンコールセットアップキット](https://github.com/anthropics/oncall-kit)を GitHub で公開しています。このキットは、あなたのチーム自身のインシデント履歴をトリアージ用のプレイブックに変換し、インシデントチャンネルに診断・エスカレーション・学習を行う読み取り専用の Claude を用意します。[架空のチームの履歴に対して実行される様子](https://github.com/anthropics/oncall-kit/blob/main/test-fixtures/RUNBOOK.md)を約 10 分で確認できます。

手順を TL;DR 形式でまとめると次のとおりです。

- [Claude Team または Claude Enterprise](https://support.claude.com/en/collections/9387370-team-and-enterprise-plans) プランが必要です
- 組織のオーナーが、Claude Tag を通じてオンコール用 Slack チャンネルに Claude を追加する必要があります
- 組織のオーナーは、オンコール用 Slack チャンネル内の Claude を適切なコネクタや GitHub リポジトリに接続し、[Claude Code Remote](https://code.claude.com/docs/en/remote-control) をセットアップする手助けも必要です
- インシデントチャンネルに Claude を追加し、インシデントを監視して即座にトリアージするよう指示します

それでは、インシデントの各段階でこの変革がどのようなものになるのか、詳しく見ていきましょう。

## **検知**

Claude はインシデントへの対応方法を変えるだけでなく、そもそもインシデントを検知する方法も変えます。以前は、インシデント検知には大きく 2 つの失敗パターンがありました。

1 つ目は、人間が常に完璧なしきい値を持つ完璧なルールを先回りして設定するのは難しい、ということです。トラフィックパターンを分析するのに十分なデータがない場合は、なおさら困難です。

これに対処するため、新しいサービスの最初の数日間は Claude にデータと受信アラートを分析させ、追加のルールを提案させたり、範囲が広すぎる・狭すぎるルールを微調整させたりしています。

インシデント検知におけるもう 1 つの大きな失敗パターンは、アラート疲れでした。発火するすべてのアラートを確認・精査するのは退屈な作業です。しかし Claude は人間と同じようには疲れません。

Claude は各アラートチャンネルで関連するすべてのアラートを監視し、[ルートの oncall.md ファイル](https://github.com/anthropics/oncall-kit/blob/main/templates/ONCALL.md)の基準に照らして、朝まで待てるものか、オンコール担当者を呼び出す必要があるものかを判断します。たとえば、データ分析に基づいて調整されたファイル内のルールは「エラー率が 5 分以上にわたって 2% を超え、かつ既知のデプロイ時間帯でない場合はオンコール担当者を呼び出し、そうでなければ lessons.md に書き込む」といったものになります。

Claude のオンコールアラートプロセスがトリガーされる経路は、ほかに 2 つあります。

- CI チームのメンバーがオンコールチャンネルで問題を報告する場合。冒頭の 44 件のテストが消えた例がこれにあたります。
- 社内の誰もが社内ページからインシデントを起票できます。それが CI インフラのインシデントとしてマークされると、そのインシデント用の Slack チャンネルが作成され、オンコールの Claude が対応を引き受けます。

![](https://assets.claude.com/9d24b607b92b034267c9c6095a6bffb2030f1158.png)

ここでの重要なポイントは、アラートのプロセスは決定論的である一方、オンコールへのエスカレーションには決定論的な経路とエージェント的な経路の両方がある、ということです。

## **トリアージ**

Claude にアラートのノイズをふるい分けさせるのも 1 つの成果ですが、本当の時間短縮は調査から生まれます。Claude はインシデントが起票されてから中央値で 14 分後に、エビデンスに基づいた最初の分析を投稿します。最も速いケースでは、4 分以内に最初の報告で根本原因を特定しています。

アラートがインシデントにエスカレーションされると、多くの場合 Claude はすでに Slack チャンネルで、私たちがレビューできるエビデンスに基づいた仮説を用意しています。Claude Tag は[動的ワークフロー](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)を開始し、オーケストレーションエージェントが実行役のサブエージェントを立ち上げて、各依存関係と信頼できる情報源を調査させます。

私たちの場合、それは Grafana、ログストア、PagerDuty、GitHub、Kubernetes、そして Slack のインシデントチャンネルで、すべて [MCP Connectors](https://code.claude.com/docs/en/mcp) で接続されています。Claude は複数の手がかりを並行して追うことができ、MTTR（平均復旧時間）の短縮に役立っています。

実行役のエージェントは調査結果をオーケストレーションエージェントに報告し、オーケストレーションエージェントはその情報を統合して、まとまった SITREP（状況報告）として提示します。

![](https://assets.claude.com/64d5b3d1b39aa8a5233ea05ac12c051e1b97f297.png)

オーケストレーターと実行役のエージェントは、やみくもに探しているわけではありません。[バグの種類ごとのより詳細なリファレンス Markdown ファイル](https://github.com/anthropics/oncall-kit/tree/main/skills/triage)を備えた調査スキルに導かれています。

たとえば、シャドウダイバージェンスのバグ向けの 617 行の調査スキルには、私が典型的な調査で行うすべての手順が書き込まれています。これは、あるインシデントの際に Claude と 1 ターンずつトラブルシューティングを進め、その経験をもとに Claude にファイルを作成させたものです。

Lessons.md も Claude のトラブルシューティングを導きます。この Markdown ファイルは、これまでに解決したすべてのインシデントの継続的なログで、何が起きたか、根本原因、修正内容、そして覚えておくべき落とし穴が記録されています。Claude は自動的にこのファイルに追記していきます。新しい調査はいずれもこのファイルを読むところから始まるため、Claude の最初の仮説は最近起きたことを踏まえたものになります。

同じパターンが十分な回数現れた場合は、それを調査スキル自体に昇格させます。私のお気に入りのエントリは、Claude が私について書いたものです。私がメトリクスを確認する前に設定ファイルから思い込みをしてしまったことがあり、lessons.md には今「まずデータをクエリし、それから仮説を立てること。設定は何が問題になりうるかを教えてくれる。メトリクスは何が実際に問題になったかを教えてくれる」と書かれています。

こうしたツールとコンテキストがあっても、Claude が最初から常に正しいとは限りません。人間の直感と経験は重要です。Claude Tag を使えば、チームはマルチプレイヤーモードでインシデントのトラブルシューティングを行えます。誰でもリアルタイムに、一緒に調査の舵を取ったり仮説を追加したりできます。

![](https://assets.claude.com/9280b3233ea5f64b3e0d83ba5602905a77cd5b36.png)

わかりやすさのため、実際の会話を再現しています。

## **解決**

Claude がアラートをエスカレーションしてトラブルシューティングできるなら、修正もできるのでしょうか？この問いへの答えはチームによって異なるでしょうが、ここでは私たちのやり方を紹介します。

私たちのチームのデプロイのほとんどは feature flag の背後で行われます。私は Claude Code で、自分の権限を持ち、これらの feature flag それぞれの背後で段階的デプロイを行える別のエージェントを作成しました。

ロールアウトプロセスの最初の段階では通常、Claude がカナリアトラフィックを管理し、問題を監視し、特定の feature flag を自動的に引き上げたり引き下げたりします。これだけで 1 本の記事になるほどの内容なので、ここではこれ以上詳しく説明しません。

Claude Tag が私のチームを助けてくれるその他の解決策には、次のようなものがあります。

- Kubernetes クラスタの特定のセクションをドレインまたはコードンする必要があるかどうかを知らせてくれる
- 需要の急増に応じてインフラの一部をスケールアップする方法を指示してくれる（これはまれですが、緩和策として具体的に何をすればよいかを Claude が返してくれるのは非常に助かります）
- そして最も頻繁なのが、オンコール担当者がレビュー・マージ・デプロイして迅速に解決できるよう、PR の形で修正を提供してくれることです

## **検証、コミュニケーション、引き継ぎ**

Claude は、修正が意図どおりに機能したことを検証するために、調査で使ったのと同じ MCP Connectors やツールの多くを使用します。oncall.md の常設指示の一部として、Claude はポストモーテムを lessons.md と引き継ぎ用の SITREP に書き込みます。

複数のインシデントにわたる全体像を伝えるために、私たちは ci-weather というエージェントを作成しました。このエージェントは、各インシデントの Slack チャンネル、ビルドメトリクス、マージキューの統計、デプロイの遅延から情報を集約します。そして、社内の誰もが閲覧できる公開チャンネル 1 つに、ニュース報道風のレポートを投稿します。今では、エンジニアはマージを保留すべきか判断したいときや「CI のどこがおかしいの？」という疑問に答えたいとき、私たちに連絡する代わりにそのチャンネルを参照できます。

正直に言っておくと、レポートの形式は何度も改良を重ねる必要がありました。Claude はステータスレポートを生成するスキルを一発で作れますが、それを読みやすくするのはチーム固有のセンスです。これは配管の問題ではなく、人間同士のコミュニケーションの問題なのです。

![](https://assets.claude.com/41a169c1eb4a8d08db5297034089c893808ab77e.png)

最後に、Claude は lessons.md に自分用の記録を残していますが、私たちは毎週月曜日に人間向けの引き継ぎレポートも作成したいと考えています。Claude は日次および週次のサマリーを作成し、チームのあるメンバーが別のメンバーの作業をそのまま引き継げるようにしています。

## **インシデントの監視から、インシデント対応システムの監視へ**

当社のソフトウェアエンジニアは、2021 年から 2025 年の期間と比べて、四半期あたり平均で [8 倍のコードを出荷しています](https://www.anthropic.com/institute/recursive-self-improvement)。品質の基準は高く保ってきましたが（すべての PR には名前のある人間のオーナーがいて、すべての変更はマージに承認が必要で、すべての変更が同じ CI ゲートを通過します）、エージェント型コーディングについていく唯一の方法は、エージェント型 CI なのです。

Claude は、時間外の割り込みやインシデントのコミュニケーションといった私の仕事の退屈な部分を引き受けてくれました。その一方で、私はシステムの信頼性を本当に向上させる中長期的なアーキテクチャの変更に集中できるようになりました。

私たちが構築したものの最も良い点は、ばらばらに感じられないことです。私たちのオンコールのプロセスは Slack の中にあり、今ではそのチャンネルに Claude が加わっています。

始め方:

- [Claude Team または Claude Enterprise](https://support.claude.com/en/collections/9387370-team-and-enterprise-plans) プランが必要です
- 組織のオーナーが、Claude Tag を通じてオンコール用 Slack チャンネルに Claude を追加する必要があります
- 組織のオーナーは、オンコール用 Slack チャンネル内の Claude を適切なコネクタや GitHub リポジトリに接続し、[Claude Code Remote](https://code.claude.com/docs/en/remote-control) をセットアップする手助けも必要です
- インシデントチャンネルに Claude を追加し、インシデントを監視して即座にトリアージするよう指示します

*[セットアップキットを使って、あなた自身の Claude オンコールを構築しましょう](https://github.com/anthropics/oncall-kit)。*
