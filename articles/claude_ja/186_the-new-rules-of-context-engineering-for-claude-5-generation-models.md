以前、[最新世代の Claude 5 モデルへのプロンプトの書き方](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)と、モデルと反復的に作業しながら自分が何を作りたいのかを見つけていく方法について書きました。

しかし、Claude にメッセージを送るとき、プロンプトは Claude が受け取るコンテキストのごく一部にすぎません。コンテキストの多くは、システムプロンプト、Skills、CLAUDE.md ファイル、メモリ、その他のソースから組み立てられています。私たちはこれを[コンテキストエンジニアリング](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)と呼んでおり、Claude Code を使うときや独自のエージェントを構築するときに得られる結果に大きな影響を与えます。

プロンプトとは異なり、コンテキストは多くのリクエストにまたがって汎用的に使われるため、それほど具体的にすることはできません。特にユーザーがどんなプロンプトを送ってくるかわからない状況で、Claude 向けのこうした汎用的なプロンプトやガイダンスをどのように構築すればよいのでしょうか。

Claude 自身の能力が進化するにつれて、これは驚くほど難しくなることがあります。最近では、最新世代の Claude モデルへのプロンプトの書き方に大きな変化があることに気づきました。Claude Opus 5 や Claude Fable 5 のようなモデル向けに、[Claude Code](https://claude.com/product/claude-code) のシステムプロンプトの 80% 以上を削除しましたが、コーディング評価では測定可能な性能低下は見られませんでした。

ここでは、この新しいクラスのモデルへのプロンプトについて私たちが学んだこと、そしてそれを活かしてコンテキストエンジニアリングを見直す方法を紹介します。これらのベストプラクティスは `claude doctor` に組み込まれています。Claude Code で `/doctor` コマンドを使うと、skills や CLAUDE.md ファイルを適切な規模に整えることができます。

## Claude の枷を外す

全体として、私たちはシステムプロンプトでも CLAUDE.md ファイルや skills でも、Claude Code を過度に制約していたことがわかりました。

たとえば、社内での Claude Code の利用トランスクリプトを読むと、システムプロンプト、skills、ユーザーのリクエストが互いに衝突し、1 つのリクエストの中に「必要に応じてドキュメントを残す」や「コメントを追加しないこと」といった矛盾するメッセージがいくつも含まれているのが見られます。

![組み立てられた 1 つのコンテキストに、システムプロンプトの「leave documentation as appropriate」、skill の「do not add comments」、ユーザーリクエストの「just make it work like the old one」が含まれている図。](/media/a0c1f3923f1e92004785e35257d3feed5081264767d0a99fa5eb397e2fb6f2e2.png)

一般に Claude はユーザーの意図を汲み取って正しい答えにたどり着けますが、こうした重複・矛盾するメッセージについては、何をすべきかを決める前により慎重に考えなければなりません。

また、これらの制約はかつては最悪のシナリオを避けるために必要でしたが、その後、多くを削除して、モデルに周囲のコンテキストと判断力を使わせられることがわかりました。

さらに、Claude Code には今や多くのツールがあります。以前の Claude は、メモリ、情報、ガイダンスの源として CLAUDE.md に頼っていました。現在はメモリ、アーティファクト、skills があり、Claude はそれらを使ってセッションをまたいでコンテキストを読み込んだり共有したりする新しい方法を生み出せます。

## かつてと今

以前のコンテキストエンジニアリングのベストプラクティスの中には、いまや迷信になってしまったものがいくつもありました。たとえば次のようなものです。

![取り消し線が引かれた 6 つの古いルールと、それぞれの置き換え先: Claude にルールを与える → Claude に判断力を与える、Claude に例を与える → インターフェースを設計する、すべてを最初に入れる → 段階的開示を使う、繰り返す → シンプルなツール説明、CLAUDE.md ファイルにメモリ → 自動メモリ、シンプルな仕様 → 豊かなリファレンス。](/media/aaa82d5934e084f1e509ac1679c26d0d2338d6c995c1c2f349fc12b8a0fd1a9c.png)

### かつて: Claude にルールを与える

### 今: Claude に判断させる

Claude Code を最初にリリースしたとき、ファイルの削除のような最悪のシナリオを Claude が確実に避けるようにする必要がありました。そのため、常に正しいとは限らない、特に強いガイダンスを与えていました。たとえば、システムプロンプトでは以前こう書いていました。

*In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max. Don't create planning, decision, or analysis documents unless the user asks for them — work from conversation context, not intermediate files.*

(コードでは、デフォルトでコメントを書かないこと。複数段落の docstring や複数行のコメントブロックは決して書かず、最大でも短い 1 行にすること。ユーザーから求められない限り、計画・意思決定・分析のドキュメントを作成しないこと。中間ファイルではなく会話のコンテキストから作業すること。)

しかし、ある種のプロンプトに対しては、このガイダンスは誤りになります。ドキュメントの場合、ユーザーには独自の好みがあるかもしれませんし、非常に複雑なコードの特定の部分では複数行のコメントブロックが必要なこともあります。

それでも、古いモデルではこうしたガードレールがなければ、Claude が書くコメントは多くの場合不適切なものになっていたため、私たちはこのトレードオフを受け入れざるを得ませんでした。しかし新しいモデルはより優れた判断力を持ち、明示的なルールがなくてもこうした判断をうまくこなせます。

新しいシステムプロンプトではこう書いています: *Write code that reads like the surrounding code: match its comment density, naming, and idiom.*(周囲のコードと同じように読めるコードを書くこと。コメントの密度、命名、イディオムを合わせること。)

### かつて: Claude に例を与える

### 今: インターフェースを設計する

ツール利用における第一のルールは、使い方の例を Claude に与えることでした。最新のモデルでは、例を与えると実際には探索空間が特定の範囲に制約されてしまうことがわかりました。

![Before: いつ使うかのリストと具体例からなる約 9,100 文字の TodoWrite ツール説明。After: 「Create and update a task list for the current session」という短い説明、pending・in_progress・completed の status enum、そして in_progress のタスクは一度に 1 つだけという 1 つのルール。](/media/8bb6f9365532bb8b19443ad00f230444087a452f776232d05045f1c6c63c3de8.png)

例を使う代わりに、ツール、スクリプト、ファイルの設計についてもっと考えてください。Claude はどんなパラメータを持っていて、それらをどうすればもっと表現力豊かにできるでしょうか。

たとえば Todo ツールの例では、status を pending、in\_progress、completed の列挙型として列挙するだけで、Claude に使い方のヒントを与えられます。in\_progress の項目を 1 つに保つという指示が、私たちが求める振る舞いを定義するのに役立っています。

### かつて: すべてを最初に入れる

### 今: 段階的開示を使う

Claude Code はコーディングに特化していたため、システムプロンプトにはコードレビューや検証の方法に関する詳細な情報が含まれていました。これらは常に必要なわけではありませんが、必要なときには極めて重要な情報でした。

その後、Claude Code は段階的開示 (progressive disclosure)、つまり適切なタイミングで適切なコンテキストを読み込むことが非常に得意になりました。たとえば、検証とコードレビューはそれぞれ独自の skill に移し、Claude Code が選択的に呼び出せるようにしました。

ただし、段階的開示は skills だけのものではなく、ツールにも使っています。一部のツールは「遅延読み込み (deferred loading)」になっており、エージェントは使う前に ToolSearch で完全な定義を検索しなければなりません。これにより、必要になるまでコンテキストを消費しないツール (Task ツールなど) をより多く持てるようになります。

同じことは、あなた自身の CLAUDE.md や Skill.md ファイルにも当てはまります。よくある迷信は、そうしないと Claude が見つけられないからと、遭遇する*かもしれない*既知のプラクティスをすべてここに集約すべきだというものです。そうではなく、[適切なタイミングで読み込めるファイルのツリーを持つことを検討してください](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)。

### かつて: 繰り返し伝える

### 今: シンプルなツール説明

以前の Claude モデルでは、指示を繰り返す必要があったり、コンテキストウィンドウの最初より最後にある指示に従いやすかったりすることがありました。そのため、私たちのシステムプロンプトでは、ツール説明内の指示に加えて、メインのシステムプロンプトでもツールに言及していることがありました。

こうした重複した例は削除し、ツールの使い方に関する指示はシステムプロンプトではなくツール説明に置けることがわかりました。

### かつて: CLAUDE.md ファイルにメモリ

### 今: 自動メモリ

以前は、# ホットキーを使って `CLAUDE.md` に自動で書き込むことで、Claude のメモリに情報を保存するようユーザーに勧めていました。現在は、作業やユーザーに関連するメモリを Claude が自動的に保存します。

### かつて: シンプルな仕様

### 今: 豊かなリファレンス

プランモードでは、Claude Code は計画を記した Markdown ファイルに大きく依存してきました。これらのファイルを計画として保存しておくことで、Claude は必要なときに参照できました。同様のベストプラクティスとして、長期のプロジェクトで作業する際に Claude が参照できるよう、仕様をコードベースに保存するというものもありました。

しかし、Claude はますます複雑なリファレンスを扱えるようになっています。シンプルな Markdown ファイルの代わりに、新しいアーティファクト機能で作成した [HTML アーティファクト](https://claude.dev/blog/using-claude-code-the-unreasonable-effectiveness-of-html/)を Claude に参照させることができます。

コードの形でリファレンスを与えることもできます。仕様は詳細なテストスイートであってもよいですし、Claude が移植する別のコードベースの関数であってもかまいません。

ルーブリックもリファレンスの一形態です。ルーブリックを使うと、[動的ワークフロー](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)を利用し、そのルーブリックを持たせた検証エージェントを立ち上げることで、特定の分野におけるあなたのセンス (たとえば、良い API 設計とはどういうものか) を Claude が試し、検証できるようになります。

## あなたのコンテキストに適用する

これらをすべてまとめると、コンテキストを組み立てるときにはどのようになるでしょうか。

![スタックとして描かれたコンテキストウィンドウ: 一番上にあなたのプロンプト、その下に @ メンションされたファイル、仕様、モックアップ、コードベース、アーティファクトなどのリファレンス、さらにその下にシステムプロンプト、CLAUDE.md ファイル、skills、メモリ。](/media/6c6b396594b664244e31fe5ba0c37619accc4777be823e699906c7a641dfcc60.png)

### システムプロンプト

システムプロンプトはプロダクトのコンテキストと強く結びついています。Claude がどのプロダクトの中で動作していて、何をしているのかを伝えるものです。Claude Code の場合、これを変更することはおそらくないでしょうが、[独自のエージェントハーネスを構築している](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)なら、ここに多くの時間をかけるべきです。

### CLAUDE.md

CLAUDE.md は軽量に保ち、リポジトリの目的は簡潔に説明するにとどめ、トークンの大半はコードベース内の落とし穴 (gotchas) に使いましょう。たとえば、型を 1 つの巨大なファイルにまとめ、それ以外の場所には置かないようにコードを整理しているかもしれません。ファイルシステムやリポジトリを見れば Claude がわかるような「自明な」ことを書くのは避けてください。

段階的開示を積極的に使いましょう。たとえば、作業の検証方法について独特な指示がいくつもあるなら、検証用の skill を作成し、CLAUDE.md からそれを参照します。

### Skills

[skills は軽量なガイド](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)であり、必要なときに Claude が情報を見つけられるようにするものだと考えてください。非常に重要な領域を除き、過度に制約しないようにしましょう。

長い skill では、できる限り段階的開示を使い、多数のファイルに分割してください。

skills は、あなた自身、あなたのチーム、あるいはプロダクトに固有の意見、知識、ベストプラクティスを表現するときに最も効果を発揮します。

### リファレンス

ファイルを @ メンションすると、リファレンスとして含めることができます。リファレンスによって、Claude は現在の計画に関する詳細な情報を参照できます。

これは仕様ファイルやモックアップ、さらにはコードベース全体であることもあります。一般的には、コードとして書かれたファイルを優先すべきです。Claude が非常によく知っている言語で、明確かつ忠実度の高い指示を与えられるからです。たとえば、デザインの HTML モックアップは、デザインの説明文やスクリーンショットよりも一般的に良い結果を生みます。

## シンプルにしてみよう

システムプロンプト、skills、CLAUDE.md ファイル全体にわたって、私たちと同じようにシンプルにする必要があるかもしれません。私たちは `claude doctor` という新しいコマンドをリリースしました。これを使えば、この作業を自動的に行うこともできます。より高度なモデルへのプロンプトについて詳しくは、[Fable フィールドガイド](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)をご覧ください。
