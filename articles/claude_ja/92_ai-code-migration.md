# Anthropic は Claude Code を使って大規模なコード移行をどう進めているか

コード移行、つまり本番のコードベースを別の言語に移植するプロジェクトは、少し前まで何年もかかる大仕事でした。

この 1 か月の間に、Anthropic の個々の開発者が、Claude Fable 5、Claude Opus 4.8、そして [dynamic workflows](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) を使って、数万〜数十万行のコードから成る 10 個のコードパッケージを移行しました。本稿では、そのうち 2 つの事例と、これらのプロジェクトから得られたベストプラクティスを紹介します。

Bun の共同創業者であり Anthropic の Member of Technical Staff である Jarred Sumner 氏は、Claude Code を使って [Bun を Zig から Rust へ移行](https://bun.com/blog/bun-in-rust) しました。2 週間足らずで 100 万行のコードが生成され、マージ前の CI では Bun の既存テストスイートの 100% がパスしました。マージ後に表面化したリグレッションは 19 件で、すべて修正済みです。Rust ポートは 6 月に Claude Code の内部で出荷されました。

Anthropic Labs の共同リーダーである Mike Krieger 氏は、ある週末のうちに Python のコードベースを 16 万 5 千行の TypeScript に移行しました。数百の agents、8 つの phase gate、3 回の敵対的レビュー、そしてすべてのコマンドの出力を Python 原本と突き合わせる最終 parity check までがここに含まれます。

Claude Code の新しい機能は、これまで先送りされてきたこの種のプロジェクトの計算を書き換えます。以下は、これらの移行から学んだ内容をもとに、私たちが現在採用している 6 ステップのプロセスです。

核心にある洞察は、コードを直すのではないということです。**コードを生み出したプロセス (ループ) の方を直す** のです。

## **なぜ、そしていつ言語を移行するのか**

*どうやるか* の話に入る前に、*いつ*、そして *なぜ* それをするのかを整理しておく価値があります。この種のプロジェクトを取り巻く前提が変わってきているからです。

チームが移行を始めるのは、最初のビルド時点と現時点との間で状況が変わったからです。既知のトレードオフが足を引っ張り始めた、より良いアプローチが登場した、あるいは元のエコシステム自体が縮小しつつある、といった理由です。

たとえば Jarred 氏はもともと、C 級の性能とラディカルなシンプルさを両立できる Zig を選びました。「LLM 以前のオークランドの狭いアパートで、1 年で Bun を書く」ソロ創業者にはうってつけの選択でした。このシンプルさには既知のトレードオフがあり、[本人がその内容を書いています](https://bun.com/blog/bun-in-rust#just-be-really-smart-and-don-t-make-mistakes)。

そして 2026 年、Bun の CLI は月間 1,000 万ダウンロードを超え、Claude Code の内部でも広く使われています。

つい先四半期であれば、それらのトレードオフだけを理由にロードマップを凍結し、数四半期にわたるプロジェクトへリソースを投じるのは正当化しづらかったでしょう。言語移行は、より小さく・より速く・より安全なシステムをもたらしうるものの、そのコストを支払いたい人は誰もいません。

ソフトウェアエンジニアは、こうしたかつての巨大プロジェクトに内在するキャリアリスクとも向き合わなければなりませんでした。2 つのコードベースを何四半期も、何年も並行して維持し続けたあげく、最終的な結果が 90% のパリティに留まれば、始めたときよりも大きな頭痛のタネを抱え込むことになります。

いまや、最悪のシナリオはブランチを削除してもう一度やり直すことです。

もちろん、正当化に足るビジネスケースは依然として必要です。100 万行規模の移行が、4 年間のプロジェクトを通じて 300 万〜400 万ドルのエンジニアリングリソースを食い潰すことはなくなりましたが、それでもなお実行には数万〜数十万ドルかそれ以上のコストがかかります。たとえば Bun の移行は、59 億のキャッシュなし入力トークンと 6 億 9,000 万の出力トークンを消費しました。API 料金で換算すればおよそ 165,000 ドルです。Mike 氏のポートの主要部分は 2,700 万トークンでした。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58f8844b99cec5d277a9ee_27e78c5a.png)

*Jarred 氏の 100 万行の PR。*

**しかし、移行を正当化する理由はもはや存続に関わるレベルである必要はありません。** チェンジログに 1 年分のメモリバグ修正が並んでいる、あるいは慢性的なボトルネックが 1 つある。そのくらいで十分正当化できるようになりました。

Mike 氏のプロジェクトのきっかけはコンパイルステップでした。彼のチームが手がける社内ツールは、単一バイナリとしてユーザーへ配布されます。Python ツールチェインでそのバイナリを生成するのに 1 プラットフォームあたり約 8 分、リリースごとにビルドマトリクス全体で合計 30 分の待ち時間が発生していました。移植後は、同じコンパイルが約 2 秒で終わるようになり、バイナリ起動は 6 倍速くなり、チームは別のデプロイパイプラインを引退させることもできました。

## **なぜ AI がコード移行の計算を変えるのか**

Claude Fable 5 は、私たちの一般提供モデルの中でもっとも高性能なモデルです。Fable と Opus 4.8 は特に、subagents による並列ワークストリームを委任・指示・検証しながら、掲げた目標に向かう複数の経路を見つけ出すのが得意です。

大規模なコード移行が、こうした先進モデルにとって特に効果的なユースケースになるのは、次のような理由からです。

- **作業が並列化できる**。ファイルや crate のように、独立した単位が何千とあるため、agent 同士が待ち合わせることなく同時並行で作業できます。
- **コンテキストが明確で網羅的である。** 古いコードそのものがモデルにとってのすぐれた仕様書になります。翻訳担当 agent が従うべきガイドを作る際の中心的なリファレンスにもなります。
- **組み込みの審判が存在する**。多くの大規模コードベースには、agent が自らの仕事を検証できるテストスイートが含まれます。検証が客観的であるほど agent の実力は発揮されます。品質を人間が仲裁しなくても、モデルが正解 (ground truth) に向かって何日でも粘り続けられるからです。
- **キューが自ずと書き上がる**。コンパイラやテストの実行が失敗したら、それが次の作業項目として agent の元に流れていきます。
- **一貫性とエッジケースの扱いが求められる**: プロセスは、ドリフトが隠れる場所を残さないように組まれています。レビュアーはすべての指摘に対して根拠となるルールを引用するため、違反は静かなズレではなくキュー項目になります。そして agent がエッジケースにぶつかったときには、その修正が、以降のすべての agent が従うルールになります。

以下で見ていくように、Mike 氏と Jarred 氏はどちらも、移行プロセスの重要なステップで Fable を使いました。特に、複数のモデルクラスを組み合わせてトークン消費を最適化する **アドバイザリーパターン** においてです。

## **大規模コード移行の 6 ステップ**

*以下のプロセスは、複数の言語やシナリオに適用できるよう一般化されています。詳細については、* [*Jarred 氏のブログ*](https://bun.com/blog/bun-in-rust) *もご覧ください。*

### **前提条件**

移行プロジェクトを開始する前提として、強力な judge を用意しておく必要があります。そうでなければ、終了条件も成功の物差しも持てなくなるからです。

judge は、元のコードとターゲットのコードを対等な条件で評価できなければなりません。元の言語で書かれたテストスイートは、多くの場合、ターゲット側のコードには存在しない内部関数に依存しています。

この judge を構築するには次のようにします。

- **既存テストを分類する**。Claude を使い、どのテストが外部呼び出しとして表現可能で、どのテストが移植不可能な内部実装に依存しているかを見極めます。
- **可搬性を持たせて書き直す。** 外部向けのテストを、元のコードと移植後のコードの両方に対して実行できるアサーションへ変換します。書き直したテストがアサーションを弱めていないか、敵対的な agent に検証させましょう。
- **judge を検証する**。まず元のコードに対して走らせ、パスすることを確認します。次に、わざと壊したコードに対して走らせ、失敗することを確認します。壊れを捉えない judge は judge ではありません。

Jarred 氏は第三の言語 (TypeScript) で書かれた大規模なテストスイートを持っていましたが、大半のプロジェクトではそうはいかないでしょう。Mike 氏は Python から TypeScript への移植にあたって、実世界の 7 つのシナリオから成る parity ハーネスを作り、挙動の変化はすべてバグとみなして直しました。

各ステージの詳細に入る前に、次の図を追いかけながら読むと分かりやすいでしょう。以下はほぼ Jarred 氏の方法論に沿ったもので、各ステージにレビューとゲートがあります。Mike 氏も似たループワークフローを使い、同じような全体構造をたどりましたが、彼の場合は移行全体をエンドツーエンドで一気に走らせ、結果に基づいてルールとワークフローを改訂し、また走らせる、というやり方をとりました。結果を毎回捨てながら、3 回目の実行にたどり着くまで繰り返したのです。

### **ステップ 1 — ルールブック、依存関係マップ、ギャップインベントリを作る**

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fa78da7794274460319e_Code-migration-step1.jpeg)

このステージでは、移行の土台を作ります。単に翻訳するだけでは済まず、リファクタが必要になる箇所のインベントリ、コードを翻訳する方法を規定するルールブック、そして移行の実装ワークストリームに順序を与える依存関係マップです。

順序が重要です。ルールブックはギャップインベントリよりも先に作らなければなりません。ギャップインベントリはルールブックのデフォルトでは扱いきれないものによって定義され、両者は同時に監査されるからです。

#### **ルールブック**

[ルールブック](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/templates/RULEBOOK.md) の具体的な形は、最初に下すいくつかの重要な設計判断によって変わってきます。中でも大きいのは、新しいコードが既存と同じ構造を踏襲するのか、それとも完全に再設計するのか、という判断です。

前者 (Jarred 氏のケース) であれば、ルールブックは主に、言語間で型やイディオムを対応付けるルックアップテーブルであり、翻訳しにくい要素についてはギャップインベントリを参照する形になります。後者 (Mike 氏のケース) であれば、それは設計ドキュメントになります。

Jarred 氏は Claude と対話しながらルールブックを作り、曖昧な領域それぞれに対して方針を定めていきました。加えて、彼自身の直観に基づく 8 種類のよくある失敗モードをそれぞれレビューする、8 つの subagents も用意しました。

#### **依存関係マップ**

並列移行のためにワークストリームを効果的に切り分けるには、ファイル間の依存関係を理解する必要があります。どのファイルを先に移行すべきか、どのファイルを同じバッチにまとめるべきかを判断するためです。言語やコードベースによっては、明示的なマニフェストがあってこれが容易にできることもありますが、レガシーコードベースや C/C++・Python のような人気言語では、依存関係を自分で発見し、地図にする必要があります。

Claude Code は agents を派遣し、決定論的なスクリプトを作成・実行してこのマップを生成できます。[migration kit のプロンプト](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/prompts/01-dependency-map.md) では、review-and-fix ループを組むためのワークフローを使っています。*注: スターターキットは、本記事で示すプロセスを一般化したテンプレートです。実際のこれらのポートで動かしたものそのものではありません。*

#### **ギャップインベントリと懐疑的なレビュアー**

新しい言語には、古い言語とは異なる要件があり、それを満たさなければなりません。Zig から Rust への移行では、その差は手動メモリ管理でした (C と C++ も同様です)。たとえば以下のとおりです。

Zig

```
fn readConfig(allocator: std.mem.Allocator) ![]u8 {
    const buf = try allocator.alloc(u8, 1024);
    // ...fill buf...
    return buf; // caller must free this — but only the comment says so
}

// A caller that forgets 'defer allocator.free(buf)' still compiles — the leak only surfaces at runtime.
```

Rust

```
fn read_config() -> Vec<u8> {
let buf = vec![0u8; 1024];
// ...fill buf...
buf // ownership moves to the caller; memory is freed automatically
}
// Use it after it's moved? Free it twice? Neither compiles.
// Forget to free it? There's no free call to forget — drop is automatic.
```

Python から TypeScript への移行では、そのギャップはインターフェースと契約でした。Python は、受け入れるオブジェクトの形や、返すオブジェクトの形を宣言する契約を要求しませんが、TypeScript は要求します。たとえば次のとおりです。

Python

```
def register(handler):
    handler.setup()
    return handler.run({"retries": 3})

# Any object with .setup() and .run() works here. Which objects actually get passed in? Read the whole codebase to find out.
```

TypeScript

```
interface RunResult { ok: boolean }

interface Handler
{ setup(): void;
run(opts: { retries: number }): Promise<RunResult>;
}

function register(handler: Handler): Promise<RunResult> {
handler.setup();
return handler.run({ retries: 3 }); }

// The contract must be written down before this compiles
```

Jarred 氏と Mike 氏はどちらも、この暗黙知を捉えるギャップインベントリファイルを作りました。Jarred 氏は先にギャップを棚卸ししました (ここではその流儀を紹介しています)。一方 Mike 氏は先に翻訳し、あとから監査してギャップインベントリを作るやり方を選びました。両方が必要になることもあるでしょう。

ギャップインベントリファイルを作るための Claude Code プロンプトのサンプルは [こちら](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/prompts/02-gap-inventory.md) を参照してください。

### **ステップ 2 — ルールをストレステストする**

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fbe31db98b8b59d39ba8_MIgration-step2.jpeg)

このステップでは、より大きな移行に向けた「試験航海」となる、ミニ移行を行います。

このステップで Jarred 氏は、1 つの agent にルールブックに従って 3 ファイルを翻訳させ、別の agent には「シニアな Rust エンジニアのように」3 ファイルを翻訳させ、さらに別の agent に両者の diff を使って新しい翻訳ルールを作らせました。この段階で、1,448 ファイル全体に展開していたら大量の問題を引き起こしていたであろう、2 つの重要な問題を捕まえることができました。

プロンプトはたとえば [このような形](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/prompts/03-stress-test.md) になります。

この種のストレステストは、**構造を保った移行の場合にのみ機能します**。同じファイルの 2 つの翻訳が行単位で比較可能であることが前提だからです。ルールブックが再設計 (Mike 氏のケース) であれば、これに相当するテストは、設計ドキュメントそのものを敵対的なレビュアーで攻撃し、その後、使い捨てのエンドツーエンド実行で検証することになります。

いずれにせよ、翻訳されたファイルはすべて捨ててください。目的はルールを洗練させることであって、部分的な進捗を積み上げることではありません。

### **ステップ 3 — すべてを翻訳する**

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fd9c8899de91189a89e0_ai-migation-step4-5-6.jpeg)

残りのステップでは、同じ multi-agent ループアーキテクチャを回します。実装、レビュー、そして修正です。

実装担当の作業はより小さなモデルに任せ、レビュアーはより大きなモデルに残してもよいでしょう。たとえば Mike 氏は、メイン移行で 12 の subagents をファンアウトさせる際に Claude Sonnet を使いました。

作業キューは機械的に動くべきです。バッチスクリプトが、翻訳済みファイルがディスク上に存在するかを見て「完了」を判定し、残ったファイルを実装担当 agents 向けのバッチにスライスします。キューは毎回ディスクから組み直されるので、この設計により移行は本質的に途中再開が可能になります。

このステージでは、agent がやたらと慎重に振る舞い、作業量を絞ってしまうことがあります。その対策は、コンパイラが次のステップで間違いを捕まえてくれるという文脈を渡したうえで、あからさまで力強いプロンプト指示を書くことです。

翻訳担当が自信を持って処理できない箇所は、// TODO(port): <reason> というマーカーで印を付け、ステップ 4 で対処します。ここから先、to-do リストは自ずと書き上がっていきます。コンパイラがエラーを列挙し、smoke test がクラッシュを見つけ、テストスイートが失敗を報告してくれるからです。

2 つの敵対的なレビュアーが、それぞれ別のコンテキストで実装担当の作業を評価し、レビュアー同士の見解が割れた場合は 3 つ目の agent に持ち込みます。あるレビュアーが複数のファイルで同じ間違いを繰り返し捕まえるようになったら、その修正はファイル単位で行うものではありません。ルールブックに 1 文を書き加え、影響するバッチを再生成します。このステップを通じてルールブックは育ち続けます。コードがルールブックに反する形で手作業でパッチされることは、決して起きません。

このステップで押さえておきたい重要な設計判断の 1 つが、コンパイラの位置づけです。Mike 氏はループの内側で TypeScript コンパイラを走らせました。ユニット単位のチェックが数秒で終わるからです。一方 Jarred 氏はコンパイラをループから完全に締め出し、次のステップに回しました。cargo は数分かかるからです。

このステップでは、重い持ち上げの多くは既に終わっており、[プロンプトも短くなり始めます](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/prompts/04-translation-kickoff.md)。

### **ステップ 4、5、6 — コンパイル、実行、そして挙動の一致**

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fd76153c143199b57e1b_ai-migration-step3.jpeg)

これら 3 つのステップは同じループアーキテクチャを共有し、必要な人間の判断も段階的に少なくなっていくため、ここでまとめて扱います。

たとえば **ステップ 4** は、言語や移行の規模によっては、そのままステップ 3 に溶け込んでしまうこともよくあります。

コンパイルステップの規模と難易度によっては、agents はここをまったく回さないこともあります。Jarred 氏の場合、ワークスペース全体に対してコンパイラを 1 度だけ呼び出す orchestrator スクリプトでこれを回しました。その後、「Fixer agents」がエラーリストの上を並列で走り、敵対的レビューが並行して行われます。そしてまたビルドを回し、これを繰り返します。

エラーリストを俯瞰することは、調整が必要な構造的問題を捕まえるうえで有効です。たとえば Jarred 氏は、Zig の遅延コンパイルが許容していた循環インポートを修正した結果、Rust の module エラーが何千件も表面化するのを経験しました。彼は、どの依存を削除するか、移動するか、あるいは境界そのものを再構成するかを分類するロジックをループに組み込むことで、この問題を解決しました。

**ステップ 5** にも、コンパイルエラーリストと同じような機械的な真理の源があります。smoke test からのクラッシュです。ここでもループを整えるやり方は、問題を分類してまとめることでした。今回は原因を root cause 単位でグルーピングし、敵対的な subagents にレビューさせました。

**ステップ 6**、そして私たちの物語の最後は、2 つのコードベースにまたがってプログラムの挙動を比較することです。

これで私たちのファイルは翻訳され、コンパイルが通り、smoke test も通っています。次はファイルをシャーディングし、前提条件のステージで作ったテストスイートを走らせます。失敗は「fixer agents」に任せ、彼らは失敗したテストを両方のコードベースに照らしてレビューします。敵対的なレビュアーが、その修正をチェックします。

このループの次のステージは、[build daemon](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/scripts/build_daemon.sh) です。これは、バイナリの再ビルドを行うことを許された唯一のプロセスです。Fixer 群がパッチを書き、daemon はそれらをバッチにまとめて 1 度だけ再ビルドし、影響を受けたテストを再実行し、結果をフィードバックします。これによって、複数の agents が独立して再ビルドを引き起こしてしまうのではなく、もっとも高価なオペレーションが直列化されます。

同じ失敗が多くのテストにまたがって繰り返し起きるようになったら、修正はより上流へ移ります。バグを生んだルールそのものを修正し、そのルールが触れたファイルだけを再生成するのです。

Mike 氏のアプローチは、ここで大きな意味を持ちます。多くの開発者は、そもそも作り込まれた、あるいは移植済みのテストスイートを持っていないからです。Mike 氏は Claude に、新しいポートと元の Python コードベースの両方に対して、7 つの実世界シナリオを実行し結果を diff する小さなスクリプトを作らせました。失敗したシナリオごとに専用の fix agent を立て、7 つすべてがパスするまでループを回しました。

そして彼はさらに一歩踏み込みました。Claude 自身にエンドツーエンドのテストスイートを設計させ、夜通し自律的に走らせて、壊れたところを直しては再実行することを 4 晩繰り返したのです。その結果、どんなシナリオリストでも予測できなかったであろう小さな綻びまで拾い上げることができました。

学びは、テストスイートが欠けていてもこのステップの障害にはならないということです。審判を継承できないなら、Claude に作らせればよいのです。いずれにせよ、元のコードベースが真理の源です。

## **コード移行のベストプラクティス**

どの実行も、私たちに、前回では学べなかったことを教えてくれました。次に取り組む移行が、このガイドでは教えられない何かを教えてくれるのはほぼ間違いありません。しかし、どのプロジェクトでも通用したいくつかの実践があります。

- **このガイドを盲目的に踏襲しない。** どの移行も違います。これを出発点として扱い、あなたの具体的な移行の計画は、実行前に Claude と一緒に立ててください。
- **個々の失敗に注意を向けない。** 個々の失敗はループの仕事です。Fixer agents がそれを片付けていきます。あなたが目を向けるべきはパターンです。
- **レビューは敵対的に、検証は機械的に。** 敵対的なレビューは長時間のタスクを可能にしてくれるもので、たいていはトークン消費に見合う価値があります。判定はスクリプト — コンパイラ、diff、テストスイート — にやらせましょう。
- **なんでもかんでも最大のモデルに任せない。** トークン消費はループに集中するので、ループは意図的に設計しましょう。小さいモデルは、大量に走る実装ファンアウトを十分にこなせます。最大のモデルは、レビュアーと、他の agents が従うルールを書くところに温存しましょう。
- **人手の時間は前倒しで投下する。** もっとも時間がかかるのはルールブックとストレステストです。それ以降は、ほぼキューを消化するだけです。
- **作業キューは機械的に、そして再開可能にする。** 「done」の意味は「出力ファイルがディスク上に存在すること」であるべきです。

## **コードではなく、ループの結果をレビューする**

Jarred 氏の Bun 移行はすでに本番投入されていますが、どんな移行にもトレードオフはあります。たとえば、Rust コードのおよそ 4% は "unsafe" ブロックの内側にあり、そのほとんどは C/C++ 境界での 1 行のポインタ操作です。

しかし、新しいコードベースは計測できる形で良くなっています。チームのツーリングが検出できるメモリリークはすべて修正されました。2,000 回のビルドを繰り返すあるベンチマークでは、メモリ使用量が 6,745 MB から 609 MB へ落ちました。バイナリは Linux と Windows で 19% 小さくなりました。そして、言語をまたぐ最適化により、HTTP サービングや `next build` と `tsc` のような実世界のワークロードで、2〜5% 高速化しました。

そろそろ、あなたが長らく先送りしてきた移行についても、計算をやり直すときかもしれません。長年我慢してきたコードベースを 1 つ選び、その移行プロセスがどのようになるか、Claude に尋ねてみてください。
