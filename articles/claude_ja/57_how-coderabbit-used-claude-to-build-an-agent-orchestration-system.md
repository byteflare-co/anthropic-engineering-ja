# CodeRabbit が Claude を使ってエージェントオーケストレーションシステムを構築した方法

*シリーズ「***スタートアップはどう Claude で作るか***」では、AI で自分たちの業界を変革しているスタートアップを取り上げています。今回は、CodeRabbit が「AI がコードを生成する前にプランを立てる」エージェントオーケストレーション層をどう構築したかをお伝えします。*

| 概要 | |
| --- | --- |
| 社名 | CodeRabbit |
| 設立 | 2023 年 |
| 創業者 | Harjot Gill (CEO) |
| 技術スタック | Claude Platform、Claude Code |
| スケール | 15,000 を超える顧客にわたり、週あたり 200 万件の PR をレビュー |

AI コーディングツールは、アイデアから動くプロトタイプまでの時間を一気に圧縮しました。AI コードレビュープラットフォームの CodeRabbit は、そのスループットの上昇と並んで、別のトレンドが立ち上がってきていることに気付いています。「コンパイルが通ってテストもパスするのに、チームが本当に作ろうとしていたものになっていないコード」が増えているのです。

CodeRabbit の VP AI を務める David Loker は、その原因をモデルの上流側に位置付けています。経験豊富な開発者は、自分が持っているのと同じコンテキストをコーディングエージェントも理解しているはずだと思い込みがちで、自分にとって自明に感じられる要件を書き下しません。すると、コーディングエージェントは「もっともらしい」と判断したもので、その隙間を埋めにかかります。

そのギャップを埋めるために、CodeRabbit は Claude を使って、コードを生成する前に構造化されたプランニングフェーズを実行するエージェントオーケストレーションシステムを設計・構築しました。彼らの仮説は、「プランの質がアウトプットの質を決める」「コード生成が安くなればなるほど、間違った方向に進むコストは高くなる」というものです。

## AI コーディングにおける内部知識のギャップに対処する

CodeRabbit のチームが顧客ベース全体にわたって AI が生成した PR を調べたところ、もっとも多い失敗パターンは「コンパイルが通り、テストもパスするのに、解こうとしていた問題を解いていない」コードでした。

「開発者として経験を積むにつれて、私たちは知識を内部化していきます」と Loker は言います。「それらはすべて自分の頭の中にあり、ほかの開発者もそれを知っていると仮定してしまう。そしてその仮定を、私たちは AI システムに対してもしてしまうのです。AI も暗黙のうちに理解しているはずだ、と。そう仮定していること自体に気付いてさえいません。」

曖昧なプロンプトは、その下のシステムに対して「もっともらしい」と思うもので隙間を埋めるよう強制します。その推測は、開発者が頭に描いていたものと食い違うことが多々あります。

Loker は自身の経験を例として挙げます。サイドプロジェクトでメモリシステムを構築していたとき、彼はコーディングエージェントと数時間にわたって反復し、すべてが動く状態までこぎ着けました。それからエージェントに使い方を尋ねると、指示にはユーザートークンを渡すように、と書かれていました。ログインページは存在しません。彼はシステムにユーザーが必要だと指定はしていたものの、ユーザーがサインインする手段が必要だとは一度も言っていませんでした。エージェントがその隙間を勝手に埋めた結果、数時間分の作業は、玄関口のないプロダクトに着地してしまったのです。

「結局のところ、その上にさらに多くのものを積み上げてしまい、ずっと後になってから問題があると気付くことになります」と Loker は言います。「AI ワークフローでは、検証が遅れることは非常に高くつき得るのです。」

## AI コーディングソリューションの前段で動くオーケストレーション層

CodeRabbit が出した答えは、コード生成の前段にプランニングシステムを差し込むことでした。このシステムは複数の Claude モデルを協調動作させて要件を分析し、前提条件を洗い出してから、「何を作るべきか」「どんな制約を満たす必要があるか」を定義する構造化された実行計画を生成します。

「このプランニングシステムは、Claude Code の Plan Mode を置き換えるためのものではありません」と Loker は説明します。「Claude Code の手前で動く、より高位のオーケストレーションです。明示すべきものをすべて明示し、なされている前提条件をすべて自覚した状態で、Claude Code を非常に狭く正しい方向に向けるためのものなのです。」

アウトプットは、協働的なプロダクト要件ドキュメント (PRD) です。完全なコンテキストの上で作られ、チーム横断のステークホルダーによって検証され、実装が始まる前にレビューされたプランです。Claude Code はそのプランを受け取り、それを使って粒度の細かい実装計画を生成します。プランは「何が決まり、なぜそう決めたか」を捉える共有アーティファクトとなり、チームが手戻りを避け、後からアウトプットが当初の意図と一致しているかを検証する助けになるだけでなく、新しいエンジニアのオンボーディングにも役立ちます。

## Claude モデルファミリーを使い分けるルーティング

CodeRabbit は、コストとレイテンシを最適化するために、各モデルのティアをタスクの複雑さに合わせて割り当てています。Opus はオーケストレーションループと、問題を理解し全体の方向性を定めるという、より高位の戦略的な仕事を担います。Sonnet はそのアウトプットを受け取り、構造化されたプランニングのステップへと並べ替えます。Haiku はコンテキストの蒸留やターゲットを絞ったツール利用といった、スコープの狭い操作を担当します。問いがはっきりしていて、より小さなモデルでも十分良い答えが返せる類のものです。

「あるタスクで Haiku が Sonnet と同じくらいうまくやれるなら、Haiku を使います」と Loker は言います。「評価ハーネスが Opus にもっと余白を与えるとプランの質が改善すると示すなら、その余白を与えます。私たちは当て推量はしません。」

## プラン品質のための評価ハーネスを構築する

CodeRabbit はコードレビューのための成熟した評価システムを持っていましたが、プランニングのアウトプットを評価するためのものは何もありませんでした。そのインフラを構築すること自体が、一つのプロジェクトとなりました。

このシステムは、手でチューニングした例と手作業の検査から始まりました。チームはプラン品質の特定の次元を採点する LLM ジャッジのライブラリを開発しました。プランは最終的にコードを生み出すので、生成されたコードが動くか、余分なスコープが含まれていないか、それを得るのにどれだけのトークンを要したか、といった点も計測できます。同じタスクをプランニングステップ「あり」と「なし」の両方で走らせることで、プランニングそれ自体の価値を切り分ける手段を得たのです。

「そのプランに対してどのくらいの粒度が適切なのか、最初は分かりませんでした」と Loker は語ります。粒度を細かくしすぎると、コードベースが少し変わった瞬間にプランは陳腐化しました。粗すぎると、エージェントが前提を埋める余地が残り、それは結局プランニング層が最初に解こうとしていた問題そのものでした。ちょうどよい抽象度を見つけるには反復が必要であり、それを可能にしたのが評価ハーネスだったのです。

## コードが書かれる前にエラーを捕まえる

AI ネイティブなコーディングワークフローでは、これまでコードレビューの段階で表面化していた決定の多くが、より早い段階、つまりプランニング層でなされるようになります。コード生成が始まる前にチームがレビューして合意できるプランを作っておけば、ミスは早期に捕まえられます。

「私たちが Claude のエコシステムを使って構築したのは、チーム全体のためのプランニングシステムです」と Loker は言います。「プランそのものが品質ゲートになるのです。そのプランの質を最初に本当に高くできれば、下流への効果は非常に顕著です。最終的に出てくるコードは、はるかに良くなります。」
