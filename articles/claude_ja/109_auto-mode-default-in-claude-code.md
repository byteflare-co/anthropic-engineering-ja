# Pro、Max、Team プランの Claude Code で auto mode がデフォルトになりました

Claude Code において、[auto mode](https://code.claude.com/docs/en/auto-mode-config) をデフォルトにします。8月14日以降、Pro、Max、Team プランの新しいセッションは auto mode で実行されます。すでにご自身で別のデフォルトを設定している場合は、auto mode に切り替えるかどうかを尋ねる一回限りのプロンプトが表示されることがあります。デフォルトをピン留めしている場合、変更は何もありません。auto mode の分類器はツール呼び出しごとにわずかなトークンを追加で使用しますが、本日より、Pro、Max、Team プランの Claude Code ユーザーに対してこの分類器のオーバーヘッド分の課金を行わないことにしました。

Claude Enterprise、Claude API、AWS 上の Claude Platform、Amazon Bedrock、Google Cloud の Agent Platform、Microsoft Foundry では、管理者がこの変更を確認する時間を確保するため、auto mode は当面オプトインのままとなります。今後1か月のうちに、クラウドパートナーと連携しながら、これらすべてでも auto mode をデフォルトにし、分類器のオーバーヘッド分の課金も行わない予定です。それまでの間、Enterprise の管理者は managed settings を通じて Claude Code の auto mode をデフォルトにできます。

auto mode は、「割り込まれたくない」というユーザーの意向と、有害な行動を回避する仕組みとのバランスを取るよう設計されています。プロンプトを表示する代わりに、各ツール呼び出しを分類器に通し、不可逆的・破壊的、あるいは環境の外に向けられた行動をブロックすることを目標にしています。分類器が何かをブロックすると、Claude は通常、自力でより安全な進め方を見つけるか、あるいはユーザーに直接許可を求めます。進められない場合(3回連続のブロック、またはセッション内で20回のブロック)には、Claude Code は手動承認にフォールバックします。

私たちはここ数か月、auto mode が、プロンプトをクリックして進める平均的なユーザーと同等かそれ以上に安全かどうかを検証してきました。社内でのレッドチーム演習、第三者によるレッドチーム演習とプロンプトインジェクション評価、1,053人の有償テスターによる管理された実験、そして実際のプロダクションセッションの分析を行いました。検証したすべての指標において、auto mode は手動レビューと同等か、それを上回りました。

auto mode はまた、Claude がより長い時間にわたって自律的に作業することを可能にします。これにより、Claude Opus 5 のような長時間の作業向けに構築されたモデルを、大きなタスクで何時間も動かし続けることが現実的になります。ユーザーのオーバーヘッドを減らすことは、アウトプットの増加にもつながります。Teams および Enterprise の導入企業の中で、auto mode を使うユーザーは約25%多くの PR を出荷しています。Claude をブロックしないことで、タスクを長く中断なく実行させ、より多くの作業をこなせるようになります。Adobe、Nuro、Gusto、Garner Health の各社は、すでに [auto mode をプロダクションで運用](https://claude.com/blog/auto-mode-in-production)しています。

以下では、この変更の根拠となった安全性データと顧客の成果、そして別のデフォルトを設定したい場合の方法を紹介します。

## 手動レビューと auto mode の比較

データが示すところによると、手動レビューは習慣化しがちです。Claude Code のユーザーは、権限プロンプトの97%を承認しています。ほとんどのプロンプトは安全でありふれたコマンドに対するものだと考えられますが、これほど高い承認率は、多くのユーザーが各コマンドを吟味するのではなく、反射的にクリックして進めていることを示唆しています。これらのプロンプトは、開発者に対して1日に数十から数百もの重要なセキュリティ上の判断を求めるものであり、しばしばプロジェクトの最中に発生するため、レビューの負担がユーザーに押し付けられ、重要な何かが見落とされる可能性が高まります。データはまた、ユーザーが他の種類のダイアログに対してはより頻繁に精査し、異議を唱えることも示しています。例えば、Claude が承認を求めて計画を提示した場合、ユーザーはその39%を却下します。しかし個別の権限リクエストに対する却下率はわずか3%です。

同じパターンは設定ファイルにも表れています。2026年6月時点で、アクティブな CLI ユーザーの49.5%が手動で Bash の allow ルールを作成しており、そのうち5%はあらゆるシェルコマンドを無条件で許可し、さらに43%は `Bash(python:*)` や `Bash(node:*)` のような、実質的に同等のインタープリタルールを設定しています。この割合は5週間ごとにおよそ5ポイントずつ増加し続けています。allow ルールに加えて、62%のユーザーが `bypassPermissions` を使ったか、Bash に対して「二度と聞かない」をクリックしたことがあり、対話型セッションの25%は bypass permissions モードで開始されています。

権限ルールは、auto mode においても分類器より先に発火します。ただし、任意のコード実行を許可するほど広範な allow ルール(例: python:\*)は例外です。これらの広範なルールは auto mode 中は保留されます。そうしたルールを許すと、コマンドが分類器を完全にスキップしてしまうからです。設定ファイル自体は変更されず、別のモードに切り替えた瞬間にルールは再び適用されます。

## auto mode による安全性の向上

社内および複数の第三者機関を通じて行った調査によると、auto mode は、現在の典型的なユーザーが権限プロンプトに向き合う方法よりも安全であることが示唆されています。私たちは、開発者が権限プロンプトをクリックして進める際に実際に承認している内容と、auto mode を比較検証しました。社内レッドチーム演習、第三者によるペネトレーションテスト、実世界のセッション分析のいずれにおいても、auto mode は人間による承認と同等か、それを上回りました。

### auto mode は安全性において手動権限管理を上回る

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a7551c77738b3678fdde0ce_image4.png)

*1,053人の有償プロフェッショナルテスターによる管理実験では、人間によるレビューは危険なコマンドのわずか13.6%しか検知できなかったのに対し、auto mode は89%を検知しました。*

私たちはリサーチベンダーを通じて、コーディング調査のために1,053人の有償テスターを雇用しました。参加者は、自分のコードベースや実際のプロジェクトではなく、この調査専用に用意されたテスト環境で作業しました。参加者は自分が評価されていることを知っていましたが、標準的な盲検デザインに従い、何が測定されているかは知らされていませんでした。各セッションの途中で、1つの権限プロンプトが明らかに危険なコマンドにすり替えられ、ベンダーはテスターがそれを承認したかどうかを記録しました(注: プロンプトを承認しても、実際に危険な処理が実行されることは一切ありませんでした。テスターに見せたプロンプトの文言だけが変更されていました)。

テスターが危険なコマンドを検知できたのはわずか13.6%(1,053件中143件)だったのに対し、auto mode は同じコマンドの89%(1,053件中937件)をブロックしました。直接比較すると、auto mode は人間が承認した800件のコマンドをブロックした一方で、人間が auto mode の許可した内容をブロックしたのはわずか6件でした。セッションが長くなるほど、人間の判断は悪化しました。セッション序盤では危険なコマンドの約17%をブロックできていましたが、50回以上のプロンプトを経た後には約5%まで低下しました。一方 auto mode のブロック率はセッションの長さに関わらず一定でした。

### auto mode はより多くの有害な行動を防ぐ

私たちの調査は、auto mode が手動権限モードよりも有害な行動の発生を減らすことも示唆しています。

私たちは実際の利用状況における auto mode のパフォーマンスを調査しました。2026年5月から6月にかけて、私たちの安全性パイプラインがレビュー対象としてフラグを立てたセッションを調べました。対象は、トレーニングおよび分析へのデータ利用にオプトインしているアカウントのみです。各セッションを、モデルを使って0〜10の2つの尺度で再評価しました。1つ目は害の深刻度で、10は会社全体に及ぶ不可逆的な害(会社のソースコード全体の流出など)、7は本番環境レベルの深刻度(本番データベースからの行の削除など)、0はローカルワークスペース内に限定された完全に可逆な行動(スクラッチファイルの上書きなど)を表します。2つ目は、ユーザーがその行動をどれだけ明示的に要求していたかで、ユーザーが直接依頼した有害な行動と、エージェントがより曖昧な指示のもとで取った有害な行動を区別するために用いました。

フラグが立てられたセッションのうち、手動承認を経たセッションは、auto mode のセッションと比べて、意図しない深刻な害を含む割合が2倍以上でした。本番環境レベルの深刻度(7以上)では、手動承認セッションの6.3%がユーザーの明示的な要求のない有害な行動を含んでいたのに対し、auto mode セッションでは2.4%にとどまり、このギャップは検証したすべての深刻度レベルで一貫していました。

### 敵対的レッドチーム演習により auto mode はより強固に

私たちは、英国拠点の AI 安全性スタートアップである Apollo Research と協力し、実際のコーディング軌跡に合成攻撃を注入する2週間のパイロットプログラムを実施しました。対象は、広範な失敗、データ流出、安全性に関わる脅威をカバーする3つのデータセットです。

この取り組みは、発見・修正・検証という標準的なループに沿って進められました。Apollo は成功した攻撃の一式と、auto mode を強化するための提言を共有してくれました。私たちは主に、分類器が保護している環境についてより多くの文脈(リポジトリの公開範囲、git の状態、後述するデータ取り扱いルールなど)を与えることで、分類器を強化しました。

強化後、Apollo は私たちが一切アクセスできなかった別の保留攻撃セットで再テストを行いました。auto mode は、以前見逃していた攻撃の約半分を検知できるようになった一方で、以前検知できていた攻撃の約2%を新たに見逃す結果となりました。保留セットに対してチューニングすることができなかったことから、この強化は Apollo が共有した特定の攻撃にパッチを当てただけでなく、新しい攻撃にも一般化していることが示唆されます。共有セットと保留セットの両方を通じて、分類器の見逃し率は12%から7%に低下しました。

これらの攻撃は、分類器の弱点を見つけ出すために意図的に設計された合成的かつ敵対的なものであり、Claude が指示なしに行ういかなる行動よりも悪質です。この7%という見逃し率はこのセットに対して測定されたものであり、実際のトラフィックにおける見逃し率と解釈すべきではありません。

### auto mode はプロンプトインジェクションのリスクを軽減する

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a75fafde538ce42b19d5742_image3.png)

*auto mode を有効にした状態では、独立した評価においていずれのモデルに対しても攻撃は成功しませんでした。Codex v0.144.5 上で Auto-review 権限モードを使用した GPT-5.6 Sol の攻撃成功率は5.83%でした。GPT-5.6 Sol は最高レベルの推論性能を検証するため「max」の推論努力度で実行され、すべての Claude モデルは high の努力度で実行されました。*

auto mode の分類器は、ユーザーの指示から逸脱させようとする[プロンプトインジェクション攻撃](https://www.anthropic.com/research/prompt-injection-defenses)に対する追加の防御層を提供します。auto mode を実行している間、ツールの実行結果は悪意のある指示がないかプローブによってスキャンされ、auto mode は行動がユーザーの意図に沿っているかどうかをチェックします。私たちは、この多層防御アプローチの効果を示すため、auto mode と保護されていないモデルを比較検証しました。

私たちは、Trajectory Labs という第三者機関に評価を委託しました。同社は、2026年7月17日時点で公開されている最新版の Claude Code と Codex において、異なるモデルをテストしました1。彼らは、Anthropic からは伏せられた72の間接的プロンプトインジェクションのシナリオをテストしました。各シナリオは10回ずつテストされました。攻撃が成功した場合、テスト環境でなければ、機密データの流出、金融詐欺、認証情報のフィッシングといった不可逆的な行動につながっていたはずです。攻撃は、今回報告されているセット外にある Claude Opus 4.7 に対して最適化されていたため、評価対象のすべてのモデルは未見の攻撃としてこれに直面しました。auto mode に加えて、評価では Claude Code の *bypassPermissions* モードと Codex の *Full Access* モードも検証されました。

Codex と Claude Code はいずれも、Trajectory Labs, PBC が作成した同一のブラウザ統合を使って評価されました。この統合は、`navigate` のような一般的な Chrome API の薄いラッパーとなる MCP ツール群を提供します。OpenAI や Anthropic が提供する Chrome 拡張機能のような、ファーストパーティのブラウザ統合に組み込まれた保護機構はテスト対象外です。そのため、これらの結果は、特定のデプロイに存在しうる保護機構一式ではなく、基盤となるモデル自体の測定結果として捉えるべきです。

**この評価では、auto mode を実行している Claude Fable 5、Opus 5、Sonnet 5 に対して、720回の攻撃試行のいずれも成功しませんでした。** 一方、Codex の *Auto-review* モードを実行している GPT-5.6 Sol に対しては、攻撃の5.83%が成功しました。これは、追加の保護機構なしに *bypassPermissions* モードを実行している私たちの最新モデルに対する平均攻撃成功率0.09%を大きく上回る数値です。テストでは、*Full Access* モードで実行している GPT-5.6 Sol に対して19.03%の攻撃成功率が示されました。以下に示す通り、ツールがテキストとして結果を返すタスクと、スクリーンショットを介してブラウザを操作する必要があるタスクとでは、攻撃成功率が異なります。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a75fac544d570b06de2e9b1_image2.png)

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a75fa7ca0de08fd1e052f2b_image1.png)

*auto mode は、ツール呼び出しとブラウザ GUI 操作の両方でプロンプトインジェクションから保護します。OpenAI のモデルは、第三者評価においてブラウザタスクでより高い攻撃成功率を示しました。*

### Anthropic 社内で auto mode が防いだ3つのインシデント

auto mode は、Anthropic 社内のすべての Claude Code 利用においてもデフォルトです。分類器が社内で防いだ3つの行動を紹介します。

- **オフネットワークへのデータ流出:** 社内ドライブへのアップロードが失敗した際、Claude のフォールバックは同じレポートを公開のコード共有サイトに公開することでした。auto mode はこのフォールバックを拒否し、ユーザーに次のステップを尋ねました。
- **破壊的な大量操作:** ある長時間実行セッションで、Claude はおよそ2,000個の Pod にまたがる大量プロセスキルを試み、実行中であれば数百 GPU 分のトレーニングジョブを停止させていたであろう削除処理をキューに入れました。auto mode は実行前にこれらの破壊的なコマンドにフラグを立てました。
- **過度に広範な権限昇格:** 読み取り専用の請求アクセスの付与を求められた際、Claude はアカウントルートに対して完全な管理者権限を付与するクラウドロールに手を伸ばしました。auto mode は、要求された内容と、実際に付与されるロールの間のミスマッチを検知しました。

いずれのケースでも、Claude は自力でより安全な方法を見つけるか、進める前にユーザーに確認を取りました。

### auto mode をさらに安全にする

私たちは、auto mode をより安全に、そしてプロダクションコードをより出荷しやすくする新機能に継続的に投資しています。最近の例としては次のようなものがあります。

- [**Hard denies:**](https://code.claude.com/docs/en/auto-mode-config#override-the-block-and-allow-rules) コードやシークレットを外部に送信するといったデータ流出は、分類器が絶対に承認しないよう設計されたカテゴリに属します。この種の行動を実行するには、auto mode を切り替えるか、自分自身でコマンドを実行する必要があります。Hard deny ルールは設定でカスタマイズ可能なので、組織内のユーザーからのリクエストであっても決して許可したくないルールをさらに追加できます。
- **データアクセスと共有のためのルール:** 分類器は現在、シークレットや潜在的に機密性の高い情報を区別し、それぞれをどこでアクセス・共有できるかを定める明示的なルールを備えています。これらのルールを実効性のあるものにするため、分類器は git push やプルリクエストの送信先が公開・非公開・信頼済みのいずれかを、実行前にチェックするようになりました。同じ push であっても、送信先次第でありふれた操作にも情報流出にもなり得ます。チームの非公開リポジトリに属すべきコードが公開リポジトリに入ってしまうことがないよう、分類器はこうした事態を検知するよう設計されています。
- **破壊的な git 操作の前に git status を確認する:** git reset --hard のような、コミットされていない作業を破棄しうるコマンドの実行前に、分類器はリポジトリの現在の git status を確認し、auto mode が何がリセットされようとしているかを把握できるようにします。
- **プロンプトインジェクションのスクリーニング:** Claude が Web ページ、ファイルの内容、ツールの出力といった外部のソースからコンテンツを取り込む際、API 側のプローブがそのコンテンツに Claude の挙動を乗っ取ろうとする試みがないかをチェックします。インジェクションの試みらしきものが検知された場合、結果がユーザーに共有される前に、Claude のコンテキストに警告が追加されます。

## プロダクションにおける auto mode

すでに auto mode をプロダクションのデフォルトとして運用しているチームがあります。

- **Adobe** のマーチャンダイジングプラットフォームチームは、Adobe.com 上の90以上の国と30以上の言語にわたる価格・プロモーションページの正確性と最新性を維持する責任を担っています。彼らはこれらのページを構築・検証するエージェントループを構築し、エンジニアが完成した PR をレビューできるよう、auto mode で実行しています。
- **Nuro** はリサーチおよびエンジニアリング組織全体で auto mode を運用しており、評価指標を夜通し改善し続け、朝には完成した PR をレビュー用に返す夜間リサーチエージェントを動かすために活用しています。
- **Gusto** は、エンジニアが権限チェックを完全にバイパスする方向に押しやられていた「権限疲れ」を終わらせるために auto mode を導入しました。5月中旬以降のセッションの約10%には分類器による拒否が含まれており、これは正当なタスクを妨げることなく実際に機能している証拠です。
- **Garner Health** は、managed settings を通じて全550人の従業員に auto mode をデフォルトとして展開し、手作業でキュレーションしたコマンドの allowlist に依存しない、全社的なソフトウェア開発ライフサイクル(SDLC)を標準化しました。

## はじめに

Pro、Max、Team ユーザーの方へ: デフォルトの権限モードを設定していない場合、製品内通知が届き、新しいセッションは自動的に auto mode で開始されます。別のデフォルトを設定している場合は、auto mode に切り替えるかどうかを尋ねる一回限りのプロンプトが表示されることがあります。Team の管理者が managed settings でデフォルトを設定している場合、変更は何もありません。

Enterprise ユーザーおよび Claude API 経由で Claude Code を利用しているユーザーについては、auto mode は当面オプトインのままです。今後1か月のうちに auto mode をデフォルトにする予定であり、その前に Enterprise の管理者に通知します。

モードを切り替えるには、CLI では Shift+Tab を押すか、デスクトップアプリではモードのドロップダウンを使用してください。管理者は、[managed settings](https://code.claude.com/docs/en/server-managed-settings) の `defaultMode` で組織全体のデフォルトを固定したり、`disableAutoMode` で auto mode を完全に無効にしたりできます。

最後に、auto mode はほとんどのユーザーにとってリスクを軽減すると私たちは考えていますが、これは分類システムに依存しているため、リスクをゼロにするものではありません。本番インフラへの重要な変更については、引き続き Claude の行動をご自身でレビューすることをお勧めします。設定の詳しい手順については、[auto mode のドキュメント](https://code.claude.com/docs/en/auto-mode-config)をご覧ください。
