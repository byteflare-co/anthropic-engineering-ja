# Cresta が CX の専門知識を Claude Agent SDK 上のエージェントビルダーへと変えた方法

*シリーズ* ***How startups build with Claude*** *では、AI プロダクトの背後にある意思決定を取り上げています。今回は、* [*Cresta*](https://cresta.com/) *が AI ネイティブな顧客体験(CX)構築で培った専門知識を、他のエージェントの構築・改善を助けるエージェントである* [*Conductor*](https://cresta.com/blog/cresta-conductor-the-agent-for-ai-agent-development) *にどう活かしたかを紹介します。*

| The quick pitch | |
| --- | --- |
| Name | Cresta |
| Founded | 2017 |
| CEO | Ping Wu |
| Growth | 2 億 7,000 万ドル以上を調達。年間経常収益 1 億ドル以上。United Airlines、CVS Health、Marriott といった組織が優れた顧客体験を届けるのを支援 |

顧客体験(CX)のユースケース向けにエンタープライズ向け AI エージェントを構築するには、幅広い顧客とのやり取りに埋め込まれたコンテキストを理解する必要があります。例えば、顧客は次のようなことをします。

- どの購入のことか言わずに返金を依頼する
- 同じメッセージの中で請求の問題とログインの問題を同時に報告する
- 返品期限が過ぎた後に返金を要求する

正しく対応するには、エージェントは顧客が何を購入したか、返金ポリシー、アカウント履歴、支払い状況などを確認する必要があるかもしれません。

Cresta はこうしたやり取りを大量に目にしています。同社のプラットフォームは、会話を自律的に処理する AI エージェント、それと並んで働く人間のエージェントにリアルタイムでガイダンスを提供する機能、そしてビジネスがどこを改善すべきかを示す会話インテリジェンスを通じて、顧客体験を支えています。

CX エージェントを構築・維持するには、組織が運用要件について重要な判断を下す必要があります。エージェントが何を知っておくべきか、どのシステムにアクセスする必要があるか、どこで挙動を柔軟にし、どこで決定論的にすべきか、といった判断です。Cresta は、各チームがゼロから始めることなく、その判断力をより多くのチームが使えるようにしたいと考えました。

その結果生まれたのが Conductor です。複雑なビジネスコンテキストを本番運用可能なエージェントへと変える、自然言語のエージェントビルダーです。ユーザーは作りたいものを説明するだけで、Conductor が根拠のあるブループリントから実装、評価、最適化まで作業をガイドします。

Cresta はもともと、顧客への導入を社内チームが支援するために、Claude Sonnet と Claude Opus を使って Conductor の初期バージョンを構築していました。残された問いは、そのシステムを、顧客がプラットフォーム内で直接エージェントを構築するために使えるプロダクトへと転換できるかどうかでした。

オープンエンドな開発作業を遂行するため、Conductor はコンテキストの収集、ツールの使用、コードの記述・実行、結果に基づく適応を行う汎用ハーネスとして Claude Agent SDK を使用しています。

「私たちは社内で Claude Code を開発ツールとして使っていました。エージェントを構築するというソフトウェア開発的な側面に非常に効果的だったからです」と、Cresta Conductor のエンジニアリングリードである Renjie Li 氏は語ります。「Claude Agent SDK は、その同じエージェント型の開発ハーネスをプログラムから使う手段を与えてくれました。Conductor では、それを Cresta の深い会話インテリジェンス、CX の専門知識、評価、ランタイムと結びつけることで、私たちが初日から欲しかったエージェント構築体験をユーザーに提供しています。」

Cresta によれば、Cresta とそのパートナー各社における初期のユースケースでは、Conductor が初期導入にかかる時間をおよそ半分に短縮したと報告されています。

## **次のエージェントを構築するメタエージェント**

Conductor は、CX エージェント開発の確立されたベストプラクティスの上に構築された、自己改善型のメタエージェントです。チームが Conductor でより多くのエージェントを構築し磨き上げていくにつれて、彼ら自身が実証済みのパターン、ワークフロー、専門家の判断を取り込んでいきます。これにより、将来の開発をより速く、より一貫したものにするナレッジフライホイールが生まれます。

ローンチ後は、本番環境でのやり取り、ワークフローの結果、フィードバックが次の改善のための新しいシグナルとなります。

Conductor は、エージェント構築から学んだことを再利用可能なメモリ成果物へと変える手助けをし、パターン、ビジネスルール、評価アプローチを取り込みます。そしてそれをスキルとしてチームの他のメンバーと共有できるため、他の人も同じ実証済みのプラクティスをもとに構築できます。

### **重要な判断をより簡単にする**

最初のプロンプトを書くことは、有用なエージェントを構築する作業のほんの一部にすぎません。より難しい判断の一つは、会話のどこを柔軟なままにし、どこに明確なビジネスルールと制御されたツールの挙動が必要かということです。

「決定論的にしすぎてはいけません。そうすると、あらゆる可能な分岐をマッピングしようとする巨大な決定木ができてしまいます……しかし、特にリスク許容度の低い規制の厳しい業界では、常に確実に動作させなければならないエンタープライズクリティカルなワークフローも存在します」と Renjie 氏は言います。「Conductor は、そうした決定論的な要件とその実装を発見し、堅牢にする一方で、全体の体験を改善するための柔軟性も残す手助けをします。」

Conductor は過去の会話を参照して、人間がループにとどまるべき箇所とモデルに適応の余地を与えられる箇所をチームが識別する手助けをします。その境界が定まった後も、開発者は決定論的な部分がそれが強制すべき要件に対してきちんと機能することをテストし、根底にあるビジネスルールが変わればそのテストを修正し続ける必要があります。

## **Cresta が Conductor を評価する方法**

Conductor は、エージェントをどれだけうまく構築できるかで評価されます。そのために Cresta は、一連のビルドタスクを通じて Conductor を実行します。

- 新しいエージェントを構築する
- そのためのテストケースを書く
- 既存のエージェントを変更する
- 根本原因分析を行う

タスクを完了することだけが基準ではありません。チームは結果だけでなく、Conductor がどうやってそこに至ったか、その過程で何を使ったかにも注目します。

| Evaluation | Question it answers |
| --- | --- |
| 結果 | Conductor は要求された、使用可能な成果物を生成したか? |
| 実行経路 | 適切なツールと必要なコンテキストを使用したか? |
| 品質 | 結果は精選されたリファレンスと比べてどうか? |
| リソース使用量 | タスクにどれだけの時間とモデル使用量を要したか? |

これらと同じタスクは、安全網としても機能します。新しい Claude モデルがローンチされたり、Conductor のフレームワークが更新されたりすると、Cresta は評価を再実行します。同じタスクと同じスコアリングを使って、何が改善し、何に変更をコミットする前にまだ取り組むべき課題が残っているかを見極めます。

この評価の規律は Conductor 自体にも組み込まれており、ユーザーは自分のエージェントが意図通りに動作しているかどうかを確認できます。Conductor は、ビルド段階で捉えた要件やエッジケースを、評価モジュール内のテストへと変換します。

これにより、チームはポリシー、連携先のシステム、会話パターンが変化していく中でも、常に動作し続けなければならないワークフローを監視できます。これにより、すでに堅牢化したワークフローの信頼性を損なうことなく、ビジネスの変化に合わせてエージェントを更新する実践的な方法が手に入ります。

## **Claude Agent SDK の上に Conductor を構築する**

Cresta は Conductor を、エージェント開発のための CX 特化型コントロールプレーンとして設計しました。会話データ、ドメインの専門知識、開発プラクティスを一つにまとめ、ポリシー、可観測性、検証、フィードバック駆動の改善を通じて各エージェントの実行を統制します。

Claude Agent SDK は、Conductor の基盤となる汎用の実行ハーネスとして機能します。コンテキストの収集、ツールの呼び出し、コードの記述と実行といった作業を管理し、その上に Conductor が Cresta の CX ワークフロー、ツール、ドメインコンテキストを重ねています。

チームは、Conductor が遂行する必要のある作業 — 複数のステップ、相当なコンテキスト、繰り返されるツール使用を伴うタスク — に照らして SDK を評価しました。そのレビューは、データプライバシー、テナントアーキテクチャ、組織レベルのキー配布、制御、そして実装全体にわたる可観測性をカバーしていました。

「Anthropic は、エージェント型のソフトウェア開発のための強力で汎用的な基盤を私たちに提供してくれます。そのおかげで、Cresta が最も持続的な顧客価値を生み出せる場所にエンジニアリングの投資を振り向けることができるのです」と、Cresta の VP of Engineering である Xiangru Chen 氏は語ります。

## **Cresta のエンジニアリングの専門知識を、顧客の手に直接届ける**

Conductor は Cresta 社内から始まり、どの開発タスクが繰り返し可能になり得るか、どこでコンテキストが最も重要になるか、構築者が作業の過程で何を点検する必要があるかを、自社のフォワードデプロイドチームが学ぶ助けとなりました。その社内での成功が、同じ能力を顧客やパートナーにも届ける自信をチームに与えました。

エンジニアがカスタムエージェントを手作業で構築できるスピードよりも速くプロダクトが顧客にカスタムエージェントを展開するあらゆるチームにとって、Cresta のアプローチは有用な参考事例です。エージェントやメタエージェントでは、最初の構築の後に続く作業こそが、しばしば最も難しい部分だからです。

[Conductor](https://cresta.com/blog/cresta-conductor-the-agent-for-ai-agent-development) がビジネスコンテキストをより良いエージェントの設計、実装、継続的な改善へとどう変えているかをご覧ください。

| Best practices from the Cresta team | |
| --- | --- |
| 自社のプロダクトをドッグフーディングする | Conductor はまず社内ツールとして動き、深い AI の専門知識を持つエンジニアが作るであろうものと出力が一致して初めてプロダクトになりました。 |
| 自社ならではの強みに集中する | Cresta は、自分たちだけが持ち込める専門知識(会話データと顧客体験への理解)と、Agent SDK から既製品として取り入れられるものとの間に明確な線を引き、その線の間違った側には何も構築しないようにしました。 |
| エージェントのどの部分を決定論的にすべきか | 決して間違ってはならないエンタープライズクリティカルなワークフローは堅牢化し、それ以外は柔軟なままにしましょう。そうしなければ、望んでいたようなインタラクティブなエージェント体験にはたどり着けません。 |
| 本番環境への到達は、実は簡単な部分にすぎない | 最初の構築は全体の労力のおよそ 20% にすぎず、残りの 80% はその後に続くテスト、最適化、継続的な改善です。ですから、ローンチではなくイテレーションのループを中心にツールを設計しましょう。 |
