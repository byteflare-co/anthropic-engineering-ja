# Claude Code を使う: HTML の理不尽なまでの有効性

Claude Code チームのメンバーが、より豊かで、より読みやすく、共有しやすいアウトプットを作るために、Markdown ではなく HTML を使う理由とその使い方について。

Markdown は、エージェントが人間とコミュニケーションを取るためのファイルフォーマットとして、いまや支配的な存在になりました。シンプルでポータブル、リッチテキストの表現力もそこそこあり、編集も容易です。Claude は Markdown ファイルの中で ASCII を使って図を描くのも、驚くほど上手くなっています。

ところが、エージェントがどんどんパワフルになるにつれて、Markdown はかえって制約の多いフォーマットになってきたと感じるようになりました。具体的には、100 行を超える Markdown ファイルは読むのが難しいと感じますし、Claude にはもっとリッチなビジュアル、色、図を生成してほしいですし、それらのアウトプットをもっと簡単に共有したいのです。

それに、最近はこうしたファイルを自分で編集することは減ってきており、仕様やリファレンスとして使うことが多くなっています。編集するときも、たいていは Claude にプロンプトで編集させているので、Markdown の大きなメリットのひとつが失われてしまっています。

そこで私は、Markdown の代わりに HTML をアウトプット形式として好むようになりました。Claude Code チームの他のメンバーにも、このパターンを採用する人が増えてきています。本記事では、私たちのチームがより豊かで読みやすい Claude Code のアウトプットを作るために、なぜ、どうやって HTML を使っているのかを共有します。一緒に試してみたい方は、よくあるユースケース向けの [HTML ファイルテンプレート](https://thariqs.github.io/html-effectiveness/#code-review) から始めてみてください。

# なぜ HTML を使うのか

いまの私が Claude Code でやっている種類の作業には、Markdown よりも HTML のほうがフィットする理由がいくつかあります。たとえば次のような作業や要件においてです。

## 情報密度

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cc2df7520821249c2495c_image10.png)

HTML は Markdown と比べてはるかに豊かな情報を伝えられます。もちろん、見出しや書式といったシンプルなドキュメント構造も表現できますが、それ以外にもさまざまな情報を表現できます。たとえば次のようなものです。

- テーブルによる表形式データ
- CSS によるデザインデータ
- SVG によるイラストレーション
- script タグによるコードスニペット
- HTML 要素 + JavaScript + CSS によるインタラクション
- SVG と HTML によるワークフロー
- 絶対配置と canvas による空間データ
- img タグによる画像

私の意見では、Claude が読める情報のうち、HTML で効率的に表現できないものはほとんどありません。これは、モデルが奥行きのある情報をあなたに伝え、あなたがそれをレビューするうえで、きわめて効率の良い方法になります。

これができないと、モデルは Markdown 内で ASCII の図を描いたり、私のお気に入りでは、unicode 文字で色を推定したりといった、より非効率な手段に出ることが多い、というのも分かってきました。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb4e_be6aa05f.png)

## 視覚的な明快さと読みやすさ

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb48_343de6c4.png)

Claude がより複雑な作業に取り組めるようになるにつれて、Claude が書く仕様書やプランもどんどん大きくなっていきます。実際、私自身、100 行を超える Markdown ファイルは読み通さなくなる傾向があると気づきましたし、組織の他のメンバーに読んでもらうのもまず無理です。

ところが HTML ドキュメントは、はるかに読みやすくなります。Claude が構造を視覚的に整理し、タブやイラスト、リンクで快適にナビゲートできるように仕上げてくれるからです。モバイル対応にもできるので、デバイスのフォームファクタに応じて違う読み方をすることもできます。

## 共有のしやすさ

Markdown ファイルは、たいていのブラウザがネイティブにきれいにレンダリングしてくれないため、共有がやや面倒です。メールやメッセージに添付して渡す必要があることが多いでしょう。

HTML ファイルなら、どこかにアップロードしてリンクを共有するだけで済みます。同僚はそれを好きな場所で開けて、簡単に参照できます。

あなたの仕様書、レポート、PR のまとめを実際に読んでもらえる可能性は、HTML のほうがずっと高くなります。

## 双方向のインタラクション

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb4b_438fa236.png)

HTML を使えば、ドキュメントと [対話する](https://x.com/trq212/status/2017024445244924382) こともできます。たとえば、デザインを調整するためのスライダーやノブを追加してもらったり、アルゴリズムのオプションをいじって挙動の変化を見たりできます。さらに、それらの変更をプロンプト用にコピーできるようにしてもらい、Claude Code にそのまま貼り戻す、という使い方もできます。

うまく使えば、いま取り組んでいる特定の問題のために、その場かぎりの個別の編集環境を作れるのです。

## データの取り込み

Claude.ai や Claude Design ではなく Claude Code で HTML ファイルを作る最大の理由のひとつは、Claude Code が取り込めるコンテキストの豊富さです。たとえば本記事を書くにあたっては、Claude Code に自分のコードフォルダを読ませて、これまで生成してきた HTML ファイルをすべて見つけ、それらをグループ化・分類して、各タイプを表す図入りの HTML ファイルを作らせました。本記事に登場する図は、その作業の直接の成果です。

ファイルシステム以外にも、Claude Code は MCP（Slack、Linear など）、ウェブブラウザ（Claude in Chrome を使えば）、Git の履歴などから、追加のコンテキストを得られます。

# 始め方

ひとつ強調しておきたいのは、Claude にこのような HTML を生成してもらうのに、特別なことはほとんど必要ない、という点です。単に「*HTML ファイルを作って*」とか「*HTML のアーティファクトを作って*」とプロンプトすれば十分です。大事なのは、そのアーティファクトに何をさせたいのか、それをどう使うつもりなのかを自分が分かっていることです。長く使っているうちに、繰り返し現れるパターンに対しては Skill として作り込むのが理に適うようになりますが、まずはゼロからプロンプトしてみるのが、さまざまなユースケースで HTML がどう機能するかを掴むうえで良い出発点になります。

## ユースケース

このアプローチをもう少し具体的にするために、Markdown よりも HTML を使うほうが理に適うと私が考えている [ユースケースの例](https://thariqs.github.io/html-effectiveness/) をいくつか紹介します。これらのユースケースの GitHub ギャラリーも [こちら](https://github.com/anthropics/html-effectiveness) から追えるようになっています。

### 仕様策定、プランニング、探索

HTML は、Claude が問題に踏み込んでいくためのリッチなキャンバスです。問題に取り組み始めるときは、シンプルな Markdown のプランではなく、HTML ファイルの網を作ることを期待するようになりました。たとえば、まず Claude Code にブレインストーミングをさせて、いくつかの異なる選択肢の探索を作らせます。次に、そのうちのひとつをさらに深掘りさせ、UI のモックアップや例を作らせるかもしれません。最後に、納得できたところで実装プランを書いてもらいます。プランに満足したら、新しいセッションを作って、これらすべてのファイルを渡して実装させます。

検証の段階でも、検証エージェントにこれらのファイルを読ませると、必要な事柄について格段に広いコンテキストを持って作業してもらえます。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb5c_7eaa0090.png)

**プロンプト例:**

- *オンボーディング画面をどの方向に持っていくか決めかねている。レイアウト・トーン・密度を変えて、はっきり異なる 6 つのアプローチを生成し、グリッド状に並べた 1 つの HTML ファイルにレイアウトして横並びで比較できるようにして。各案について、どんなトレードオフを取っているかをラベルとして添えて。*
- *HTML ファイルで丹念な実装プランを作って。モックアップを添え、データフローを示し、レビューしたい重要なコードスニペットも入れて。読みやすく、消化しやすい形にして。*

**こんなときに使う:**

- コードでの実装方法の別案を探るとき
- 複数のビジュアルデザインを同時に試したいとき

### コードレビューと理解

コードは Markdown ファイルだと読みづらくなりがちですが、HTML なら差分・注釈・フローチャート・モジュールをレンダリングできます。エージェントが書いたコードを理解する、コードをレビューする、自分のコードをレビュアーに説明する、といった用途に HTML を使いましょう。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb5f_ce1ada20.png)

**プロンプト例:**

*この PR を説明する HTML アーティファクトを作って、レビューを手伝って。streaming/backpressure のロジックに馴染みがないので、そこにフォーカスして。実際の diff をインラインのマージン注釈付きでレンダリングし、深刻度ごとに findings を色分けして、概念をうまく伝えるために必要なことは何でもやって。*

**こんなときに使う:**

- PR を作るとき
- PR をレビューするとき
- コードのトピックを理解するとき

### デザインとプロトタイプ

Claude Design は HTML をベースにしています。最終的な提供面が HTML でなくとも、HTML はデザインの表現力がきわめて高いからです。Claude は HTML でデザインをスケッチしてから、React や Swift など、あなたが選んだ言語に書き直すこともできます。

アニメーションやアクションといったインタラクションのプロトタイピングもできます。スライダーやノブを作ってもらい、求めているものにピタリと合わせる、という使い方も検討してみてください。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb51_2f351343.png)

**プロンプト例:**

*新しいチェックアウトボタンのプロトタイプを作りたい。クリックすると再生アニメーションを行い、それから素早く紫色に変わる。このアニメーションのいろいろなオプションを試せるよう、いくつかのスライダーとオプションを備えた HTML ファイルを作って。うまくいったパラメータをコピーできるコピーボタンも付けて。*

**こんなときに使う:**

- デザインシステムのアーティファクトを作るとき
- コンポーネントを調整するとき
- コンポーネントライブラリを可視化するとき
- アニメーションのプロトタイピング

### レポート、リサーチ、学習

Claude Code は複数のデータソースをまたいで情報を統合し、それを読みやすいレポートに変換するのがとても得意です。Slack、コードベース、Git の履歴、インターネットなどを検索させ、それを元に読みやすいレポートを生成させることができます。

長い HTML ドキュメント、インタラクティブな説明資料、あるいはスライドショー/デッキの形にまとめてもよいでしょう。可視化のために SVG で図を描いてもらうのもおすすめです。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb54_e0306f54.png)

**プロンプト例:**

*うちのレートリミッターが実際どう動くのか分かっていない。関連するコードを読んで、1 枚の HTML 解説ページを作って。トークンバケットのフロー図、注釈を付けた 3〜4 つの主要コードスニペット、末尾には「落とし穴」セクションを置いて。一度読めば理解できる作りに最適化して。*

**こんなときに使う:**

- 機能のサマリーを書くとき
- 解説資料を生成するとき
- 週次のステータスレポートを下書きするとき
- インシデントレポートを作るとき
- SVG のイラスト、フローチャート、技術図を生成するとき

### カスタム編集インターフェース

テキストボックスだけでは欲しいものを言い表すのが難しい場面があります。こうしたケースで私がよく使うのが、いま取り組んでいるその対象専用に、使い捨ての編集ツールを Claude に作らせる、というやり方です。プロダクトでも再利用可能なツールでもなく、その 1 つのデータ片のために特化した、1 つの HTML ファイルです。

ポイントは、必ず最後に「エクスポート」を備えること。UI 上での操作結果を、Claude Code に貼り直したりファイルにコミットしたりできる形に変える「copy as JSON」や「copy as prompt」ボタンです。あなたはループの中にいながら、そのループはずっとタイトになります。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a0cccd2c085977fc720eb57_0e3ace42.png)

**プロンプト例:**

- *この 30 件の Linear チケットを優先順位付けし直したい。各チケットをカードにして、Now / Next / Later / Cut の各カラムをまたいでドラッグ可能にした HTML ファイルを作って。最良の推測に基づいて事前にソートしておいて。「copy as Markdown」ボタンを追加して、最終的な並びを、各バケットの 1 行ずつの理由付きでエクスポートできるようにして。*
- *これがうちの feature flag の設定。フォームベースのエディタを作って。フラグを領域ごとにグループ化して、フラグ間の依存関係を表示し、前提が off のフラグを enable しようとしたら警告して。「copy diff」ボタンも付けて、変更されたキーだけを出せるようにして。*
- *いまこのシステムプロンプトをチューニングしている。左右並びのエディタを作って。左側に編集可能なプロンプト、変数スロットはハイライトされていて、右側に 3 つのサンプル入力があって、テンプレートが埋まった状態でライブに再レンダリングされる。文字/トークンカウンタとコピーボタンも追加して。*

**こんなときに使う:**

- 何かを並べ替えたり、トリアージしたり、バケットに分けたいとき（チケット、テストケース、フィードバック）
- 構造化された設定（feature flag、環境変数、制約付きの JSON/YAML）を編集するとき
- プロンプト、テンプレート、コピーをライブプレビュー付きでチューニングするとき
- データセットをキュレーションするとき（行ごとの承認/却下、例へのタグ付け、選択分のエクスポート）
- ドキュメント、トランスクリプト、diff に注釈を付けて、注釈をエクスポートするとき
- テキストでは表しにくい値を選ぶとき（色、イージングカーブ、クロップ領域、cron スケジュール、正規表現）

### よくある質問

Claude Code で HTML を使うことについて、私がよく聞かれる質問と、日々の運用の中で辿り着いた現実的な習慣を組み合わせて並べておきます。

**非効率ではありませんか?**

たしかに Markdown のほうが消費トークンは少ないことが多いです。ですが、HTML がもたらす表現力の高さと、自分が実際に読む可能性の格段の高さによって、トータルではより良いアウトプットが得られることが分かってきました。Opus 4.7 の 1MM コンテキストウィンドウがあれば、トークン使用量の増加もコンテキストウィンドウ上ではほとんど気になりません。

**いまでも Markdown を使うのはどんなときですか?**

正直に言うと、ほとんどすべての用途で Markdown を使うのをやめてしまいました。ただし、私はかなり HTML マキシマリスト寄りの極端な側にいる、とは思います。

**これでプランニングを置き換えたということですか?**

ひとつのプランを持つかわりに、プランの各パート/段階ごとに複数の HTML ファイルを持つ傾向が強くなっています。たとえば実装プランを HTML で作り、別ファイルで UI の探索をやり、最後にすべてのデザインを並べる HTML コンポーネントを作る、といった具合です。これらのファイルは、将来のリファレンスとしても、また検証のためにも、そのまま手元に残しておくことが多いです。

## Claude とループの中にい続けるために

ここまで述べてきたことを総合すると、私が Markdown ではなく HTML を使う本当の理由は、それが「Claude とのループの中にしっかり入っている」という感覚を強く与えてくれるからです。Claude がより多くを引き受けるようになるにつれて、自分がプランを以前ほど丁寧に読まなくなっていることに気づきました。Claude の判断にただ仕事を渡すのではなく、ちゃんと向き合い続けるための方法が欲しかったのです。HTML がまさにその答えだった、というわけです。今は、これまでのどんなときよりも、ループの中にいる感覚があります。

[Claude Code](https://code.claude.com/docs/en/quickstart) を始めてみましょう。
