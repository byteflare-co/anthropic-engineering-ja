多くの問題には *生成と検証のギャップ（generator–verifier gap）* があります。解を考え出すよりも、その解が正しいかを確かめるほうがはるかに簡単なことが多いのです。数独はその典型例です。解の確認は簡単ですが（各行・各列・各ブロックの数字を数えるだけです）、解を見つけるには長い時間がかかることがあります。Claude を使った野心的なプロジェクトの多くは、このギャップを利用してきました。数学における[証明](https://alpo.ge/remark.pdf)の形式化や、十分にテストされた大規模コードベースの[移行](https://bun.com/blog/bun-in-rust)は、自分の作業を確実に検証する手段さえあれば Claude が引き受けられるタスクです。

しかし Claude の能力が高まるにつれ、Claude は稼働中のシステムでのプロジェクトにも取り組むようになりました。そこでは、作業を生成するほうが検証するよりも簡単です。こうしたシステムでは、ユーザーは[テストスイートの範囲外](https://github.blog/2016-02-03-scientist/)にあるエッジケースや癖に依存していることが多く、[すべてをカバーする「正しさ」の定義](https://www.anthropic.com/research/formal-verification)を書くことは困難です。Claude の作業を確実にチェックする手段がなければ、Claude がどれほど速くコードを生成できたとしても、稼働中のシステムの移行を信頼することは難しいのです。

私たちは、[Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) を Python から Rust に移行したときに、この問題に直面しました。この API は、お客様、そして Claude Code や Cowork といった私たち自身のアプリが Claude にアクセスするための主要な手段です。2024 年初頭から 2026 年秋にかけて、API のトラフィックはおよそ 1,800 倍に増加しました。Rust を使えば、リクエストあたりの CPU 使用量を大幅に削減できます。Claude は、API の中核となるリクエストパスの最初のバージョンをおよそ 1 週間で書き上げました。しかし、移行への信頼を築くには、Rust 版 API が本番 API と同等（パリティ）であることを検証する方法を見つける必要がありました。これはいくつかの理由で困難でした。移行期間中も Python 版 API は変更され続けたため、パリティは動く標的でした。Claude は同じリクエストに対して非決定的に応答することがあるため、2 つの出力の違いが必ずしもバグを意味するわけではありませんでした。そして私たちはお客様のリクエストを読むことができないため、2 つのバージョンがどこで食い違っているのかを簡単には確認できませんでした。

この記事では、本番の Messages API そのものを検証器（verifier）に変えた方法を紹介します。そしてそれによって、新しい Rust 版を本番トラフィックでテストし、差異がある箇所を見つけ、その差異を修正するエージェントを自動的に派遣できるようになった経緯をお伝えします。その結果、サービスを一度も停止することなく、機能開発を凍結することもなく、リクエストあたりの CPU 使用量を約 70% 削減し、最初のトークンまでの時間（time to first token）の中央値を約 20% 短縮した Rust 製 API をリリースできました。

## なぜ移行するのか？

私たちは 2023 年に Messages API を構築し、社内の研究コードの多くで広く使われていた Python で書きました。当初、それはシンプルなものでした。Messages API はリクエストをモデルに渡し、モデルが書いたものを返すだけでした（当時のあるエンジニアは「基本的にはリクエストフォワーダー」と呼んでいました）。しかし Messages API がより高機能になり、私たちのコードベースと深く統合されるにつれて、研究チームや推論チームが所有する Python ライブラリとの共有依存関係も生まれ、移行が難しくなっていきました。もし別の言語に移行しようとすれば、ロギング、メトリクス、ツールをすべて作り直すことになります。

この損得勘定は徐々に変わり始めました。2025 年後半には、すべての Messages API リクエストについて、バリデーション、プロンプトへの変換、トークン化、そして安全性分類器によるスクリーニングが必要になっていました。応答が届くたびに、トークンのストリームをテキスト、思考（thinking）、ツール呼び出しに振り分ける必要があり、Python はオブジェクトの生成、メモリの解放、次のタスクへの処理の受け渡しのたびに、これらすべてのステップにオーバーヘッドを加えていました。最終的に、トラフィックは当初の Python サービスが想定していた規模をはるかに超えて増大し（図 1）、私たちはサービスを大幅に効率化する方法を早急に見つける必要に迫られました。

![2024 年 1 月から 2026 年 10 月までの月ごとの 1 日あたり API リクエスト数を示す棒グラフ。2024 年中は棒がほとんど見えず、2025 年に徐々に伸び、2026 年に急上昇して 10 月に最高値に達している。](https://assets.claude.com/b4764d8023bcde58a15900b16cbb8dd2a6f82010.png?w=3840&q=75&fm=webp&fit=max)

私たちのプラットフォームにおける 1 日あたり API リクエスト数の月平均（社内利用を含む）。

### 段階的に進めるか、一気に進めるか？

大規模な本番システムの全面的な書き直しは、少なくとも 2 つの理由から慎重に扱われることが多いものです。第一に、テストスイートが本番コードの挙動を 100% カバーしている保証はなく、書き直しはリスクを伴います。第二に、必要な労力が膨大であるため、そうした作業は手に負えないことが多いのです（2024 年に、あるエンジニアが Go か Rust への移行を提案した際、別のエンジニアが「*API を go や rust で書き直したりはしない！*」と言って、ひとまずこの議論に決着をつけました）。

そのため、パフォーマンス向上を求める場合の定石は、システムを遅くしている部分だけを書き直すことです。私たちもそこから始めました。モデルの出力をパースするコードを Rust で書き直し、それを Python から呼び出すようにしました。これにより API の CPU 使用量は約 8〜10% 削減されました。しかし、段階的な解決策は複雑さの増加を伴うことが多く、段階的な改善がそのコストに見合うかを確認することが重要です。私たちのケースでは、得られた効果は増した複雑さに見合いませんでした。各トークンが Python と Rust の間を 3 回行き来するようになり（図 2）、新たなオーバーヘッドの発生源となったのです。

![リクエストパスを示す 2 つの図。部分的な書き直し（2026 年 3 月）では、Rust がトークンを受け取ってパースし、Python がその他のステップを行うため、各トークンは言語間を 3 回行き来する。全面的な書き直し（2026 年 9 月）では、Python はリクエストを引き渡し、Rust がモデル前後の他のすべてのステップを行う。](https://assets.claude.com/a518c8d4f3c915a99fc745d5cced4fa806274650.png?w=3840&q=75&fm=webp&fit=max)

段階的な書き直しの後、応答の各トークンは Python と Rust の間を 3 回行き来していました。

Claude の能力が高まるにつれ、全面移行を避ける通常の理由がまだ当てはまるのか、私たちは疑問を持ち始めました。プロジェクトに必要な労力は急速に低下していました。2026 年 5 月までに、Claude は [Anthropic がマージするコードの 80% 以上](https://www.anthropic.com/institute/recursive-self-improvement)を書いていたのです。私たちは、本番システムのあらゆる挙動と修正を経験的に捉えるコードを、今なら Claude が書く手助けをしてくれるのではないかと考えました。しかし問題は、移行後の挙動が正しいことをどう検証するか、ということでした。ボトルネックは生成ではなく、検証になっていたのです。

## 移行をどう検証したか

### 一般的なアプローチ

移行を検証するには、まず「正しい」とは何を意味するのかを定義する必要がありました。これにはいくつかの方法があります（図 3）。運が良ければ、単純にルールを書くことができます。[数学の定理](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)は厳密な命題であり、証明支援系（Lean など）は証明の各ステップを固定されたルールセットに照らしてチェックできます。それ以外の場合、そしてソフトウェアエンジニアリングではこちらのほうが多いのですが、テストのような例の集合によって「正しさ」を定義します。たとえば [Bun が Zig から Rust に移行した](https://bun.com/blog/bun-in-rust)際には、テストスイートが TypeScript で書かれていたため、同じテストで両方のバージョンを判定できました。私たちのケースではどちらのアプローチも十分ではなかったため、既存のシステムをオラクルとして使い、移行中のパリティをテストしました。この場合、既存システム（Messages API）は変化し続けていました。新しいモデルのリリースや新機能の出荷を定期的に行っていたため、「正しさ」の定義は動く標的となっていたのです。

![3 つの行があり、それぞれが Claude エージェントにシグナルを送っている。証明における Lean のようなルールは、すべてが書き下されており、従わないステップを指摘する。Bun のテストスイートのような例は、部分的に書き下されており、失敗したテストを指摘する。私たちの Python サービスのような既存システムは、答えが何も書き下されていないため、両者が異なる箇所を指摘するチェッカーを構築する。](https://assets.claude.com/339fa8648be547a2bbcef4a3023ae1df2ec8ab71.png?w=3840&q=75&fm=webp&fit=max)

「正しさ」の一般的な 3 つの拠り所。

### テスト

既に約 700 件の統合テストがあったため、テストは最も手をつけやすい出発点でした。しかし、これほど重要な移行の正しさを検証するものとしてテストを信頼するには、2 つの問題がありました（図 4）。

**テストが Python の実装と結合していました。** 統合テストはリクエストを送り、応答と他のサービスに送られた内容をチェックします。私たちのテストは、テストのプロセス内で Python API を実行し、課金やレート制限といったサービスを Python のメモリ内でモック化していました。テストはコードとともに変更する必要があり、Claude はその両方を手伝いました。すると「合格」が、コードが正しいことを意味する場合もあれば、誤ったコードを通してしまうようにテストが変更されたことを意味する場合もあるようになりました。実際にそれが起きていました。移植されたテストを監査したところ、弱められたアサーションが 100 件以上見つかったのです。

**テストが不完全でした。** Messages API には数十の機能があり、構成の組み合わせは網羅的にテストするには多すぎます。2 値のオプションが 20 個あるだけで 100 万通り以上の組み合わせになります。1 件 1 秒としても、1 つのモデルについて 12 日分のテストになり、しかもその中のプロンプトを変化させる前の話です。実際には、エンジニアは本番を近似しようとするサブセットをテストしますが、その過程ではどうしても取りこぼしが生じます。Bun のように、書き直しを判定できるほど充実した独立のテストスイートを持つプロジェクトもあります。しかし多くの本番サービスはそうではありません。何が正しいかは、テストやドキュメントの内容と同じくらい、サービスがどう振る舞うかに依存しているのです。

![2 つのパネル。左は、レガシー実装と結合したテスト。Python のテストが、Claude が同じく書いた Rust のテストに移植されるが、チェックする範囲が狭くなり差異を見逃す。右は、不完全なテスト。機能の組み合わせの大きなグリッドの中に、チェックされたケースの小さなクラスタがいくつかあるだけで、その外側で多くの差異が見逃されている。](https://assets.claude.com/d62ca948354e121f976d85764b91d117d5481523.png?w=3840&q=75&fm=webp&fit=max)

移植されたテストは元のテストよりもチェックする範囲が狭くなることがあり（破線）、テストは誰かが思いついた組み合わせしかカバーしません。

### 本番とのパリティを検出する

本番データは、新しいコードが古いコードと同じように振る舞うことを確かめる「[唯一の真のテスト](https://github.blog/2016-02-03-scientist/)」となることがあります。リクエストを古いコードと新しいコードの両方に流して結果を比較することは、しばしば *シャドーイング（shadowing）* と呼ばれます。何を比較する必要があったかを理解するには、Messages API で 1 つのリクエストに何が起きるかを順に追うとわかりやすいでしょう（図 5）。API は各リクエストをバリデーションし、モデルが読めるプロンプト（推論用プロンプト）に変換し、トークン化し、安全性分類器にかけます。その後モデルが応答を 1 トークンずつ書きます。出力側では、API がそれらのトークンをテキスト、思考、ツール呼び出しに振り分け、お客様にストリーミングし、制限や課金のために使用量をカウントします。

![リクエストのフロー図。入力パスでは、リクエストを受理または拒否し、設定を解決し、プロンプトを構築する。当初一致した入力は約 4 分の 1 だった。Claude は 1 回だけ実行される。出力パスでは、応答を振り分け、ストリーミングし、使用量をカウントする。差異の例として、拒否されたフィールド、1M の制限が 200K と読まれたもの、欠落したツール説明、取り除かれた改行、欠落した使用量フィールドがある。設計上防ぐべきリスクは、1 つのコピーが 2 回カウントされること。](https://assets.claude.com/4903891e9b23665e42dcc20a72be12336b8eba18.png?w=3840&q=75&fm=webp&fit=max)

Messages API の入力パスと出力パス。塗りつぶされた点は、Python と Rust の間で見つかった差異の例です。白抜きの点は、防ぐ必要があったリスクです。

移行は入力パスと出力パスの両方にわたりました。Python が受理していたリクエストを Rust API が拒否した場合など、明白な差異もありました。しかし多くは微妙なものでした。たとえば Rust API がプロンプトの一部を欠落させても、リクエストは成功し、モデルは応答します。ただし、ときに応答にわずかな違いが生じます。

Rust API は 4 月の時点でテストの約 98% に合格していましたが、本番トラフィックで一致した入力は約 4 分の 1 にすぎませんでした（図 6）。このギャップの一因は、テストがカバーしていない本番トラフィック中のケースでした。たとえば Python は JSON のツール呼び出しを書き出す際、特定の文字（絵文字など）をテキストコードに置き換えてエスケープします。Rust はそれらの文字をそのまま書き出していたため、2 つのプロンプトは数バイト異なっていました。また、本番ではバグの重みも異なっていました。テストスイートでは各ケースは 1 回ずつしかカウントされませんが、実トラフィックではバグはそれが発生するすべてのリクエストに現れるため、よくある 1 つのバグが多数の不一致を引き起こすことがあります。

![4 月下旬から 8 月までの、一致した入力の割合を示す折れ線グラフ。24% から始まり、5 月初旬に 6.5% まで下がり、その後修正が展開されるにつれて急上昇する。Rust 側の変更による 2 回の下落があり、最終的に 99.6% に達する。比較は私たち自身のトラフィックから始まり、その後より広いサンプルに移行した。](https://assets.claude.com/7de2a8325622d82fedbce7ef4ff369b2e27c3042.png?w=3840&q=75&fm=webp&fit=max)

比較したリクエストにおいて、Rust の入力が Python の入力と一致した頻度。応答は別途比較しました。各点は 1 日を表し、線は 7 日間の中央値です。比較対象は時期によって変化しており、誤解を招く 6 日分は除外しています。

シャドーイングのための[一般的な](https://github.blog/2016-02-03-scientist/)[ツール](https://blog.x.com/en/engineering/diffy-testing-services-without-writing-tests)は、リクエストを安全に 2 回実行できること、あるいはサービスが決定的であることを前提としていることが多いです。私たちのケースでは、これらの前提は当てはまりませんでした。リクエストがお客様の制限や請求に 1 回しかカウントされないようにする必要がありました。さらに Claude は非決定的であり、[同じ入力に対しても応答が異なる場合があります](https://platform.claude.com/docs/en/about-claude/glossary)（図 7）。これに対処するため、モデルは 1 回だけ実行し、そのモデル出力を Rust に再生（リプレイ）しました。

両方のバージョンが同じモデル出力を扱うようになっても、モデル呼び出しの前後のすべての段階を比較する必要があり、結果は完全に一致しなければなりませんでした。多くのシステムでは、不正な入力はスタックのどこかでエラーを引き起こします。しかし Claude はほぼどんなプロンプトでも受け付けるため、わずかなずれでもエラーを起こさずに応答を変えてしまう可能性があります。私たちはモデル呼び出しの前後の各ステップを比較し、お客様が受け取る内容を変えうるずれを特定できるようにしました。

![2 つの比較。一般的なサービスでは、2 つの旧コピーと 1 つの新コピーが ID で一致し、新コピーは合計値にバグを示し、時刻は変動するのでノイズとして無視される。推論 API では、2 つの Python コピーと Rust がそれぞれ「91 は素数か？」への答えを異なる言い回しで書くため、応答全体がノイズとみなされ、チェックされないままになる。](https://assets.claude.com/2219fb4da126171dd071056b7290e47ed37bf0f3.png?w=3840&q=75&fm=webp&fit=max)

差分ツールは、古いコードを 2 回実行して自然に変動する部分を学習し、それを無視することがよくあります。Claude の応答は変動するため、そうしたツールは応答を、そこに含まれるバグもろとも無視してしまいます。

私たちにとって、ユーザーのプライバシーを保護する方法でこれを行うことが重要でした。そのためには、ユーザーのリクエストやそれに対する Claude の応答を読まずに作業する必要があり、Rust 版と Python 版の API がどこで異なるかを簡単には確認できませんでした。そこでテキストを見る代わりに、各差異の *形状* 、つまりサービス内のどこで発生したか、どれくらいの大きさかを記録しました。これにはいくつかのアプローチを用いました。

- **チェックポイント。** 両方の API バージョンは、同じステップでリクエストを処理します。受理または拒否し、設定を解決し、プロンプトを構築します。各ステップはエラーやプロンプトの断片などの何らかの結果を生成するので、それをステップごとに、プロンプト内では断片ごとに比較できました。最初に差異が生じた箇所が、移行コードが本番コードとおおよそどこで異なるかを示していました（図 8）。

![各ステップで比較される Python と Rust。モデルは 1 回だけ呼び出され、その出力が Rust に再生される。プロンプトの構築が最初に差異の生じるステップで、断片 2 において、バイト 17 から 2 つのキーの順序が異なっている。Claude エージェントに渡される記録には、ステップ、断片、両方の長さ 190 バイト、最初に異なるバイトが記載されているが、テキストは含まれない。](https://assets.claude.com/32dee017ccc9f7496eb80f0b926bf655215edb83.png?w=3840&q=75&fm=webp&fit=max)

チェックポイントでの比較（簡略化した図で、値は架空のものです）。最初に差異が生じたステップが、調べるべき場所を示します。記録には断片、長さ、最初に異なる位置が含まれますが、テキストは含まれません。

- **フィンガープリント。** 各差分がおおよそどこにあるかがわかっても、あるバグと別のバグを区別する方法が必要でした。私たちは、プロンプト内で各差異が始まる位置と、2 つのバージョン間の長さの差を記録しました。チェックポイントで特定したステップとプロンプトの断片と組み合わせると、バグがそれぞれ特有のフィンガープリントを示すことがわかりました。つまり、1 つのバグは影響を与えるすべてのリクエストに同じフィンガープリントを残す傾向があるのです（図 9）。これによりエラーをフィンガープリントでグループ化でき、修正のトリアージに役立ちました。

![4 つのドットグリッドが、不一致がカウントされ、フィンガープリントでグループ化され、ビルドごとに分割され、修正後に再グループ化される様子を示している。フィンガープリント A がほぼすべての不一致を占めており、それを修正すると 2 つの古いグループ B と C が現れる。下の表は、プロンプト内の断片と位置、長さの差、ハッシュによって 3 つを区別している。](https://assets.claude.com/92be3b81d1414839e070e7ab04406fb397e320c7.png?w=3840&q=75&fm=webp&fit=max)

ある種類のリクエストから得られたフィンガープリント。プロンプトの先頭にある A が、より古い差異を覆い隠していました。A が修正されると、それらが B と C として現れました。ドットは説明用のものです。

その結果、Rust 版と Python 版の API の間の各差異について小さな記録を生成するシャドーイングシステムができあがりました。以下は架空の値を使った例です。

```
step:        build prompt     ← where in the code
piece:       2                ← where in the prompt
first diff:  byte 17          ← fingerprint
python:      190 bytes        ← fingerprint
rust:        190 bytes        ← fingerprint
```

そして、この記録をエージェントに渡して修正させることができました。

## 検証ループ

差異のあった各リクエストは、ログに記録を残しました。1 つのバグが、ほぼ同一の差分記録を数十万件生み出すこともありました。それぞれをエージェントに送る代わりに、10〜30 分ごとにスクリプトを実行し、どのフィールドが異なるかで記録をグループ化して、新しい *種類* の記録を見つけたときだけ、調整役の Claude エージェント（コーディネーター）に通知しました。コーディネーターは、新しい種類の記録ごとに担当するワーカーエージェントを割り当てました。また、共有の Slack チャンネルに新しいスレッドを作成し、人間のエンジニアが経過を追い、必要に応じて舵取りできるようにしました。

多数のバグに取り組むため、私たちは一連の検証ループを構築しました。高速な *内側* のループでは、エージェントにアイデアを試して修正を提案できるサンドボックスを与えました。より低速な *外側* のループでは、修正を本番で検証しました。さらに *メモリループ* では、途中で生じた誤りを記録・保存し、エージェントが時間とともに学習できるようにしました（図 10）。

![3 つの入れ子になったループ。内側のループは、比較に 1 秒もかからないローカルチェックを使い、編集が差異を修正するかを問う。外側のループは、数時間から数日にわたるシャドーイングされた実トラフィックを使い、本番で差異が消えたかを問う。メモリループは、なぜそれが繰り返し起きるのかを問い、人間による修正を新しいルールに変える。](https://assets.claude.com/3a4d129ebad6ab2c1188fe6cd02dbc34c2a06e5b.png?w=3840&q=75&fm=webp&fit=max)

検証ループ。編集はサンドボックスでチェックされ、次にシャドーイングされた実トラフィックでチェックされます。人間による修正はルールになります。各ループは、その内側のループが見逃したものを捉えることができます。

### 内側のループ

4 月にこれを初めてテストし始めたとき、私たちは各エージェントに、Rust 版と Python 版がどこで異なるかを示す記録を渡しました。エージェントはコードから根本原因を推測し、プルリクエストを作成しました。修正がレビューされマージされると、エージェントはそれをステージング環境、つまりテストトラフィックに対して同じシャドー比較を実行する Rust API の本番前コピーにデプロイしました。そしてエージェントは差異が解消されたかを確認しました。すべての仮説にレビューとデプロイが必要だったため、フィードバックには数時間から数日かかっていました。

エージェントが検証からもっと早くシグナルを得られるようにする必要があったため、私たちはエージェントを専用のワークスペースに移しました。内側のループを再設計し、エージェントがアイデアを素早く試し、安全に失敗できる場所を持てるようにしたのです。各エージェントは、両方のコードベースと、モデル呼び出しの前後で何が起きるかを確認する高速なローカルチェックを備えたクラウドサンドボックスで実行されました。入力チェックはリクエストを受け取り、各バージョンがモデルに送るプロンプトを構築し、何が異なるかを示しました。このチェックは実際にはモデルを呼び出さないため、バージョンの比較には 1 秒もかかりませんでした。後に出力チェックも追加しました。これは偽のモデルに対して両方のバージョンを実行するものです。出力チェックは、ツール呼び出しなどのスクリプト化された応答を各バージョンに通し、結果を比較しました。

主な制約は、エージェントがフィンガープリントしか見ることができず、各記録の背後にあるリクエストを見られないことでした。そのためエージェントは、差異の原因について仮説を立て、それを再現するためのリクエストやモデル応答を自分で書きました。各エージェントがこれらを自分で書いているため、両方の結果を完全に読むことができました。結果が一致すれば推測は間違っており、エージェントは再挑戦しました。記録が示すのと同じ形で結果が異なれば、エージェントは 2 つのバージョンが一致するまで Rust を編集し、古いコードでは失敗し新しいコードでは合格するテストを追加しました（図 11）。

![内側のループを強調表示した図。エージェントはフィンガープリントから原因を推測し、それを引き起こすリクエストまたは応答を書く。入力チェックと出力チェックがそれを両方のバージョンに通す。一致すれば再度推測し、記録と同じ形で異なれば Rust を編集して再チェックする。編集後に一致すれば、修正とテストを含む PR を作成する。](https://assets.claude.com/52e44ff8f08880a4d0f6877c97cdf77a140a8552.png?w=3840&q=75&fm=webp&fit=max)

内側のループ。エージェントはフィンガープリントから原因を推測し、それを引き起こすはずのリクエストまたは応答を書きます。ローカルチェックが、編集によって両者が一致するまで、それを両方のバージョンに通します。

内側のループと外側のループの継ぎ目は、人間によるレビューに適したチェックポイントでした。サンドボックス内では、誤った推測でエージェントが失うのは数秒だけで、ユーザーへの影響はありません。エージェントは自律的に反復できました。修正が外側のループに進むのは PR レビューを経た後に限りました。これにより、エンジニアは（推測ではなく）提案された修正と、Rust 版と Python 版の API の差異がバグによるものか意図的な変更によるものか、といった検証器が答えられない問いに注意を集中できました。

エージェントは修正と根拠を Slack スレッドに投稿し、エンジニアがレビューしました。5 月中旬、Rust 版と Python 版の API の間に残っていた最大級の差異の 1 つは、ウェブ検索に由来するものでした。本番 API はウェブ検索ツールの説明文を社内サービスから取得していました。Rust API はまだこのサービスを呼び出していなかったため、プロンプトからツールの説明文が欠落していました。あるエージェントは、そのテキストを Rust が読めるファイルにコピーするという近道を提案しました。するとプロンプトは一致し、修正はローカルの検証器にも合格しました。しかし、あるエンジニアはこれを却下しました。問題を解決していなかったからです。Rust はリリース前にいずれそのサービスを呼び出す必要があり、その時点でこの回避策は捨てられることになります（図 12）。

しかし、検証器は出力の一致に報酬を与えるものであり、エージェントはそれを生み出す最も安上がりな方法を見つけたのです。検証器はエージェントに出力が一致したかどうかを伝えることはできますが、その修正が出荷に足るほど良いものかどうかは伝えられません。だからこそ、人間によるレビューが重要な関門となっていたのです。

![#rust-migration という Slack チャンネル。あるエンジニアが調整役の Claude エージェントに次のターゲットの説明を求める。Claude エージェントたちは不一致をウェブ検索まで追跡し、それが既に追跡されていることを確認し、テキストファイルから説明文を読み込む修正を作成する。別のエンジニアが返信する。「リリース前にそのテキストを取得する必要があるのはわかっているので、これは使い捨てのコードに見えます。その PR は破棄してください。」](https://assets.claude.com/6be648dd915614c56b00d3d0cb392f86bd6ef031.png?w=3840&q=75&fm=webp&fit=max)

エージェントたちが 4 つの Slack スレッドにまたがって不一致をウェブ検索ツールまで追跡し、修正を提案しますが、エンジニアがそれを使い捨てのコードとして却下します。メッセージは短縮・言い換えし、スレッド名とエージェントのラベルを追加しています。

### 外側のループ

内側のループでは、エージェントが差異をデバッグし、修正を提案しました。内側のループと外側のループの継ぎ目で、エンジニアが提案された修正をレビューし、フィードバックを与え、デプロイを承認しました。そして外側のループでは、各修正の有無で Rust API のデプロイを比較しました。

この比較を公平にするため、比較した各リクエストについて、テキストではなく、使用されたモデルや API 機能（たとえばプロンプトキャッシング、ツール、拡張思考（extended thinking）など）といった事実を記録しました。これらの詳細により、エージェントは同じ種類のリクエスト同士を比較し（図 13）、修正のあるビルドとないビルドでバグのフィンガープリントがどれくらいの頻度で現れるかを調べることができました。こうしてエージェントは、新しいビルドでバグを監視できるようになりました。

![外側のループを強調表示した図。エンジニアが PR をレビューし、マージされてテスト環境、次に本番環境にデプロイされる。シャドーイングされた実トラフィックでフィンガープリントを監視する。残っていれば作業は内側のループに戻る。繰り返しのチェックで消えたことが確認されればタスクはクローズされ、再発すればスレッドが再開される。](https://assets.claude.com/79fc91e736881cb4d25983fbf989076d3e7c0014.png?w=3840&q=75&fm=webp&fit=max)

外側のループ。エンジニアが修正をレビューし、それがデプロイされ、シャドーイングされたトラフィックによってフィンガープリントが消えたかどうかがわかります。消えていなければ、タスクは内側のループに戻ります。

私たちは、内側のループが見逃した問題を捉えるように外側のループを設計しました。内側のループは本番を素早く、しかし不完全にシミュレートするものでした。エージェントは仮説を数秒でテストできましたが、それは自分が書いたリクエストに対してだけであり、ローカルの検証器も必ずしも本番とまったく同じ構成ではありませんでした。

そのため、修正がサンドボックスでは合格しても、本番ではまだ差異が現れることがありました。バグを担当するエージェントは、新しいビルドの記録で差異を確認するか、調整役のエージェントから通知を受けました。そして内側のループに戻り、その証拠をもとに新しい仮説を立てました。

### メモリループ

内側と外側のループは、差異を 1 つずつ修正するものでした。[メモリ](https://www.anthropic.com/research/components-of-agent-memory)ループは、エージェントがそうした修正を行う方法そのものを改善しました。エンジニアが同じ指摘を 2 度しなくて済むように、レビューやエージェント自身の作業から得られたものを記録し、後続のすべてのエージェントに適用したのです。

たとえば、エンジニアがウェブ検索の近道を却下したとき（図 12）、エージェントはその決定、その理由、そして正しい修正（Rust がツールの説明文を提供するサービスを呼び出すようにすること）を説明するメモをメモリに保存しました。

その呼び出しの構築にはチームで数週間かかり、その間もバグは記録を生み出し続けました。欠落したテキストがプロンプト内の別の位置にあったり、同じサービスを使う別のツールのものであったりしたため、新しいフィンガープリントを持つ記録もありました。エージェントはメモリのメモを確認して既知のバグであると認識し、新たな回避策を書く代わりに、それらの記録を既知のバグに紐づけました（図 14）。

他の教訓は、移植や Rust の記述に関する一般的なルールになりました。あるエージェントが Python の挙動を推測で済ませた後、エンジニアは Python が行っていることを正確に移植するというルールを定めました。するとあるエージェントが既存のコードをそのルールと照らし合わせ、移植が推測に頼っていた箇所をさらに 7 つ見つけました。

6 月には、あるエージェントがチームのレビューコメント約 60 件を精査し、繰り返し現れる問題をグループ化してルールを提案しました。エンジニアがそれを編集・承認し、[CLAUDE.md](https://code.claude.com/docs/en/memory) に追加しました（図 14）。

メモリループは、一部の教訓を恒久的なチェックとしても組み込みました。これには、Rust が Python からずれたときに失敗する新しいテスト、レビュアーが繰り返し指摘するパターンを禁止する lint、そして後には、Python コードを変更する人に対して Rust にも対応する変更を加えるか、免除を申請することを求めるマージチェックが含まれていました。

![メモリループを強調表示した図。繰り返される誤りが、エンジニアによる「それは自分ででっち上げたのですか？」という指摘を促す。それは、新しいエージェントが最初に読むルール、別のエージェントが同じ誤りを 7 箇所で見つける検索、そしてバージョンがずれたときに失敗するテストになる。マージされた変更を毎日読み、Rust が反映する必要がありそうなものにフラグを立てる。](https://assets.claude.com/086ed2a9f3c27c6bfd24e67a3cea341417d40ffe.png?w=3840&q=75&fm=webp&fit=max)

メモリループ。エンジニアによる 1 つの指摘が、各新規エージェントが読むルール、同じ誤りの検索、そしてテストという 3 つのものになります。

## 今後に向けて

パフォーマンスやセキュリティの向上のために、API を停止したり機能開発を遅らせたりすることなく、Claude を使って本番システムを移行することがますます現実的になっています。新しいコードを書くことがもはや難しい部分ではなくなった今、私たちは新しいシステムが古いシステムと同じように振る舞うという十分な確信を築く必要があります。

通常の移行のアプローチは、古い船の板を 1 枚ずつ取り替えていく「テセウスの船」の再建に少し似ています。一般に、船が航行している間に板を取り替えることは可能でしたが、一度に多くの板を替えるには入港する必要がありました。この比喩をとことん広げるなら、Claude によって、最初の船が航行を続け、その板が取り替えられ続けている間にも、それとまったく同じように機能する船をその隣に建造できるようになったのです。エージェントは古い船の変化に合わせて新しい船を同期させ続け、私たちは 2 つが同じように振る舞うことを確認し続けました。そうであると信頼できたところで、乗客を少しずつ移しました。新しい船は古い船よりも速く、効率的に航行しています。

### 得られた教訓

**検証が新たなボトルネックです。** これまで、移行のような大規模なソフトウェアプロジェクトは、労力がかかりすぎ、リスクも大きすぎるため、正当化が困難でした。しかしコードを書くことがもはやボトルネックでないなら、主な制約は結果をどれだけ速く検証できるかになります。一般に、Claude が正しさを検証する手段がある限り、野心を高めることができます。

**検証こそが確信を得る方法です。** 数学では、Claude が書いた証明の各ステップが妥当であることを、証明支援系を使って検証します。ソフトウェアでは、テストや[形式検証](https://www.anthropic.com/research/formal-verification)が同様の確信を得る助けになります。しかし、そうしたチェックだけでは不十分な場合、本番システムそのものも検証器になりえます。

**検証シグナルを注意深く設計しましょう。** 検証器は、Claude が行動に移せるシグナルを提供します。このシグナルを調整して、どこで問題が起きたかを Claude に示すことができます。証明支援系が失敗したステップを指し示し、テストが失敗したケースを名指しするのに対し、本番システムはデフォルトではそうしたシグナルを提供しないことが多いです。このプロジェクトにおける私たちの労力の多くは、そうしたシグナルの構築に費やされました。今回のケースでは、チェックポイントが各差異の *コード内での* 位置を特定し、フィンガープリントが *バグ同士を区別する* のに役立ちました。

**Claude がシグナルに基づいて自律的に行動できるループを構築しましょう。** 内側のループは高速で、サンドボックス内でローカルに実行されました。エージェントは自分で書いたリクエストを使って、数秒で仮説をテストしました。外側のループはより低速で、シャドーイングされた本番トラフィックで修正をチェックしました。最も外側のループは単なる文章であり、指摘がルールとしてメモリに保存され、プロセスの後半ですべてのエージェントが読めるようになっていました。これらのループを組み合わせることで、私たちは Messages API を Rust に移行し、リクエストあたりの CPU 使用量を約 70% 削減し、最初のトークンまでの時間の中央値を約 20% 短縮することができました（図 15）。

![Python から Rust への移行を示す 3 つのグラフ。リクエストあたりの CPU 使用量は約 70%、リクエストあたりのメモリ使用量は 80% 以上減少しており、いずれも 8 月から 10 月にかけてのもの。最初のトークンまでの時間の中央値は、おおよそ 9 月 7 日から 21 日の間に約 20% 減少している。](https://assets.claude.com/5991f46db78fd73fa00095ab708ffd1eaf240a76.png?w=3840&q=75&fm=webp&fit=max)

リクエストが Python（灰色）から Rust（青）に移行するにつれての、リクエストあたりの CPU とメモリの使用量、および最初のトークンまでの時間の中央値。線は 7 日間平均で、100 は移行直前のおおよその水準を表し、各矢印は 1 つ目の点から 2 つ目の点への変化を示しています。CPU は 1 つのリージョン、メモリは本番全体、最初のトークンまでの時間はより短い期間におけるお客様の Claude Code リクエストを対象としています。3 つ目のパネルで 1 つ目の点より前に見られる低下は、それらのリクエストのほぼすべてがまだ Python 上にあった時期に生じたものです。

**Claude の能力に合わせてスケールするよう、ループはシンプルに保ちましょう。** 私たちは、人間の判断を「何を正しいとみなすか」にのみ込めるようにし、それ以外のそこへの到達方法は Claude に任せました。どの仮説をテストするか、各バグをどう再現するか、どう修正するかはエージェントが選びました。結果を判定したのは検証器です。強力な検証器を囲むシンプルなループによって、私たちは時間とともに生産的に前進できました（図 16）。

![2026 年 4 月 6 日から 9 月 7 日までの、2 週間ごとにマージされた変更数を示す棒グラフ。変更数は 100 未満から 6 月下旬には約 1,000 まで増え、7 月中は横ばいとなり、8 月 10 日から始まる期間には 3,000 以上に跳ね上がり、その後の 2 期間も 2,500 以上を維持している。](https://assets.claude.com/f3fe7bd0615da0366ab5c2f3181579ee7ca94647.png?w=3840&q=75&fm=webp&fit=max)

4 月から、公開トラフィックが Rust に移行した 2026 年 9 月までの、2 週間ごとに API の Rust コードにマージされた変更数。すべてが移行作業というわけではありません。

**外側のループへと移っていきましょう。** 当初、エンジニアは内側のループの中で作業し、自ら Claude を実行して差異を追いかけていました。その後、ループの継ぎ目に移り、エージェントの舵取りを助け、Slack で修正をレビューするようになりました。しかしシステムが成熟するにつれ、エンジニアはますます外縁へと移り、そこでエージェントが従うルールやチェックを書くという、最も高いレバレッジを発揮できる役割を担うようになりました。Claude がより賢くなるにつれて（そして私たちが Claude と協働することに長けるにつれて）、私たちは Claude に指示する形から Claude が自らを方向づける形へと進化し、人間には主に重要な判断を委ねるようになりました。
